## Azure first

- A **Log Analytics workspace** is the Azure resource that stores logs as tables. It lives in one **subscription**, one **resource group** and one **region**.
- **Microsoft Sentinel** is not a separate store. It is a solution you *add on top of* a workspace. "A Sentinel workspace" means "a Log Analytics workspace with Sentinel enabled".
- The **Defender portal** (`security.microsoft.com`) is where Sentinel is used day to day now. Connecting a workspace to it is a separate step from enabling Sentinel.
- **Azure Lighthouse** lets users in one Entra tenant manage Azure resources in another tenant without guest accounts.

See the Foundations pages listed above: Log Analytics workspace, Defender portal tour, Azure resource hierarchy, and Azure RBAC vs Entra roles.

## In one sentence

You create (or pick) a Log Analytics workspace in the right region, add Microsoft Sentinel to it, then connect it to the Defender portal as the **primary** or a **secondary** workspace.

## What's new for an engineer

As an analyst the workspace was just there. Now you make four decisions, all hard to undo:

1. **Region.** Data is stored where the workspace is. A workspace ==!can't move between regions== — you recreate it. Once Sentinel is on it, it also can't move to another resource group or subscription.
2. **How many workspaces.** One central workspace is simplest. Regional workspaces are for data-residency rules or cross-region bandwidth cost.
3. **Who onboards.** Enabling Sentinel needs **Contributor** on the subscription. Connecting to the Defender portal needs **Owner** (an *unconditional* assignment at subscription scope) **or** **User Access Administrator + Microsoft Sentinel Contributor**. With more than one Sentinel workspace in the tenant you also need at least **Security Administrator** in Entra ID.
4. **Which workspace is primary.** Only the primary gets Defender XDR alerts and incidents correlated with Sentinel alerts.

## What actually matters

- **Portal retirement.** After ==@March 31, 2027== Sentinel is no longer supported in the Azure portal; users are redirected to the Defender portal. New customers (first workspace in the tenant, Owner or User Access Administrator, not Lighthouse-delegated) have been auto-onboarded to the Defender portal since **July 2025**.
- **Primary vs secondary.** One primary and an unlimited number of secondary workspaces per tenant (no limit on onboarded workspaces since July 2025). The Defender XDR connector attaches to the primary only. Secondary workspaces keep their own incidents; they never include Defender XDR alerts. On onboarding, standalone connectors for tenant-wide alerts (Entra ID Protection, Defender for Office 365, Cloud Apps, Endpoint, Identity) are disconnected so alerts are not duplicated.
- **Defender for Cloud's default workspace** never appears in the Sentinel list. Create your own workspace and point Defender for Cloud at it if you want one shared store.
- **Cross-workspace queries** use `workspace("name").Table` with `union`. A scheduled analytics rule can reference up to 20 workspaces (5 recommended), and its alerts live only in the workspace where the rule is defined.
- **Multitenant (MSSP).** In the Azure portal, Azure Lighthouse delegates customer subscriptions to your tenant; register `Microsoft.OperationalInsights` and `Microsoft.SecurityInsights` in every tenant. In the Defender portal, Lighthouse with GDAP is ==!not supported for Sentinel data== — use Entra B2B and the **Defender multitenant portal** (`mto.security.microsoft.com`).
- **Retention starts here.** A new workspace may sit on 30-day retention; raise it to the **90 days** Sentinel includes free. Analytics retention goes up to 2 years and total retention up to 12 years — details in D4.2.9.

## Where it lives

| Task | Portal and path |
|---|---|
| Create workspace + add Sentinel | Azure portal > Microsoft Sentinel > **Create** > Create a new workspace (or pick one) > **Add** |
| Connect to Defender portal | Defender portal > **System > Settings > Microsoft Sentinel > Connect a workspace** > pick workspaces > choose **Primary** > Connect |
| Change primary / disconnect | Defender portal > System > Settings > Microsoft Sentinel > **Workspaces** > Set as primary / Disconnect workspace |
| Workspace retention (legacy path) | Azure portal > Log Analytics workspace > Usage and estimated costs > **Retention** (30–730 days) |
| Table tiers and retention | Defender portal > Microsoft Sentinel > **Configuration > Tables** |
| MSSP access (Azure portal) | Directory + subscription filter > select delegated directories and subscriptions |

## Exam traps

- ==!"Sentinel has its own database"== — no. It always sits on a Log Analytics workspace. The workspace name *is* the Sentinel workspace name.
- ==!"Use the Defender for Cloud default workspace"== — it is hidden from Sentinel. Create your own.
- ==!"Move the workspace to another region later"== — not possible. Recreate it.
- **Region choice** answers data-residency questions. Regional workspaces = no cross-region bandwidth cost, split billing and granular retention, but content must be deployed many times.
- **Primary workspace** is the only one with Defender XDR correlation. A question about "XDR alerts not appearing in workspace B" — B is secondary.
- **Contributor on the subscription** enables Sentinel; it does **not** connect it to the Defender portal.
- **Retirement date:** March 31, 2027, not July 2026 (the original, since-extended plan).
- **Workspace manager** (central workspace publishes content to member workspaces) is preview and Azure-portal only; it is not available in the Defender portal.
