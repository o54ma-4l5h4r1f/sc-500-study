## Azure first

- A **storage account** holds **containers** of **blobs** (plus file shares, queues and tables). Every data request must be *authorized*.
- **Microsoft Entra ID** issues tokens to users, groups, **service principals** and **managed identities** (an identity Azure creates for a resource, such as a Function App, with no password to store).
- **Azure RBAC** assigns a *role* to an identity at a *scope* (management group, subscription, resource group, account, container). Roles have **Actions** (management plane: change the account) and **DataActions** (data plane: read a blob).
- An **account key** is a 512-bit master secret for the whole account. A **shared access signature (SAS)** is a signed URL query string that grants limited rights for a limited time.

Read first: storage-accounts-basics, azure-rbac-and-entra-roles, entra-id-basics, keys-secrets-and-certificates.

## In one sentence

Storage access is decided by **how the request is signed**: an Entra token checked against RBAC data roles (best), a SAS (user delegation SAS if you must), or the account key (eliminate), with stored access policies as the only way to revoke a key-signed service SAS without rotating keys.

## Why it exists

Shared Key is a master key with no name on it. Anyone holding it can do anything, and logs show only "AccountKey". Revoking it means rotating the key and breaking every app that uses it. As an analyst you could not answer "who read this blob?" when the answer was "the key".

Entra ID gives every caller a name, short-lived tokens and Conditional Access. SAS exists for the one case Entra cannot cover: handing a time-boxed link to someone outside your tenant.

Think of a hotel. **Entra ID + RBAC** is a staff badge with your name on it. A **user delegation SAS** is a guest key card a named staff member printed; void the staff badge or the printer and the card dies. A **service SAS** is a key card cut from the master key; with a **stored access policy** it points at a rule on the front desk you can tear up. An **account SAS** is a master-key copy with no desk rule. The **account key** is the master key itself.

## What actually matters

| | Signed with | Scope | Stored access policy | Works if Shared Key disabled | Revoke by |
|---|---|---|---|---|---|
| ==+User delegation SAS== | user delegation key from Entra ID | Blob (incl. Data Lake), Queue, Table, Azure Files (current SAS docs; older articles and the module say Blob only) | ==!No== (ad hoc only) | ==+Yes== | Revoke user delegation keys, or remove the creator's RBAC role |
| Service SAS | account key | one service (Blob, Queue, Table or Files) | ==+Yes== | ==!No== (403) | Delete/modify the stored policy, or rotate the key |
| Account SAS | account key | one or more services, plus service-level operations | ==!No== | ==!No== (403) | Rotate the key |

1. **Prefer Entra ID with managed identities.** For a Function App: turn on the system-assigned identity, then grant **Storage Blob Data Reader** (or Contributor) on the account or container. Code uses `DefaultAzureCredential`; no secret in config.
2. **Data-plane roles** (DataActions) are the only built-in roles that read data through Entra ID:

| Role | Gives |
|---|---|
| ==@Storage Blob Data Reader== | read and list containers and blobs |
| ==@Storage Blob Data Contributor== | read, write, delete blobs |
| ==@Storage Blob Data Owner== | full blob data control, including POSIX ACLs on Data Lake and blob index tag operations |
| ==@Storage Blob Delegator== | only gets a user delegation key (to mint a user delegation SAS) |
| Storage Queue Data Reader/Contributor, Storage Table Data Reader/Contributor, Storage File Data SMB Share Reader/Contributor | the same idea for queues, tables and file shares |

   ==!Owner, Contributor and Storage Account Contributor are management roles.== They give no data access through Entra ID. They do include `listkeys`, so the portal falls back to the account key. To browse blobs in the portal with Entra ID only, a user needs **Reader** (ARM) plus a data role.
3. **Scope narrowly.** Container is the narrowest RBAC scope for blobs. Assignments take up to 10 minutes to apply (the module says 30; product docs say 10, and several hours for data access granted at management-group scope). A **managed identity** can take several hours to see a change, because its tokens are cached for about 24 hours.
4. **ABAC conditions** add an attribute test to a role assignment, for example "read only blobs tagged `Project=Sierra`". They work on DataActions for Blob, Data Lake and Queue, with the built-in Storage Blob Data Reader/Contributor/Owner roles or custom roles. ==!Conditions do not apply to management Actions.==
5. **Stored access policy**: created on a container (or queue, table, share) with an identifier, start, expiry and permissions. A service SAS references it via `signedidentifier`. Change the expiry or delete the policy and every linked SAS changes or dies at once. Limit: ==@5 per container/queue/table/share==.
6. **User delegation SAS**: the creator needs `.../generateUserDelegationKey/action` (in Storage Blob Delegator and the data roles). The key lives **at most 7 days**, so the SAS dies with it. Revoke all keys with `az storage account revoke-delegation-keys`. Revocation can lag because keys and role assignments are cached. A newer **user-bound** user delegation SAS ties the token to one named end user, so a leaked link is useless to anyone else.
7. **SAS expiration policy** on the account sets an upper limit for any SAS validity. Action **Log** (default) only records violations; **Block** rejects out-of-policy SAS. It does not apply to a service SAS that uses a stored access policy.

## Where it lives

| Task | Portal (Azure portal) |
|---|---|
| Data role assignment | `Storage account (or container) > Access control (IAM) > Add role assignment` |
| ABAC condition | Same wizard, **Conditions** tab |
| Stored access policy | `Storage account > Data storage > Containers > {container} > Access policy > Add policy` |
| Generate SAS | `Storage account > Security + networking > Shared access signature` (account SAS) or `{container} > Generate SAS` |
| SAS expiration policy | `Storage account > Settings > Configuration > Upper limit for SAS expiry interval` |
| Managed identity | `Function App > Settings > Identity > System assigned > On` |

```bash
# User delegation SAS (signed with your Entra credentials, not a key)
az storage container generate-sas --account-name contosodocs --name invoices \
  --permissions rl --expiry 2026-11-20T00:00Z --auth-mode login --as-user

# Service SAS bound to a stored access policy (still needs the account key)
az storage blob generate-sas --account-name contosodocs --container-name invoices \
  --name document.pdf --policy-name vendor-read-policy --account-key <key>

# Kill every user delegation SAS on the account
az storage account revoke-delegation-keys -g rg-sec -n contosodocs
```

## Exam traps

- "Revoke one vendor's SAS without breaking other apps" with a **service SAS**: ==+delete the stored access policy==. Rotating the key works but breaks everyone.
- "Use a stored access policy with a user delegation SAS or account SAS": ==!not supported==.
- "Grant an app blob read access with least privilege and no secrets": ==+managed identity + Storage Blob Data Reader== at the container. Not Reader, not Contributor, not an account key in Key Vault.
- A user with **Contributor** on the account cannot read blobs once Shared Key is disabled. They lack a data role.
- **Storage Blob Delegator** cannot read blobs. It only mints the key.
- A user delegation SAS with a 30-day expiry is valid for ==!7 days at most==.
- After disabling Shared Key, the service SAS and account SAS fail with 403. The user delegation SAS keeps working.
- SAS start time set to "now" can fail for a few minutes due to clock skew. Docs suggest starting 15 minutes earlier.
