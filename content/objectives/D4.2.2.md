## Azure first

- **Azure RBAC** grants rights on Azure resources (subscriptions, resource groups, workspaces, Logic Apps). A role assignment = *who* + *which role* + *at what scope*. Assignments are inherited downward and add up.
- **Entra roles** (Security Administrator, Security Operator, Global Reader…) grant rights across the tenant's Microsoft 365 and security services. They are a separate system from Azure RBAC.
- A Sentinel **workspace** is an Azure resource, so most Sentinel rights are Azure RBAC roles. A **playbook** is a separate Azure resource — a Logic App — with its own permissions.
- **Defender unified RBAC** is the Defender portal's own role system. It can take over Sentinel permissions per workspace.

See the Foundations pages listed above: Azure RBAC vs Entra roles, Log Analytics workspace, Logic Apps basics, Defender portal tour.

## In one sentence

You give each person the smallest built-in **Microsoft Sentinel** Azure role at the **resource group** that holds the workspace, add **Logic App Contributor** or **Playbook Operator** for playbooks, and grant Sentinel's own service account rights on the playbook resource group.

## What's new for an engineer

As an analyst you *had* Responder. Now you hand roles out, and three things trip people up:

1. **Scope.** Microsoft recommends the **resource group** that holds the workspace. If you assign at the workspace itself, you must also assign the same role on the **SecurityInsights** solution resource.
2. **Playbooks live outside Sentinel.** Sentinel roles don't let anyone create Logic Apps. That takes **Logic App Contributor** on the playbook's resource group.
3. **Sentinel itself needs permission.** Automation rules run playbooks as a Sentinel service account, not as you. Someone with **Owner** or **User Access Administrator** on the playbook resource group must grant it explicit permissions (the **Microsoft Sentinel Automation Contributor** role, set from Settings > Playbook permissions). After that, any automation rule can run any playbook in that resource group.

## What actually matters

| Role | Adds on top of the row above | Typical holder |
|---|---|---|
| ==@Microsoft Sentinel Reader== | View data, incidents, workbooks, recommendations | Auditor, read-only analyst |
| ==@Microsoft Sentinel Responder== | Manage incidents (assign, change status, close) | Analyst |
| ==@Microsoft Sentinel Contributor== | Create/edit analytics rules, workbooks, watchlists; attach playbooks to automation rules; **install/update content hub solutions** | Security engineer, automation service principal |
| ==@Microsoft Sentinel Playbook Operator== | List, view and **manually run** playbooks (not edit) | Analyst who runs playbooks |
| ==@Microsoft Sentinel Automation Contributor== | Lets **Sentinel** attach playbooks to automation rules | ==!Not for user accounts== |
| ==@Logic App Contributor== | Create, edit and run Logic Apps (playbooks) | Automation engineer |

- **All Sentinel roles read workspace data.** Reader cannot create workbooks unless you add **Workbook Contributor**.
- **Broader roles also reach Sentinel.** Azure **Owner / Contributor / Reader** and **Log Analytics Contributor / Log Analytics Reader** grant access to the workspace too. Assignments are cumulative: Sentinel Reader + Azure Contributor can edit Sentinel. To lock someone down, remove the broad role.
- **Connecting data** needs **write on the workspace** plus each connector's own prerequisites (often an Entra role such as Security Administrator — see D4.2.4).
- **Guest users** need **Directory Reader** (an Entra role) plus Responder to assign incidents.
- **Least privilege beyond the workspace:** resource-context RBAC or table-level RBAC limits which data a user sees. For the Sentinel data lake, use Entra roles (Security Operator/Administrator to write and run jobs) or Defender unified RBAC custom roles.
- **Defender unified RBAC.** You activate it **per workspace** (needs **Security Administrator** in Entra ID **plus** Owner, or User Access Administrator + Sentinel Contributor, on the workspace). Once active, it becomes the source of Sentinel permissions; changing roles in the Azure portal afterwards can cause sync errors. It does **not** support Playbook Operator, Automation Contributor or Workbook Contributor (they stay in Azure), and it does not support assigning roles to a **service principal**.
- **Onboarding roles** (Owner unconditional, or User Access Administrator + Sentinel Contributor, plus Security Administrator for multi-workspace) are covered in D4.2.1.

## Where it lives

| Task | Portal and path |
|---|---|
| Assign Sentinel roles | Azure portal > Resource groups > *workspace RG* > **Access control (IAM)** > Add role assignment |
| Grant Sentinel rights to run playbooks | Defender portal > **Settings > Sentinel** > *workspace* > **Playbook permissions** > Configure permissions > pick resource groups (needs Owner or User Access Administrator on them). Azure portal: Sentinel > Settings > Settings tab > Playbook permissions |
| Activate unified RBAC for Sentinel | Defender portal > **System > Permissions** > Microsoft Defender XDR > Roles > **Workload settings** (or Activate workloads) > Sentinel > **View Workspaces** |
| Entra roles (Security Administrator, Directory Reader) | Microsoft Entra admin center > Roles & admins |

```bash
# Give an analyst Responder at the Sentinel resource group
az role assignment create --assignee analyst@contoso.com \
  --role "Microsoft Sentinel Responder" \
  --scope /subscriptions/<sub-id>/resourceGroups/rg-sentinel
```

## Exam traps

- ==!"Sentinel Contributor can create playbooks"== — no. Playbooks are Logic Apps: ==+Logic App Contributor==.
- ==!"Give an analyst Automation Contributor so they can attach playbooks"== — that role is for the Sentinel service account only.
- **Who can only *run* playbooks?** ==+Microsoft Sentinel Playbook Operator==. The training unit's table says "Sentinel Contributor + Logic App Contributor" is needed to "create and run playbooks" and omits Playbook Operator; the product doc lists Playbook Operator for running. Product doc wins.
- **Who installs content hub solutions?** Sentinel Contributor at the resource group — not Responder.
- **"The automation rule can't run the playbook"** → Sentinel lacks permissions on the playbook's resource group. Fix needs **Owner** or **User Access Administrator** on that resource group.
- **Unified RBAC + service principal** → not supported; keep Azure RBAC for that workspace.
- **Contradiction:** one Defender article says GDAP user groups *are* supported in unified RBAC for Sentinel; the activation article says they aren't. If asked, the safe answer for service principals is "not supported"; treat GDAP as unsettled.

## Skip

- **Skip** the custom role authoring detail (JSON `Actions` lists). Know that Azure custom roles are the answer when built-in roles don't fit.
- **Skip** the long action-by-action permission tables in the onboarding article (`Microsoft.SecurityInsights/incidents/write`…). The exam asks role names, not action strings.
- **Skip** support-request roles (Support Request Contributor). Off-objective.
