## Azure first

- **Azure SQL Database** is a managed database. Databases live on a **logical server** (`contoso.database.windows.net`), which is just a management and security boundary: firewall, admins, TDE key and auditing are set there and inherited by its databases.
- **Azure SQL Managed Instance (MI)** is a near-full SQL Server deployed **inside your VNet subnet** from day one. It has a private IP; a public endpoint (port 3342) is optional and off by default.
- **Logins and users**: a *login* lives in the server's `master` database; a **contained database user** lives in one database and can map straight to a Microsoft Entra identity.
- **Managed identity**: an Entra identity for an Azure resource (a Function App, or the SQL server itself) with no password.
- **Key Vault** holds the customer-managed key used for TDE (see keys-secrets-and-certificates).

Read first: azure-sql-basics, entra-id-basics, virtual-networks-and-subnets, keys-secrets-and-certificates, azure-rbac-and-entra-roles.

## In one sentence

Azure SQL platform security is four layers you configure on the server and database: **who** may connect (Entra-only authentication), **from where** (firewall rules, private endpoint, public access off), **how data is protected** (TLS 1.2+, TDE with an optional customer-managed key, Always Encrypted), and **what each user sees** (dynamic data masking, row-level security).

## Why it exists

The default database has a shared SQL password in an app setting, a public endpoint and a service-managed key. As an analyst you have seen what follows: password spray against `*.database.windows.net`, then data pulled through a valid login. Each layer removes one piece of that chain: no passwords to spray, no public door, and keys and rows the attacker cannot use.

## Mental model

A **bank branch**. Entra-only authentication is "staff badges only, no shared PINs". The firewall is the door guard with a visitor list; a private endpoint plus public access **Disabled** bricks up the street door and leaves only the staff tunnel. TDE locks the vault at night (data at rest). Always Encrypted means even the branch manager receives sealed envelopes. Masking and row-level security decide which pages of the ledger each clerk sees, and which digits are blacked out.

## What actually matters

**1. Authentication: Entra-only**

- Set a **Microsoft Entra admin** first: exactly one user or (recommended) **group** per server or MI. It sits alongside the SQL admin and is the first account that can create other Entra principals.
- **Microsoft Entra-only authentication** disables every SQL login, including the server admin. Existing SQL users remain but cannot connect. Azure Policy can force new servers to be created with it on.
- Apps use a **managed identity** mapped to a contained user: `CREATE USER [FraudFunc] FROM EXTERNAL PROVIDER; ALTER ROLE db_datareader ADD MEMBER [FraudFunc];`. Benefits: no passwords, MFA and Conditional Access apply to people.

| Azure RBAC role (management plane) | Set Entra admin | Toggle Entra-only | Firewall rules, TDE | Auditing, masking, Defender/VA settings | Read data |
|---|---|---|---|---|---|
| ==@SQL Security Manager== | ==!No== | ==+Yes== | Yes | ==+Yes== | No |
| SQL Server Contributor / SQL Managed Instance Contributor | ==+Yes== | ==!No== | Yes | ==!No== (excluded by NotActions) | No |
| SQL DB Contributor | No | No | No | No | No |
| Owner / Contributor | Yes | Yes | Yes | Yes | No |

> The training unit says SQL Security Manager is used to "configure authentication settings like the Microsoft Entra admin", and its table says SQL Server Contributor has no security permissions at all. The product docs say ==!SQL Security Manager cannot set or remove the Entra admin== (separation of duties), and the built-in role definition shows SQL Server Contributor *can* change firewall rules and TDE but not auditing, masking or Entra-only. Product docs win.

- **Server identity.** The logical server (or MI) has its own managed identity, system- or user-assigned. To resolve Entra names in `CREATE USER ... FROM EXTERNAL PROVIDER` on behalf of an app or service principal, that identity needs the Entra **Directory Readers** role or the Graph permissions **User.Read.All**, **GroupMember.Read.All** and **Application.Read.All**. On ==@SQL MI, Directory Readers (or those permissions) is required before you can set the Entra admin==. Only a **Privileged Role Administrator** (or higher) can grant them.
- **Logins vs users.** `CREATE LOGIN ... FROM EXTERNAL PROVIDER` in `master` makes an Entra **server principal**; `CREATE USER ... FROM EXTERNAL PROVIDER` in a database makes a **contained user**. Apps normally get a contained user.
- While Entra-only is on, the Entra admin ==!cannot be removed== (it can be changed). Enabling or disabling Entra-only writes an **Activity log** entry.

**2. Network isolation (SQL Database)**

| Control | Where configured | Scope |
|---|---|---|
| Server-level IP rule | portal, PowerShell, CLI, or T-SQL `sp_set_firewall_rule` in `master` | all databases; max 256 |
| Database-level IP rule | ==@T-SQL only==: `sp_set_database_firewall_rule` | one database; checked ==@first== |
| Allow Azure services and resources | portal toggle (default **No**) | adds `0.0.0.0` rule: ==!every Azure customer's resources== |
| Virtual network rule | portal (subnet with `Microsoft.Sql` service endpoint) | server; public endpoint stays |
| Private endpoint | `privatelink.database.windows.net` zone; SQL admin approves the connection | private IP in your VNet |
| Public network access = **Disable** | portal | ==+only private endpoints connect== |

- A private endpoint ==!does not block public access by itself==. Disable public access afterwards.
- **SQL MI** is VNet-native in a subnet delegated to `Microsoft.Sql/managedInstances`. It has ==!no server-level IP firewall==; traffic is filtered by the **NSG** on its subnet. Keep its public endpoint (port **3342**) off; if you must turn it on, also allow 3342 inbound in the NSG from known sources only. Prefer peering or VPN/ExpressRoute.
- **Outbound networking** (SQL Database): *Restrict outbound networking* limits the server's own outbound connections (for example, to storage for auditing or import) to an allowlist of FQDNs. It is a data-exfiltration control, not an inbound one.

**3. Encryption**

- **TLS**: every connection is encrypted. **Minimum TLS version** is set on the server; **TLS 1.2** is the lowest you can pick (1.0/1.1 retired 31 August 2025). The default ("no minimum") already accepts only TLS 1.2 and 1.3. Clients can negotiate TLS 1.3, but ==!do not assume TLS 1.3 is selectable as the minimum== on SQL Database. Once you set a minimum, you cannot go back to "no minimum". A client below the minimum gets error **47072** (*Login failed with invalid TLS version*).
- **TDE** encrypts data files, logs and backups at rest with a database encryption key (DEK, AES-256). ==+On by default== for new SQL Database databases and on MI. Cannot encrypt `master`.
  - **Service-managed** (default): DEK protected by a built-in server certificate.
  - **Customer-managed (BYOK)**: the **TDE protector** is your RSA key (2048 or 3072 bit) in Key Vault or Managed HSM, set at **server** level (database-level CMK also exists). Requirements: ==@soft delete + purge protection==; server **managed identity** with **Key Vault Crypto Service Encryption User** (or access policy get, wrapKey, unwrapKey); if the vault has a firewall, **Allow trusted Microsoft services** (unless private endpoint). Revoke the key and databases become **Inaccessible** (permission changes take about 10 minutes); restore access and they recover. Automated protector rotation is **off by default**.
- **Always Encrypted** encrypts chosen columns **in the client driver**; the engine and DBAs only see ciphertext. Keys: column master key (e.g., in Key Vault) wraps the column encryption key. Plain AE allows only equality on **deterministic** columns. **Always Encrypted with secure enclaves** (VBS or Intel SGX enclaves) lets the engine do pattern matching, range comparisons and sorting inside a protected memory area. Intel SGX enclave support ends **October 31, 2027**.

**4. Who sees what**

- **Dynamic data masking (DDM)** masks values **in query results** only; data is not encrypted. Masking methods (portal names): **Default**, **Credit card** (last four digits), **Email**, **Random number**, **Custom text** (prefix, padding, suffix), **Datetime**. The portal also recommends columns to mask. Grant `UNMASK` at database, schema, table or column level. Admins (server admin, Entra admin, `db_owner`) always see real data. ==!Not a security boundary== against users who can run ad hoc queries (inference).
- **Ledger** makes a table tamper-evident: every change is hashed into a blockchain-style chain you can verify later. It proves rows were not altered; it does not hide them.
- **Row-level security (RLS)** uses an inline table-valued function + `CREATE SECURITY POLICY`. **Filter predicates** hide rows on SELECT/UPDATE/DELETE; **block predicates** stop writes that violate the rule. Use `SESSION_CONTEXT` for middle-tier apps.

| | Protects against | Engine sees plaintext? | App change? |
|---|---|---|---|
| TDE | stolen disks/backups | yes | no |
| Always Encrypted | DBAs, cloud operators, malware on server | ==+no== | yes (driver, keys) |
| DDM | casual over-the-shoulder viewing | yes | no |
| RLS | users seeing other tenants' rows | yes | predicate only |

## Where it lives

All in the **Azure portal** on the SQL server (or MI) unless noted.

| Task | Path |
|---|---|
| Entra admin, Entra-only | `SQL server > Settings > Microsoft Entra ID` |
| Firewall, Allow Azure services, public access, private endpoints, min TLS, connection policy | `SQL server > Security > Networking` |
| TDE key (service vs customer-managed) | `SQL server > Security > Transparent data encryption` |
| DDM | `SQL database > Security > Dynamic Data Masking` |
| RLS, contained users, Always Encrypted keys | T-SQL / SSMS (no portal switch) |

```bash
az sql server ad-admin create -g rg-sec -s contoso-sql --display-name "SQL Admins" --object-id <group-id>
az sql server ad-only-auth enable -g rg-sec -n contoso-sql
az sql server update -g rg-sec -n contoso-sql --set publicNetworkAccess=Disabled minimalTlsVersion=1.2
```

## Exam traps

- "Block all password logins": ==+Entra-only authentication==. Requires an Entra admin first.
- "Least-privilege role to enable Entra-only without data access": ==+SQL Security Manager==. To set the Entra admin, SQL Server Contributor (or higher). Doing both needs Contributor or a custom role.
- "SQL MI: allow one partner IP": there is no MI firewall rule. ==+NSG rule on the MI subnet== (plus the public endpoint, if they come over the internet).
- "Entra admin set on the MI fails": the MI identity is missing ==+Directory Readers==.
- "Allow only one database for a partner IP": ==+database-level IP rule== (T-SQL). Server-level opens every database.
- "Allow Azure services" ==!is not "my subscription only"==.
- "Regulator wants to control and revoke the key": TDE with ==+customer-managed key==. Not Always Encrypted (that is column-level, app-side).
- "DBAs must never see SSNs": ==+Always Encrypted==. DDM fails (admins are excluded from masking; inference works).
- CMK vault without purge protection = configuration fails. Vault firewall without trusted-services bypass = TDE protector cannot be read.
- On MI, there is no private endpoint step to "isolate" it; it already lives in your VNet.

## Skip

- **Skip** the connection policy detail (Proxy vs Redirect ports). Know Redirect is lower latency and Proxy uses 1433 only.
- **Skip** `DBCC FLUSHAUTHCACHE` beyond one line, firewall rule naming limits and Data Sync / Import-Export side effects.
- **Skip** TDS 8.0 strict encryption and driver versions.
- **Skip** Hyperscale page-server limits, geo-replication key rules and cross-tenant CMK.
- **Skip** Always Encrypted key-provisioning steps and enclave attestation. Know what AE and enclaves are for.
- **Skip** the RLS T-SQL syntax beyond "inline TVF + security policy + filter/block predicates".
- **Skip** the training's `sqlcmd` verification steps and the Contoso banking narrative.
