## Azure first

- **Azure SQL Database** databases sit on a **logical server**; settings made on the server are inherited by every database on it. **SQL Managed Instance (MI)** behaves like a full SQL Server inside your VNet and is managed mostly with **T-SQL**.
- A **Log Analytics workspace** stores logs as queryable tables (KQL). **Event Hubs** is a streaming buffer that forwards events to a SIEM.
- A **diagnostic setting** is the Azure Monitor object that sends a resource's logs to a workspace, an event hub or storage.
- **Immutable (WORM) storage** on a blob container stops anyone deleting or changing blobs until a retention period ends (see D2.1.1).

Read first: azure-sql-basics, log-analytics-workspace, diagnostic-settings-and-activity-log, storage-accounts-basics, azure-policy-basics.

## In one sentence

SQL auditing records database events (by default every completed batch plus successful and failed logins) and writes them to blob storage, a Log Analytics workspace and/or Event Hubs; on SQL Database you switch it on in the portal at server or database level, on Managed Instance you create a `SERVER AUDIT` in T-SQL.

## Why it exists

Firewalls and Entra-only authentication decide who gets in. A regulator then asks: "prove who read customer record 4411 last March". Without an audit trail you cannot answer. As an analyst you queried `SQLSecurityAuditEvents` rows in Sentinel; this is the setting that creates them.

## Mental model

A **visitor book at the vault door, copied three ways**: one copy is sealed in a tamper-proof archive for the regulator (blob storage with WORM), one goes on the security desk where you can search it (Log Analytics), and one is read out live over the radio to the guard room (Event Hubs to a SIEM).

## What actually matters

1. **Default action groups** (what the portal turns on): ==@BATCH_COMPLETED_GROUP==, ==@SUCCESSFUL_DATABASE_AUTHENTICATION_GROUP==, ==@FAILED_DATABASE_AUTHENTICATION_GROUP==. That covers every query and stored procedure plus every login attempt. Other groups (schema object access, permission changes, logout) and custom audit specifications narrow or widen it via PowerShell/T-SQL.
2. **Server vs database level (SQL Database).** A **server audit** applies to all existing and new databases on the server. A **database audit** applies to one database. If both are on, they run side by side and ==!both log independently== (duplicate events), so turn on a database audit only when one database needs different settings. Since the July 2025 re-architecture, server auditing runs one extended-events session for the whole server and writes all server-audit logs to a single **`master`** folder. For many heavy OLTP databases the docs recommend database-level auditing (each database gets its own folder, faster to query).
3. **Destinations** (any combination, written to each):

| Destination | Format / table | Auth | Use |
|---|---|---|---|
| Storage account | `.xel` in append blobs; read in SSMS | ==+managed identity== (system- or user-assigned, needs Storage Blob Data Contributor) or storage access keys | long-term, tamper-resistant archive |
| Log Analytics | `AzureDiagnostics`, Category `SQLSecurityAuditEvents` | diagnostic setting | KQL, alerts, Sentinel |
| Event Hubs | stream | diagnostic setting (same region) | forward to a SIEM; no long-term retention |

4. **Retention** (storage): default ==@0 = unlimited==. Changing from 0 to N days applies only to logs written after the change. With an immutable time-based policy on the container, the storage retention interval must be **shorter** than the SQL audit retention, and SQL retention 0 with a WORM policy is ==!not supported==. Set **Allow protected append writes** (append blobs) on the immutable policy. If the storage account allows Entra ID only (Shared Key disabled), use managed identity auth.
5. **The silent-failure trap.** Choosing Log Analytics or Event Hubs creates a diagnostic setting named `SQLSecurityAuditEvents_xxxx`. ==!Delete it and auditing stops with no error==, while the Auditing blade still says On. Add an Activity log alert on diagnostic-setting deletion.
6. **SQL Managed Instance** uses SQL Server audit syntax:
   - Storage: create a SAS for the container, `CREATE CREDENTIAL [{container-url}] WITH IDENTITY='SHARED ACCESS SIGNATURE', SECRET='{sas-without-?}'`, then `CREATE SERVER AUDIT ... TO URL (PATH=..., RETENTION_DAYS=n)`. Renew the SAS before it expires or auditing fails.
   - Log Analytics / Event Hubs: `CREATE SERVER AUDIT ... TO EXTERNAL_MONITOR`, plus a diagnostic setting on the MI with category **SQLSecurityAuditEvents**.
   - Then `CREATE SERVER AUDIT SPECIFICATION` (or database audit specification) and `ALTER SERVER AUDIT ... WITH (STATE = ON)`.
7. **Auditing of Microsoft support operations** logs what Microsoft engineers do during a support case. SQL Database: toggle **Enable Auditing of Microsoft support operations** on the server Auditing page; Log Analytics category `DevOpsOperationsAudit`. MI: create a **separate** server audit with **Microsoft support operations** ticked (ticking it on an existing audit turns that audit into support-only); diagnostic category **DevOps operations Audit Logs**.
8. **Enforce with Azure Policy**: *Auditing on SQL server should be enabled* (AuditIfNotExists, reports only), *Configure SQL servers to have auditing enabled* (DeployIfNotExists) and *Configure SQL servers to have auditing enabled to Log Analytics workspace* (DeployIfNotExists, fixes).
9. **Auditing is best-effort.** Under very high activity or network load, the engine can let transactions proceed without recording every event. Audit is evidence, not a guaranteed ledger; narrow the action groups to reduce event loss.

> The training unit's comparison table says support operations auditing is "Not available" for Azure SQL Database. The product doc *Auditing Microsoft support operations* applies to Azure SQL Database and shows the portal toggle. Product docs win.

## Where it lives

| Task | Path |
|---|---|
| Server audit (SQL Database) | `Azure portal > SQL server > Security > Auditing` |
| Database audit | `Azure portal > SQL database > Security > Auditing` (**View server settings** link shows the inherited server audit) |
| Support operations | Server Auditing page > **Enable Auditing of Microsoft support operations** |
| MI audit | SSMS / T-SQL on the MI; `Azure portal > SQL managed instance > Monitoring > Diagnostic settings` for external targets |
| Policy | `Azure portal > Policy > Definitions`, search "auditing" |

```kql
AzureDiagnostics
| where Category == "SQLSecurityAuditEvents"
| where statement_s has "DROP" or statement_s has "TRUNCATE"
| project TimeGenerated, server_instance_name_s, database_name_s, client_ip_s, statement_s
```

```bash
az sql server audit-policy update -g rg-sec -n contoso-sql --state Enabled \
  --blob-storage-target-state Enabled --storage-account contosoaudit \
  --log-analytics-target-state Enabled --log-analytics-workspace-resource-id <workspace-id>
```

## Exam traps

- "Audit every SELECT that reads customer data": ==+BATCH_COMPLETED_GROUP== (in the default set).
- "Tamper-proof archive kept 7 years": ==+storage account + immutable time-based policy==, SQL retention longer than the WORM interval. Not Event Hubs (buffer only), not Log Analytics alone.
- "Real-time feed to a third-party SIEM": ==+Event Hubs==.
- "Configure MI auditing to Log Analytics from the portal only": ==!not enough==. MI needs `TO EXTERNAL_MONITOR` in T-SQL **plus** the diagnostic setting.
- MI storage auth in the docs is a **SAS credential**; SQL Database storage auth recommends **managed identity**.
- Server and database audits both on = double logging, not an override.
- Retention change from 0 to 90 days does ==!not delete== older logs.
- Policy *Auditing on SQL server should be enabled* only reports; the *Configure...* policy remediates.
