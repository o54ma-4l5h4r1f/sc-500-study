## Azure first

- **Azure Policy** checks Azure *resources* against rules. Normal policies only see what Azure Resource Manager sees: a VM's size, its tags, whether a disk is encrypted. They can't see *inside* the operating system.
- A **policy effect** decides what a rule does: `Audit` / `AuditIfNotExists` report; `DeployIfNotExists` and `Modify` change things, using the **assignment's managed identity**, and fix existing resources only through a **remediation task**.
- An **initiative** is a bundle of policy definitions assigned together.
- An **Azure Arc-enabled server** is a non-Azure machine (on-premises, AWS, GCP) that appears in Azure through the **Connected Machine agent**.

Before you start: Foundations **azure-policy-basics**, **virtual-machines-and-disks**, **azure-arc-and-hybrid-machines**, **defender-for-cloud-basics**.

## In one sentence

**Azure Machine Configuration** (formerly *Azure Policy guest configuration*) is the part of Azure Policy that looks inside the guest OS — registry, services, password rules, SSH settings — and either **audits** them or **applies and keeps** a desired setting, on Azure VMs and Arc-enabled servers.

## Why it exists

As an analyst you saw the result of weak server settings: a guessable local admin password, SMBv1 left on, root login over SSH. Somebody had to set those; nobody checked them afterwards. Group Policy only reaches domain-joined Windows machines. Linux, workgroup servers and machines in other clouds escape it.

Think of a building inspector with a checklist. Ordinary Azure Policy inspects the outside of the building: does it have a fire door? Machine Configuration goes inside and checks the fire extinguishers are charged. In **audit** mode it writes a report. In **apply** mode it also recharges any empty extinguisher it finds, and in **autocorrect** mode it comes back on every visit to recharge again.

## What actually matters

**1. Prerequisites differ for Azure VMs and Arc servers.**

| | Azure VM | Arc-enabled server |
|---|---|---|
| Agent | **Machine Configuration extension** (`AzurePolicyforWindows` / `AzurePolicyforLinux`) | ==@Built into the Connected Machine agent== — don't add the extension |
| Identity | ==@System-assigned managed identity== required | Comes with the Arc agent |
| How to deploy at scale | Initiative `Deploy prerequisites to enable Guest Configuration policies on virtual machines` | Onboard to Arc; check agent health |
| Version to *apply* settings | extension 1.26.24+ | Connected Machine agent 1.10.0+ |

The prerequisites initiative uses `Modify` to add the identity and `DeployIfNotExists` to add the extension. New VMs get them automatically. ==!Existing VMs need a remediation task.== The resource provider `Microsoft.GuestConfiguration` must be registered (the portal and Defender for Cloud do it for you). Adding a system-assigned identity can change which identity an app gets from the instance metadata service, so test first.

**2. Three identities, three jobs.** The **machine's** system-assigned identity authenticates to the service and can download private packages (grant it **Storage Blob Data Reader** on the container). The **policy assignment's** managed identity deploys or modifies Azure resources during remediation (it needs roles such as **Guest Configuration Resource Contributor**). Configurations run locally as **LocalSystem** (Windows) or **root** (Linux).

**3. Assignment types — the core exam fact.**

| `assignmentType` | Behaviour |
|---|---|
| `Audit` | Report only. Changes nothing. |
| `ApplyAndMonitor` | Apply once (on remediation, or when the VM is created/updated), then ==@report drift without fixing it== |
| `ApplyAndAutoCorrect` | Apply, then ==+fix drift at every evaluation== — no recurring remediation task needed |

A package also has a type: `Audit` (checks only) or `AuditAndSet` (contains code that can set values). ==!An audit-only package can't apply anything==, whatever assignment type or policy effect you pick. Policy's `enforcementMode` (`Default` / `DoNotEnforce`) controls the policy effect, not the guest assignment, and isn't a stop switch for autocorrect.

**4. Built-in security baselines are audit-only.** `Windows machines should meet requirements of the Azure compute security baseline` and `Linux machines should meet requirements for the Azure compute security baseline` support only `AuditIfNotExists` and `Disabled`. They check password policy, audit policy, user rights, Defender settings (Windows) and SSH, file permissions, kernel parameters, services (Linux). To include Arc servers, set the parameter ==!`IncludeArcMachines` to `true`== — it defaults to `false`. A preview adds remediation for selected baseline settings (Azure Security Baselines, CIS and DISA STIG for Linux) using `DeployIfNotExists` and `RemediationLocations`.

**5. Custom configurations use PowerShell DSC.** Write a DSC configuration → compile to a `.mof` → `New-GuestConfigurationPackage` (type `Audit` or `AuditAndSet`) → test with `Get-GuestConfigurationPackageComplianceStatus` / `Start-GuestConfigurationPackageRemediation` → upload the zip to HTTPS storage (Blob recommended) → `New-GuestConfigurationPolicy` (mode `Audit`, `ApplyAndMonitor` or `ApplyAndAutoCorrect`) → `New-AzPolicyDefinition` → assign. The policy pins a **SHA256 content hash**, so overwriting the blob breaks it; publish a new version. Never put secrets in a package. Uncompressed size limit: **100 MB**.

**6. Limits and links.** Up to **50 guest assignments per machine**. Agent capped at **5% CPU**. Outbound HTTPS 443 to the service and package storage (service tags `AzureArcInfrastructure` and `Storage`). Defender for Servers **Plan 2** uses Machine Configuration for its OS configuration (security baseline) assessment, shown as OS misconfiguration recommendations ([D3.2.6](D3.2.6.html), [D4.1.3](D4.1.3.html)). It is ==!not== vulnerability scanning or EDR. Unsupported: ARM64 Azure VMs and **uniform** scale sets (flexible scale sets work).

## Where it lives

- `Azure portal > Policy > Definitions` — filter **Category = Guest Configuration**. Assign the prerequisites initiative, then the baseline policies.
- `Azure portal > Policy > Assignments > (assignment) > Create remediation task` — for existing machines.
- `Azure portal > Policy > Compliance > (assignment) > (resource)` — per-setting expected vs actual value.
- `Azure portal > Guest Assignments` (search the portal for it) — every `Microsoft.GuestConfiguration/guestConfigurationAssignments` resource across the tenant, with per-setting reasons.
- Defender for Cloud: recommendation `Virtual machines' Guest Configuration extension should be deployed with system-assigned managed identity`.

```powershell
Install-Module GuestConfiguration
New-GuestConfigurationPackage -Name 'Baseline' -Configuration '.\output\localhost.mof' `
  -Type AuditAndSet -Path '.\pkg'
New-GuestConfigurationPolicy -PolicyId (New-Guid) -ContentUri $uri -LocalContentPath '.\pkg\Baseline.zip' `
  -DisplayName 'Apply baseline' -Platform Windows -PolicyVersion 1.0.0 `
  -Mode ApplyAndAutoCorrect -Path '.\policy' -UseSystemAssignedIdentity
```

Agent logs: `C:\ProgramData\GuestConfig\gc_agent_logs\gc_agent.log` (Windows Azure VM), `/var/lib/GuestConfig/gc_agent_logs/gc_agent.log` (Linux Azure VM); Arc servers use `arc_policy_logs`.

## Exam traps

- "Audit OS settings inside VMs and on-premises servers" → ==+Machine Configuration== (+ Arc for on-prem). Not Azure Policy alone, not Defender for Cloud alone.
- "Correct drift automatically" → ==+`ApplyAndAutoCorrect`==. `ApplyAndMonitor` only reports drift after the first apply.
- No managed identity or no extension on an Azure VM → no report. The fix is the prerequisites initiative **plus a remediation task** for existing VMs.
- Installing the VM extension on an Arc server is wrong — the Arc agent already contains it.
- Assigning a baseline at a scope containing Arc servers does ==!not== include them until `IncludeArcMachines = true`.
- The built-in baselines can't be switched to `DeployIfNotExists`. Enforcement needs a custom `AuditAndSet` package (or the preview).
- Deleting a policy assignment removes its guest assignment; removing a policy *from an initiative* does not — clean up manually. Deleting never restores old settings.
- The tag `CustomGuestConfigurationSetPolicy=disable` stops remediation for **custom** content only.
