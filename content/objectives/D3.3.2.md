## Azure first

- An **AKS cluster** has two halves. The **control plane** (API server, scheduler, etcd database) is run by Microsoft. The **nodes** are VMs in your subscription that run your **pods**.
- The **API server** is the only door into the cluster. `kubectl` talks to it. Whoever reaches it with valid credentials controls the cluster.
- A **namespace** is a folder inside the cluster that separates teams. A **service account** is a Kubernetes identity for a pod (not a person).
- A **managed identity** is an Entra ID identity Azure creates for a resource, with no password you handle. The **Azure Instance Metadata Service (IMDS)** at `169.254.169.254` hands out tokens for the node's managed identity.

See the Foundations pages listed above, especially *containers-and-kubernetes-basics* and *azure-rbac-and-entra-roles*.

## In one sentence

AKS security means locking four doors: who can sign in to the API server (Entra ID, no local accounts), what they can do once in (Kubernetes RBAC or Azure RBAC), who can reach the API server and which pods can talk to each other (private cluster or authorized IPs, network policies), and what each pod is allowed to be and hold (workload identity, Key Vault CSI driver, Pod Security admission, Azure Policy, patched nodes).

## Why it exists

A default cluster is an open-plan office. The front desk (API server) has a public address. A master key (the local admin kubeconfig) works forever and never shows in a sign-in log. Every pod can walk into every other pod's room. Any pod can ask IMDS for the node's identity token. And secrets sit in etcd as base64, which is encoding, not encryption.

As an analyst you saw incidents where one leaked kubeconfig or one compromised pod became the whole cluster. These controls are how an engineer prevents that.

## What actually matters

**1. Authentication: Entra ID in, local accounts out.**

- `az aks update --enable-aad --aad-admin-group-object-ids <group>` turns on **AKS-managed Microsoft Entra integration**. Users get short-lived Entra tokens. Conditional Access and sign-in logs now apply.
- Entra integration ==!doesn't remove local accounts==. The static admin kubeconfig still works until you run `az aks update --disable-local-accounts`.
- ==!Set an Entra admin group first==, or you lock yourself out.
- Entra integration ==!can't be disabled== once enabled.

**2. Authorization: two models, use both.**

| | Kubernetes RBAC | Azure RBAC for Kubernetes |
|---|---|---|
| Objects | Role, ClusterRole, RoleBinding, ClusterRoleBinding | Azure role assignments |
| Where stored | In each cluster | Azure control plane |
| Scope of one grant | One cluster | Cluster, RG, subscription, management group |
| CA / PIM | No | Yes |
| Audit | Cluster audit log | Azure Activity Log |
| Built-in roles | `view`, `edit`, `admin`, `cluster-admin` | ==@Azure Kubernetes Service RBAC Reader / Writer / Admin / Cluster Admin== |

Separately, two Azure roles decide **who can download a kubeconfig**: ==@Azure Kubernetes Service Cluster User Role== (user kubeconfig, no rights by itself) and ==@Azure Kubernetes Service Cluster Admin Role== (admin kubeconfig, full access). Recommended pattern: Azure RBAC controls credential download; Kubernetes RBAC grants namespace rights; bind **Entra groups**, not users. Neither Reader role can read Secrets.

**3. API server network exposure.**

- **Private cluster** (`--enable-private-cluster`): API server gets a **private IP** in your VNet via a private endpoint; DNS resolves through a private DNS zone (`privatelink.<region>.azmk8s.io`). Admin access needs a jump box, Bastion, VPN/ExpressRoute or self-hosted agents.
- **Authorized IP ranges** (`--api-server-authorized-ip-ranges`): public endpoint stays, but only listed CIDRs connect. Up to **200** ranges. Needs the Standard load balancer. ==!Can't be combined with a private cluster.== `0.0.0.0/32` means "only the cluster's own outbound IP".

**4. Network policies (pod-to-pod).** By default every pod can reach every pod. A `NetworkPolicy` selects pods and lists allowed ingress/egress; everything else is denied. Engines:

| Engine | Pick it when |
|---|---|
| ==@Cilium== (Azure CNI Powered by Cilium) | New clusters; eBPF, recommended; L7/FQDN via ACNS |
| ==@Calico== | ==+Windows node pools== (Cilium is Linux-only); also cross-cloud consistency |
| Azure Network Policy Manager (NPM) | ==!Legacy==: Windows support ended **30 September 2026**, Linux support ends **30 September 2028**; migrate Linux clusters to Cilium |

Add a policy that blocks pod egress to `169.254.169.254/32` so pods can't steal the node's identity token.

**5. Workload identity and secrets.**

- **Microsoft Entra Workload ID** replaces stored secrets. Pieces: the cluster **OIDC issuer** (`--enable-oidc-issuer`), `--enable-workload-identity`, a **service account annotated** with a client ID, a **federated identity credential** on the app registration or user-assigned managed identity (subject `system:serviceaccount:<ns>:<sa>`), and a mutating webhook that injects a projected token. The SDK swaps that token for an Entra access token.
- **Azure Key Vault provider for Secrets Store CSI Driver** mounts Key Vault secrets, keys and certificates as files via a `SecretProviderClass`. Secrets ==+never land in etcd== unless you turn on optional sync to Kubernetes Secrets.
- `az aks update --attach-acr <acr>` gives the cluster's kubelet identity **AcrPull**, so no `imagePullSecret` is needed.
- Kubernetes Secrets are ==!base64, not encrypted==.

**6. Pod hardening and governance.**

- **Pod Security admission** (built in since Kubernetes 1.25) applies **Pod Security Standards** per namespace via labels. Standards: **Privileged**, **Baseline**, **Restricted**. Modes: **enforce**, **warn**, **audit**.
- **Security context** in the pod spec: `runAsNonRoot`, `readOnlyRootFilesystem`, `allowPrivilegeEscalation: false`, drop `ALL` capabilities, `seccompProfile: RuntimeDefault`. Extras: user namespaces (`hostUsers: false`), AppArmor.
- **Azure Policy add-on for AKS** (Gatekeeper) applies the same idea from Azure, at scale. Built-in initiatives: *Kubernetes cluster pod security baseline standards for Linux-based workloads* and *...restricted standards...*. Default effect **audit**; change to **deny** to block.

**7. Node patching.** Node OS auto-upgrade channel: `None`, `Unmanaged`, ==@`SecurityPatch`== (security-only, faster, may live-patch), ==@`NodeImage`== (weekly new VHD; the default for new AKS Standard clusters). Kubernetes version upgrades use the separate cluster auto-upgrade channel.

## Where it lives

- **Azure portal > Kubernetes services > *cluster* > Settings > Security configuration** (Entra auth, Azure RBAC, local accounts).
- **> Settings > Networking** (private cluster, authorized IP ranges, network policy).
- **> Settings > Cluster configuration** (upgrade channels); **> Settings > Policies** (Azure Policy add-on).
- **Azure portal > Policy > Definitions > Category: Kubernetes** (initiatives).

```bash
az aks update -g rg -n aks --enable-aad --aad-admin-group-object-ids <grp> --enable-azure-rbac
az aks update -g rg -n aks --disable-local-accounts
az aks update -g rg -n aks --api-server-authorized-ip-ranges 203.0.113.0/24
az aks update -g rg -n aks --enable-oidc-issuer --enable-workload-identity
az aks enable-addons -g rg -n aks --addons azure-keyvault-secrets-provider,azure-policy
az aks update -g rg -n aks --node-os-upgrade-channel SecurityPatch
kubectl label ns retail-app pod-security.kubernetes.io/enforce=restricted
```

## Exam traps

- "Entra integration is on, but a leaked admin kubeconfig still works" → ==+disable local accounts==.
- "One assignment must govern all clusters in a resource group, with PIM" → Azure RBAC for Kubernetes, not Kubernetes RBAC.
- "Developer can run `az aks get-credentials` but every `kubectl` call is forbidden" → has Cluster User Role but no RBAC permission. Expected.
- "Restrict API server to office IPs **and** make it private" → ==!not both==. Choose one.
- "Stop pods using the node's managed identity" → NetworkPolicy blocking `169.254.169.254` + workload identity.
- "App reads DB password without it being stored in the cluster" → ==+workload identity + Key Vault CSI driver==. Kubernetes Secret is the distractor.
- Network policy on Windows nodes → ==+Calico==. Not Cilium (Linux-only) and ==!not Azure NPM== (Windows support ended 30 September 2026; older study material still says NPM).
- "Block privileged pods across 40 clusters" → Azure Policy initiative with **deny** at subscription scope. Namespace labels are per cluster.
- Pod-managed identity (preview) is the old approach; workload identity replaced it.

**Training module vs product docs (product docs win):** unit 3 recommends Azure NPM ("`--network-policy azure`") when you need Windows node pools. The AKS docs say NPM support for Windows nodes ==!ended 30 September 2026== (new subscriptions can no longer enable it) and recommend ==+Calico== for Windows; NPM on Linux ends 30 September 2028.

**Name change to know:** the training module says *Azure RBAC for Kubernetes authorization*. Current AKS docs call the same feature *Microsoft Entra ID authorization for the Kubernetes API*. Same roles, same CLI flag (`--enable-azure-rbac`). Expect either name.
