## Azure first

- A **container image** is a sealed package of an app plus everything it needs. A **registry** (Azure Container Registry, ACR) stores images. A **container** is a running copy of an image.
- **AKS (Azure Kubernetes Service)** is Microsoft-run Kubernetes. Your containers run in **pods** on **nodes** (VMs). The **API server** is the cluster's front desk: every `kubectl` command and every deployment goes through it.
- A **DaemonSet** is a Kubernetes object that runs one copy of a pod on every node — the way an agent gets onto every machine.
- **Defender for Cloud** is the Azure security posture and workload-protection service. It is sold as *plans*; **Defender for Containers** is one plan, switched on per subscription (or per AWS/GCP connector).

See the Foundations pages listed above, especially *containers-and-kubernetes-basics* and *defender-for-cloud-basics*.

## In one sentence

Defender for Containers is the Defender for Cloud plan that scans container images for known vulnerabilities, checks Kubernetes clusters for risky configuration, watches running containers and the API server for attacks, and can block bad deployments at the cluster's door.

## Why it exists

A container image is built once and copied everywhere. One vulnerable library in the base image ends up in every pod. Kubernetes also adds a new control plane that attackers target: secrets, service accounts, cluster roles. As an analyst you triaged alerts like "Binary drift detected" or "Exposed Kubernetes dashboard". Those alerts come from this plan. As the engineer, you now decide whether it is on, which components it deploys, and where its alerts go.

Think of a warehouse. Registry scanning inspects every box as it arrives. Posture checks walk the aisles looking for propped-open fire doors. The runtime sensor is the CCTV. The admission controller is the loading-dock guard who refuses a pallet that fails inspection.

## What actually matters

**1. The components.** Turn the plan on at **Environment settings > subscription > Defender plans > Containers = On**, then open **Settings**. All five components are on by default:

| Component | What it is | What it gives you |
|---|---|---|
| ==@Defender sensor== | DaemonSet on every node, eBPF-based, deployed as the AKS **Security profile** | Runtime threat alerts, binary drift, anti-malware (sub-option), security gating (sub-option) |
| ==@Azure Policy== (add-on) | Gatekeeper v3 admission webhook | Data-plane hardening: audit or **deny** non-compliant pods |
| ==@Agentless scanning for machines== | Periodic disk snapshots of node VMs | Node OS vulnerability findings, no agent |
| ==@Kubernetes API access== | Managed identity + **Kubernetes Agentless Operator** role, AKS Trusted Access | Agentless discovery, posture, runtime vulnerability assessment, response actions |
| ==@Registry access== | Direct connection to ACR | Agentless image vulnerability assessment |

Control-plane threat detection from **Kubernetes audit logs** has no toggle. It is collected agentlessly from Azure. Alerts only fire for activity *after* the plan is enabled.

**2. Vulnerability assessment = Microsoft Defender Vulnerability Management (MDVM).** One engine for both paths.

- **Registry:** scans an image within a few hours of push or import. Rescans **daily** any image pushed, imported or pulled in the last **30 days**, or running on a monitored cluster.
- **Runtime:** shows which vulnerable images are actually running, by cluster and namespace. It covers images from any registry, not only ACR.
- Two recommendations: *Azure registry container images should have vulnerabilities resolved* and *Azure running container images should have vulnerabilities resolved*.
- Findings carry CVE, CVSS, fixed version and **exploitability**. Fix = update the package, rebuild, push, redeploy.

**3. Posture (misconfigurations).** Kubernetes API access compares cluster config with the CIS Kubernetes Benchmark and your assigned initiatives. Typical findings: containers running as root or privileged, no network policies, broad ClusterRoleBindings, untrusted registries. **Attack path analysis** and **Cloud Security Explorer** need ==@Defender CSPM== as well. Without CSPM you still get the recommendations.

**4. Runtime threats.** Two sources:

- **Audit logs** (control plane): secret access, ClusterRoleBinding changes, odd source IPs.
- **Defender sensor** (workload): shells in web containers, crypto miners, C2 connections, privilege escalation, suspicious DNS.
- **Binary drift**: a process starts from a file that wasn't in the original image. Configure at **Environment settings > Containers drift policy**. Each rule has an action (**Drift detection alert**, **Drift detection blocking**, **Ignore drift detection**), a cloud scope, a resource scope (namespace, image, label, cluster) and a process allow list. Highest-priority matching rule wins; otherwise the default rule applies. ==!Blocking is preview== and needs the Helm-deployed sensor (version 0.10.2+); alerting is GA.

**5. Gated deployment.** The Azure Policy add-on (and the newer **Defender Security Gating** option) evaluates each pod spec at admission. **Audit** records, **Deny** rejects. Roll out in audit first.

**6. Roles and plumbing.** Enable with **Security Admin** (or Contributor). The first enablement also needs **Owner** or **User Access Administrator**, because Defender for Cloud creates identities and assigns roles for auto-provisioning. **Security Reader** views findings. Alerts reach Sentinel only after you connect the **Microsoft Defender for Cloud** data connector.

**Multicloud one-liner:** EKS (via an AWS connector) and GKE (via a GCP connector) get the same plan. Audit logs come agentlessly from CloudWatch or Cloud Logging. The sensor and Policy add-on install as **Azure Arc-enabled Kubernetes extensions**. ECR, GCR and Artifact Registry are scanned. Connector details belong to D4.1.4.

## Where it lives

- **Azure portal > Microsoft Defender for Cloud > Environment settings > *subscription* > Defender plans > Containers > Settings** (components).
- **Defender for Cloud > Environment settings > Containers drift policy** (drift rules).
- **Defender for Cloud > Recommendations**, filter *Resource type = Kubernetes services*. Look for *Azure Kubernetes Service clusters should have Defender profile enabled* and *Azure Policy for Kubernetes should be installed and enabled on your clusters*, then **Fix**.
- **Defender for Cloud > Security alerts**; the same alerts appear in the **Defender portal** incidents queue.

```bash
# enable the plan on the current subscription
az security pricing create --name Containers --tier Standard

# put the Defender sensor (security profile) on one cluster
az aks update -g rg-aks -n aks-prod --enable-defender
```

## Exam traps

- "See vulnerabilities in images pulled from Docker Hub that are running in AKS" → ==+runtime vulnerability assessment== (Kubernetes API access). Registry scanning only covers connected registries.
- "Attack paths for a vulnerable container" with only Defender for Containers on → ==!not available==. Needs Defender CSPM.
- "Block deployment of privileged pods" → ==+Azure Policy add-on in Deny==. Not the sensor, not a recommendation.
- "Stop a process that wasn't in the image" → drift policy with **Drift detection blocking** (preview). Alert-only is the GA option.
- Runtime alerts missing → the **sensor** isn't deployed. Control-plane alerts don't need it.
- The person enabling the plan has Security Admin only and auto-provisioning fails → needs ==@Owner or User Access Administrator== for the role assignments.
- Alerts not in Sentinel → no data connector. Routing isn't automatic.
- Old names: "Defender profile" = the sensor; "Microsoft Defender for container registries" and "Defender for Kubernetes" are the retired plans this replaced.

## Skip

- **Skip:** the MCR image table (`security-publisher`, `low-level-collector`, `pod-collector`...). Know "Microsoft maintains the sensor images", not their names.
- **Skip:** the AWS IAM role names (`MDCContainersAgentlessDiscoveryK8sRole`) and GCP service-account names in the architecture article. Know only that connectors create an identity for discovery.
- **Skip:** the managed identity name `CloudPosture/securityOperator/DefenderForContainersSecurityOperator` and the ClusterRole string. Know "Kubernetes Agentless Operator role via Trusted Access".
- **Skip:** the CVSS score bands in unit 4. You know severity ratings from analyst work.
- **Skip:** unit 5's Sentinel connector click-path and KQL. That's D4.2 (and analyst ground).
- **Skip:** support-matrix rows for every Kubernetes distribution and OS. Know AKS, EKS, GKE, Arc.
- **Skip:** pricing per vCore. Reference material, not exam content.

**Where the training module and product docs disagree (product docs win):** unit 2 calls out four "pillars"; the product overview lists five domains (adding *software supply chain protection* and *deployment & monitoring*). Same features, different grouping. Unit 5 marks its Defender XDR settings path with an unresolved "[REVIEW]" note — don't memorise that path.
