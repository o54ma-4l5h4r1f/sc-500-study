## Azure first

- **Azure Container Instances (ACI)** runs one **container group** (one or more containers sharing a host, network and lifecycle) on demand. No cluster, no scaling. Think "a VM, but for one container".
- **Azure Container Apps (ACA)** runs many container apps inside a shared **Container Apps environment** — a managed Kubernetes underneath that you never see, with scaling, revisions and built-in ingress.
- **Ingress** is the front door that accepts HTTP/TCP traffic and routes it to your app.
- A **delegated subnet** is a subnet handed over to one Azure service so it can drop its resources into your VNet.
- A **managed identity** lets the container prove who it is to Key Vault, ACR or Storage with no stored secret.

See the Foundations pages listed above, especially *containers-and-kubernetes-basics* and *virtual-networks-and-subnets*.

## In one sentence

For both services you give the workload a managed identity (to pull from ACR and read Key Vault), keep secrets out of plain environment variables, and take it off the public internet — ACI by deploying the container group into a delegated subnet, Container Apps by using an internal environment, internal ingress, IP restrictions and built-in authentication.

## Why it exists

Serverless containers feel "safe by default" because there is no OS to patch. They aren't. A default ACI group gets a **public IP**. A default Container Apps setup often has every app on **external ingress**. Connection strings get pasted into environment variables that anyone with **Reader** can see. ACI is a garden shed: one thing in it, lock its door. Container Apps is a block of flats: the building (environment) is the security boundary, and each flat (app) still needs its own door rules.

## What actually matters

**Azure Container Instances**

- **Managed identity.** System-assigned (dies with the group) or user-assigned (shared, independent). Grant it **Key Vault Secrets User**, **AcrPull** and so on. For ==@image pulls from ACR, ACI supports only a user-assigned identity== (`--acr-identity <identity-resource-id>`); system-assigned can't be used for the pull.
- **Secrets.** Use `secureValue` instead of `value` for environment variables. Secure values aren't returned by `GET`, the portal or the CLI. Plain `value` entries are readable by anyone with Reader. In Bicep, `keyVaultRef.getSecret(...)` feeds a secure value at deployment time.
- **VNet deployment.** Delegate a subnet to `Microsoft.ContainerInstance/containerGroups`, then `az container create --vnet --subnet`. The group gets a private IP and can reach private endpoints (ACR, Key Vault). Limits: ==!no public IP or DNS label==, no global peering, outbound only through a **NAT gateway**, and the ACR private endpoint must sit in a ==!different subnet== from the delegated one.
- **Security context.** `runAsUser`/`runAsGroup` (non-root) and `readOnlyRootFilesystem: true`, with `emptyDir` volumes for writes. ACI doesn't allow privileged containers.
- **Confidential containers (one-liner):** the Confidential SKU runs the group in a Hyper-V isolated TEE on AMD SEV-SNP hardware, with memory encryption, a verifiable execution policy and remote attestation.

**Azure Container Apps**

- **Environment = boundary.** Apps in one environment share a subnet, Log Analytics workspace and Dapr config, and can call each other privately. Put apps of different trust levels in **separate environments**. An environment in a custom VNet can be **internal** (private IP only) or external.
- **Ingress.** **External** = reachable from the internet (public FQDN). **Internal** = reachable only inside the environment / VNet. Set back-end APIs and workers to internal. `allowInsecure` defaults to **false** (HTTP redirects to HTTPS). **Client certificate mode** `Require` / `Accept` / `Ignore` (default) gives inbound mTLS. **Private endpoints** to the environment and **Front Door via Private Link** are also supported.
- **IP restrictions.** Rules are CIDR + Allow or Deny. ==!All rules must be the same type== — you can't mix allow and deny. No rules = all traffic allowed. Blocked callers get *RBAC: Access Denied*.
- **Built-in authentication** (Easy Auth). Platform middleware that signs users in with Entra ID (or other providers) before traffic reaches your code. No code changes. Works for external ingress apps.
- **Managed identity.** System- or user-assigned; a user-assigned identity can be shared across apps. Use it for ACR pull, Key Vault, Storage, AI endpoints.
- **Secrets.** App-level secrets are stored by the platform. ==+Key Vault references== (`keyvaultref:<secret-uri>,identityref:<identity-id>`) fetch the value with the app's identity; with a versionless URI, Container Apps fetches a new version ==@within 30 minutes== and restarts active revisions that use it as an environment variable (App Service / Functions references refresh within 24 hours — don't mix the two numbers). Plain app-level secrets you edit by hand need a restart or a new revision.
- **In-environment encryption.** **Peer-to-peer encryption** (environment setting, ==!off by default==) TLS-encrypts traffic between apps. Dapr sidecars add automatic **mTLS** for Dapr service invocation; scope Dapr components to the apps that need them.

## Where it lives

- **ACI:** Azure portal > Container instances > Create > **Networking** tab (Public / Private / None), **Advanced** tab (environment variables with *Secure* = Yes); **Settings > Identity**.
- **Container Apps:** Azure portal > Container Apps > *app* > **Settings > Ingress** (enabled, *Accepting traffic from anywhere* vs *Limited to Container Apps Environment*, IP security restrictions mode, client certificate mode); **Settings > Authentication**; **Settings > Identity**; **Settings > Secrets**.
- **Environment:** Container Apps Environment > **Networking** (VNet, internal/external, private endpoint, peer-to-peer encryption).

```bash
# ACI in a VNet, pulling from ACR with a user-assigned identity
az network vnet subnet update -g rg --vnet-name vnet -n aci --delegations Microsoft.ContainerInstance/containerGroups
az container create -g rg -n api --image contosoacr.azurecr.io/api:1.0 \
  --vnet vnet --subnet aci --assign-identity <uami-id> --acr-identity <uami-id>

# Container Apps: internal ingress, IP allow rule, Key Vault-backed secret
az containerapp ingress enable -g rg -n orders --type internal --target-port 8080
az containerapp ingress access-restriction set -g rg -n web --rule-name corp --ip-address 203.0.113.0/24 --action Allow
az containerapp secret set -g rg -n orders --secrets "db=keyvaultref:<secret-uri>,identityref:<uami-id>"
```

## Exam traps

- "ACI must pull from a private ACR with no stored credentials" → ==+user-assigned managed identity with AcrPull== + `--acr-identity`. System-assigned is the trap; admin credentials are the other.
- "ACI in a VNet and also reachable on a public IP" → ==!not supported==. Front it with Application Gateway.
- Connection string visible to a Reader on the container group → it was `value`, not `secureValue`.
- "Back-end Container App must not be internet-facing" → ==+internal ingress== (or an internal environment). IP rules alone still leave it public.
- "Allow 10.0.0.0/8 and deny one IP inside it" → ==!can't mix== allow and deny rules in Container Apps.
- "Require Entra sign-in for a Container App with no code change" → built-in authentication.
- "Encrypt traffic between apps in the environment" → peer-to-peer encryption (or Dapr mTLS for Dapr calls). It's off by default.
