## Azure first

- A **virtual network (VNet)** is your private network in Azure. A **subnet** is a slice of its address range. **VNet peering** joins two VNets so their machines can reach each other by private IP.
- A **VM** gets a private IP from its subnet. It only gets a **public IP** (an internet address) if you attach one.
- **RDP** (port 3389) is how you get a Windows desktop remotely. **SSH** (port 22) is the Linux command-line equivalent. Leaving either open to the internet invites password-spraying bots within minutes.
- A **network security group (NSG)** is a list of allow/deny rules on a subnet or network card. A **service tag** (such as `GatewayManager` or `AzureCloud`) is a Microsoft-maintained name for a set of IP ranges.

See the Foundations pages listed above, especially *virtual-networks-and-subnets*.

## In one sentence

Azure Bastion is a Microsoft-managed jump box that lives in your VNet: you reach it over HTTPS 443 (browser or native client), and it opens the RDP/SSH session to your VM's **private** IP, so the VM needs no public IP and no open 3389/22 to the internet.

## Why it exists

As an analyst you have triaged the alert "RDP brute force against a VM with a public IP". Bastion removes the target. Think of a building with a single guest badge desk. Visitors never walk up to an office door from the street. They check in at the desk (Bastion, port 443), and the desk escorts them inside to the office (the VM, over the private network).

Before Bastion you had two bad choices: a public IP on every VM, or your own jump-box VM that you had to patch and harden. Bastion is the jump box, run and patched by Microsoft.

## What actually matters

**1. Pick the SKU from the feature you need.** There are four. You can ==@upgrade but never downgrade== (downgrade = delete and recreate).

| Feature | Developer | Basic | Standard | Premium |
|---|---|---|---|---|
| Cost | ==+Free== (shared infra) | Hourly | Hourly | Hourly |
| Needs AzureBastionSubnet + public IP | No | Yes | Yes | Subnet yes; public IP ==@not for private-only== |
| VMs in peered VNets | ==!No== | Yes | Yes | Yes |
| Concurrent connections | 1 VM at a time | Yes | Yes | Yes |
| Host scaling (instances) | No | 2 (fixed) | 2–50 | 2–50 |
| Native client (`az network bastion`) | No | No | ==@Yes== | Yes |
| Shareable link | No | No | ==@Yes== | Yes |
| IP-based connection, custom ports, file transfer | No | No | Yes | Yes |
| Linux via RDP / Windows via SSH | No | No | Yes | Yes |
| Kerberos authentication | Yes | Yes | Yes | Yes |
| Session recording | No | No | No | ==@Premium only== |
| Private-only deployment (no public IP) | No | No | No | ==@Premium only== |

Each instance carries **20 RDP + 40 SSH** concurrent sessions. Basic is fixed at 2 instances (40 RDP / 80 SSH). Standard and Premium go to 50 instances (1,000 RDP / 2,000 SSH). Developer is a shared pool in select regions only, for dev/test.

**2. The subnet rules are strict.** The subnet must be named exactly ==@AzureBastionSubnet==. It must be ==@/26 or larger== (/25, /24…). Bastions created before 2 November 2021 on /27 still work. It holds nothing else. It must be in the same VNet and resource group as the Bastion. User-defined routes (UDRs) are not supported on it. The public IP must be **Standard** SKU, **Static**.

**3. An NSG on AzureBastionSubnet is optional, but if you add one it needs all eight rules.** Miss one and Bastion stops receiving platform updates or connecting.

| Direction | Source → Destination | Port | Why |
|---|---|---|---|
| Inbound | `Internet` → any | 443 | users connect (can narrow to your public IPs) |
| Inbound | `GatewayManager` → any | 443 | Azure control plane |
| Inbound | `AzureLoadBalancer` → any | 443 | health probes |
| Inbound | `VirtualNetwork` → `VirtualNetwork` | 8080, 5701 | Bastion's internal components |
| Outbound | any → `VirtualNetwork` | 22, 3389 | sessions to target VMs |
| Outbound | any → `AzureCloud` | 443 | diagnostics and metering logs |
| Outbound | `VirtualNetwork` → `VirtualNetwork` | 8080, 5701 | internal components |
| Outbound | any → `Internet` | 80 | session and certificate validation, shareable links |

On the **target VM subnet**, allow 3389/22 inbound with source = the AzureBastionSubnet range. 3389 and 22 are ==!not== needed inbound on AzureBastionSubnet itself.

**4. Know the four advanced features.**

- **Native client** (Standard+): turn on *Native client support*, then use your own RDP/SSH client via `az network bastion rdp`, `az network bastion ssh` or `az network bastion tunnel`. It adds file upload/download.
- **Shareable link** (Standard+): a URL that lets someone without Azure portal access sign in to one VM. The link holds ==!no credentials==; you hand those over separately. You set an expiry and can delete a link to revoke it. Limit: 500 links per Bastion. Creating links needs the `Microsoft.Network/bastionHosts/createShareableLinks/action` permission; by default users can only read them. Not supported for on-premises VMs, across tenants or over Virtual WAN.
- **Session recording** (Premium): records ==@every== graphical session through that Bastion to a blob container. Bastion authenticates with a SAS URL or (recommended) a managed identity holding Storage Blob Data Contributor. Viewers need **Storage Blob Data Reader**. Recording does ==!not== cover native-client sessions.
- **Private-only** (Premium): Bastion gets only a private IP. Users arrive over ExpressRoute private peering or VPN, with **IP-based connection** turned on. You choose it at deployment time. An existing Bastion ==!can't be converted==; delete and redeploy (the subnet can stay).

**5. Who can connect.** A user needs **Reader** on the VM, on its NIC and on the Bastion resource. Add Reader on the target VNet when Bastion sits in a peered VNet. They still need a working sign-in inside the guest OS (for example, membership of Remote Desktop Users).

**6. Hub-and-spoke.** One Basic-or-higher Bastion in the hub reaches VMs in peered spokes. Use Standard/Premium if you want IP-based connection (connect by private IP instead of picking the VM).

## Where it lives

- **Azure portal > Virtual networks > *vnet* > Bastion**, or **Azure portal > Bastions > Create**. Choose Tier, Instance count, VNet, public IP.
- **Azure portal > Bastions > *bastion* > Settings > Configuration**: tier upgrade, instance count, and the toggles for Native client support, Shareable Link, IP-based connection, Session recording and Kerberos.
- **Bastion > Shareable links** (create, see expiry, delete). **Bastion > Session recordings** (watch recordings). **Bastion > Sessions** (see and disconnect live sessions).
- **VM > Connect > Bastion**: the browser session.

```bash
az network bastion create --name bas-hub --resource-group rg-net \
  --vnet-name vnet-hub --public-ip-address pip-bas --sku Standard \
  --enable-tunneling true --scale-units 2

az network bastion rdp --name bas-hub --resource-group rg-net \
  --target-resource-id <vm-resource-id>
```

## Exam traps

- "Remove the public IP from the VMs but keep RDP for admins" → ==+Azure Bastion==. JIT still uses the VM's own public path; Bastion removes it.
- Subnet called `BastionSubnet` or sized /27 for a new deployment → ==!fails==. Exactly `AzureBastionSubnet`, /26 or larger.
- "Admins must use mstsc / their own SSH client" → ==+Standard or Premium== with native client. Basic is browser-only.
- "Record sessions for auditors" or "no public IP on Bastion itself" → ==+Premium==. Standard is the distractor.
- "Free Bastion that reaches VMs in a peered VNet" → impossible. Developer has ==!no peering==.
- Bastion is ==!agentless==. Nothing is installed on the VM.
- NSG on AzureBastionSubnet that allows only `Internet` 443 → broken. `GatewayManager`, `AzureLoadBalancer` and the 8080/5701 rules are the usual missing pieces.
- Shareable links give access ==!without an Azure account==, but ==!not without VM credentials==.
- Downgrading Premium to Standard to save money → ==!not supported==; redeploy.

## Skip

- **Skip:** unit 2's Contoso host-unit sizing story (40 engineers, 15 peak, 4 units). Know 20 RDP / 40 SSH per instance and 2–50 instances; nothing more.
- **Skip:** the availability-zone region list and IPv6 dual-stack preview in the configuration-settings article. Preview details, region lists — not exam material.
- **Skip:** the PowerShell NSG script in the NSG article. Learn the eight rules from the table, not the loop.
- **Skip:** unit 4's list of RDP client goodies (multi-monitor, audio, printer redirection). The exam asks *which SKU* gives native client, not what mstsc does.
- **Skip:** pricing and the 5 GB free outbound data. That's a reference-page fact, not an exam fact.
- **Skip:** Entra ID authentication for Bastion sessions (VM Administrator Login / VM User Login roles). It's a sign-in detail. Know only that it can't be combined with session recording for portal RDP.

**Where the training module and product docs disagree (product docs win):**

- Unit 3 says you can scope session recording to "specific users/groups". The product article says Bastion records ==@ALL sessions== once recording is on.
- Unit 2's NSG summary lists only four rules. Unit 3 and the product article list eight. Use eight.
