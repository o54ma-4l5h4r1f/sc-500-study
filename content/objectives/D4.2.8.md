## Azure first

- An **automation rule** is a setting inside Microsoft Sentinel: "when an incident matching X appears, do Y". No code, no separate Azure resource you pay for.
- A **playbook** is an **Azure Logic App** — a separate Azure resource in a resource group — whose workflow starts with a Microsoft Sentinel trigger. It can call anything with a connector or an API.
- A **managed identity** is an identity Azure creates for a resource (here, the logic app) so it can sign in to other services without a password. You give it Azure roles like any user.
- **Azure RBAC** roles are assigned at a scope (subscription, resource group, resource). Sentinel's roles sit on the workspace; Logic Apps roles sit on the playbook's resource group.

See the Foundations pages listed above: Logic Apps, Azure RBAC and Entra roles, the Defender portal, and the Log Analytics workspace.

## In one sentence

Automation rules are Sentinel's built-in, ordered triage rules (assign, tag, change status or severity, add tasks, run a playbook); playbooks are Logic Apps that reach outside Sentinel, and Sentinel can only run them after you grant its service account **Microsoft Sentinel Automation Contributor** on the playbook's resource group.

## What's new for an engineer

As an analyst you saw incidents arrive already tagged and assigned. As the engineer you build that, and the hard part is permissions:

- **Grant Sentinel permission** on each playbook resource group (needs **Owner** or **User Access Administrator** there). Otherwise the playbook is greyed out in the rule.
- **Give the playbook an identity** — a system-assigned managed identity with **Microsoft Sentinel Responder** on the workspace if it updates incidents, **Microsoft Sentinel Reader** if it only reads.
- **Hand out least privilege** to people (table below).
- **Monitor it.** Turn on Sentinel health monitoring; rule runs land in `SentinelHealth` (not billed), playbook step logs in `AzureDiagnostics` once Logic Apps diagnostics are sent to the workspace. Configuration changes go to `SentinelAudit` (billed).

## What actually matters

1. **Triggers.** **When incident is created**, **When incident is updated**, **When alert is created** (Scheduled/NRT rules; classic action is **Run playbook** only). Microsoft recommends incident triggers for most work.
2. **Conditions** are AND; use condition groups for OR. The update trigger adds **Changed**, **Changed from**, **Changed to**, **Added** and **Updated by** (use it to stop loops).
3. **Order.** Each trigger type has its own queue; ==@lower order number runs first==. Two rules with the same number run in ==!random order==. If rule 1 lowers severity, rule 2 conditioned on High no longer matches.
4. **Expiration** (default *Indefinite*) disables the rule at a date — the classic use is closing noise during a planned pen test without touching the analytics rule.
5. **Playbook triggers match rule triggers.** Incident-trigger rules run incident-trigger playbooks; alert to alert. The **entity** trigger is manual only. After **2 minutes** a rule moves on whether the playbook finished or not.
6. **Plans.** **Consumption** (multitenant, pay per run, templates work) is the default choice; **Standard** (single-tenant, VNet integration, must be **Stateful**, no template support).

| Need | Role (scope) |
|---|---|
| Create/edit automation rules, attach playbooks | ==@Microsoft Sentinel Contributor== (workspace) |
| Create/edit playbooks | ==@Logic App Contributor== (playbook RG) |
| Run playbooks manually, nothing more | ==@Microsoft Sentinel Playbook Operator== |
| Let Sentinel run playbooks | ==@Microsoft Sentinel Automation Contributor== — Sentinel's service account, ==!never a person== |
| Grant that permission | Owner / User Access Administrator (playbook RG) |
| Playbook identity updates incidents | Microsoft Sentinel Responder (workspace) |

## Where it lives

**Defender portal:** **Microsoft Sentinel > Configuration > Automation** > **Create > Automation rule** (or **Playbook**); **Active playbooks** and **Playbook templates** tabs. Grant Sentinel permission: **Settings > Sentinel > *workspace* > Playbook permissions > Configure permissions** (Azure portal: **Microsoft Sentinel > Settings > Settings > Playbook permissions**), or the **Manage playbook permissions** link in the rule. Content hub playbooks: **Microsoft Sentinel > Content management > Content hub**, filter **Content type: Playbook**. Same pages under **Microsoft Sentinel** in the Azure portal until March 31, 2027.

**Azure portal (playbook side):** **Logic apps > *playbook* > Identity** (turn on system-assigned) → **workspace > Access control (IAM) > Add role assignment** → **Microsoft Sentinel Responder** → member type **Managed identity**.

## Exam traps

- "Close pen-test noise for two weeks, no code." ==+Automation rule with close action and expiration==, not ==!a playbook== or disabling the analytics rule.
- "Alert-trigger rule must change severity." ==!Not possible== — Run playbook only.
- "Playbook greyed out in the rule." ==+Grant Sentinel permission (Automation Contributor) on its resource group.==
- "Analysts may only run playbooks." ==+Playbook Operator==, not ==!Logic App Contributor==.
- "Managed identity must update incidents." ==+Responder==; ==!Reader== only reads.
- "Two rules, same order number, run in parallel." ==!False== — random sequence.
- "Run a playbook on an IP while hunting." ==+Entity trigger, manual== — no automation rule can call it.
