## Azure first

- Azure has two doors. The **control plane** (`https://management.azure.com`, Azure Resource Manager) creates, changes and deletes *resources*. The **data plane** (for example `https://<account>.blob.core.windows.net`) reads and writes the *data inside* them.
- Many "read-looking" control-plane operations are really **POST** requests: listing storage keys, starting a VM, checking App Gateway backend health.
- Locks attach at **subscription, resource group or resource** — the same hierarchy RBAC uses, minus management groups.

See the Foundations pages listed above, especially *azure-resource-hierarchy*.

## In one sentence

A resource lock is a "do not remove" sticker on a subscription, resource group or resource that blocks deletes (**CanNotDelete**) or deletes and changes (**ReadOnly**) for **everyone**, Owners included, until someone with lock permission removes it.

## Why it exists

RBAC grants rights to people; a lock overrides those rights for all of them at once. It stops the tired admin and the runaway script that would delete the production VNet or the Recovery Services vault. ==!It is not a security boundary against an attacker who holds `Microsoft.Authorization/locks/delete`== — they just delete the lock first.

## What actually matters

**1. Two levels, two names each.** Portal **Delete** = API `CanNotDelete`. Portal **Read-only** = API `ReadOnly`. ReadOnly behaves roughly like restricting everyone to the Reader role.

**2. Inheritance.** A lock on a parent applies to every child, including resources added later. The **most restrictive** lock wins. Extension resources (a diagnostic setting on a storage account) inherit from their parent. A CanNotDelete lock on **one resource** blocks deleting its **whole resource group** — no partial delete. ==!You cannot lock a management group.== A policy at management-group scope can *deploy* locks to subscriptions and resources below it.

**3. Control plane only.** A lock on a storage account does ==!not== stop anyone deleting blobs, queues, tables or files through the data plane. A ReadOnly lock on a SQL logical server still allows inserts, updates and deletes in the database. Use the service's own protection (soft delete, immutability, backups).

**4. The surprising side effects — the exam's favourite.**

| Lock | Where | Side effect |
|---|---|---|
| ReadOnly | storage account | ==!cannot list account keys== (POST); also blocks RBAC role assignments scoped to the account or a container, and blob-container creation through the control plane |
| ReadOnly | resource group with VMs | ==!cannot start or restart VMs== (POST) |
| ReadOnly | resource group with App Service plan | cannot scale up or out |
| ReadOnly | resource group with Automation account | runbooks cannot start |
| ReadOnly | resource group | cannot move resources in or out |
| ReadOnly | NSG | cannot create the NSG flow log |
| ReadOnly | Application Gateway | cannot get backend health |
| ReadOnly | Log Analytics workspace | cannot enable UEBA |
| ReadOnly | subscription | Azure Advisor cannot store results |
| CanNotDelete | resource or resource group | ==!cannot delete Azure RBAC role assignments== |
| CanNotDelete | resource group | deployment history is not auto-pruned; at **800** deployments new deployments fail |
| CanNotDelete | resource group created by Azure Backup | restore points (max 18) cannot be cleaned up, so ==!backups fail== |
| CanNotDelete | Log Analytics workspace | does **not** stop data purge — remove the Data Purger role instead |

**5. Who can manage locks.** Creating or deleting needs `Microsoft.Authorization/locks/*` (or `Microsoft.Authorization/*`). ==+Owner== and ==+User Access Administrator== have it. ==!Contributor does not.== Remove an inherited lock only at the scope where it was created.

**6. Limits of locks.** A lock does not block **subscription cancellation**. Managed applications (Azure Databricks, for example) create a locked infrastructure resource group whose lock a "system application" owns: delete the *service*, not the lock.

**7. Locks at scale.** A `deployIfNotExists` policy can deploy a `Microsoft.Authorization/locks` resource with level `CanNotDelete`. The lock appears only after the resource is created and the evaluation delay passes (default 10 minutes); existing resources need a remediation task, and the assignment's identity needs `locks/write`. The policy effect **`denyAction`** blocks DELETE requests directly, without a lock — but it cannot protect locks or policy assignments themselves and does not stop subscription deletion.

## Where it lives

Azure portal > *resource / resource group* > **Settings > Locks** > **+ Add** > name, **Lock type** (Delete / Read-only), notes. On a subscription the blade is called **Resource locks**.

![Select Locks](https://learn.microsoft.com/en-us/azure/includes/media/resource-manager-lock-resources/select-lock.png){Settings > Locks}

![Add lock](https://learn.microsoft.com/en-us/azure/includes/media/resource-manager-lock-resources/add-lock.png){+ Add; inherited parent locks are listed too}

```bash
az lock create --name rg-nodelete --lock-type CanNotDelete --resource-group rg-network
az lock create --name kv-readonly --lock-type ReadOnly --resource-group rg-sec \
  --resource-name kv-prod --resource-type Microsoft.KeyVault/vaults
az lock list --resource-group rg-network
az lock delete --name rg-nodelete --resource-group rg-network
```

```bicep
// Deployed at resource-group scope: no scope property = lock the deployment scope
resource rgLock 'Microsoft.Authorization/locks@2016-09-01' = {
  name: 'rgLock'
  properties: { level: 'CanNotDelete', notes: 'Core network - do not delete' }
}
```

PowerShell: `New-AzResourceLock`, `Get-AzResourceLock -AtScope`, `Remove-AzResourceLock`.

## Exam traps

- "Admins must keep changing NSG rules but nobody may delete the NSG" → **CanNotDelete**, not ReadOnly.
- "After a ReadOnly lock, the app cannot get storage keys / VMs will not restart" → that is the lock (POST blocked).
- "Lock on the storage account, yet blobs were deleted" → data plane; locks do not cover it.
- "Owner cannot delete the resource" → a lock (possibly inherited from the resource group or subscription).
- "Developer with Contributor wants to remove a lock" → cannot without a role holding `locks/delete`.
- "Protect every subscription under a management group" → policy that deploys locks (or `denyAction`); a lock on the management group itself is impossible.
- "Backups started failing after locking resource groups" → Delete lock on the Azure Backup restore-point resource group.
