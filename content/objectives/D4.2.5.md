## Azure first

- A **Log Analytics workspace** is the database Sentinel reads. Every connector ends in one of its tables.
- The **Azure Monitor Agent (AMA)** is the program on a machine that ships logs to the workspace. It only runs on Azure VMs or on machines connected through **Azure Arc** (the agent that makes a non-Azure server an Azure resource).
- A **data collection rule (DCR)** is an Azure resource that tells AMA what to collect and where to send it. You associate it with machines; change the DCR once and every machine follows.
- **Syslog** is the standard logging protocol of Linux and network appliances. **CEF** (Common Event Format) is a Syslog message with labelled key=value fields.

See the Foundations pages listed above: Azure Monitor Agent and DCRs, Log Analytics workspace, Azure Arc, and VMs.

## In one sentence

**Syslog via AMA** and **Common Event Format (CEF) via AMA** are two Sentinel connectors that create a DCR, install AMA on a Linux machine (the source itself or a dedicated **log forwarder**), and pick facilities and minimum severities — plain Syslog lands in `Syslog`, CEF lands already parsed in `CommonSecurityLog`.

## What's new for an engineer

As an analyst you queried `CommonSecurityLog` for firewall events. Someone built the pipe. Now you build it:

- **You stand up the forwarder.** Firewalls and switches cannot run AMA. You deploy a 64-bit Linux VM with rsyslog or syslog-ng, Arc-enable it if it is not in Azure, and point appliances at it.
- **You write the DCR.** Facility by facility, you choose the minimum log level. That choice is the volume (and cost) lever.
- **You own the roles.** **Virtual Machine Contributor** or **Azure Connected Machine Resource Administrator** to push the agent; **Monitoring Contributor** to create or edit DCRs.
- **You prevent double billing.** One facility in two DCRs = every event stored twice.

## What actually matters

| | Syslog via AMA | CEF via AMA |
|---|---|---|
| Message | Plain Syslog | CEF over Syslog |
| Table | `Syslog` | `CommonSecurityLog` |
| Fields | Payload in one string, `SyslogMessage` | Parsed columns: `DeviceVendor`, `DeviceProduct`, IPs… |
| DCR stream | `Microsoft-Syslog` | `Microsoft-CommonSecurityLog` |
| Querying | Needs a **parser** (a saved KQL function) | Query columns directly |

1. **Two architectures.** AMA directly on a Linux server that logs for itself; or a **log forwarder** that receives from many appliances. A non-Azure forwarder needs **Azure Arc** first, or it will not appear on the DCR's **Resources** tab.
2. **Ports.** Appliance → forwarder daemon: **UDP/TCP 514** by default. Daemon → AMA on the same box: **TCP 28330** (AMA 1.28.11 and later). AMA → workspace: HTTPS.
3. **Minimum log level** means that level and everything more severe. `LOG_ERR` also brings `LOG_CRIT`, `LOG_ALERT`, `LOG_EMERG`. **NONE** skips a facility. The portal only offers a minimum; exact levels need the API.
4. **The forwarder script.** Creating the DCR installs AMA. The product docs still have you run the **installation script** from the connector page so the daemon listens on 514 and hands messages to AMA.
5. **Duplication fix.** Use different facilities for CEF and Syslog sources, or add a DCR **transformation** on the Syslog stream that drops CEF messages.
6. **Scale.** Plan about **10,000 events per second** per Linux forwarder. Beyond that, several forwarders behind a load balancer.

```kql
// Transformation on the Syslog stream: keep CEF out of Syslog
source
| where ProcessName !contains "CEF" and SyslogMessage !contains "CEF:0"
```

## Where it lives

**Defender portal:** **Microsoft Sentinel > Content management > Content hub** → install **Syslog** or **Common Event Format**. Then **Microsoft Sentinel > Configuration > Data connectors** > **Syslog via AMA** or **Common Event Format (CEF) via AMA** > **Open connector page** > **+Create data collection rule** → **Basic** (name, subscription, resource group) → **Resources** (pick the forwarder) → **Collect** (minimum level per facility) → **Review + create**. Same path under **Microsoft Sentinel** in the Azure portal until March 31, 2027.

**Plain Azure Monitor route (Syslog only):** **Azure portal > Monitor > Data Collection Rules > + Create**, data source **Linux Syslog**.

```bash
# Run on the forwarder (from the connector page)
sudo wget -O Forwarder_AMA_installer.py https://raw.githubusercontent.com/Azure/Azure-Sentinel/master/DataConnectors/Syslog/Forwarder_AMA_installer.py && sudo python Forwarder_AMA_installer.py
sudo systemctl status azuremonitoragent.service
```

```kql
CommonSecurityLog
| where TimeGenerated > ago(1d)
| summarize count() by DeviceVendor, DeviceProduct
```

## Exam traps

- "Firewall sends CEF; analysts want parsed fields." ==+CEF via AMA → `CommonSecurityLog`==, not ==!Syslog via AMA==.
- "Install AMA on the firewall." ==!Not possible.== ==+Dedicated Linux forwarder.==
- "Windows Server as the CEF forwarder." ==!No== — Linux, 64-bit.
- "On-premises forwarder missing from the Resources list." ==+Arc-enable it first.==
- "Minimum level Error collects only Error." ==!False== — Error and worse.
- "Events in both `Syslog` and `CommonSecurityLog`." Same facility in both DCRs. ==+Separate facilities or a transformation.==
- Ports: ==@514== inbound from appliances, ==@28330== daemon to AMA. Don't swap.
- "Creating the DCR configures the daemon." ==!Not per product docs== — ==+run the installation script==.

- **Skip** the regex in the Squid parser (training unit 5 of *Connect syslog data sources*, "Parse syslog data with KQL"). Know only that Syslog needs a parser and a parser is a saved KQL function.

- **Skip** full rsyslog/syslog-ng config listings, SELinux notes and per-appliance vendor guides.
