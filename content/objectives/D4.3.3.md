## Azure first

- A **plugin** is a bundle of *tools* (also called *skills*) that Security Copilot can call to fetch data or take action — for example "list Sentinel incidents" or "look up an IP's reputation".
- **On-behalf-of (OBO) authentication** means a Microsoft plugin acts as the signed-in user, with that user's own Entra / Azure RBAC rights.
- A **manifest** is the definition file (`.yaml` or `.json`) that describes a custom plugin's tools and how to call them.
- Plugin settings are **per workspace** — each workspace has its own plugin set.

See the Foundations pages listed above: AI agents and MCP basics, the security stack map, and RBAC vs Entra roles.

## In one sentence

Plugins are the connectors that let Security Copilot reach data and actions — Microsoft, non-Microsoft and your own custom ones — and as an owner you control which are on, who may add custom ones, and which preinstalled ones are restricted to owners.

## What's new for an engineer

As an analyst you toggled a plugin on in the *Sources* list. The engineer sets the rules behind that list: who may upload a custom plugin, whether it stays private or is published to everyone, and which preinstalled plugins are locked to owners.

## What actually matters

- **Three plugin families.**

| Family | Examples | Notes |
|---|---|---|
| ==@Microsoft== (preinstalled) | Defender XDR, Microsoft Sentinel, Intune, Entra, Purview, Natural Language to KQL, Microsoft Threat Intelligence | Use OBO; you still need each product's own role and licence |
| ==@Non-Microsoft== (preinstalled) | ServiceNow and other partner services, public web | The partner product is bought separately |
| ==@Custom== | Your own Security Copilot plugin (`.yaml`/`.json` manifest, file or link) or an OpenAI plugin (link to manifest) | Uploaded by owners, or by contributors if allowed |

- **Custom plugin permissions — a two-step dependency.**
  1. *Who can add and manage their own custom plugins?* **Owners only** (default) or **Owners and Contributors**. This is *user scope* — a private catalog.
  2. *Who can add and manage custom plugins for everyone?* This setting ==!only unlocks once step 1 is "Owners and Contributors"==. Again Owners only or Owners and Contributors. This is *organization scope*.
- **Private vs everyone.** At upload you choose "just me" (gets a **Private** tag) or "anyone in the organization". An org-wide plugin added by an owner can be used and toggled on or off by every Copilot user, but ==!only owners can modify it==; contributors can't edit owners' custom plugins.
- **Restricting preinstalled plugins.** By default all owners and contributors can use preinstalled Microsoft and non-Microsoft plugins. An owner can set any plugin to **Owners only**. After you restrict one, ==!newly added preinstalled plugins default to Owners only== too. The change is immediate.
- **Restrictions hit embedded experiences.** Restrict the Defender XDR or Natural Language to KQL plugin and Copilot inside the Defender portal degrades or disappears for analysts.
- **Agents bypass your toggles — narrowly.** Setting up an agent auto-enables the plugins it needs *for that agent only*. Your users' plugin availability does not change. Disable the agent to stop it.
- **Per-user setup.** Plugins with a gear or **Set up** button (Microsoft Sentinel, Azure AI Search) are configured by each user for themselves — for example, which Sentinel workspace to query.
- **Microsoft 365 data access.** The owner setting *Allow Security Copilot to access data from your Microsoft 365 services* must be on for the Purview plugin to work. Changing it needs the Copilot owner role (Global Administrator inherits owner).
- **Vet first.** Microsoft's guidance: test a custom plugin at user scope before publishing it to the whole organization.

![Plugin governance dependency](https://learn.microsoft.com/en-us/training/wwl-sci/manage-plugins-agents-security-copilot/media/plug-in-permission-dependency.png){User scope must be "Owners and Contributors" before the organization-scope setting appears}

## Where it lives

| Task | Where (Security Copilot portal) |
|---|---|
| Custom-plugin permissions, restrict preinstalled plugins | Home menu > **Owner > Plugin settings** |
| Turn plugins on/off, set up a plugin | Prompt bar > **Sources** icon > **Manage plugins** |
| Upload a custom plugin | **Manage plugins** > *Custom* section > **Upload plugin** > choose scope > Security Copilot plugin or OpenAI plugin > **Add** > **Setup** |
| Edit / delete a custom plugin | *Custom* section > gear icon > **Edit file** or **Delete** |
| Microsoft 365 data access | **Owner settings** |

## Exam traps

- ==!"Enable the Sentinel plugin and every contributor can read incidents"== — no. OBO means each user also needs **Microsoft Sentinel Reader** (or higher).
- ==!"Contributors can publish org-wide plugins as soon as the org-scope toggle is set"== — the org-scope toggle does not even appear until user scope allows contributors.
- Enabling a plugin in one workspace does **not** enable it in another.
- Restricting a preinstalled plugin does **not** stop an agent that needs it; the agent gets its own enablement.
- Custom plugin formats: Security Copilot manifest (`.yaml`/`.json`) or OpenAI plugin manifest link.

## Skip

- **Skip:** writing plugin manifests (API, GPT, KQL skill formats). That is developer work, not configuration.
- **Skip:** the full catalog of every Microsoft and partner plugin. Know the three families and the Defender XDR / NL2KQL embedded-experience example.
- **Skip:** responsible-AI policy text on the manage-plugins page. One line: vet custom plugins before publishing.
