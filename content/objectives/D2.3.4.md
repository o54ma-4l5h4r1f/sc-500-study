## Azure first

- A **VPN gateway** is a pair of Microsoft-managed VMs that terminates encrypted tunnels into one VNet. It lives in a subnet that must be named **GatewaySubnet** (/27 or larger). One VNet can have one VPN gateway.
- **IPsec/IKE** is the protocol family for site tunnels. **IKE** (Internet Key Exchange) agrees the keys: Phase 1 (Main Mode) sets up a safe channel; Phase 2 (Quick Mode) sets up the IPsec tunnel that carries data.
- A **local network gateway** is an Azure object that describes the office: its VPN device's public IP and its address ranges.
- **Conditional Access** is the Entra rule engine that can demand MFA or a compliant device at sign-in.

See the Foundations pages listed above, especially *virtual-networks-and-subnets* and *conditional-access-basics*.

## In one sentence

Securing an Azure VPN means choosing the right connection type and gateway SKU, forcing strong IPsec/IKE algorithms on site tunnels, authenticating remote users with Microsoft Entra ID (so MFA and Conditional Access apply), and deciding where internet traffic goes (forced tunnelling).

## Why it exists

In the training module, one stolen point-to-site certificate let an attacker into production databases, APIs and AKS endpoints. A VPN is a key to the whole building, not one office. The incident had four causes you will see in questions: a copied certificate, IKEv1 with weak defaults (SHA-1, DH Group 2), no MFA, and every user getting the same network-wide access. Hardening the gateway fixes the first three. Only per-app access (Entra Private Access, D2.3.5) fixes the last.

## What actually matters

**1. Gateway SKU and generation.** New gateways use the zone-redundant **AZ** SKUs: VpnGw1AZ–VpnGw5AZ. Generation1 covers VpnGw1AZ–3AZ; Generation2 covers VpnGw2AZ–5AZ (more throughput). Non-AZ VpnGw1–5 cannot be created since 1 November 2025 and were retired on 30 September 2026 (existing ones are migrated to the matching AZ SKU). A new gateway needs a **Standard** public IP.

**2. The Basic SKU is the trap.**

| Basic SKU limitation | Consequence |
|---|---|
| No OpenVPN | ==!No Microsoft Entra ID authentication== (Entra needs OpenVPN) |
| No RADIUS | Certificate auth only for P2S (IKEv2) |
| No custom IPsec/IKE policy | You cannot enforce AES-256/SHA-256 |
| No active-active, no BGP | No instance redundancy |
| Max 10 S2S tunnels, 100 Mbps; created only with PowerShell/CLI | Dev/test only, not production |

**3. Custom IPsec/IKE policy (S2S and VNet-to-VNet).** Set per **connection**, one policy per connection, and you must specify ==@every parameter== for both phases. Once set, the gateway ==@only proposes and accepts those algorithms== on that connection, which blocks downgrade. The on-premises device must match, or the tunnel does not come up. A sensible baseline from the module: IKEv2, AES256, SHA256, DHGroup14, IPsec AES256/SHA256, PFS14. If you choose GCMAES for IPsec encryption, use the same GCMAES for integrity. IKE Main Mode SA lifetime is fixed at 28,800 seconds; Quick Mode defaults are 27,000 seconds and 102,400,000 KB. `UsePolicyBasedTrafficSelectors` lets a route-based gateway talk to a policy-based on-premises firewall. Prefer **IKEv2**; IKEv1 is legacy. S2S tunnels normally authenticate with a **pre-shared key**; since May 2026 VPN Gateway also supports **certificate authentication** for S2S connections, which removes a shared secret that can leak.

**4. P2S authentication: three types.**

| Type | How | Tunnel types | Security notes |
|---|---|---|---|
| ==@Azure certificate== | Upload trusted root cert public key (up to 20 roots); each client has a cert issued from it | OpenVPN, IKEv2, SSTP | Possession only, no MFA. Revoke by thumbprint (up to 300 revoked client certs per gateway) |
| ==@RADIUS== (AD domain) | Gateway passes auth to your RADIUS server (needs network reach to it) | OpenVPN, IKEv2, SSTP | MFA only if the RADIUS server provides it. Not on Basic |
| ==+Microsoft Entra ID== | User signs in with Entra credentials in the **Azure VPN Client** | ==@OpenVPN only== | MFA and Conditional Access apply per user. Needs VpnGw1(AZ)+ |

For Entra ID you set the **Tenant ID**, **Issuer** and **Audience**. The Microsoft-registered Azure VPN Client audience is `c632b3df-fb67-4d84-bdcf-b95ad541b5c8`; it needs no app registration in your tenant. Manually registered client app IDs retire on 31 March 2028 (Azure Public). You can enable several auth types at once; a client must match one.

**5. Active-active.** Both gateway instances hold tunnels, each with its own Standard static public IP (a third IP if P2S is on). Less disruption during maintenance; same gateway price. Needs a route-based, non-Basic gateway. Routing can be asymmetric, which matters for stateful on-premises firewalls.

**6. Forced tunnelling: two different things.**

- **S2S forced tunnelling**: Azure VMs' internet-bound traffic is sent *back down the tunnel to on-premises* for inspection. Configure with BGP (on-premises advertises 0.0.0.0/0) or a **Default Site** set with PowerShell (`Set-AzVirtualNetworkGatewayDefaultSite`); the on-premises device uses 0.0.0.0/0 traffic selectors. You can exempt subnets with a UDR to `Internet`.
- **P2S forced tunnelling**: the *client's* traffic all goes into Azure instead of out through home broadband (split tunnelling is the default). Configure by advertising custom routes `0.0.0.0/1` and `128.0.0.0/1` or by editing the Azure VPN Client profile XML. ==!The VPN gateway itself provides no internet egress==; without a firewall/NVA path, internet traffic is dropped.

**7. Hard rules.** ==!No NSG on GatewaySubnet== and no 0.0.0.0/0 UDR on it. Keep BGP route propagation on for that subnet.

**8. Logs.** Diagnostic settings on the gateway send `GatewayDiagnosticLog`, `TunnelDiagnosticLog`, `RouteDiagnosticLog`, `IKEDiagnosticLog` and `P2SDiagnosticLog` to Log Analytics. IKE logs prove which algorithms were negotiated; gateway logs show auth failures.

## Where it lives

**Azure portal** for the gateway; **Entra admin center** for the Conditional Access policy that covers VPN sign-in.

- Gateway: `Azure portal > Virtual network gateways > + Create` (Gateway type **VPN**, SKU, Generation, **Enable active-active mode**).
- Custom policy: `Virtual network gateways > vpngw1 > Settings > Connections > conn-site1 > Configuration > IPsec / IKE policy: Custom`.
- P2S: `Virtual network gateways > vpngw1 > Settings > Point-to-site configuration` → Tunnel type **OpenVPN (SSL)**, Authentication type **Azure Active Directory** (portal label for Entra ID) → Tenant, Audience, Issuer.
- Logs: `Virtual network gateways > vpngw1 > Monitoring > Diagnostic settings`.

```powershell
$p = New-AzIpsecPolicy -IkeEncryption AES256 -IkeIntegrity SHA256 -DhGroup DHGroup14 `
  -IpsecEncryption AES256 -IpsecIntegrity SHA256 -PfsGroup PFS2048 `
  -SALifeTimeSeconds 27000 -SADataSizeKilobytes 102400000
$c = Get-AzVirtualNetworkGatewayConnection -Name conn-site1 -ResourceGroupName rg-net
Set-AzVirtualNetworkGatewayConnection -VirtualNetworkGatewayConnection $c -IpsecPolicies $p
```

## Exam traps

- **"Use Entra ID auth on a Basic gateway."** ==!Impossible.== Basic has no OpenVPN.
- **Entra ID with IKEv2 or SSTP.** ==!Not supported.== OpenVPN only, Azure VPN Client only.
- **"Require MFA for certificate-based P2S."** Certificates cannot do MFA; switch to Entra ID (or a RADIUS server with MFA).
- **Custom IPsec policy on P2S.** The custom connection policy is for S2S and VNet-to-VNet connections.
- **"ExpressRoute is encrypted because it is private."** ==!No.== Use MACsec (ExpressRoute Direct) or IPsec over private peering.
- **Forced tunnelling direction.** S2S forced tunnelling sends Azure VM internet traffic to on-premises; P2S forced tunnelling pulls client traffic into Azure. Read which one the question means.
- **NSG on GatewaySubnet.** Never the right answer.
- **Hardening ≠ least privilege.** A perfectly hardened VPN still gives network-wide access. Per-app access is Entra Private Access (D2.3.5).
- **Policy-based VPN.** IKEv1 only on Basic, one S2S tunnel, no P2S, no active-active; you cannot convert it to route-based without deleting it.

## Skip

- **Skip:** the per-SKU throughput, packets-per-second and "supported number of VMs" tables. Know Basic's limits and that AZ SKUs are current.
- **Skip:** P2S default IKE/IPsec and TLS cipher tables. The exam tests custom S2S policy, not P2S cipher lists.
- **Skip:** legacy Standard/HighPerformance SKU migration and Basic public IP migration timelines. Operational.
- **Skip:** memorising unit 3's exact SA lifetime values and click order. Know that a custom policy must specify every parameter and that defaults exist if you don't set lifetimes.
- **Skip:** VPN client install details per OS and the retired Azure VPN Client for Linux (retired 31 August 2026).
- **Skip:** NAT rules, BGP ASN choices and multi-site designs. Routing engineering, not a security control.
