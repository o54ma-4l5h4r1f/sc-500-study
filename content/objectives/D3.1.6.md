## Azure first

- **Microsoft Entra Agent ID** adds four directory object types: **agent identity blueprint** (the template, like an app registration), **agent identity blueprint principal** (the blueprint's presence in a tenant, like a service principal), **agent identity** (one agent's own account) and **agent user** (an optional user-type account paired 1:1 with an agent identity).
- **Entitlement management** is Entra ID Governance's "access shop". An **access package** bundles resources (groups, API permissions, roles) with rules: who may request, who approves, when it expires.
- **OAuth permissions** come as **delegated** (act for a user) or **application** (act alone). See D1.1.5.
- **My Account** (`myaccount.microsoft.com`) and **My Access** (`myaccess.microsoft.com`) are the self-service portals where non-admins manage things they're responsible for.
- **Licence:** `license_blocked`. Agent ID itself is available to all Entra customers, but Entra *security and governance* for agents needs ==@Microsoft Agent 365== with at least Entra ID P1 (or Microsoft 365 E3), or ==@Microsoft 365 E7==. The default inactivity policy needs no licence. Portal tour only.

New to these? Read the Foundations pages listed in "Before you start".

## In one sentence

Managing agent access means giving every agent identity an accountable human sponsor, granting it only time-bound access through access packages, and switching it off — per agent, per blueprint or tenant-wide — when it's no longer needed.

## Why it exists

Service principals taught us a hard lesson: nobody owns them, their permissions only grow, and they outlive the project. Agents multiply faster and act on their own, so the same mess arrives quicker. Agent ID fixes it with three habits borrowed from people management: a named boss (sponsor), a badge that expires (access package), and an automatic clear-out of desks nobody uses (inactivity policy).

Think of a hotel. The **blueprint** is the room type, each **agent identity** a booked room, the **sponsor** the guest who booked and answers for it. Key cards (access packages) expire at checkout unless the guest extends. Rooms left empty too long get cleared.

## What actually matters

**1. Owners, sponsors, managers — and the admin roles.**

| | Owner | ==@Sponsor== | Manager |
|---|---|---|---|
| Who | technical admin (developer, IT) | business person accountable for purpose and lifecycle | user in the org hierarchy |
| Required? | optional | ==@required on create== for agent identities and blueprints | optional |
| Can be | users, guests, service principals — ==!not groups== | users, guests, dynamic groups, assigned Microsoft 365 groups — ==!not role-assignable or assigned security groups== | individual user |
| Can do | edit settings, credentials; disable, ==+re-enable==, restore, hard-delete | disable, soft-delete, change sponsors, request access packages — ==!can't re-enable or restore== | request access packages for the agent user |

Up to 100 sponsors (no more than 5 groups) per agent identity; an agent's *user account* allows only 5 sponsors and they can't modify it. Blueprint principals are exempt from the sponsor-on-create rule. If a sponsor leaves, sponsorship ==+transfers to their manager==. Lifecycle Workflows has mover/leaver tasks that email the manager and co-sponsors. Directory roles: **Agent ID Administrator** or **Cloud Application Administrator** manage agent identities; **Agent ID Developer** creates blueprints.

**2. Granting access.** New agent identities get only the **inheritable permissions** set on their blueprint — delegated scopes, either enumerated or "all allowed" (enumerated: max 40 scopes per resource app; resource apps per blueprint: ==!10 in the admin guide, 50 in the inheritable-permissions article== — Microsoft's docs disagree, so don't bank on either number; some high-privilege scopes can never be inherited). Everything else should come through an ==@access package==:

- Resource roles allowed: ==+security group membership, OAuth API permissions (delegated and application), Entra roles==. ==!Not app roles, SAP roles or SharePoint site roles.==
- Policy: **Who can get access** = **For users, service principals, and agent identities in your directory** > **All agents**. Add an **All Service principals** policy for agents still on plain service principals.
- Three request routes: the agent requests via Graph (`accessPackageAssignmentRequest`), the ==@sponsor requests on its behalf== in My Access, or an admin assigns directly.
- Expiry: the sponsor is notified, then extends (new approval) or lets it lapse. No action = access removed.
- Roles: Identity Governance Administrator to build the package; ==@Global Administrator== if it contains API permissions or directory roles (the catalog becomes privileged).

**3. Removing access — three scopes.**

| Scope | How | Effect |
|---|---|---|
| One agent | Entra admin center > Entra ID > Agents > Agent identities > **Disable** (sponsors/owners use My Account) | blocks token issuance; identity and metadata kept |
| A class of agents | Agents > Agent blueprints > **Disable** | blocks existing children and stops new ones being created |
| Whole tenant | Conditional Access block (D3.1.4) + per-product creation controls | blocks tokens; ==!doesn't stop creation== |

Per-product creation controls: Copilot Studio (licences, roles, Power Platform DLP to stop publishing), Foundry (==@Foundry Account Owner== to create projects, ==@Foundry User== to create agents — formerly Azure AI Account Owner / Azure AI User), Security Copilot (workspace Owner/Contributor), and Agent 365 settings in the Microsoft 365 admin center (D3.1.11).

**4. Lifecycle automation.** The **default inactivity policy** (preview, no licence) runs on all tenants once enabled: ==@60 days== inactive → notify sponsors and owners; ==@90 days== → disable; ==@455 days== → delete. You can exclude chosen agents and set fallback email recipients. Custom lifecycle policies need a licence and always run before the default.

**5. Watch it happen.** Audit logs record agent events under the base object type: an agent identity shows as a service principal event, an agent user as **Create user**. Check the `agentType` property (anything but `notAgentic` = agent). Sign-in logs filter by **Agent type** (Agent ID user, Agent Identity, Agent Identity Blueprint, Not Agentic) and **Is Agent**. Key events: add/update/delete service principal, add app role assignment to service principal.

**6. Agent 365 approval is a second gate.** In the Microsoft 365 admin center an admin approves a published agent and sets **user scope** (who may use it) through **Manage access** — approval ==!doesn't grant every user access==. Copilot Studio agents use OBO by default, so the user's own permissions cap what the agent reaches. Full workflow in D3.1.11.

## Exam traps

- **Sponsor = owner.** ==!No.== Sponsor = business accountability, limited rights; owner = technical admin.
- **Sponsor disabled an agent by mistake** → an ==+owner or admin== must re-enable it.
- **Assign a group as owner.** ==!Not supported.== Groups can be sponsors (supported types only).
- **Give an agent time-limited Graph permissions with approval** → ==+access package== with an expiry.
- **Add a SharePoint site role to an agent's access package.** ==!Not supported.==
- **Stop all agents created from one project template** → ==+disable the blueprint==.
- **CA blocks agent creation.** ==!No== — it blocks tokens; use product controls.
- **Inactive agent timeline** → notify 60, disable 90, delete 455 days.

> **Contradictions — training module vs product docs.** (1) The module says agent creation appears as **Add service principal** in the *ApplicationManagement* category; the manage-agents product doc says "Create service principal". Expect either wording; check `agentType` to be sure. (2) The module sets up **access reviews** with a *Workload identities* scope for agents; the governance product doc centres on **access packages with expiry and sponsor renewal** and the inactivity policy. Know both, prefer the product's model. (3) The module says Agent 365 is GA; Agent ID lifecycle policies are still **preview** in the product.
