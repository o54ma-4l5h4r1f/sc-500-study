## Azure first

- A **resource group** is a folder in a subscription. A key vault is one resource inside it, in one **region**.
- A **key** is used to encrypt, decrypt or sign — the program never sees the key itself. A **secret** is any short sensitive string (password, connection string). A **certificate** is a key plus an identity document signed by a certificate authority.
- An **HSM** (hardware security module) is a tamper-resistant box that creates and uses keys without ever letting them out. **FIPS 140** is the US standard that grades how well a crypto module does that (Level 1 = software, Level 3 = hardened hardware).
- **Multitenant** means you share Microsoft's hardware with other customers, isolated by software. **Single-tenant** means the hardware is yours alone.

See the Foundations pages listed above, especially *keys-secrets-and-certificates*.

## In one sentence

Deploying Key Vault means creating a **vault** (or, for the strictest key requirements, a **Managed HSM**) in a resource group and choosing at creation the pricing tier, the recovery options, the permission model and the network exposure.

## Why it exists

Before Key Vault, connection strings lived in `web.config` files, pipeline variables and Teams messages. As an analyst you have seen what happens next: an attacker lands on one VM, reads a config file, and walks into the database. Key Vault is the bank vault with a sign-out sheet: one locked place for secrets, keys and certificates, with every withdrawal logged.

Getting the vault right **at deployment** matters because some choices can never be changed later (the soft-delete retention days, purge protection once on). Others are open by default and must be closed before the vault holds anything real.

## What actually matters

- **Standard vs Premium is a compliance decision, not a performance one.** Standard protects keys in software (==@FIPS 140-2 Level 1==). Premium adds keys generated and used inside ==@FIPS 140-3 Level 3== HSMs (Marvell LiquidSecurity hardware). Older Premium key versions created on HSM Platform 1 stay at FIPS 140-2 Level 2; every new key and key version lands on HSM Platform 2 (140-3 Level 3). Both tiers store secrets and certificates. If a requirement says "keys must be HSM-protected", Standard is wrong.
- **Managed HSM is a different resource, not a third tier.** It is a single-tenant pool of HSMs for high-value keys. It stores ==!only HSM-protected keys== — no secrets, no certificates. Its admins control access through a **local RBAC** model that subscription Owners cannot override, and the customer holds the **security domain** (the root of trust). Pick it when the requirement says "single-tenant", "customer-controlled root of trust" or "full key sovereignty".
- **Names are global.** A vault name is 3–24 characters (letters, digits, single hyphens) and becomes the DNS name `https://{name}.vault.azure.net`. A soft-deleted vault keeps its name reserved until the retention period ends.
- **One vault per application per environment** (dev, pre-prod, prod) is Microsoft's recommended design. Role assignments then sit at vault scope, and a leak in dev cannot touch prod secrets.
- **Defaults at creation** — know what you get if you click through:

| Setting | Default on a new vault | Changeable later? | Taught in |
|---|---|---|---|
| Soft delete | ==@On, 90 days== | Days: no. Soft delete: cannot be turned off | D1.2.2 |
| Purge protection | Off | Turn on any time; ==!never off again== | D1.2.2 |
| Permission model | Azure RBAC (portal; API `2026-02-01`+) | Yes (needs Owner / User Access Administrator) | D1.2.3 |
| Public network access | Enabled, firewall off | Yes | D1.2.4 |
| Diagnostic logging | Off | Yes | D1.2.2 |

- **Azure RBAC is now the default everywhere.** The portal already preselected it. From control-plane API version `2026-02-01`, any create call (CLI, PowerShell, Bicep, ARM, Terraform) that omits `enableRbacAuthorization` gets RBAC. Older API versions defaulted to access policies. All control-plane API versions before `2026-02-01` retire on **February 27, 2027**.

## Where it lives

**Azure portal > Key vaults > + Create.** The wizard has five tabs: **Basics** (subscription, resource group, name, region, **pricing tier**, and the **Recovery options** block), **Access configuration**, **Networking**, **Tags**, **Review + create**.

![Create a key vault - Basics tab with Recovery options](https://learn.microsoft.com/en-us/training/wwl-sci/configure-secure-key-vault/media/soft-delete-purge-protect-enabled.png){Basics tab: pricing tier, then Recovery options (soft delete Enabled, 90 days, purge protection). The training unit text says these sit on a "Recovery tab"; its own screenshot and the live portal show them on the Basics tab — the product UI wins.}

To create a vault you need control-plane rights on the resource group, such as **Key Vault Contributor** or Contributor. Neither grants access to the secrets inside (D1.2.3).

```bash
az keyvault create \
  --name kv-payroll-prod-01 \
  --resource-group rg-payroll-prod \
  --location westeurope \
  --sku premium \
  --retention-days 90 \
  --enable-purge-protection true \
  --enable-rbac-authorization true \
  --public-network-access Disabled
```

```bicep
resource kv 'Microsoft.KeyVault/vaults@2026-02-01' = {
  name: 'kv-payroll-prod-01'
  location: location
  properties: {
    tenantId: subscription().tenantId
    sku: { family: 'A', name: 'premium' }
    enableRbacAuthorization: true
    enablePurgeProtection: true
    softDeleteRetentionInDays: 90
    publicNetworkAccess: 'Disabled'
  }
}
```

A Managed HSM is created separately (`az keyvault create --hsm-name ...`) and must be **activated** by downloading its security domain before use.

## Exam traps

- "Store secrets with HSM protection, cheapest option" → ==+Key Vault Premium==, not Managed HSM. ==!Managed HSM cannot store secrets or certificates at all.==
- "Single-tenant, FIPS 140-3 Level 3, subscription admins must not be able to override access" → ==+Managed HSM==.
- Premium and Managed HSM are **both** FIPS 140-3 Level 3. The difference is **tenancy and root-of-trust control**, not the FIPS level.
- Standard vs Premium is chosen at creation as the **pricing tier**. A question that asks for HSM keys in an existing Standard vault expects you to know the tier must be Premium.
- Creating a vault does ==!not== give you access to its secrets. Contributor manages the vault resource; data access is separate (D1.2.3).
- A deleted vault name ==!cannot be reused== until the soft-delete retention period ends (or the vault is purged).

## Skip

- **Skip:** Azure Cloud HSM, Azure Payment HSM and Payment HSM v2. They are IaaS HSMs for lift-and-shift and payment cryptography. They do not integrate with Azure PaaS customer-managed keys and are not on this bullet. Know only that they exist.
- **Skip:** the Contoso Health storyline in the unit (PCI DSS, HIPAA, FedRAMP paragraphs). The exam tests the rule "HSM required → Premium (or Managed HSM)", not which regulation says so.
- **Skip:** Managed HSM activation details (security-domain quorum, key shares, geo-replication, external key management). Know *that* the customer owns the security domain; the ceremony steps are out of scope.
- **Skip:** the `hsmPlatform` key attribute and how to query it. Know the three levels above (Standard 140-2 L1; Premium 140-3 L3 for new keys, 140-2 L2 for old Platform 1 versions; Managed HSM 140-3 L3); the per-version lookup is trivia.
- **Skip:** pricing per operation and per HSM key — it belongs in a reference page, never on the exam.
- The unit's **Azure Policy** section (enforce soft delete / purge protection at scale) is taught on D1.2.2 with the settings it enforces.
