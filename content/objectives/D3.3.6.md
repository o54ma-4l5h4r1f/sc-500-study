## Azure first

- A **Logic App** runs **workflows**: a **trigger** (for example *When an HTTP request is received*) followed by **actions** that call **connectors** (Office 365, SQL, Blob Storage, any HTTP API).
- Two hosting models. **Consumption**: multitenant, shared Microsoft infrastructure, one workflow per resource. **Standard**: single-tenant, runs on the Functions/App Service runtime, many workflows per resource.
- **Run history** stores every run's inputs and outputs so you can debug — including any secrets that passed through.
- A **SAS (shared access signature)** is a signed URL; whoever holds it can call the endpoint.

See the Foundations pages listed above, especially *logic-apps-basics*.

## In one sentence

Securing a Logic App means choosing the plan that supports the controls you need (Standard for private networking), protecting the request trigger (SAS keys, Entra OAuth policy or Easy Auth, IP restrictions), using a managed identity for connectors, and hiding secrets from run history with secure inputs/outputs.

## Why it exists

The request trigger's URL contains a SAS signature. Anyone with the URL can start the workflow. Connections store credentials that anyone with access to the resource can reuse. Run history shows passwords and tokens to anyone with read access. As an analyst you met Logic Apps as Sentinel playbooks; as an engineer you now secure the platform those playbooks run on.

## Mental model

Consumption is a shared office tower: you control who has your door code, but you can't move the door inside your own campus. Standard is your own building on the campus: you also get private corridors in and out.

| Control | Consumption | Standard |
|---|---|---|
| IP restriction on trigger | ==+Yes== (Workflow settings > Access control configuration) | ==+Yes== (Networking > Access restrictions, App Service model) |
| Entra OAuth on request trigger | ==+Yes== (authorization policy: issuer + audience) | Easy Auth (App Service Authentication) |
| Disable SAS on request trigger | Yes | Not needed (other auth types work alongside SAS) |
| Private endpoint (inbound) | ==!No== | ==+Yes== |
| VNet integration (outbound) | ==!No== | ==+Yes== |
| Single-tenant isolation | No | Yes |
| Managed identity for connectors | Yes | Yes |
| Secure inputs/outputs | Yes | Yes |

Plan choice is a security decision. ==!There's no in-place upgrade== from Consumption to Standard; you rebuild.

## What actually matters

**1. Request trigger authentication.**

- **SAS** (default): URL carries `sp`, `sv`, `sig`. Rotate by **regenerating access keys** (Settings > Access Keys), which invalidates all old URLs. You can also issue expiring callback URLs and use primary/secondary keys.
- **Entra OAuth** (Consumption): add an **authorization policy** with at least **Issuer** (`https://sts.windows.net/...` or `https://login.microsoftonline.com/...`) and **Audience** claims. A call must use ==!one scheme only== — sending SAS and a bearer token together fails. You can **disable SAS** so only OAuth works.
- **Easy Auth** (Standard request trigger): the App Service Authentication model, often with managed identity callers.
- Expose the workflow through **API Management** for richer auth, then IP-restrict the trigger to the APIM address.

**2. Inbound IP restrictions.** Consumption: *Only other Logic Apps* (callable only as a nested workflow via the built-in action) or *Specific IP ranges*. Service tags (for example `AzureEventGrid`) work on Standard. A separate setting restricts which IPs can read **run history content**.

**3. Managed identity for connectors.** Enable system- or user-assigned identity, choose **Managed identity** as the connection's authentication type, then grant a role on the target (for example *Storage Blob Data Contributor*). Supported by many Azure connectors (Blob, Service Bus, SQL, Cosmos DB, Key Vault), not all. Otherwise keep credentials in Key Vault, not typed into connections.

**4. Secure inputs and outputs.** Per action or trigger, in **Settings**. Run history shows the content as hidden. Configured ==!per action, not per workflow==: an earlier unsecured action still leaks the data. Secured outputs used as inputs downstream are also hidden.

**5. Private networking (Standard only).** Private endpoint makes the trigger reachable only from the VNet. VNet integration lets connector actions reach private SQL, storage or APIs. Consumption must bridge through API Management or the **on-premises data gateway**.

## Where it lives

- **Consumption:** Azure portal > Logic app > **Settings > Workflow settings > Access control configuration** (trigger and content IP ranges); **Settings > Authorization** (OAuth policies); **Settings > Access keys**; **Settings > Identity**.
- **Standard:** Logic app > **Settings > Networking** (access restrictions, private endpoints, VNet integration); **Settings > Authentication** (Easy Auth); **Settings > Identity**.
- **Designer:** action > **Settings > Security > Secure inputs / Secure outputs**.

## Exam traps

- "Logic App must call a SQL server with no public endpoint" → ==+Standard + VNet integration==. Consumption can't.
- "Only Entra-authenticated apps may start this Consumption workflow" → authorization policy (issuer + audience) and **disable SAS**.
- Caller sends SAS URL plus bearer token → error; pick one scheme.
- Leaked trigger URL → **regenerate access keys**.
- Password visible in run history → **secure inputs/outputs** on each action that touches it.
- "Restrict trigger to API Management" → IP restriction to the APIM instance's IPs.

## Skip

- **Skip:** ISE (integration service environment). Retired; Standard replaced it.
- **Skip:** PoP-token details, claim limits per policy and the REST calls to add `sasAuthenticationPolicy`. Know you can disable SAS.
- **Skip:** the regional inbound/outbound IP lists and `LogicAppsManagement`/`LogicApps`/`AzureConnectors` tag details. Firewall plumbing.
- **Skip:** TLS cipher-suite lists. The platform's job.
- **Skip:** step-by-step connector managed-identity screens per connector. Know the three steps.
