## Azure first

- **Authentication** proves who you are (Microsoft Entra ID issues a token). **Authorization** decides what that identity may do.
- **Azure RBAC** gives a *role* (a bundle of permissions) to a *security principal* (user, group, service principal, managed identity) at a *scope* (management group, subscription, resource group, resource). Assignments at a high scope flow down.
- An Azure role has **Actions** (manage the resource through Azure Resource Manager) and **DataActions** (touch the data inside it). Owner and Contributor have Actions only — that is why they cannot read secrets on an RBAC vault.
- A **managed identity** is an identity Azure gives a resource (a VM, a function app) so it can sign in without a stored password.
- **PIM** (Privileged Identity Management) makes a role *eligible* instead of permanent: you activate it for a few hours when needed.

See *azure-rbac-and-entra-roles* and *entra-id-basics* in Foundations.

## In one sentence

Access to Key Vault is split into a **control plane** (manage the vault resource, always Azure RBAC) and a **data plane** (read and use keys, secrets and certificates), and the data plane is authorized either by **Azure RBAC** (recommended, now the default) or by the legacy **vault access policy**.

## Why it exists

A vault has two kinds of users. The platform engineer who changes its network rules does not need the payroll database password. The payroll app that reads the password does not need to change network rules. Splitting the planes lets you give each one only its half.

The permission model choice exists because of history. Access policies came first and are native to Key Vault. They have a dangerous gap: anyone who can *write* the vault resource can edit its access policy and grant themselves every secret. Azure RBAC closes that gap.

## What actually matters

**1. The two planes are independent.** Control-plane rights never imply data-plane rights, and the reverse. A **Key Vault Contributor** can create and configure vaults ==!but cannot read a single secret== on an RBAC vault. An app with **Key Vault Secrets User** can read secrets but cannot change the firewall.

**2. RBAC vs access policy — the comparison the exam wants.**

| | Azure RBAC (recommended) | Vault access policy (legacy) |
|---|---|---|
| Planes | Control **and** data | Data plane only |
| Who can grant data access | Holders of `Microsoft.Authorization/roleAssignments/write` — **Owner**, **User Access Administrator**, **Key Vault Data Access Administrator** | ==!Anyone with `Microsoft.KeyVault/vaults/write`== — Contributor, Key Vault Contributor |
| Scope | Management group down to a **single secret, key or certificate** | Whole vault only |
| PIM (just-in-time) | ==+Supported== | Not supported |
| Deny assignments | Supported | Not supported |
| Limit | Azure RBAC assignment limits | Up to **1,024** access-policy entries per vault |
| Compound identity (user + app, on-behalf-of) | Not supported | Supported |
| Default for new vaults | Portal; any API `2026-02-01`+ create call | Older API versions, or `enableRbacAuthorization = false` |

The property is `enableRbacAuthorization`. When `true`, access policies are ignored. **Switching an existing vault to RBAC invalidates every access policy at once** — outages follow unless equivalent roles are assigned first. Changing the model needs unrestricted `roleAssignments/write` (Owner, or User Access Administrator plus `Microsoft.KeyVault/vaults/write`). Key Vault Data Access Administrator ==!cannot== change the model.

**3. The Key Vault built-in roles.**

| Role | Plane | What it can do |
|---|---|---|
| **Key Vault Contributor** | Control | Manage vaults (create, network, settings). No data access. |
| **Key Vault Administrator** | Data | All data operations on keys, secrets, certificates. Cannot manage the vault resource or role assignments. |
| **Key Vault Reader** | Data | Read **metadata** of vault and objects. ==!Cannot read secret values or key material.== |
| **Key Vault Secrets Officer** | Data | Any action on secrets (create, update, delete, rotate) |
| **Key Vault Secrets User** | Data | ==@Read secret contents== — includes the secret (private-key) portion of a certificate |
| **Key Vault Crypto Officer** | Data | Any action on keys (create, import, rotation policy) |
| **Key Vault Crypto User** | Data | Use keys for cryptographic operations (encrypt, decrypt, sign, verify, wrap, unwrap) |
| **Key Vault Crypto Service Encryption User** | Data | Read key metadata + **wrap/unwrap** only — ==@the role for a service's CMK identity== (Storage, SQL, disk encryption sets) |
| **Key Vault Crypto Service Release User** | Data | Release keys to confidential-computing environments |
| **Key Vault Certificates Officer** | Data | Any action on certificates (create, import, issuers, contacts) |
| **Key Vault Certificate User** | Data | Read entire certificate contents including key and secret portions |
| **Key Vault Purge Operator** | Data | Permanently delete soft-deleted vaults and objects |
| **Key Vault Data Access Administrator** | Access mgmt | Add/remove assignments of the Key Vault data roles only (ABAC-constrained) |

All data roles ==!work only on vaults set to the Azure RBAC permission model==.

**4. Scope choice.** Assign at **vault scope**, with one vault per application per environment. Object-scope assignments (one secret) are for exceptions — a user who must read only their own SSH key, a secret shared by two apps. Object scope ==!does not isolate teams== sharing one vault: network, monitoring and object management still need vault-level rights.

**5. Least privilege in practice.**
- App reads a connection string → **Key Vault Secrets User** on its managed identity.
- Storage account encrypts with a CMK → **Key Vault Crypto Service Encryption User**.
- Rotation function writes new secret versions → **Key Vault Secrets Officer**.
- Humans who need Administrator → make it a PIM **eligible** assignment, with approval, MFA and a maximum activation time.
- AI agents and other workload identities ==!cannot hold eligible PIM assignments== (activation needs a human). Time-bound them with an **active** assignment that has a start and end date.
- **Azure ABAC conditions** (preview) can narrow a role further — for example to secrets whose name matches a pattern. In the preview they apply to secret data actions only.

**6. Conditional Access** adds a second layer independent of roles: require MFA or a compliant device, block risky sign-ins. It acts at Entra sign-in, not inside Key Vault.

## Where it lives

- **Azure portal > Key vaults > *vault* > Settings > Access configuration** — permission model (Azure role-based access control / Vault access policy).
- **Azure portal > Key vaults > *vault* > Access control (IAM) > Add > Add role assignment** — RBAC at vault scope. The same **Access control (IAM)** tab exists on an individual secret, key or certificate.
- **Azure portal > Key vaults > *vault* > Access policies** — only when the vault uses the legacy model.
- **Microsoft Entra admin center > ID Governance > Privileged Identity Management > Azure resources** — make the assignment eligible.

```bash
# Switch an existing vault to RBAC (assign roles FIRST)
az keyvault update -n kv-payroll-prod-01 -g rg-payroll-prod --enable-rbac-authorization true

# Least-privilege read access for an app's managed identity
az role assignment create --role "Key Vault Secrets User" \
  --assignee <managed-identity-principal-id> \
  --scope /subscriptions/<sub>/resourceGroups/rg-payroll-prod/providers/Microsoft.KeyVault/vaults/kv-payroll-prod-01
```

## Exam traps

- "A Contributor read secrets they were never granted" → the vault uses ==!access policies==; Contributor can write the policy. Fix → ==+switch to Azure RBAC==.
- "Give an auditor visibility of which secrets exist, not their values" → ==+Key Vault Reader==. Reader on the *resource* (generic Reader) does not list objects either.
- "App must read a secret" → ==+Key Vault Secrets User==, not Secrets Officer, not Administrator.
- "Storage CMK identity" → ==+Crypto Service Encryption User==, not Crypto User (too broad) and not Secrets User (wrong object type).
- Key Vault Administrator ==!cannot assign roles==. Owner can assign roles ==!but cannot read secrets== until it assigns itself a data role.
- "Just-in-time access to Key Vault data" → requires Azure RBAC; ==!PIM cannot govern access policies==.
- Access policies grant permissions per object type (keys / secrets / certificates) but ==!always for the whole vault== — no per-secret policy.
