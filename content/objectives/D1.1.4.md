## Azure first

- A **tenant** is your organisation's private copy of Microsoft Entra ID — the directory holding users, groups and apps.
- A **security principal** is anything that can sign in and be given permissions. People are *user principals*. Software is a ==@service principal==.
- An app that wants Entra ID to sign people in, or wants a token to call an API, must first be **registered**. Registration is free; you can practise it in your Azure-only lab.
- **Coverage note:** Microsoft's training course has **no unit** for this bullet. This page is written entirely from the product documentation.

New to these? Read the Foundations pages listed in "Before you start".

## In one sentence

An **app registration** is the app's global blueprint (the *application object*, one per app, in its home tenant); an **enterprise application** is the app's local copy in a particular tenant (the *service principal*), and that local copy is what gets permissions, user assignments and Conditional Access.

## Why it exists

As an analyst you saw "OAuth app" alerts and service principal sign-ins. Each of those was one of these objects. Separating blueprint from copy lets one vendor app live in thousands of customer tenants. Each customer controls its own copy: who can use it, what it may touch, whether it is switched off.

Think of a franchise. Head office writes the operations manual once (application object). Every shop that opens has its own premises, staff list and keys (service principal). Closing one shop doesn't change the manual. Rewriting the manual changes only head office's own shop straight away.

## What actually matters

**1. The two objects side by side.**

| | App registration (application object) | Enterprise application (service principal) |
|---|---|---|
| Blade | **App registrations** | **Enterprise applications** |
| How many | One per app, ever | One per tenant that uses the app |
| Lives in | The home tenant | Every tenant that uses it |
| Holds | Credentials, redirect URIs, *requested* API permissions, exposed scopes, app roles, supported account types | Granted permissions and consents, user/group assignments, sign-in settings, SSO config, sign-in logs |
| ID you'll see | **Application (client) ID** — same everywhere, plus the app object's own **Object ID** | Its own **Object ID** — different in each tenant |

Registering in the portal creates **both** objects in your tenant. Creating an app with Microsoft Graph creates only the application object; the service principal is a separate step. Deleting the app object deletes its home-tenant service principal. Restoring the app object ==!doesn't restore== that service principal. To suspend an app without deleting it, **deactivate** it — no new tokens, objects kept for investigation.

**2. Three kinds of service principal.**

- **Application** — a local instance of an app object (normal case).
- **Managed identity** — represents a managed identity; ==!no app object==; you can grant it access but can't edit it directly.
- **Legacy** — an app made before app registrations existed; no app object; usable only in its own tenant.

**3. Single-tenant vs multitenant.** At registration you choose **supported account types**. Single-tenant: only your tenant's accounts; one service principal. Multitenant: other organisations can consent and get their own service principal.

That gives the three ways a service principal appears in your tenant: someone registers an app here; an admin creates one with PowerShell, the Azure CLI or Microsoft Graph; or a user or admin **consents** to someone else's multitenant app (D1.1.5). The last path needs no admin at all when user consent is allowed. That is why an enterprise app you never created can show up — and why reviewing the Enterprise applications list is a security task, not housekeeping.

**4. App credentials — how the app proves it's itself.** Only *confidential clients* (web apps, APIs, daemons) hold credentials.

| Credential | Verdict |
|---|---|
| ==+Federated identity credential== | Best. No secret at all. Trusts tokens from GitHub Actions, Kubernetes, another OpenID Connect issuer, or an Azure **managed identity** (workload identity federation). |
| ==+Certificate== | Recommended over secrets. Upload the public key (`.cer`, `.pem`, `.crt`); keep the private key in Key Vault. |
| ==!Client secret== | A password string. Max lifetime ==@24 months==; Microsoft recommends ==@under 12 months==. Value is shown ==!once==. Not for production. |

**5. Enterprise app properties — the access switches.**

| Property | Effect |
|---|---|
| **Enabled for users to sign-in?** | No = no tokens issued to anyone, ==!including other apps using application permissions==. Maps to the service principal's `accountEnabled`. |
| **Assignment required?** | Yes = only assigned users, groups and apps get a token. It also ==!blocks user consent== for the app — an admin must grant consent. Global Administrators sign in regardless. |
| **Visible to users?** | Shows the app in My Apps — but only to assigned users. Visibility is not access. |

Assign users or groups under **Users and groups**, optionally to an **app role** the app defines (for example Reader, Approver).

**6. Who can create and manage apps.** By default **every user can register applications** (`Entra ID > Users > User settings > Users can register applications`). Set it to **No** and grant the ==@Application Developer== role to the few who need it; they become owners of what they create. **Owners** of an app can manage that one app. Tenant-wide:

| Role | Can do |
|---|---|
| ==@Application Administrator== | All app registrations and enterprise apps, **plus** application proxy |
| ==@Cloud Application Administrator== | Same, **except** application proxy |
| ==@Application Developer== | Create registrations (when users can't); no enterprise-app management |

A similar user setting, **Users can create agent blueprints**, controls who can create agent identity blueprints for AI agents (Agent ID Developer role when off).

**7. Workload identities.** Applications, service principals and managed identities together are **workload identities**. They can't do MFA. Protect them with least-privilege permissions, certificate or federated credentials, Conditional Access for workload identities (block by location or risk; needs Workload Identities Premium; single-tenant service principals only), and access reviews.

## Where it lives

**Microsoft Entra admin center** (`entra.microsoft.com`). The same blades also appear in the Azure portal under *Microsoft Entra ID*.

| Task | Path |
|---|---|
| Register an app | `Entra ID > App registrations > New registration` |
| Add credentials | `App registrations > {app} > Certificates & secrets` (Certificates / Client secrets / Federated credentials) |
| Find the app's service principal | `App registrations > {app} > Overview > Managed application in local directory` |
| Properties, assignment | `Entra ID > Enterprise apps > All applications > {app} > Properties` / `Users and groups` |
| Restrict app creation | `Entra ID > Users > User settings > Users can register applications = No` |

```bash
az ad app create --display-name contoso-api          # application object only
az ad sp create --id <appId>                         # its service principal
az ad sp list --filter "appId eq '<appId>'"         # find SPs for an app
```

```powershell
Get-MgServicePrincipal -Filter "appId eq '<appId>'"
```

## Exam traps

- **"Grant the app access in App registrations so it works in the customer's tenant."** ==!No== — access in a tenant lives on that tenant's ==+service principal (enterprise app)==.
- **Which Object ID does Conditional Access need for a workload policy?** The ==+enterprise app's (service principal's)== Object ID, not the app registration's.
- **Stop an app getting any token right now** — set **Enabled for users to sign-in = No** (or deactivate). Deleting the app is the destructive option.
- **Only certain users may use an app** — ==+Assignment required = Yes== plus user/group assignment. "Visible to users = No" ==!only hides it==.
- **Assignment required and user consent** — users ==!can't consent== to such an app; grant admin consent.
- **Production credential** — ==+certificate or federated credential==, never a client secret. Secrets max out at 24 months.
- **Least-privilege role to manage enterprise apps but not app proxy** — ==+Cloud Application Administrator==.
- **Users can't register apps but one developer must** — ==+Application Developer==, not Application Administrator.
- **Code running on an Azure VM needs an identity** — use a managed identity (D1.1.6), not an app registration with a secret.
- **Microsoft Graph–created app has no service principal** — creating the SP is a separate call.

## Skip

- **Skip:** SAML / password-based / linked SSO configuration walk-throughs for gallery apps. Know enterprise apps can do SSO; the exam bullet is about identity and access, not SAML claim mapping.
- **Skip:** application proxy setup. Know only that Application Administrator can manage it and Cloud Application Administrator can't.
- **Skip:** the application manifest and `keyCredentials` JSON editing. Use the portal or CLI concept.
- **Skip:** logo size rules, homepage URL, notes field. Furniture.
- **Skip:** MSAL code and token-request parameters (`client_assertion`, PKCE details). Developer material.
- **Skip:** the legacy service principal type beyond its one-line definition.
- **Skip:** custom role definitions for app management (`microsoft.directory/applications/...` actions). Know custom roles can scope app management to one app.
