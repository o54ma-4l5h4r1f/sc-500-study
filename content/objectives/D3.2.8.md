## Azure first

- A VM's **generation** decides its virtual firmware. **Generation 1 (Gen1)** VMs boot with old-style BIOS and an **MBR** disk layout. **Generation 2 (Gen2)** VMs boot with **UEFI** firmware and a **GPT** disk layout. Every feature on this page needs Gen2.
- The **security type** is a VM property with three values: **Standard**, **Trusted launch** and **Confidential virtual machine**. You see it on the VM's Overview page.
- A **VM extension** is a small agent Azure installs inside a VM to do one job. A **managed identity** lets that extension authenticate to Azure.
- **Microsoft Defender for Cloud** turns findings into **recommendations** (fix this) and **alerts** (something bad happened).

Before you start: Foundations **virtual-machines-and-disks**, **azure-policy-basics**, **defender-for-cloud-basics**.

## In one sentence

**Trusted launch** is a free VM security type for Gen2 VMs that turns on **Secure Boot** (only signed boot code runs), a **virtual TPM** (a tamper-proof record of what booted) and **integrity monitoring** (Defender for Cloud checks that record and alerts on a bad boot).

## Why it exists

Some malware hides *below* the operating system. A **bootkit** or **rootkit** replaces the boot loader or a kernel driver. It loads before your antivirus or EDR, so those tools never see it. From SOC work you know how hard such an infection is to prove.

Think of a building's night shift. **Secure Boot** is the guard who checks every badge at the door and refuses unsigned ones. The **vTPM** is a sealed logbook that records who came in, which nobody inside the building can edit. **Integrity monitoring** is the head office that reads the logbook each morning and phones you if an entry looks wrong.

Each layer includes the one below it. The exam asks which layer a requirement needs.

| | Standard | Trusted launch | Confidential VM |
|---|---|---|---|
| Generation | Gen1 or Gen2 | ==@Gen2 only== | Gen2, confidential sizes only |
| Secure Boot / vTPM | No | Yes (each can be toggled) | Yes (vTPM required) |
| Boot integrity monitoring | No | Yes, with Guest Attestation extension | Yes |
| Memory encryption | No | ==!No== | Yes (hardware) |
| Disk encryption options | SSE, encryption at host, ADE | SSE, encryption at host, ADE | Confidential OS disk encryption, encryption at host |
| Change later? | Upgrade to Trusted launch | Roll back to Standard (one-way) | ==!Can't convert to or from== |
| Extra cost | — | ==+None== | Yes, specialised sizes |

## What actually matters

**1. The three components.**

- **Secure Boot** — UEFI firmware checks the boot loader's signature, the loader checks the kernel, the kernel checks drivers. If a component isn't signed by a trusted publisher, the VM ==!fails to boot==. Linux VMs with unsigned custom kernel modules (some GPU drivers) may need Secure Boot off.
- **vTPM** — a virtual TPM 2.0 that runs outside the VM's reach. It hashes each boot stage into Platform Configuration Registers and can store keys. It enables **remote attestation**: proving to an outside service what booted.
- **Integrity monitoring (boot integrity monitoring)** — installs the **Guest Attestation extension** (`GuestAttestation` on Windows, `GuestAttestationLinuxExtension` on Linux). It sends vTPM measurements to **Microsoft Azure Attestation**. Defender for Cloud then raises a ==@medium-severity alert for VM attestation failure==. It needs Secure Boot **and** vTPM on; ==!turning off vTPM also kills integrity monitoring==, and attestation fails if Secure Boot is off.

**2. Defaults.** Trusted launch is the default for new Gen2 VMs created in the portal, CLI and PowerShell. Secure Boot and vTPM are on. **Integrity monitoring is a separate tick box.** For ARM/Bicep/Terraform, Trusted launch becomes the default with API version 2025-11-01 or later (or by registering `TrustedLaunchByDefaultPreview`); older templates without a `securityProfile` deploy Standard.

**3. Upgrading an existing Gen2 VM.** Deallocate, then set security type to Trusted launch, Secure Boot and vTPM. Disks, IP and identity stay. Prerequisites: supported size and OS. If Azure Backup protects it, the portal needs the **Enhanced** backup policy. Rolling back to Standard is ==!one-way== — you can't re-enable Trusted launch on that VM — and the portal can't do the rollback.

**4. Gen1 → Trusted launch.** You ==!can't go Gen1 → Gen2 without Trusted launch==; the two happen together, in place, on the same VM resource. Steps: convert the OS disk MBR → GPT (`MBR2GPT /validate /allowFullOS`, then `/convert`), deallocate, set Trusted launch. Not supported for Windows Server 2016 (no `MBR2GPT.exe` — upgrade the OS first), Debian or Azure Linux. Turn off BitLocker on the Windows OS volume first. After a Gen1 upgrade, vTPM is on by default but ==!Secure Boot is not== — enable it. There is no rollback to Gen1 except restoring a backup taken before.

**5. Network.** Attestation calls out. Allow the **AzureAttestation** service tag outbound in NSGs, and `*.attest.azure.net` through firewalls. Otherwise the extension fails to provision.

**6. Extras Trusted launch unlocks on Windows**: **virtualization-based security (VBS)**, **hypervisor-enforced code integrity (HVCI)** and **Credential Guard** (blocks pass-the-hash credential theft).

**7. Not supported with Trusted launch:** **Managed Images** (use Azure Compute Gallery instead) and Linux VM hibernation. Trusted launch protects the OS disk only, not data disks.

## Where it lives

**Azure portal**, on the VM:

- New VM: `Virtual machines > Create > Basics > Security type = Trusted launch virtual machines` → **Configure security features**: Secure Boot, vTPM, Integrity monitoring.
- Existing VM: `Virtual machines > (your VM) > Settings > Configuration > Security type`. Toggling components on a running VM restarts it.
- Check: VM **Overview > Properties > Security type**, and `Extensions + applications` for the Guest Attestation extension.

```bash
az vm deallocate -g rg -n vm1
az vm update -g rg -n vm1 --security-type TrustedLaunch \
  --enable-secure-boot true --enable-vtpm true
az vm start -g rg -n vm1
# integrity monitoring on create:
az vm create ... --security-type TrustedLaunch --enable-integrity-monitoring
```

**Azure Policy** (`Azure portal > Policy > Definitions`, category *Trusted Launch*):

| Policy | Effect | Answers |
|---|---|---|
| `Disks and OS image should support TrustedLaunch` | Audit | which VMs *could* run Trusted launch |
| `Virtual Machine should have TrustedLaunch enabled` | Audit | which VMs *do* |
| `[Preview]: Secure Boot should be enabled on supported Windows virtual machines` | Audit | component left off |
| `[Preview]: vTPM should be enabled on supported virtual machines` | Audit | component left off |
| `Guest Attestation extension should be installed on supported ... virtual machines` | AuditIfNotExists | integrity monitoring missing |
| Initiative `[Preview]: Configure prerequisites to enable Guest Attestation on Trusted Launch enabled VMs` | deploys | installs the extension and a ==@system-assigned managed identity== |

**Defender for Cloud** recommendations (low severity): enable Secure Boot, enable vTPM, install the guest attestation extension; plus `Virtual machines guest attestation status should be healthy` (medium). See [D4.1.3](D4.1.3.html) for the plans.

## Exam traps

- "Protect against bootkits and rootkits" → ==+Trusted launch==. "Protect data in use / from the cloud operator" → ==+Confidential VM==. Trusted launch does ==!not== encrypt memory.
- Trusted launch costs nothing extra. Confidential VM does.
- A Gen1 VM can't get Secure Boot or vTPM without the Gen2 + Trusted launch upgrade.
- You can't convert an existing VM to Confidential. Recreate it.
- Integrity monitoring isn't on by default. No extension → no attestation alerts.
- The policies above **audit**. They don't flip VMs to Trusted launch, and they can't stop running VMs.
- Disabling vTPM silently disables integrity monitoring too.
- Attestation failing on many VMs at once → check the **AzureAttestation** outbound NSG rule before suspecting malware.

## Skip

- **Skip:** the size-family and OS-version tables. Know "Gen2, most current sizes; M-series and confidential DC/EC sizes are not Trusted launch sizes".
- **Skip:** MBR2GPT troubleshooting (four-partition limit, ReAgent.xml, drive-letter swap, Windows 11 boot fix). Operations, not exam.
- **Skip:** the ARM template walkthrough and the Azure Compute Gallery `TrustedLaunchSupported` image types.
- **Skip:** the firewall application-rule screenshots beyond "allow AzureAttestation / `*.attest.azure.net`".
- **Skip:** Trusted launch for scale sets and Azure Local VMs. Same idea.
- **Skip:** units 1, 6 and 7 of *Configure Trusted Launch for Azure virtual machines* (introduction, knowledge check, summary).

> **Module vs product docs.** Unit 5 says "Azure doesn't provide a built-in initiative" for Trusted launch, and describes remediation tasks that switch VMs to Trusted launch. The product docs list a built-in Trusted Launch initiative (the two Audit policies) and a built-in Guest Attestation prerequisites initiative. Remediation tasks only work for `DeployIfNotExists`/`Modify` effects, and the Trusted Launch policies are **Audit** only. The product docs win: these policies report; you upgrade VMs yourself.
