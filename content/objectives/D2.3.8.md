## Azure first

- A **hub-spoke** network has one central VNet (the **hub**) peered to many workload VNets (**spokes**). Shared services such as the firewall live in the hub.
- A **route table** with **user-defined routes (UDRs)** overrides Azure's default routing for a subnet. "Send `0.0.0.0/0` to `10.0.0.4` (next hop type **Virtual appliance**)" makes every internet-bound packet go to that IP first.
- An **NSG** (D2.3.1) filters by IP, port and protocol at a subnet or NIC. It knows nothing about domain names.
- An **FQDN** is a full domain name such as `api.github.com`. **SNI** is the hostname a client announces at the start of a TLS (HTTPS) connection.
- A **Key Vault** stores certificates; a **managed identity** lets an Azure resource read it without a password.

Read first: virtual-networks-and-subnets, private-dns-and-name-resolution, keys-secrets-and-certificates, diagnostic-settings-and-activity-log.

## In one sentence

Azure Firewall is a managed, stateful firewall you place in a hub VNet (or a Virtual WAN hub) and force traffic through with routes, so one Firewall Policy can filter by IP, by domain name and by threat intelligence for every spoke.

## Why it exists

As an analyst you chased beacons to command-and-control (C2) domains on port 443. An NSG can't stop that. It sees `10.1.2.5 → 52.x.x.x:443` and nothing more. It cannot tell `api.github.com` from `evil.example.com`. It also has no threat feed and no single choke point: each subnet has its own NSG.

Azure Firewall is the **building's single loading dock with a guard and a watch list**. Every delivery in or out passes the dock (UDRs). The guard checks the address label (FQDN), the watch list (threat intelligence) and, on Premium, opens the boxes (TLS inspection, IDPS).

> **Training vs product docs.** Unit 2 says NSGs apply rules "in a stateless manner". ==!That's wrong.== The NSG product doc says NSGs are **stateful**: return traffic for an allowed flow is allowed automatically. The real gap is FQDN, threat intelligence and content inspection, not state.

## What actually matters

### 1. Pick the SKU

| | Basic | Standard | Premium |
|---|---|---|---|
| Network rules, DNAT, application FQDN filtering (SNI) | ✓ | ✓ | ✓ |
| Threat intelligence | ==!Alert only== | Alert and deny | Alert and deny |
| DNS proxy, custom DNS, FQDNs in network rules | — | ✓ | ✓ |
| Web categories | — | ✓ (FQDN level) | ✓ (full URL) |
| ==@TLS inspection== (outbound) | — | — | ✓ |
| ==@IDPS== (signatures) | — | — | ✓ |
| ==@URL filtering== (full path) | — | — | ✓ |
| Throughput | 250 Mbps | 30 Gbps | 100 Gbps |
| Management NIC | Always required | Optional | Optional |

Standard upgrades to Premium in place; Premium to Standard means redeploying.

> **Training vs product docs.** Unit 2's table says Basic has no "DNS proxy + FQDN filtering". The SKU doc says Basic **does** filter FQDNs in **application** rules; it lacks DNS proxy and **network-level** FQDN filtering. Product docs win.

### 2. Firewall Policy, not classic rules

**Classic rules** live on one firewall and can't be shared. A **Firewall Policy** is its own Azure resource. One policy can attach to many firewalls in any region. It supports **parent/child inheritance** and Azure Firewall Manager. Policy tiers match SKUs: a Basic policy for Basic, Standard policy for Standard or Premium, Premium policy (TLS inspection, IDPS, URL filtering) for Premium only. Use a policy for anything new.

Hierarchy: **policy → rule collection group** (priority) **→ rule collection** (priority + one action, Allow or Deny, one rule type) **→ rules**. Inheritance details that get tested:

- Parent rule collection groups ==@always win== over the child's, whatever the numbers.
- **DNAT rule collections are not inherited.** Define them in the child.
- Threat intelligence mode is inherited; the child may only make it **stricter**.

### 3. Rule types and default stance

- **Default deny.** No rule, no traffic. Rules are **terminating**.
- **DNAT rules**: firewall public IP + port → private IP + port. A matching DNAT is allowed implicitly. Use a specific source, not `*`.
- **Network rules**: stateful 5-tuple (source, destination, port, protocol). They run before application rules: a network rule allowing 443 to `*` means your application deny for `google.com` never fires.
- **Application rules**: outbound/east-west HTTP, HTTPS and MSSQL by FQDN. HTTPS matches on **SNI** only (Premium with TLS inspection can also match the URL path). ==!Application rules never apply to inbound traffic==: filter inbound web traffic with WAF on Application Gateway or Front Door.
- **FQDN tags / service tags** stand in for Microsoft services (for example `WindowsUpdate`) so you don't list hostnames.
- **Infrastructure rule collection**: built-in allows for platform FQDNs, processed after application rules and before the final deny.

### 4. Threat intelligence

Modes: **Off**, **Alert** (log only), **Alert and deny**. The ==@default is Alert==. It uses the Microsoft Threat Intelligence feed. It is evaluated **before** any DNAT, network or application rule, so it blocks a known-bad FQDN even if you allowed it. An **allowlist** exempts FQDNs or IP ranges.

### 5. DNS proxy

Off by default. When on, the firewall listens on **port 53** and forwards to Azure DNS or up to 15 custom DNS servers. Three steps: enable DNS proxy; optionally set custom DNS; set the spoke VNet's **DNS servers** to the firewall's private IP (restart VMs to pick it up). Purpose: client and firewall resolve the same name to the same IP. ==@DNS proxy is required for FQDNs in network rules.==

> **Training vs product docs.** Unit 2 says application rules "require the DNS proxy feature". The DNS settings doc ties DNS proxy to FQDN filtering in **network** rules. Application rules match on the Host header or SNI and work without it. Product docs win.

### 6. Premium: TLS inspection and IDPS

- **TLS inspection** decrypts outbound and east-west HTTPS, inspects it, then re-encrypts. It needs an ==@intermediate CA certificate== stored in **Key Vault**. A **user-assigned managed identity** reads it with **Get** and **List** on *secrets*. Clients must trust your root CA.
- **IDPS** uses signature-based detection, with modes **Off / Alert / Alert and deny**. It drops silently (no TCP reset). It inspects encrypted payloads only when TLS inspection is on.

### 7. Getting traffic to it

- Subnet named exactly ==@AzureFirewallSubnet==, at least **/26**.
- On every spoke subnet, a UDR `0.0.0.0/0 → Virtual appliance → {firewall private IP}`. ==!No route, no inspection==: spokes otherwise go straight out via system routes. Add spoke-to-spoke routes if east-west must be inspected too.
- **Forced tunnelling** sends the firewall's own internet traffic on to an on-premises firewall or NVA. It needs the **Management NIC**: an `AzureFirewallManagementSubnet` (/26) with its own public IP for Microsoft-only traffic. Basic SKU and secured-hub firewalls always have one. ==!DNAT isn't supported when forced tunnelling is on.==
- **Secured virtual hub** (D2.3.3): deploy the firewall into a Virtual WAN hub from **Firewall Manager**. No AzureFirewallSubnet to create, and no UDRs. **Routing intent** (Private traffic and/or Internet traffic → Azure Firewall, Inter-hub enabled) programs the routes for you.

### 8. Central management and governance

**Azure Firewall Manager** manages policies across many firewalls, both hub VNets and secured virtual hubs. It also handles partner security providers (hub only) and DDoS and WAF policy association. Built-in **Azure Policy** definitions (names as in the built-in reference) govern firewalls: *Azure Firewall Policy should enable Threat Intelligence* (Audit, Deny), *Azure Firewall Policy should have DNS Proxy Enabled* (Audit), *Azure Firewall Classic Rules should be migrated to Firewall Policy*, *Azure Firewall Standard should be upgraded to Premium for next generation protection*, and *[Preview]: All Internet traffic should be routed via your deployed Azure Firewall* (AuditIfNotExists). The Azure Firewall *Use Azure Policy* article lists the same controls under short descriptive titles (for example "Enable Threat Intelligence in Azure Firewall Policy") and adds IDPS and TLS-inspection policies; expect the built-in names in the portal. Firewall logs (network rule, application rule, threat intel, IDPS) go to Log Analytics through **diagnostic settings**.

## Where it lives

All in the **Azure portal**.

- Deploy: `Azure portal > Firewalls > + Create`. Choose **Firewall tier** (Basic/Standard/Premium), **Firewall management: Use a Firewall Policy**, VNet (creates `AzureFirewallSubnet`), public IP, and **Enable Firewall Management NIC** if needed.
- Policy: `Azure portal > Firewall Policies > {policy}`. Blades: **Rule collections**, **DNAT rules**, **Network rules**, **Application rules**, **Threat Intelligence**, **DNS** (DNS proxy), **TLS inspection** and **IDPS** (Premium).
- Central: `Azure portal > Firewall Manager > Virtual hubs | Virtual networks | Azure Firewall Policies`.
- Spoke routing: `Route tables > + Create > Routes > 0.0.0.0/0, Virtual appliance, {fw private IP}`, then **Subnets > Associate**.

```bash
az network firewall policy create -g rg-hub -n fwpol --sku Standard --threat-intel-mode Deny
az network firewall policy update -g rg-hub -n fwpol --enable-dns-proxy true
az network firewall policy rule-collection-group create -g rg-hub --policy-name fwpol \
  -n rcg-egress --priority 200
az network firewall policy rule-collection-group collection add-filter-collection \
  -g rg-hub --policy-name fwpol --rcg-name rcg-egress -n allow-openai \
  --collection-priority 210 --action Allow --rule-type ApplicationRule --rule-name openai \
  --source-addresses 10.20.1.0/24 --protocols Https=443 --target-fqdns "*.openai.azure.com"
az network route-table route create -g rg-spoke --route-table-name rt-spoke -n default \
  --address-prefix 0.0.0.0/0 --next-hop-type VirtualAppliance --next-hop-ip-address 10.0.0.4
```

## Exam traps

- "Allow outbound only to `*.openai.azure.com` from one subnet" → ==+application rule (FQDN)==. NSG with a service tag is the distractor.
- "Block known-malicious IPs and domains automatically" → threat intelligence in **Alert and deny**. Basic can't deny. Default mode is Alert, so "enabled by default" does not mean "blocking".
- "Decrypt and inspect outbound HTTPS" / "signature-based intrusion prevention" / "allow `/api/*` but not `/admin/*`" → ==+Premium== (TLS inspection, IDPS, URL filtering). Web categories alone do **not** need Premium.
- A network rule allows 443 to Any, and an application rule denies a site → traffic is **allowed**. Network rules run first and terminate.
- Parent policy priority 300 vs child priority 100 → **parent first** anyway.
- FQDN in a **network** rule isn't matching → enable **DNS proxy** and point the VNet DNS at the firewall.
- Inbound HTTP filtering by URL → **WAF**, not Azure Firewall application rules.
- Spoke VMs bypass the firewall → no **UDR** on the spoke subnet (or a /32 private endpoint route wins; see D2.3.6).
- Forced tunnelling + DNAT → not supported together; forced tunnelling needs the Management NIC.
- Virtual WAN hub → **Secured virtual hub + routing intent**; you don't create `AzureFirewallSubnet` or UDRs there.
- Reuse one rule set across 10 firewalls in 3 regions → **Firewall Policy** (with Firewall Manager), not classic rules.

## Skip

- **Skip** the per-SKU throughput, fat-flow and pricing rows. The exam asks *which SKU adds which feature*.
- **Skip** IDPS signature counts (67,000+ rules, 50+ categories), signature-override modes and IDPS private ranges.
- **Skip** the self-signed CA scripts (`cert.sh`, `cert.ps1`, `openssl.cnf`). Know: intermediate CA in Key Vault, managed identity with secret Get/List.
- **Skip** the DNS proxy cache timers (1 h positive, 30 min negative) and health-check loops.
- **Skip** SNAT private-range tuning and split tunnelling through route tables on `AzureFirewallSubnet`.
- **Skip** the "Any protocol meant TCP/UDP/ICMP before 9 November 2020" note. History, not exam.
- **Skip** unit 3's `WindowsVirtualDesktop` FQDN tag as a Microsoft 365 example. Just know FQDN tags exist.
- **Skip** Firewall Manager known-issues table and partner SECaaS provider list.
- **Skip** unit 4's Virtual WAN deployment clicks; D2.3.3 owns Virtual WAN. Keep the one-liner: secured hub + routing intent = automatic routing.
