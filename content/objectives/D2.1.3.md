## Azure first

- **Microsoft Defender for Cloud** is Azure's security service. Its paid **Defender plans** (one per workload type: Servers, Storage, Databases, Containers…) are switched on per **subscription** under **Environment settings**, and some can be tuned per resource.
- A **storage account** holds Blob, Azure Files and Data Lake data. Uploads land as **blobs**. A **blob index tag** is a searchable key-value label on a blob.
- **Azure Event Grid** delivers events (such as "blob uploaded") to code like Functions or Logic Apps.
- **Azure Policy** with a **DeployIfNotExists** effect switches a setting on wherever it is missing.

Read first: defender-for-cloud-basics, storage-accounts-basics, azure-policy-basics, log-analytics-workspace.

## In one sentence

Defender for Storage is an agentless, per-storage-account plan that watches every storage request for attacks (activity monitoring), scans uploaded blobs with Microsoft Defender Antivirus (malware scanning, paid per GB with a monthly cap), and raises the priority of alerts on accounts that hold sensitive data.

## Why it exists

Firewall rules and RBAC decide who may upload. They cannot tell whether the file is malware or whether a valid SAS token is being abused from a Tor exit node. As an analyst you triaged "Malicious blob uploaded" and "access from a suspicious IP" alerts. This is the plan that produces them, and now you are the one who turns it on and sizes the cost.

## Mental model

A **bank's night-deposit box** with three guards. One watches the cameras for odd behaviour (activity monitoring). One X-rays every envelope dropped in (malware scanning, paid per kilo, with a monthly budget). One knows which boxes hold the crown jewels and shouts louder when those are touched (sensitive data threat detection).

## What actually matters

| Feature | What it does | Cost | Default |
|---|---|---|---|
| ==@Activity monitoring== | analyzes data- and control-plane telemetry for Blob, Files and Data Lake; Microsoft Threat Intelligence + anomaly models; detects SAS misuse ("entities without identities"), Tor, exfiltration | in the per-account price | always on with the plan |
| ==@Malware scanning== (on-upload) | full Defender Antivirus scan when a blob is created, overwritten or committed | ==!extra, per GB scanned== | configurable; cap ==@10,000 GB per account per month== |
| On-demand malware scanning | scan existing blobs/containers/prefixes when you choose | per GB, ==!no monthly cap== | manual |
| ==@Sensitive data threat detection== | uses Sensitive Data Discovery (Purview sensitive info types and labels) to raise priority of alerts on sensitive resources; ==!no new alert types== | no extra cost | configurable (on in plan settings) |

1. **Plan versions.** The current plan is priced **per storage account**. The **classic** plan was per transaction and only did hash reputation for malware. The per-transaction plan cannot be newly enabled after 5 February 2025; classic customers must migrate to get malware scanning.
2. **Enable at subscription scope (recommended).** All existing accounts are covered; new accounts are picked up automatically (product docs: protection starts up to 24 hours after creation). Use the built-in policy ==@Configure Microsoft Defender for Storage to be enabled== (DeployIfNotExists) at management-group scope; its parameters set malware scanning, sensitive data detection and the cap. Two cousins: ==@Configure basic Microsoft Defender for Storage to be enabled (Activity Monitoring only)== (DeployIfNotExists, no malware scanning) and ==@Microsoft Defender for Storage should be enabled== (AuditIfNotExists, reports only).
3. **Override per account.** On a storage account, set ==@Override Defender for Storage subscription-level settings== to On, then give that account its own cap, features, or exclusion. Account-level settings win over subscription defaults. You must also use the override to set an Event Grid custom topic for scan results.
4. **Malware scanning details.** Results land as two **blob index tags**: *Malware scanning scan result* (**No threats found**, **Malicious**, **Error**, **Not scanned**, **Scan timed out**) and *scan time (UTC)*. Optional outputs: Defender for Cloud alert (always for malicious), **Event Grid custom topic**, **Log Analytics** table `StorageMalwareScanningResults`. Built-in **soft delete of malicious blobs** is available. Limits: up to **50 GB** per blob; no legacy v1 accounts, append or page blobs, NFS 3.0 uploads or client-side-encrypted blobs; on-upload scanning does not cover Azure Files (on-demand can). Enabling creates an **Event Grid system topic** in the account's resource group; ==!deleting it stops scanning==. Index tags are ==!not tamper-proof==; do not use them as the only control.
5. **Cap alerts.** One alert at **75%** of the cap, one at **100%** when scanning stops. After the cap, new uploads go ==!unscanned until next month==. Scanning filters (prefix, suffix, size) can exclude noise.
6. **Alert routing** (same as every Defender for Cloud alert): **Email notifications** per subscription, **Microsoft Sentinel** via the Defender for Cloud connector (tenant-based connector for new deployments), **suppression rules** for known-good patterns, **sample alerts** to test the pipeline. Coverage view: **Storage Center** in the Azure portal (Protected / Partly protected / Not protected), added April 2026.

## Where it lives

| Task | Path (Azure portal) |
|---|---|
| Subscription plan + settings (cap, features) | `Microsoft Defender for Cloud > Environment settings > {subscription} > Defender plans > Storage > Settings` |
| Per-account override | `Storage account > Microsoft Defender for Cloud > Settings` |
| On-demand scan | Same storage account Defender for Cloud blade (on-demand scan option) |
| Email recipients | `Defender for Cloud > Environment settings > {subscription} > Email notifications` |
| Suppression / sample alerts | `Defender for Cloud > Security alerts > Suppression rules` / `Sample alerts` |
| Policy | `Azure Policy > Definitions > "Configure Microsoft Defender for Storage to be enabled"` |

## Exam traps

- "Detect malware in uploads **and** keep cost predictable": ==+malware scanning with a per-account monthly cap==. Not the classic plan, not on-demand.
- "Cap reached, what happens?": scanning ==!stops for the rest of the month==; uploads still succeed.
- "One account needs a higher cap than the subscription default": ==+override subscription-level settings on that account==.
- Sensitive data threat detection ==!does not create new alerts==; it re-prioritizes existing ones and costs nothing extra.
- Activity monitoring ==!does not need diagnostic logs== on the account.
- Subscription-level enablement covers **new** accounts; resource-level enablement does not.
- The module says sensitive data detection needs Purview sensitive data discovery configured; product docs say Defender's own **Sensitive Data Discovery** engine finds the data and reuses Purview info types and labels. Product docs win.

## Skip

- **Skip** hash-reputation internals (Put Block/Put Block List gap). Know only that full malware scanning includes hash reputation and the classic plan had hash reputation alone.
- **Skip** the module's example caps (25,000 / 5,000 / 2,000 GB). Only the default 10,000 GB is a fact.
- **Skip** the response-automation recipes (Logic App playbooks, DMZ storage account, ABAC blocking of unscanned blobs). Know the options exist.
- **Skip** the REST API and IaC enablement syntax.
- **Skip** the StorageDataScanner and DefenderForStorageSecurityOperator resource details. Know that malware scanning deploys helper resources that must not be deleted.
- **Skip** Azure Files sensitive data detection (needs Defender CSPM) and Amazon/GCP storage coverage.
- **Skip** Contoso's partner-upload incident story; the lesson is "valid SAS + valid IP still let malware in".
