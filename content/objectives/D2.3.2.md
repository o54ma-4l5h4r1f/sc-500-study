## Azure first

- A **management group** is a folder of subscriptions. Settings applied to it flow down to every subscription inside.
- A **virtual network (VNet)** is a private network in one region. Large companies have hundreds, owned by different teams.
- An **NSG** (D2.3.1) is a rule list a workload team can edit on its own subnet or NIC. Anyone with write access to that NSG can open a port.
- **Azure Policy** evaluates resources against conditions. Here it is used for one job only: deciding which VNets belong to a group.

See the Foundations pages listed above, especially *azure-policy-basics* and *azure-resource-hierarchy*.

## In one sentence

Azure Virtual Network Manager (AVNM) lets a central network team group VNets across subscriptions and push **security admin rules** to them, and those rules are checked before any team's NSG, so a team cannot undo them.

## Why it exists

NSGs belong to whoever owns the subnet. In the training module, application teams with Owner rights opened RDP (3389) from the internet, against policy. Azure Policy can block an NSG rule at creation time, but it does not sit in the traffic path.

AVNM puts a rule in the traffic path, above every NSG. Picture a building where each tenant controls the locks on its own office doors (NSGs), but security controls the front-door rule that says "nobody brings in a blowtorch" (Deny). Security can also keep the fire exit always open (Always Allow) even if a tenant bolts it.

The three actions are the whole exam topic:

| Action | What happens | Typical use |
|---|---|---|
| ==@Deny== | Traffic stops. NSG rules are not consulted. | Block 3389/22 from `Internet` everywhere |
| ==@Always Allow== | Traffic is delivered. NSG rules are not consulted. | Keep Bastion, monitoring or backup traffic flowing even if a team's NSG would block it |
| ==@Allow== | Traffic is passed to the NSGs, which still decide. | Permit a class of traffic but let teams tighten it |

## What actually matters

**1. Four building blocks.**

- **Network manager** (the AVNM instance) with a **scope**: a list of subscriptions and/or management groups. It can only touch VNets inside that scope. You also tick which **features** it may deploy: Connectivity, Security admin, Routing.
- **Network group**: a set of VNets, from any region. A VNet can be in several groups.
- **Configuration**: what to apply to a group. **Security admin configuration** (rules), **connectivity configuration** (builds hub-and-spoke or mesh peering for you), or **routing configuration** (user-defined routes at scale).
- **Deployment**: pushing configurations to chosen **regions**. ==!Nothing takes effect until you deploy.==

**2. Static vs dynamic membership.**

| | Static | Dynamic |
|---|---|---|
| How | You pick VNets by hand | ==@Azure Policy== adds VNets that match a condition (tag, name, subscription, resource group) |
| Policy detail | none | custom definition, mode `Microsoft.Network.Data`, effect ==@addToNetworkGroup== |
| Good for | a few VNets, exceptions | many VNets, VNets created later |
| Permissions | rights to join the group | plus read/write on the policy |

Dynamic membership does not need a redeploy when a matching VNet appears. The policy also outlives the network manager; delete it by hand.

**3. Rule structure.** Security admin configuration → **rule collections** (each targets one or more network groups) → **rules**. A rule has priority (==@1–4096==, unlike NSG's 100–4096), action, direction, protocol (TCP, UDP, ICMP, ESP, AH, Any), source/destination (IPs, CIDR or service tags) and ports. Admin rules apply at **VNet level**; NSGs apply at subnet/NIC level.

**4. One security admin configuration per region per network manager.** Need more rule sets? Add rule collections to that one configuration. Multiple connectivity configurations per region are allowed.

**5. Goal-state deployment.** A deployment states the full set of configurations a region should have. Deploy Config1+Config3 after Config1+Config2 and Config2 is removed. To remove everything, deploy **None**. Rules reach resources with **eventual consistency**: new VMs get them shortly after creation, not instantly.

**6. Where admin rules do not apply.**

- VNets containing **Azure SQL Managed Instance** or **Azure Databricks** are skipped by default (you can apply Allow rules only via `AllowRulesOnly`).
- Subnets holding **Application Gateway** (unless network isolation is on), **Azure Bastion**, **Azure Firewall**, **Route Server**, **VPN Gateway**, **Virtual WAN** or **ExpressRoute Gateway** are skipped; other subnets in the same VNet still get the rules.
- The service tags `AzurePlatformDNS`, `AzurePlatformIMDS` and `AzurePlatformLKM` are not supported in admin rules.
- Private endpoints inside a *managed* virtual network are not covered.

**7. Overlapping managers.** Two network managers can overlap only if they have different features ticked; you cannot create two with overlapping scope and the same feature. When configurations conflict on the same VNet, the manager with the ==@higher scope== (for example, the root management group) wins.

**8. Exceptions.** To exempt one team, put its VNets in a smaller network group and give that group a higher-priority (lower number) rule.

**9. Visibility.** VNet flow logs record admin-rule decisions. Network Watcher effective security rules show admin rules next to NSG rules (D2.3.9). Deployments are logged in the Activity log.

## Where it lives

**Azure portal** only.

- Create: `Azure portal > Network managers > + Create` → scope and **Features** (tick **Security admin**).
- Groups: `Network managers > avnm-contoso > Settings > Network groups > + Create` → **Add virtual networks** (static) or **Create Azure policy** (dynamic).
- Rules: `Network managers > avnm-contoso > Settings > Configurations > + Create > Security admin configuration` → **Add rule collection** → **Add** rule.
- Deploy: `Network managers > avnm-contoso > Settings > Deployments > Deploy configurations` → pick configuration and regions.
- Verify on a VNet: `Virtual networks > vnet-prod > Settings > Network Manager` (tabs for connectivity and security admin configurations).
- Role: **Network Contributor** at the scope is the commonly assigned role for managing AVNM.

```bash
az network manager create -g rg-net -n avnm-contoso -l westeurope \
  --scope-accesses SecurityAdmin --network-manager-scopes subscriptions="/subscriptions/<sub-id>"
az network manager group create -g rg-net --network-manager-name avnm-contoso -n ng-prod
az network manager security-admin-config create -g rg-net \
  --network-manager-name avnm-contoso -n sec-baseline
# rule collections and rules: az network manager security-admin-config rule-collection ... rule create
az network manager post-commit -g rg-net --network-manager-name avnm-contoso \
  --commit-type SecurityAdmin --target-locations westeurope \
  --configuration-ids <config-resource-id>
```

## Exam traps

- **"An NSG Allow can override an admin Deny."** ==!No.== Admin rules are evaluated first. A Deny ends evaluation.
- **Allow vs Always Allow.** Only **Always Allow** guarantees delivery past NSGs. Plain **Allow** hands the decision to the NSGs.
- **Training module vs product docs.** The module says a "definitive Allow" bypasses NSGs. The product docs say ==!plain Allow continues to NSG evaluation==; only Always Allow and Deny terminate. Product docs win.
- **"I created the rule, so it is live."** Not until you **deploy** the configuration to the region.
- **Second security admin configuration in the same region.** Not allowed from one network manager. Use another rule collection.
- **Dynamic membership = Azure Policy.** Not tags on the network group, not an Entra dynamic group. Effect `addToNetworkGroup`.
- **Priority range.** Admin rules 1–4096; NSG rules 100–4096.
- **Admin rules vs Azure Policy deny.** Policy blocks *creating* a bad NSG rule; admin rules block *traffic*. A question about "teams can still create NSG rules but RDP from the internet must never work" wants AVNM.
- **Admin rules vs Azure Firewall.** Admin rules are layer 3–4, no FQDNs, no inspection. Inspection needs Azure Firewall (D2.3.8).
- **Scope.** A VNet outside the network manager's scope cannot be added to its groups.

## Skip

- **Skip:** connectivity configurations in depth (hub-and-spoke, mesh, direct connectivity, global mesh). Know the one-liner: AVNM can create peerings for you. The security exam tests admin rules.
- **Skip:** routing configurations and IP address management (IPAM pools). Same reason; name-level only.
- **Skip:** the 20-row high-risk port table in the product doc. Know the pattern (deny management and cleartext ports from `Internet`), not the list.
- **Skip:** pricing models (per-VNet vs subscription-based). Reference material, not exam content.
- **Skip:** cross-tenant connections and the network verifier tool. Not on the blueprint bullet.
- **Skip:** unit 5's six-step portal walkthrough as a memory exercise. Remember the order: instance → group → configuration → rule collection → rule → deploy.
