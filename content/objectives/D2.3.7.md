## Azure first

- A **load balancer** spreads incoming connections across a pool of VMs. A **Standard internal load balancer** has a private frontend IP only. (Basic Load Balancer was retired on 30 September 2025.)
- **VNet peering** joins two VNets into one flat network. Every resource in each can reach the other, subject to NSGs, and the address ranges must not overlap.
- **NAT** (network address translation) swaps one IP address for another as traffic passes through.
- A **private endpoint** (D2.3.6) is the consumer's NIC that connects to one Private Link resource.

Read first: virtual-networks-and-subnets, private-dns-and-name-resolution, azure-rbac-and-entra-roles.

## In one sentence

Private Link service is how *you* become the provider: you put your own app behind a Standard internal load balancer, and other VNets (other subscriptions, other tenants) reach it through private endpoints, never through a public IP or peering.

## Why it exists

D2.3.6 was the consumer side: you reach Microsoft's storage account privately. Now flip it. Your team built an API. A partner, or another business unit, needs it. Before Private Link service you had two bad choices:

- **Peering**: exposes both whole networks to each other, and fails when both sides use `10.0.0.0/8`.
- **A public IP**: back on the internet.

Private Link service is a **hotel's guest-only service hatch**. Guests (consumers) get a hatch in their own room. Behind it is only the kitchen counter (the load balancer frontend), never the rest of the hotel. The kitchen sees "room 412" (the NAT IP), not the guest's home address.

Traffic is one-way: the consumer opens connections; the provider can never open a connection back into the consumer's VNet.

## What actually matters

1. **Standard internal load balancer only.** The service ties to one **frontend IP configuration** of a Standard Load Balancer. ==!Basic is not supported.== The backend pool must be configured **by NIC**, not by IP address. One Private Link service per frontend IP; use extra frontends for more services.
2. **Same region on the provider side.** The Private Link service must be in the same region as its VNet and load balancer. Consumers can be in **any** public region, in peered VNets, or on-premises over VPN/ExpressRoute.
3. **NAT IP.** Every consumer packet arrives with a **NAT IP** from a provider subnet as its source. That is why ==+overlapping address spaces don't matter==. Up to **eight** NAT IPs per service (more ports per IP to scale); keep at least one. The NAT subnet must have `privateLinkServiceNetworkPolicies` **Disabled**; the portal does this for you, CLI and templates do not.
4. **Alias.** Azure generates a globally unique name: `prefix.{GUID}.region.azure.privatelinkservice`. Share the alias (or the resource ID) offline. ==!The alias is a routing identifier, not a secret and not a grant.==
5. **Visibility vs auto-approval.** Two separate settings:
   - **Visibility** = who may *request* a connection: **Role-based access control only** (most restrictive), **Restricted by subscription**, or **Anyone with your alias**.
   - **Auto-approval** = which subscriptions connect *without* the provider clicking Approve. It is a subset of visibility. Everyone else lands as **Pending** until you approve, reject or delete.
6. **Who sees the real client IP.** Backends see the NAT IP. To get the consumer's source IP and the endpoint's **LinkID**, enable **TCP Proxy v2** (`EnableProxyProtocol`). Your app must then parse the PROXY v2 header, or requests fail. VNet flow log version 5 also adds the PLS link ID and source NAT IP/port (limited regions at the time of writing).

### Private Link service vs peering

| Need | VNet peering | Private Link service |
|---|---|---|
| Same org, no overlap, full connectivity | ==+Simpler== | Possible, unnecessary |
| Overlapping IP ranges | Fails | ==+NAT solves it== |
| Expose one service, not the network | Exposes whole VNet | Only the LB frontend |
| Cross-tenant without mutual visibility | Full mutual visibility | Consumer VNet stays opaque |
| Who starts connections | Both sides | Consumer only |

Other limits worth one line each: IPv4 only; TCP and UDP only; about 5-minute (300 s) idle timeout, so use TCP keepalives below that.

## Where it lives

All in the **Azure portal** (provider and consumer both).

- Provider: `Azure portal > Private Link (Private Link Center) > Private link services > + Create`. Tabs: **Basics** (region = LB region), **Outbound settings** (load balancer, frontend IP, NAT subnet), **Access security** (visibility, auto-approval subscriptions). Copy the **Alias** from **Overview**.
- Approve requests: `{private link service} > Settings > Private endpoint connections`.
- Consumer: `Private Link > Private endpoints > + Create > Resource tab > Connect to an Azure resource by resource ID or alias`.
- DNS: no automatic zone for custom services. The consumer creates their own private DNS A record for whatever name they use, pointing at their endpoint IP.

```bash
az network vnet subnet update -g rg-prov --vnet-name vnet-prov -n snet-nat \
  --private-link-service-network-policies Disabled
az network private-link-service create -g rg-prov -n pls-api \
  --vnet-name vnet-prov --subnet snet-nat \
  --lb-name lb-api --lb-frontend-ip-configs fe-api \
  --visibility <consumer-sub-id> --auto-approval <trusted-sub-id>
```

## Exam traps

- "Expose an app to a partner whose VNet overlaps yours, without a public IP" → ==+Private Link service==. Peering is the distractor (overlap breaks it). A VPN also needs non-overlapping ranges.
- Load balancer choice: **Standard, internal**. Public LB, Basic LB and Application Gateway as the PLS frontend are wrong answers.
- Creation fails from CLI on the NAT subnet → `privateLinkServiceNetworkPolicies` not disabled.
- "Backend logs show only 10.x addresses from one subnet" → that's the NAT IP, by design. Fix = TCP Proxy v2, not removing NAT.
- "Partner connected but traffic doesn't flow" → the connection is **Pending**; approve it, or add their subscription to auto-approval.
- Private Link *service* (provider) vs private *endpoint* (consumer): every Private Link service connection still uses a consumer private endpoint.
- The consumer can be cross-region; the PLS itself cannot be in a different region from its LB.

## Skip

- **Skip** the TCP Proxy v2 TLV byte layout (type 0xEE, subtype 0x01, little-endian LinkID). Know only what it gives you: real source IP + LinkID.
- **Skip** Private Link Service Direct Connect (public preview, no load balancer). Preview features are not on the exam.
- **Skip** the per-LB and per-subscription service-count limits. Look them up when you hit them.
- **Skip** unit 4's three Contoso scenarios beyond the rule they teach: SaaS, hub-to-spoke shared service, overlapping partner.
- **Skip** unit 4's description of the visibility options as an approval switch ("Restricted by subscription = manual approval for every request"; "RBAC only = connect automatically"). The product doc separates **visibility** (who may request) from **auto-approval** (who skips manual approval). Product docs win; learn the doc version.
- **Skip** unit 4's wording "source NAT" vs the property doc's "destination side NAT-ing". Both describe the same result: the backend sees the NAT IP as the source.
