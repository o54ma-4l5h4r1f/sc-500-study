## Azure first

- A **virtual network (VNet)** is your private network in Azure. A **subnet** is a slice of its address range. Subnets organise addresses; they are ==!not walls==. Everything in a VNet can talk to everything else by default.
- A **network interface (NIC)** is the virtual network card on a VM. It holds the VM's private IP address.
- A **service tag** is a Microsoft-maintained name for a group of IP ranges, such as `Internet` or `Storage`. You write the name; Microsoft keeps the list current.
- **Stateful** means the filter remembers a connection. If the request was allowed, the reply is allowed back automatically.

See the Foundations pages listed above, especially *virtual-networks-and-subnets*.

## In one sentence

An NSG is a numbered list of allow/deny rules that Azure checks against every new connection into or out of a subnet or a NIC; an ASG is a named group of NICs you can use in those rules instead of IP addresses.

## Why it exists

As an analyst you have seen the lateral-movement chain: one web server is compromised, then the attacker reaches the database on port 1433. In a flat Azure VNet that chain needs no exploit. The default rules let every resource reach every other resource on every port. The training module's Contoso story is exactly that: web tier, app tier, database and dev VMs in one subnet, so the web VM can query SQL directly.

Think of a building with locked floors. The VNet is the building. Subnets are floors. An NSG is the badge reader on a floor door (subnet) or an office door (NIC). An ASG is a badge group such as "finance staff": you grant the group, and anyone given that badge gets in.

Two rules about that picture decide most exam questions:

- **Both layers must allow.** If the subnet NSG denies, the NIC NSG never sees the packet. To let port 80 in, ==@both NSGs must allow it== when both exist.
- **Order flips with direction.** Inbound: subnet, then NIC. Outbound: NIC, then subnet. The same order applies to traffic between two VMs in the same subnet.

## What actually matters

**1. A rule has seven fields.** Name, **priority**, source, destination, **protocol** (TCP, UDP, ICMP, ESP, AH or Any; ESP and AH only via ARM templates, not the portal), **direction** (inbound or outbound), port range, and **action** (Allow or Deny). Matching uses the five-tuple: source IP, source port, destination IP, destination port, protocol.

**2. Priority is 100–4096. Lower number wins.** Processing stops at the first match. Two rules cannot share the same priority and direction. Leave gaps (100, 110, 120) so you can insert rules later. Limit: **2,000 rules per NSG** (the count includes the default rules).

**3. Six default rules you cannot delete.** You can only override them with a lower number.

| Direction | Name | Priority | Source → Destination | Action |
|---|---|---|---|---|
| Inbound | ==@AllowVNetInBound== | 65000 | VirtualNetwork → VirtualNetwork | Allow |
| Inbound | ==@AllowAzureLoadBalancerInBound== | 65001 | AzureLoadBalancer → any | Allow |
| Inbound | DenyAllInbound | 65500 | any → any | Deny |
| Outbound | AllowVnetOutBound | 65000 | VirtualNetwork → VirtualNetwork | Allow |
| Outbound | ==@AllowInternetOutBound== | 65001 | any → Internet | Allow |
| Outbound | DenyAllOutBound | 65500 | any → any | Deny |

Read that table as a security engineer: internet inbound is blocked, but ==!everything inside the VNet is allowed== and ==!outbound internet is allowed==. Segmentation means adding your own Deny rules, for example deny 1433 from the web tier at priority 100, allow 1433 from the app tier at 110.

**4. Source and destination can be five things.** Any, one IP, a CIDR range, a **service tag**, or an **ASG**. Use the private IP of a resource: inbound rules are checked after public-to-private translation, outbound before.

**5. Service tags.** `VirtualNetwork`, `Internet`, `AzureLoadBalancer` (which covers the platform probe address 168.63.129.16), plus service tags such as `Storage` or `Sql`, some with a region suffix (`Storage.WestEurope`). Microsoft updates the IP lists. You cannot create your own service tag.

**6. Augmented rules.** One rule can list several ports (`80, 443, 10000-10005`) and several IPs or ranges. It ==!cannot list several service tags or several ASGs== in one field.

**7. Stateful, new connections only.** Allow inbound 443 and the reply goes out without an outbound rule. Deleting a rule does not cut an existing session; it only blocks new ones.

**8. Association.** One NSG per subnet, one per NIC. One NSG can be attached to many subnets and NICs. Microsoft's advice is to pick subnet *or* NIC, not both, because two layers are hard to troubleshoot. Subnet is the usual choice for tiers.

**9. ASGs.** Create an ASG resource (for example `asg-app`), add NICs to it, then write `source = asg-app` in an NSG rule. New VMs join the ASG and inherit the rules; no IP edits. Constraints:

- All NICs in an ASG must be in the ==@same virtual network== as the first NIC added.
- If a rule uses ASGs as both source and destination, both ASGs must be in the same VNet.
- A NIC can be in several ASGs (up to 20 per IP configuration). Up to 3,000 ASGs per subscription; up to 10 ASGs referenced per rule field.
- An ASG does nothing on its own. It is not a filter, not a subnet and changes no routing. Only NSG rules that name it have an effect.

**10. Flow logs.** Network Watcher flow logs record which flows were allowed or denied. ==!NSG flow logs are retiring==: no new NSG flow logs since 30 June 2025, full retirement 30 September 2027. Use **virtual network flow logs** instead. They log at VNet level, avoid duplicate records, and also record AVNM security admin rule decisions. Logs land in a storage account; Traffic Analytics can send them to Log Analytics for Sentinel.

**11. Platform traffic you might break.** DHCP, DNS and the instance metadata service use 168.63.129.16 and 169.254.169.254 and are not filtered unless you deny the tags `AzurePlatformDNS`, `AzurePlatformIMDS` or `AzurePlatformLKM`. ==!Do not attach an NSG to `GatewaySubnet`== (VPN/ExpressRoute gateways); it is unsupported.

## Where it lives

All in the **Azure portal** (not the Entra admin center).

- Create: `Azure portal > Network security groups > + Create`.
- Rules: `Network security groups > nsg-db > Settings > Inbound security rules` / `Outbound security rules`.
- Attach: `Network security groups > nsg-db > Settings > Subnets > Associate` or `Network interfaces > Associate`.
- ASG membership: `Virtual machines > vm-app1 > Networking > Application security groups > Add application security groups`.
- Check the result: `Network interfaces > vm-app1-nic > Help > Effective security rules` (detail in D2.3.9).
- Flow logs: `Network Watcher > Logs > Flow logs > + Create`, flow log type **Virtual network**.

```bash
az network nsg create -g rg-lab -n nsg-db
az network asg create -g rg-lab -n asg-app
az network nsg rule create -g rg-lab --nsg-name nsg-db -n deny-sql-all \
  --priority 120 --direction Inbound --access Deny --protocol Tcp \
  --destination-port-ranges 1433
az network nsg rule create -g rg-lab --nsg-name nsg-db -n allow-sql-app \
  --priority 110 --direction Inbound --access Allow --protocol Tcp \
  --source-asgs asg-app --destination-port-ranges 1433
az network vnet subnet update -g rg-lab --vnet-name vnet-lab -n snet-db \
  --network-security-group nsg-db
```

## Exam traps

- **"Subnets isolate workloads."** ==!False.== `AllowVNetInBound` allows the whole VNet, and `VirtualNetwork` includes peered VNets and on-premises ranges reached through a gateway. Isolation needs Deny rules.
- **Priority direction.** 100 beats 4096. A Deny at 200 loses to an Allow at 150 for the same traffic.
- **Subnet + NIC NSG.** Traffic must pass both. Inbound checks subnet first; outbound checks NIC first. A NIC-level Allow does not rescue traffic the subnet NSG denied.
- **No NSG at all.** Traffic inside the VNet flows. Internet traffic to a VM with a **Standard** public IP is blocked until an NSG allows it (Standard public IPs are secure by default).
- **ASG across VNets.** A question that puts web NICs in VNet1 and database NICs in VNet2 into one ASG rule is the distractor. ASGs are single-VNet.
- **ASG vs NSG.** ASGs never replace NSGs. "Associate the ASG with the subnet" is not a thing; ASGs are attached to NICs.
- **Service tags vs ASG.** Tags represent Microsoft services and broad ranges; ASGs represent *your* VMs. You cannot define a custom service tag.
- **"Removing the rule cuts the attacker's RDP session."** ==!No==; existing flows continue. Only new connections are blocked.
- **NSG vs Azure Firewall.** NSG is layer 3–4 (IP, port, protocol), free, distributed. FQDN filtering, threat intelligence and TLS inspection need Azure Firewall (D2.3.8).
- **NSG vs AVNM security admin rule.** Admin rules are evaluated *before* NSGs and a workload owner cannot override them (D2.3.2).
- **Flow logs.** Any answer that creates a new *NSG* flow log today is wrong; choose ==+virtual network flow logs==.
