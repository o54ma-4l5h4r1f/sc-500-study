## Azure first

- **Conditional Access (CA)** is Entra ID's if-then rule engine. It runs ==@when Entra issues or refreshes a token==: if these conditions match, enforce these controls (block, require MFA). You met it for users in D1.1.2.
- Every **access token** has a **subject** (who receives it) and an **audience** (the resource it's for). CA looks at both.
- **Microsoft Entra Agent ID** gives AI agents their own directory objects: an **agent identity** (the agent's own account, a special service principal), an **agent identity blueprint** (the template many agent identities are created from), and an optional **agent's user account** (a user-type account paired 1:1 with an agent identity, for a "digital worker" with a mailbox).
- **Custom security attributes** are your own key-value tags (for example `AgentApprovalStatus = HR_Approved`) that policies can filter on.
- **Licence:** `license_blocked`. Needs ==@Microsoft Agent 365 + Entra ID P1== (or Microsoft 365 E3), or ==@Microsoft 365 E7==. Agent-risk policies need P2 or E5 on top. No lab in an Azure-only tenant.

New to these? Read the Foundations pages listed in "Before you start".

## In one sentence

Conditional Access for agents lets you block agents from getting tokens — all of them, all but an approved list, or only risky ones — and you must aim the policy at whichever identity is actually the token's subject.

## Why it exists

By default, ==!every token request from an agent identity is allowed==. If an attacker steals one agent's credentials, they pivot through everything it can reach. User CA policies don't help, because an autonomous agent never shows up as a user.

Think of a building's badge desk. Staff badges (users) get checked for photo ID and a second factor. Delivery robots (agents) can't show a photo or type a PIN. So the desk keeps a separate list for robots: which robots may enter at all, and which are flagged as tampered with. That separate list is CA for agents.

## What actually matters

**1. Find the token subject first.** An agent can use more than one pattern, so you may need more than one policy.

| If the agent… | Pattern | Policy target |
|---|---|---|
| acts for a signed-in user (reads *your* mail) | ==@On-behalf-of== (delegated) | ==@users and groups== |
| acts as itself, no user (scheduled report, public web bot) | ==@Application-only== (client credentials) | ==@agent identity or agent identity blueprint== |
| acts through its own user account (mailbox, Teams) | ==@Agent-user access== | ==@agent's user account== (Agents > agent users) |

A policy on an agent identity ==!doesn't cover its agent user==, and vice versa. A policy assigned through **Users** (all users, groups, roles) ==!doesn't cover agent users==. You ==!can't scope agent users by group membership==.

**2. What a policy for agent identities can do.** Assignment: **Users, agents or workload identities** > *What does this policy apply to?* = **Agents** > **All agent identities**, selected agent identities or blueprints, or **Select agent identities based on attributes**. Condition: ==@Agent risk (Preview)== (high, medium, low from Entra ID Protection). Grant: ==@Block== only. No MFA, no compliant device, no session controls — nobody is there to answer a prompt.

**3. Three patterns to build.**

- **Allow only approved agents:** include **All agent identities**, exclude approved identities or blueprints (object picker), or exclude by attribute (`AgentApprovalStatus` *Contains* `HR_Approved`). Target **All resources**. Grant **Block**.
- **Block high-risk agents:** include All agent identities, condition **Agent risk = High**, grant **Block**. Agent risk comes from Entra ID Protection for agents and needs ==@Entra ID P2 or Microsoft 365 E5== on top of Agent 365. When an admin selects **Confirm compromise** in the **Risky agents** report, risk becomes High and this policy blocks the agent automatically.
- **Agent users on managed endpoints:** use the **Agent execution environments (Preview)** condition to require a compliant device or compliant network for agents running on Windows 365 Cloud PCs for Agents.

**4. Scale with blueprints and attributes.** A policy on a ==@blueprint== covers every agent identity created from it, ==+including future ones==, but ==!not their agent users==. Attribute-based policies apply to any agent that later gets the matching tag.

**5. Where CA doesn't reach.** Not when a **blueprint** gets a Graph token to *create* agent identities or agent users. Not on the intermediate exchange at `AAD Token Exchange Endpoint: Public`. Not when **security defaults** are on. Not for agents using ==!API keys== — no Entra token, no CA.

**6. Roll out safely.** Create in **Report-only**, check sign-in logs (filter **Agent type** / **Is Agent**), then set **On**. Review broad user policies ("All users must use MFA") so they don't break agent flows. A wrong block can stop a production agent instantly.

## Where it lives

**Microsoft Entra admin center** > Entra ID > Conditional Access > Policies > New policy. Role: ==@Conditional Access Administrator==. Agent risk report: Entra ID Protection > Risky agents (Security Administrator, Security Operator or Security Reader). Graph collections: `riskyAgents`, `agentRiskDetections`.

## Exam traps

- **OBO agent ignores your agent-targeted block** → the user is the subject; ==+target users/groups==.
- **"Require MFA for the autonomous agent."** ==!Impossible== — ==+Block== is the only grant.
- **Policy on "All users" protects agent user accounts.** ==!No== — target ==+agent users== under Agents.
- **One policy for all agents from a project** → target the ==+agent identity blueprint==.
- **Auto-block a compromised agent** → ==+Agent risk = High + Block==, then *Confirm compromise*.
- **CA can't stop agents creating new agents.** True — blueprints aren't subject to CA when creating identities. Use per-product creation controls (D3.1.6).
- **Least-privileged role** → ==@Conditional Access Administrator==.
- **Agent authenticates with an API key** → CA ==!doesn't apply==.

> **Contradictions — training units vs product docs (product wins).** (1) Unit 2 says policies on agent identities allow only **agent risk** and **Block**. Unit 3 says you can use **named locations**, **sign-in risk**, application filters, **Require compliant network** and **sign-in frequency**. The product docs back unit 2; location and device controls exist only for **agent users on managed endpoints**. (2) Unit 3 says CA for agents needs "Entra ID P1 or Microsoft 365 E3"; the CA docs require **Microsoft Agent 365 paired with P1/E3**, or **Microsoft 365 E7**, and P2/E5 for agent risk. (3) The unit path *Protection > Conditional Access* is the older menu; the product says *Entra ID > Conditional Access*. Preview status: **Agent risk** and **Agent execution environments** are labelled Preview. The Zero Trust assessment calls the whole feature "Conditional Access for Agent ID (Preview)", while the CA article carries no banner — treat it as preview.
