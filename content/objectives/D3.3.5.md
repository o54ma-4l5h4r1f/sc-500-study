## Azure first

- A **function app** is a container for small pieces of code (**functions**) that run when a **trigger** fires — an HTTP request, a queue message, a timer. It runs on App Service infrastructure, so it shares App Service's security features.
- The **hosting plan** decides what the platform gives you: **Flex Consumption** (serverless, Linux, network features), **Consumption** (legacy serverless), **Elastic Premium**, **Dedicated** (an App Service plan).
- **Inbound** traffic is callers reaching your function. **Outbound** traffic is your function calling databases, Key Vault and APIs. Different controls handle each direction.
- An **app setting** is an environment variable for the app. It is visible to anyone who can read the app's configuration.

See the Foundations pages listed above, especially *app-service-and-functions-basics* and *oauth-tokens-and-consent*.

## In one sentence

Lock down a function app by requiring Entra ID sign-in with built-in App Service Authentication (keys are only a secondary gate), giving it a managed identity instead of connection strings, restricting inbound with access restrictions or a private endpoint, routing outbound through VNet integration, and choosing a hosting plan that supports those network features.

## Why it exists

An HTTP-triggered function is a public URL. If its authorization level is `anonymous`, anyone who finds the URL can run your code. If it uses a function key, anyone who copies that key from a script or a log can run it — the key says "someone has the password", not "who is calling". Connection strings in app settings are another gift to whoever gets Reader on the app.

Anchor: a function key is a building entry code shared on a sticky note. Easy Auth with Entra is the badge reader that knows each person. Access restrictions are the gate in the car park. A private endpoint moves the entrance inside the company campus.

## What actually matters

**1. App Service Authentication ("Easy Auth").** Platform middleware that runs before your code. Configure under **Settings > Authentication > Add identity provider > Microsoft**.

- **Express** setup creates a new app registration; **Advanced** uses an existing one (client ID + issuer URL).
- **Unauthenticated requests:** ==+Require authentication== (401 or redirect; code never runs) vs **Allow unauthenticated** (your code decides).
- Turning it on forces HTTPS.
- By default ==!any user in the tenant can get a token== for the app. To restrict, set the enterprise app to **Assignment required** and assign groups, or check **allowed client applications / identities**.
- It authenticates; authorization inside the app is still your code's job.

**2. Function access keys and authorization levels.**

| Level | Needs | Key types |
|---|---|---|
| `anonymous` | nothing | — |
| `function` | a function key or a host key | **Function** (`default` + custom, one function), **Host** (`default` + custom, all functions) |
| `admin` | master key | **Master** `_master` — also opens the `/admin/*` runtime APIs |

Plus **system keys** for extensions (Event Grid, Durable Functions). Keys travel as `?code=` or the `x-functions-key` header. Default level is `function` in C#, Java, PowerShell and Python, but ==!`anonymous` in the Node.js v4 model==.

==!Keys aren't identity.== They are shared secrets with no user, no Conditional Access, no per-caller audit. Use them only as defence in depth behind Easy Auth or API Management. Keys are stored encrypted in Blob storage by default (`AzureWebJobsSecretStorageType` can move them to Key Vault). Deleting a function ==!doesn't rotate its keys== — rotate explicitly. Never hand out the master key.

**3. Managed identity for outbound.** Turn on **Identity > System assigned** (or attach a user-assigned identity). Grant data roles on targets: *Storage Blob Data Contributor*, *Key Vault Secrets User*, *Cosmos DB Built-in Data Contributor*, *Service Bus Data Sender/Receiver*, *Cognitive Services OpenAI User*. Use `DefaultAzureCredential` in code and **identity-based connections** for triggers and bindings.

**4. Key Vault references.** App setting value `@Microsoft.KeyVault(SecretUri=https://<vault>.vault.azure.net/secrets/<name>/)`. The app's identity needs **Key Vault Secrets User**. Without a version, the latest is used and refreshed within **24 hours** (or at restart/config change). A firewalled vault needs **VNet integration** for the app to reach it.

**5. Inbound network.**

- **Access restrictions**: priority-ordered allow/deny rules by IP/CIDR, **service tag** (for example `AzureEventGrid`, `AzureFrontDoor.Backend`) or VNet subnet. Once one allow rule exists, everything else is denied. Separate rules can protect the **SCM (Kudu) site**.
- **Private endpoint**: function gets a private IP; disable public network access. Needs private DNS.
- Access restrictions ==!don't apply to private endpoint traffic==.

**6. Outbound network: regional VNet integration.** The app sends outbound calls through a **delegated subnet** in a same-region VNet. It ==!doesn't give private inbound==. The subnet can't host other resources.

**7. Plan decides what's possible.**

| Plan | Access restrictions | Private endpoint (in) | VNet integration (out) |
|---|---|---|---|
| ==@Flex Consumption== | Yes | Yes | Yes |
| Consumption (legacy) | Yes | ==!No== | ==!No== |
| Elastic Premium | Yes | Yes | Yes |
| Dedicated (App Service plan) | Yes | Yes | Yes |

Linux Consumption ==@retires 30 September 2028==; migrate to Flex Consumption. CORS limits which **browser origins** may call; it's not server-side access control, and `*` should never be used in production.

## Where it lives

- **Azure portal > Function App > *app* > Settings > Authentication** (Easy Auth).
- **> Functions > App keys** (host, master, system keys); **> *function* > Function Keys**.
- **> Settings > Identity**; **> Settings > Environment variables** (Key Vault references).
- **> Settings > Networking** — Inbound: **Public network access**, **Access restriction**, **Private endpoints**; Outbound: **Virtual network integration**.
- **> API > CORS**.

```bash
az functionapp identity assign -g rg -n func-orders
az functionapp config access-restriction add -g rg -n func-orders --rule-name eventgrid \
  --action Allow --service-tag AzureEventGrid --priority 100
az functionapp vnet-integration add -g rg -n func-orders --vnet vnet --subnet func-out
az functionapp keys list -g rg -n func-orders
```

## Exam traps

- "Only users in our tenant may call the function, no code change" → ==+App Service Authentication, Require authentication==. A function key is the distractor.
- "Only users in group X" → also set **Assignment required** on the enterprise app.
- Node.js v4 function exposed with no protection → its default level is `anonymous`.
- "Function must reach a Key Vault with public access disabled" → VNet integration (outbound) + private endpoint on the vault. A private endpoint on the **function** is the wrong direction.
- "Private endpoint on a Consumption plan function" → ==!not supported==. Flex Consumption, Premium or Dedicated.
- "Accept webhooks only from Event Grid" → access restriction with the `AzureEventGrid` service tag.
- Partner shares the master key → it also controls `/admin`; issue a function key (or better, Entra) instead.
- CORS presented as a way to block a server-side caller → ==!it isn't==.
