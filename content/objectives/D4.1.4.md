## Azure first

- **AWS:** an *account* is AWS's unit of billing and isolation (roughly an Azure subscription). A *management account* sits above member accounts in **AWS Organizations**. Permissions are **IAM roles**. **CloudFormation** is AWS's template engine (its ARM/Bicep).
- **GCP:** a *project* is the unit (roughly a subscription); an *organization* sits above projects. Identities for software are **service accounts**. **Workload identity federation** lets an outside identity (here Microsoft Entra ID) act as a service account without a stored key.
- **Azure Arc** installs the **Azure Connected Machine agent** on a non-Azure server so it appears in Azure as a resource you can apply policy and Defender plans to.
- A Defender for Cloud **connector** (security connector) is itself an Azure resource, created in a subscription and resource group you choose.

See the Foundations pages listed above, especially *aws-and-gcp-for-azure-people* and *azure-arc-and-hybrid-machines*.

## In one sentence

A multicloud connector sets up keyless, federated trust from Defender for Cloud into an AWS account or GCP project so posture is read agentlessly through the cloud's APIs; on-premises and multicloud **machines** additionally need Azure Arc before workload protection can reach them.

## Why it exists

Your attackers don't care which cloud the weak server is in. As an analyst you pivoted between three consoles to follow one intruder. A connector puts AWS and GCP resources into the same inventory, recommendations, secure score, compliance dashboard and attack paths as Azure — one pane, one policy language.

Think of a security firm taking over two more buildings. First it gets read-only access to their floor plans (connector). Then it fits its own sensors on the doors that matter (Arc + plans).

## What actually matters

**1. No stored secrets — federated trust.** Defender for Cloud gets a token from Microsoft Entra ID and swaps it at the other cloud's Security Token Service for short-lived credentials. AWS checks it against the **IAM role** trust policy (default monitoring role `CspmMonitorAws`); GCP checks it against the **workload identity provider** and lets it impersonate a **service account**. ==!No access keys or service-account key files are created==.

**2. AWS vs GCP connector, side by side.**

| | AWS | GCP |
|---|---|---|
| Scope options | **Single account** or **Management account** | **Single project** or **Organization** |
| Organisation-wide mechanism | CloudFormation **StackSets** auto-create connectors for member accounts, including new ones | org-level bindings cover all current and future projects |
| Exclusions | account IDs | project numbers, folder IDs |
| Trust setup | **CloudFormation** template (or Terraform) you run in AWS | **gcloud** script, usually in Google Cloud Shell |
| Creates | OIDC identity provider + IAM roles | workload identity pool, **one provider per plan**, service accounts, policy bindings |
| Must-have on the other side | AWS Organizations trusted access for StackSets | 5 APIs: `iam`, `sts`, `cloudresourcemanager`, `iamcredentials`, `compute` (on the management project for org onboarding) |
| Scan interval | 4, 6, 12 or 24 h | 4, 6, 12 or 24 h |
| Arc auto-provisioning needs | **SSM Agent** + `AmazonSSMManagedInstanceCore` policy | **OS Config** agent |

Both offer **Default access** (permissions for today and future features) or **Least privilege access** (only what selected plans need). After adding a plan you must ==!update the CloudFormation stack or rerun the gcloud script==, or the connector shows *Has issues*. Some collectors ignore the interval (EC2 instances and GCP Compute instances refresh hourly). For AWS, only the **management account** works for organisation onboarding — ==!delegated administrator accounts aren't supported==.

**3. Who you need to be.** **Contributor** on the Azure subscription creates the connector. **Owner** on that subscription is needed for Arc **auto-provisioning** (and for full Defender CSPM, D4.1.1). On the other side you need admin rights in the AWS account, or owner-level access to the GCP project/organization. An AWS account already connected to Microsoft Sentinel needs special steps before it can join Defender for Cloud. The AWS connector isn't available in Azure Government or Azure operated by 21Vianet.

**4. Which plans need Arc on non-Azure resources.**

| Plan on a connector | Protects | Arc needed? |
|---|---|---|
| Foundational CSPM / Defender CSPM | all resources' configuration | ==+No== — API only |
| Defender for Servers | EC2, Compute Engine VMs | ==@Yes== (auto-provisioned) |
| Defender for SQL Servers on Machines | SQL Server on EC2, RDS Custom for SQL Server, GCP VMs | ==@Yes== (plus AMA) |
| Defender for open-source relational DBs | AWS RDS (Aurora, PostgreSQL, MySQL, MariaDB) | No |
| Defender for Databases (GCP) | Cloud SQL | No |
| Defender for Containers | EKS, GKE | ==@Yes== — Arc-enabled Kubernetes onboards the sensor |

> **Contradiction — product docs win.** Units 5 and 6 list Defender for Containers on EKS/GKE as "Azure Arc required: No". The multicloud dependencies article lists the **Azure Arc agent as required** for Defender for Containers, to connect EKS/GKE clusters and onboard the Defender sensor.

> **Contradiction — product docs win.** Units 2, 5 and 6 say "Defender CSPM is always on and can't be disabled" in a connector. Product docs: the **Foundational** CSPM (Security Posture Management) plan is always on; **Defender CSPM** is the optional paid plan.

**5. On-premises = Arc, done by you.** One server: Defender for Cloud > Environment settings > **Add environment > On-premises servers** (or Azure Arc > Machines > Add) generates a script to run as local admin. Many servers: a **service principal** with the **Azure Connected Machine Onboarding** role, pushed by Group Policy, Configuration Manager or Ansible. The agent needs outbound **443**. The Log Analytics agent (MMA) retired in **August 2024**; Arc is the path. The alternative, **direct onboarding** through Defender for Endpoint, skips Arc but gives only Plan 1 features plus premium MDVM (D3.2.5).

> **Contradiction — product docs win.** Unit 4 says Plan 2 on Arc-connected on-premises servers gives JIT access and agentless scanning. Product docs: **JIT** covers Azure and AWS only, and **agentless scanning** covers Azure VMs, EC2 and Compute Engine — ==!neither works on on-premises Arc servers== (D3.2.5, D3.2.7).

**6. Prove it works.** Environment settings shows each connector's **Connectivity status**: **Healthy**, **Has issues** or **Connecting**. Select it for the **Environment details** page, which lists problems and often a remediation script. Then check **Inventory** (filter by cloud), the recommendations for AWS/GCP, and the auto-assigned **AWS Foundational Security Best Practices** or **GCP Default** standard (D4.1.2). First posture results take a few hours (the unit says 4–6 hours). Arc resources for EC2/GCP VMs that no longer exist are removed after **7 days**. Plans set on a connector apply to that environment independently of the subscription's own plan settings.

## Where it lives

- **Azure portal** > Microsoft Defender for Cloud > **Environment settings** > **Add environment** > Amazon Web Services | Google Cloud Platform | On-premises servers. Tabs: Account details → Select plans (Settings per plan) → Configure access → Review and generate.
- **AWS console** > CloudFormation > Create stack (or update stack after plan changes); StackSets for management accounts.
- **GCP Cloud Shell**: paste and run the generated gcloud script.
- The Defender portal's plan management (preview) covers **Azure commercial only** — ==!AWS and GCP connectors are still created and managed in the Azure portal==.

## Exam traps

- "Onboard all 60 AWS accounts, including future ones" → connector on the ==+management account== (StackSets). Not 60 single-account connectors.
- "Onboard every GCP project under the company" → **Organization** scope.
- "EC2 instances show in inventory but have no Defender for Servers protection" → **SSM Agent** missing (or Arc auto-provisioning failed / no Owner).
- "Added Defender for Containers to an existing AWS connector; connector now Has issues" → **update the CloudFormation stack**.
- "Avoid storing AWS access keys in Azure" → nothing to do; the connector is keyless by design.
- "Least privilege access chosen, AI posture added later" → regenerate and redeploy the template/script.
- "On-premises server, no internet except 443" → fine for Arc; configure a proxy or Arc private link scope if needed.
- ==!"On-premises servers can use a connector."== There is no on-premises connector; it's Arc (or MDE direct onboarding).

## Skip

- **Skip:** the fixed-interval collector lists (IAM policy versions every 12 h, the GCP collector names). Know "some collectors run hourly regardless".
- **Skip:** the S3 bucket policy JSON for staged CloudFormation templates. It just stops your own bucket raising an SSL recommendation.
- **Skip:** CIEM role prerequisites on connectors (Security Admin plus `Application.ReadWrite.All`, or Application Administrator). CIEM is a Defender CSPM component, not a connector decision.
- **Skip:** unit 4's Arc endpoint list and TLS-inspection note. Arc networking is D3.2.4.
- **Skip:** the CloudFormation error-resolution table and the 30-day EC2 IAM-profile automation scan.
- **Skip:** the "10,000 resources per portal view" performance advice.
