## Azure first

- A **virtual network (VNet)** is your private network in Azure, split into **subnets**. Resources in it get private IPs such as `10.1.0.5`.
- Key Vault is a **PaaS** service: by default it answers on a public address at `https://{name}.vault.azure.net`.
- A **service endpoint** tags traffic from one subnet so a PaaS firewall can recognise it. The service keeps its public address.
- A **private endpoint** is a network card in your subnet that carries a private IP for one specific vault. A **private DNS zone** (`privatelink.vaultcore.azure.net`) makes the vault's name resolve to that private IP inside the VNet.

See *virtual-networks-and-subnets* and *private-dns-and-name-resolution* in Foundations.

## In one sentence

The Key Vault firewall decides **which networks may reach the vault's data plane** — all public networks, only listed public IPs and VNet subnets, or nothing public at all (private endpoints only) — with an optional bypass for trusted Microsoft services.

## Why it exists

RBAC decides *who* may open the vault. The firewall decides *from where* a request may even arrive. With the defaults, any internet address can knock: an attacker who phished a token can use it from anywhere. A mailroom that only accepts post from listed senders turns a stolen token into a useless one unless the attacker is also inside your network.

## What actually matters

- **The firewall guards the data plane only.** Control-plane calls through `management.azure.com` — creating the vault, changing network rules, setting access policies, even deploying secrets through an ARM template — ==!ignore the firewall==. Lock those down with RBAC.
- **Firewall enabled with no rules blocks everything** (`--default-action Deny`). You then add exceptions:
  - **IP rules:** public IPv4 addresses or CIDR ranges, up to **1,000**. ==!No private RFC 1918 ranges== (`10.x`, `172.16–31.x`, `192.168.x`) and ==!no IPv6==. Good for build agents or an on-premises egress IP that never changes.
  - **Virtual network rules:** up to **200**. Each needs the `Microsoft.KeyVault` **service endpoint** on the subnet (the portal offers to enable it; it can take up to 15 minutes). Traffic stays on the Azure backbone, but the vault's DNS name still resolves to a public IP.
- **Private endpoint + public access disabled = full isolation.** Create a private endpoint (target sub-resource `vault`) in a subnet. The endpoint must be in the same region as its VNet; the vault can be elsewhere. Link the **`privatelink.vaultcore.azure.net`** private DNS zone to every VNet that calls the vault — without it, clients resolve the public IP and fail. A private-endpoint connection made by someone without rights on the vault sits **Pending** until the vault owner approves it. Configure the endpoint ==!before== selecting **Disable public access**, or you lock yourself out.
- **Public DNS still answers.** With public access disabled, `nslookup` from the internet still returns a public Key Vault front-end IP. That front end refuses every request. DNS visibility is by design and is not a control.
- **Trusted Microsoft services bypass** (`--bypass AzureServices`). Lets a fixed list of services where Microsoft controls all the code reach the vault through the firewall — for example Azure Backup, Azure Disk Encryption, Azure Storage and Azure SQL (CMK), App Service certificate deployment, Application Gateway, Azure Resource Manager template deployment. ==!Azure DevOps is not on the list.== The bypass ==+keeps working when public access is disabled==. Those services still need an RBAC role or access policy — the bypass opens the network, not the door.
- **Network security perimeter (NSP)** is a logical boundary around several PaaS resources (Key Vault, Storage, SQL). In **Transition** mode it only logs what would be denied. In **Enforced** mode its rules override `publicNetworkAccess`. Setting public network access to **Secure by perimeter** ==!blocks even trusted services== unless a perimeter rule admits them. Private-endpoint traffic is never subject to NSP rules.
- **The portal is a data-plane client too.** If your own laptop IP is not allowed, you can open the vault blade but cannot list secrets. That is the firewall working, not an RBAC problem.

## Where it lives

**Azure portal > Key vaults > *vault* > Settings > Networking.**

- **Firewalls and virtual networks** tab → **Allow access from**: *Allow public access from all networks* / *Allow public access from specific virtual networks and IP addresses* / *Disable public access*. Below: **+ Add a virtual network**, the **Firewall** IP list, and **Exception: Allow trusted Microsoft services to bypass this firewall**.
- **Private endpoint connections** tab → **+ Create**, **Approve**, **Reject**.

```bash
az network vnet subnet update -g rg-net --vnet-name vnet-app -n snet-app --service-endpoints Microsoft.KeyVault
az keyvault network-rule add -g rg-kv -n kv-payroll-prod-01 --subnet <subnet-id>
az keyvault network-rule add -g rg-kv -n kv-payroll-prod-01 --ip-address 203.0.113.0/24
az keyvault update -g rg-kv -n kv-payroll-prod-01 --default-action Deny --bypass AzureServices
az keyvault update -g rg-kv -n kv-payroll-prod-01 --public-network-access Disabled
```

## Exam traps

- "Allow `10.0.1.0/24` in the Key Vault IP firewall" → ==!rejected==. Private ranges are not allowed; use a **VNet rule** or a **private endpoint**.
- "Remove all public exposure, VNet clients only" → ==+private endpoint + Disable public access== (+ private DNS zone). Service endpoints leave the public endpoint in place.
- "After adding a private endpoint, the VM still resolves a public IP" → the ==+private DNS zone is missing or not linked== to the VNet.
- "Azure Backup fails after public access was disabled" → enable ==+Allow trusted Microsoft services==. "Azure DevOps pipeline fails" → the bypass ==!won't help==; use a private endpoint or a self-hosted agent with an allowed IP.
- "Firewall stops an ARM deployment that writes a secret" → ==!it doesn't==; ARM goes through the control plane.
- "Trusted services blocked even though bypass is on" → the vault is in an NSP with ==!Secure by perimeter==.
- The firewall is ==!not a substitute for RBAC== — a trusted service or an allowed subnet still needs a data-plane role.
