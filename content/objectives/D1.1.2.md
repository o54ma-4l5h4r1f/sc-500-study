## Azure first

- **Microsoft Entra ID** is the sign-in service for Azure and Microsoft 365. When anyone — a person, an app, an agent — wants to reach a resource, Entra ID checks who they are and then hands out an **access token** (a signed pass the resource trusts).
- **Conditional Access** sits at the moment Entra ID is about to issue that token. It can add a requirement, or refuse.
- **Microsoft Entra ID P1** is the licence that unlocks Conditional Access. Risk-based conditions need **P2**. Your Azure-only lab has neither, so this is a portal-tour page.
- **Coverage note:** Microsoft's training course has **no unit** for this bullet. This page is written entirely from the product documentation.

New to these? Read the Foundations pages listed in "Before you start".

## In one sentence

A Conditional Access policy is an **if-then rule** checked at sign-in: *if* this identity reaches this resource under these conditions, *then* block it or make it satisfy something first (MFA, a compliant device, a stronger method).

## Why it exists

Passwords travel. A stolen password works from any country, any laptop, at 3 a.m. As an analyst you triaged those sign-ins *after* they happened. Conditional Access stops them *before* the token is issued.

Think of the guard desk in an office building. The guard doesn't just check your badge. They check *which floor* you're going to, *what time it is*, and *whether you're carrying a company laptop*. Lobby: badge is enough. Server floor: badge plus fingerprint. Out of hours from a foreign site: no entry. Same badge, different rules by context.

Important limit: Conditional Access runs ==!after first-factor authentication==. It is not a defence against password spraying or denial of service.

## What actually matters

**1. How evaluation works.**

- There is ==@no priority order== between policies. Every policy that matches applies. All their requirements must be met. One block = blocked.
- Inside one policy, all configured assignments must match (AND).
- Grant controls default to **Require all the selected controls**. You can switch to **Require one of the selected controls**.
- Two phases: phase 1 collects session details (location, device) for enabled *and* report-only policies; phase 2 enforces enabled policies. Block stops at once; otherwise the user is prompted in a fixed order — MFA, compliant device, hybrid joined device, approved client app, app protection policy, password change, terms of use, custom controls — and then session controls apply.
- Policies that target roles or groups are evaluated when a **token is issued**. A user added to a group keeps their old token until it refreshes. That's why PIM can trigger evaluation at activation (D1.1.1).

**2. Assignments — the "if".**

| Part | Options worth knowing |
|---|---|
| Users | All users, groups, directory roles, guests/external users. Include *and* exclude. Directory-role targeting covers ==!built-in roles only== — not custom roles or administrative-unit-scoped assignments. |
| Workload identities | Single-tenant service principals. Needs ==@Workload Identities Premium==. |
| Agents (preview) | Agent identities and agent users. Needs ==@Microsoft Agent 365== paired with at least Entra ID P1 or Microsoft 365 E3, or **Microsoft 365 E7** (includes Agent 365 + Entra Suite). Agent **risk** conditions also need P2 / E5. Policies for "All users" ==!don't include agent user accounts==. |
| Target resources | Cloud apps (resources), **user actions** (*Register security information*, *Register or join devices*), **authentication context** (a label an app or PIM can ask for, such as "sensitive action"). |
| Network | **Named locations**: IP ranges or countries/regions. Mark some as **trusted**. |
| Conditions | Sign-in risk and user risk (need ID Protection = P2), device platforms, client apps, filter for devices. |

Device platform comes from the user-agent string, which ==!can be faked==. Don't use it as a security boundary on its own. New policies apply to ==@all client app types== even if you never touch the client apps condition — so legacy-authentication clients are in scope.

**3. Access controls — the "then".**

- **Block** — most restrictive.
- **Grant** with: require MFA; require **authentication strength** (pick the *kind* of MFA, such as phishing-resistant — D1.1.3); require device marked compliant (Intune); require Microsoft Entra hybrid joined device; require approved client app; require app protection policy; require password change; require terms of use.
- You ==!can't combine== *Require multifactor authentication* and *Require authentication strength* in one policy. The built-in "Multifactor authentication" strength already equals require MFA.
- **Session controls**: app enforced restrictions (Exchange Online and SharePoint Online only); Conditional Access App Control (Defender for Cloud Apps — block download, monitor sessions); **sign-in frequency** (how often to re-prompt; *Every time* forces fresh auth); persistent browser session; customise continuous access evaluation; disable resilience defaults.

**4. Roll out safely.**

- Every policy has a state: **Report-only**, **On** or **Off**. Report-only evaluates and logs but ==!never prompts or blocks==. It can't test policies scoped to **User actions**.
- Results show in sign-in logs (**Conditional Access** and **Report-only** tabs), in **Policy impact**, and in the **Conditional Access Insights and Reporting workbook** (needs a Log Analytics workspace receiving sign-in logs).
- **What If** simulates one sign-in for a user, agent identity or single-tenant service principal. It includes enabled and report-only policies. You must supply identity, target resource, device platform and client app. It ==!ignores service dependencies== (testing Teams doesn't consider an Exchange Online policy).
- **Exclude emergency access accounts** (a dedicated group) from every policy that blocks or restricts. Report-only policies don't need the exclusion. Test the accounts quarterly.

**5. Workload identities and agents can't do MFA.** Conditional Access for workload identities can only **Block** — based on location (outside allowed IP ranges) or **service principal risk**. It covers single-tenant service principals registered in your tenant. ==!Managed identities aren't covered== — put them in an access review instead. ==!Multitenant and Microsoft SaaS apps aren't covered.== Adding a service principal to a group does ==!not== make a group-targeted policy apply; assign it directly. Agent policies follow the same idea: block all agents except approved ones, or block **high agent risk** (preview). Policies apply when an agent requests a token with *its own* identity, not when it acts on behalf of a user.

**6. Licensing and alternatives.** Conditional Access needs ==@Entra ID P1== (Microsoft 365 Business Premium also includes it). Risk conditions need ==@P2==. Without P1, **security defaults** give baseline MFA for everyone — free, but no exclusions or conditions. If P1 expires, policies ==!stay in force==: you can view and delete them but not edit them.

## Where it lives

**Microsoft Entra admin center** (`entra.microsoft.com`) `> Entra ID > Conditional Access`.

| Task | Path / role |
|---|---|
| Create a policy | `Conditional Access > Policies > New policy` — at least ==@Conditional Access Administrator== (Security Administrator can too) |

| Named locations | `Conditional Access > Named locations` |
| Authentication contexts | `Conditional Access > Authentication contexts` |
| Simulate | `Conditional Access > Policies > What If` |
| View only | **Security Reader** can open Conditional Access |
| Service principal results | `Entra ID > Monitoring & health > Sign-in logs > Service principal sign-ins > Conditional Access` tab |

A classic engineer policy — MFA for anyone using the Azure portal, Azure CLI or Azure PowerShell:

```text
Users:            Include All users; Exclude EmergencyAccess group
Target resources: Windows Azure Service Management API
Grant:            Require multifactor authentication
Enable policy:    Report-only  ->  On after checking impact
```

In Microsoft Graph a policy is a `conditionalAccessPolicy`. Its `state` is `enabled`, `disabled` or `enabledForReportingButNotEnforced` (report-only).

## Exam traps

- **"Order the policies so the allow policy wins."** ==!There is no order.== All matching policies apply; block wins.
- **"Report-only will prompt a few users for MFA to test."** ==!No==, it never prompts or blocks. (It can show certificate prompts on macOS/iOS/Android for compliant-device checks — exclude those platforms.)
- **MFA for Azure management** = target resource ==+Windows Azure Service Management API== — not "Azure portal" as a separate app.
- **Protect MFA registration** = target the user action ==+Register security information== and require a trusted location or a Temporary Access Pass.
- **Block a service principal from outside your IP range** = ==+Conditional Access for workload identities== (Workload Identities Premium). User-targeted policies ==!don't touch service principals==.
- **Block a managed identity with Conditional Access** — ==!not possible==. Use RBAC scope and access reviews.
- **Require MFA + require authentication strength in one policy** — ==!not allowed==.
- **Phishing-resistant MFA for admins** = grant control ==+Require authentication strength: Phishing-resistant MFA==.
- **Risky sign-in policies** need ==!P2== (ID Protection); everything else needs P1.
- **Lockout** — always exclude break-glass accounts and start in report-only. Users with a valid token added to a group aren't caught until token refresh.
- **Security defaults and Conditional Access** are alternatives. Security defaults are for tenants with ==!no== Conditional Access policies; once you need exclusions or conditions, move to Conditional Access.

## Skip

- **Skip:** the long list of Microsoft template policies one by one. Know the common ones by name (MFA for admins, MFA for Azure management, block legacy authentication, protect security info registration, block risky sign-ins).
- **Skip:** the What If API vs legacy What If comparison table. Know What If exists and what it needs.
- **Skip:** the **Conditional Access Optimization Agent** detail. It's a Security Copilot agent (needs P1 plus SCUs) that suggests policies in report-only. One line is enough.
- **Skip:** Global Secure Access "compliant network" and custom controls. Outside this bullet.
- **Skip:** continuous access evaluation internals and token protection. Know CAE exists as a session-control option.
- **Skip:** the Graph JSON for workload-identity policies. Know the `state` values.
- **Skip:** agent identity blueprints in depth — targeting a blueprint covers all agents derived from it, and that's all you need here.
- **Skip:** emergency-access alert setup in Azure Monitor (action groups, alert logic). Know you should alert on any break-glass sign-in.
