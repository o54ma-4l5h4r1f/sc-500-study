## Azure first

- **OAuth 2.0** is the standard that lets an app get an **access token** to call an API (Microsoft Graph, your own API) without ever seeing the user's password.
- A **permission** is one thing the app asks to do, written like `Mail.Read` or `User.Read.All`. The API (the *resource*) defines its permissions.
- **Consent** is someone saying "yes, this app may have these permissions". The record of that "yes" is a **permission grant**, stored on the app's **service principal** (enterprise app) in your tenant — see D1.1.4.
- **Coverage note:** the only training unit mapped here is from a Microsoft 365 *developer* module. This page takes its one relevant idea and builds the rest from product documentation.

New to these? Read the Foundations pages listed in "Before you start".

## In one sentence

Consent settings decide *who* may approve an app's permission requests (any user, users within limits, or only admins), and permission grants are the resulting approvals you review and revoke on each enterprise app.

## Why it exists

In SOC work you may have handled an **illicit consent grant** (consent phishing): a user clicks "Accept" on a malicious app asking for `Mail.Read`, and the attacker reads mail with a token — no password, no MFA, nothing to reset. Consent settings are the control that stops that.

Think of a building where staff can sign in their own visitors. You probably let staff sign in a courier to their own desk. You do *not* let them hand a visitor a master key to every office. Delegated permissions are "visitor at my desk". Application permissions are the master key. Admin consent is security signing off the master key.

## What actually matters

**1. Two permission types.**

| | ==@Delegated permissions== | ==@Application permissions== |
|---|---|---|
| Also called | Scopes, OAuth2 permission scopes | App roles, app-only permissions |
| Access | On behalf of a signed-in user | No user (daemons, automation, backup) |
| Who can consent | Users for their own data (if policy allows); admins for everyone | ==!Admins only== |
| Requested how | Static list, or dynamically at sign-in | Static list on the app registration only |
| Graph record | `OAuth2PermissionGrant` | `appRoleAssignment` |

Delegated access can never exceed what the user can do. Application access isn't limited by any user.

**2. User consent settings — the tenant dial.** `Enterprise apps > Consent and permissions > User consent settings`. Options:

| Setting | Policy ID | Meaning |
|---|---|---|
| Do not allow user consent | — | Users can't consent to anything new. Admins must. |
| Allow user consent for apps from verified publishers, for selected permissions | `microsoft-user-default-low` | Only apps from a **verified publisher** or registered in your tenant, and only permissions you classified **low impact**. |
| ==+Let Microsoft manage your consent settings== | `microsoft-user-default-recommended` | Default for new tenants. Users can consent to user-consentable delegated permissions **except** a Microsoft-maintained list of sensitive ones (`Mail.Read`, `Files.Read.All`, `Sites.Read.All`, `Calendars.Read`, `Chat.Read` and more). |
| Allow user consent for apps | `microsoft-user-default-legacy` | ==!Any app, any permission not needing admin consent.== |

**Permission classifications** let you mark delegated permissions as low impact for the "selected permissions" option. Application permissions ==!can't be classified low==. A custom **app consent policy** (Graph/PowerShell) can define your own conditions.

Changing the setting affects ==!only future consent==. Existing grants stay until you revoke them.

**3. Admin consent workflow — the request button.** With user consent restricted, users hit a wall. The workflow lets them **request** approval from the consent screen. Settings: who can review (users, groups or roles), email notifications, expiry reminders, and **Consent request expires after (days)**. Turning it on needs a **Global Administrator** and can take up to an hour. Being a reviewer ==!grants no extra rights== — the reviewer must already hold a role that can grant that consent.

**4. Granting tenant-wide admin consent.** From `Enterprise apps > {app} > Security > Permissions > Grant admin consent`, or `App registrations > {app} > API permissions > Grant admin consent` for your own apps. Roles:

| Role | Can grant |
|---|---|
| ==@Privileged Role Administrator== | Any permission, any API |
| Cloud Application Administrator, Application Administrator, AI Administrator | Any permission ==!except Microsoft Graph application permissions== |
| Custom role with grant-permission rights | What the role allows |

After admin consent, every user can use the app unless you set **Assignment required = Yes** (D1.1.4). An app that requires assignment can ==!only get admin consent==, never user consent. Granting admin consent again may revoke earlier tenant-wide grants for that app; users' own grants are untouched.

**5. Review and revoke.** `Enterprise apps > {app} > Permissions` has two tabs: **Admin consent** (tenant-wide) and **User consent** (per user). You can revoke admin-consented permissions in the portal. User-consented ones ==!can't be revoked in the portal== — use Microsoft Graph or PowerShell (delete the `oAuth2PermissionGrant` or `appRoleAssignment`). Revoking ==!doesn't stop re-consent==: also restrict consent or fix the app's requests. Role: Cloud Application Administrator or Application Administrator.

**6. Agents and plugins (the training unit).** A Microsoft 365 Copilot declarative agent calling an OAuth-protected API uses the **authorization code flow** on behalf of the user. The app's client ID and secret plus the identity provider's endpoints are stored in a Microsoft 365 **vault** entry; the plugin only references the entry's ID. Microsoft recommends **PKCE** (Proof Key for Code Exchange) even for confidential clients. In production an *administrator* registers the OAuth client and hands developers the vault ID. For you, the engineer: the agent still runs on delegated permissions, so the user's consent rules above still decide what it can reach.

## Where it lives

**Microsoft Entra admin center** (`entra.microsoft.com`).

| Task | Path | Role |
|---|---|---|
| User consent setting | `Entra ID > Enterprise apps > Consent and permissions > User consent settings` | Global Administrator in the portal; Privileged Role Administrator via Graph/PowerShell |
| Classify low-impact permissions | `… > Consent and permissions > Permission classifications` | Cloud Application Administrator |
| Admin consent workflow | `… > Consent and permissions > Admin consent settings` | Global Administrator |
| Review pending requests | `Enterprise apps > Admin consent requests` (**My Pending** tab) | designated reviewer |
| Grant admin consent | `Enterprise apps > {app} > Permissions > Grant admin consent` | see table above |
| Review / revoke grants | `Enterprise apps > {app} > Permissions` (Admin consent / User consent tabs) | Cloud Application Administrator |

# Who has been granted what on one app (delegated grants)
Get-MgOauth2PermissionGrant -Filter "clientId eq '<servicePrincipalObjectId>'"

## Exam traps

- **"Users can consent to an app with application permissions if user consent is allowed."** ==!Never.== Application permissions always need admin consent.
- **Stop consent phishing but don't break low-risk apps** — ==+verified publishers + selected (low-impact) permissions==, plus the ==+admin consent workflow==.
- **Least-privileged role to consent to Microsoft Graph application permissions** — ==+Privileged Role Administrator==. Cloud Application Administrator ==!can't==.
- **Revoke one user's consent in the portal** — ==!not possible==; use Graph/PowerShell.
- **Made consent stricter yesterday — malicious app still works** — settings don't touch existing grants; ==+revoke== them and consider disabling the app's sign-in.
- **Reviewer added to the workflow can't approve** — reviewers need a role that can grant that consent.
- **Assignment required = Yes** forces admin consent.
- **Delegated `Files.Read.All` ≠ application `Files.Read.All`.** Read the permission *type*, not just its name.
- **"Users can consent to apps accessing company data on their behalf" = No but a developer must consent for their own app** — ==+Application Developer== role.

> **Two Microsoft pages differ on Graph application permissions.** The admin consent workflow page says only **Global Administrators** can approve *requests* for Microsoft Graph app roles. The grant-admin-consent page says a **Privileged Role Administrator** can grant consent for *any* permission. Read them as: approving through the workflow queue needs Global Administrator; granting directly needs at least Privileged Role Administrator. If a question asks for the least-privileged role to grant Graph application permissions, answer Privileged Role Administrator.
