## Azure first

- **Azure RBAC** controls Azure *resources* (VMs, storage, subscriptions). **Microsoft Entra roles** control the *directory* (users, groups, app registrations, Conditional Access). Two separate permission systems.
- Azure permissions look like `Microsoft.Compute/virtualMachines/restart/action` — provider / resource type / operation. Entra permissions look like `microsoft.directory/users/password/update`.
- An **administrative unit** is a container inside Entra ID (like "Paris office users") used to scope admin rights.
- **Microsoft Entra ID P1** is a paid licence tier; several Entra features, including custom roles, need it.

See the Foundations pages listed above, especially *azure-rbac-and-entra-roles*.

## In one sentence

A custom role is your own permission list when no built-in role fits: in **Azure** it is a JSON definition of `Actions`/`NotActions`/`DataActions`/`NotDataActions` assignable at the scopes in `AssignableScopes`; in **Microsoft Entra ID** it is a set of `microsoft.directory/...` permissions assignable tenant-wide, to an administrative unit, or to one directory object — and it needs **Entra ID P1**.

## Why it exists

Built-in roles are cut for common jobs. Your DevOps team needs to *restart* VMs and *read* one vault's secrets, nothing else. **Virtual Machine Contributor** lets them delete VMs; **Reader** lets them restart nothing. A custom role is the tailor-made key that opens exactly those doors.

==!Neither system grants anything in the other.== An Azure custom role cannot reset a password; an Entra custom role cannot restart a VM.

## What actually matters

**1. Azure custom role JSON.**

```json
{
  "Name": "Contoso VM Operator",
  "IsCustom": true,
  "Description": "Restart VMs and read one vault's secrets. No create or delete.",
  "Actions": [
    "Microsoft.Compute/virtualMachines/read",
    "Microsoft.Compute/virtualMachines/restart/action",
    "Microsoft.Insights/diagnosticSettings/read"
  ],
  "NotActions": [],
  "DataActions": [ "Microsoft.KeyVault/vaults/secrets/getSecret/action" ],
  "NotDataActions": [],
  "AssignableScopes": [ "/subscriptions/00000000-0000-0000-0000-000000000000" ]
}
```

| Property | Meaning |
|---|---|
| `Actions` | control-plane operations allowed (manage the resource) |
| `NotActions` | subtracted from `Actions`, usually to trim a wildcard |
| `DataActions` | data-plane operations allowed (read a blob, get a secret value) |
| `NotDataActions` | subtracted from `DataActions` |
| `AssignableScopes` | where the role may be **assigned** — management group, subscriptions, resource groups |

- ==!`NotActions` is not a deny.== It only removes operations from *this* role. Another role assignment can still grant the same operation. True denies come from **deny assignments** (or an Azure Policy deny on configuration).
- Wildcards: only **one** `*` per action string (`Microsoft.Compute/*`).
- `AssignableScopes` rules: ==!no root `/`, no wildcards, at most one management group==. A role with `DataActions` ==!cannot be assigned at management-group scope== (it can list one MG and be assigned on subscriptions beneath it).
- Limits: **5,000** Azure custom roles per tenant; **2,000** assignable scopes per role. Custom roles are shared by all subscriptions that trust the same tenant.
- Creating, updating or deleting needs `Microsoft.Authorization/roleDefinitions/write`/`delete` at every assignable scope — ==+Owner== or ==+User Access Administrator==.
- **Maintenance:** when a provider adds new operations, your custom role does ==!not== get them. Wildcards pick them up, which can be worse.

> **Contradiction:** the training unit adds "up to 2,000 role assignments per subscription for each custom role". Product limits list **2,000 assignable scopes** per custom role and **5,000 role assignments** per subscription; there is no per-custom-role assignment limit. Product docs win.

**2. Do you even need one?** Try a built-in role at a narrower scope first. "VM Contributor, but only for dev resource groups" is a scope problem, not a custom-role problem. Build custom roles for stable, well-understood permission sets. **Clone** a built-in role and remove permissions — faster and keeps the read permissions the main operation needs.

**3. Microsoft Entra custom roles.**

- **Licence:** ==@Microsoft Entra ID P1== for every user with a custom role assignment. Built-in Entra roles are free.
- **Who creates:** at least ==@Privileged Role Administrator==.
- **Where:** Microsoft Entra admin center > **Entra ID > Roles & admins > New custom role** > Basics > Permissions > Review + create.
- **Permissions** come from a fixed catalogue (`microsoft.directory/users/password/update`, `microsoft.directory/groups/members/update`, `microsoft.directory/applications/credentials/update`). Not every directory operation is available for custom roles.
- **Clone:** you can start from another *custom* role; ==!you cannot clone a built-in Entra role==.
- **Scope at assignment:** **tenant** (organization-wide), **administrative unit** (if the role has user, group or device permissions), or a **single Entra resource** — an app registration, an enterprise application, a group. Example: credentials-only rights on *one* app registration.
- **Limits:** **100** custom roles per organization; **150** custom role assignments per principal.

> **Contradiction:** the training unit says Entra custom roles scope only "tenant-wide or a specific application registration" and "can't be scoped to groups or users". Product docs list tenant, **administrative unit**, and single resources including **groups**, enterprise apps and app registrations. Product docs win.

**4. Side by side.** Azure: scopes MG/sub/RG/resource; 5,000; Azure portal IAM, CLI, PowerShell, Bicep/ARM, REST. Entra: tenant/AU/object; 100; Entra admin center, Microsoft Graph, Graph PowerShell. Both support custom roles; only Entra charges a licence for them.

## Where it lives

- **Azure:** Azure portal > *subscription or management group* > **Access control (IAM)** > **+ Add > Add custom role** (Basics: start from scratch / clone a role / start from JSON > Permissions > Assignable scopes > JSON > Review + create). Edit later from the **Roles** tab, type CustomRole.
- **Entra:** Microsoft Entra admin center > **Entra ID > Roles & admins > New custom role**. Assign from the role, or from an app registration's **Roles and administrators** blade for object scope.

![Add custom role menu](https://learn.microsoft.com/en-us/azure/role-based-access-control/media/custom-roles-portal/add-custom-role-menu.png){Access control (IAM) > + Add > Add custom role}

![Entra roles and admins page](https://learn.microsoft.com/en-us/entra/media/common/entra-roles-admins.png){Entra admin center > Roles & admins > New custom role}

```bash
az role definition create --role-definition @vm-operator.json
az role definition update --role-definition @vm-operator.json
az role definition list --custom-role-only true --output table
az role assignment create --assignee <group-object-id> --role "Contoso VM Operator" \
  --scope /subscriptions/<sub>/resourceGroups/rg-app
```

```powershell
# Azure: clone a built-in role as a starting point
$role = Get-AzRoleDefinition "Virtual Machine Contributor"
$role.Id = $null; $role.IsCustom = $true; $role.Name = "Contoso VM Operator"
$role.Actions.Clear(); $role.Actions.Add("Microsoft.Compute/virtualMachines/restart/action")
$role.AssignableScopes.Clear(); $role.AssignableScopes.Add("/subscriptions/<sub>")
New-AzRoleDefinition -Role $role

# Entra: custom role via Microsoft Graph PowerShell
New-MgRoleManagementDirectoryRoleDefinition -DisplayName "App Credential Admin" -IsEnabled:$true `
  -RolePermissions @(@{AllowedResourceActions = @("microsoft.directory/applications/credentials/update")})
```

## Exam traps

- "Reset passwords and manage group membership only" → **Entra** custom role (P1), not Azure.
- "Restart VMs, nothing else" → **Azure** custom role with `.../restart/action` (+ `read`).
- "Role must be usable in all 30 subscriptions" → one custom role; put a management group (one only) or the subscriptions in `AssignableScopes`.
- "Assign a custom role with DataActions at the management group" → not allowed; assign at the subscriptions.
- "User still deletes VMs although the custom role has `delete` in NotActions" → another assignment grants it; NotActions is not a deny.
- "Manage credentials of one app registration only" → Entra custom role scoped to that **app registration**.
- "Who can create an Entra custom role?" → Privileged Role Administrator (or Global Administrator). "Azure custom role?" → Owner / User Access Administrator.
- "Clone the Helpdesk Administrator built-in role in Entra" → not possible.
