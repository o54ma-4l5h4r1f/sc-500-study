## Azure first

- **Azure Application Gateway** is a regional layer-7 (HTTP) load balancer that lives in its own subnet in your VNet. A **listener** is one hostname/port it answers on; **path-based rules** route URLs to back ends.
- **Azure Front Door** is Microsoft's global edge: requests are accepted at points of presence worldwide and sent to your origins. Tiers: **Standard** and **Premium** (plus **classic**, legacy).
- A **WAF (web application firewall)** reads HTTP requests — URL, headers, cookies, body — and blocks attack patterns (SQL injection, XSS). An NSG or Azure Firewall works on IPs and ports and can't see these.
- A **WAF policy** is a separate Azure resource holding mode, rule sets, custom rules and exclusions. You **associate** it with a gateway, listener, path or Front Door endpoint.

See the Foundations pages listed above, especially *virtual-networks-and-subnets*.

## In one sentence

Azure WAF is a policy you attach to Application Gateway (regional) or Front Door (global) that runs Microsoft-managed rule sets (DRS) plus your own custom rules — evaluated first, including rate limits and geo/IP filters — in Detection or Prevention mode, with narrow exclusions for false positives and optional bot protection, scoped globally, per site or per URI.

## Why it exists

Your penetration test found SQL injection in the checkout page. Fixing the code takes a sprint; the WAF blocks the pattern today. It's the doorman who searches bags, where the NSG only checks which street you came from. From SOC work you know WAF logs (`AzureDiagnostics`, *ApplicationGatewayFirewallLog*). Now you're the one choosing the rules that write them.

## What actually matters

**1. Where WAF runs.**

| | Application Gateway WAF v2 | Front Door WAF |
|---|---|---|
| Scope | Regional, in your VNet | Global edge PoPs |
| Managed rule sets | DRS 2.2, DRS 2.1, CRS 3.2 | DRS 2.2 / 2.1 / 2.0 — ==!Premium tier only== |
| Standard tier | n/a | ==!custom rules only== |
| Bot protection | Yes (Bot Manager 1.0 / 1.1) | Premium only |
| Rate limiting | Yes | Yes |
| Policy scope | Global, per-site (listener), per-URI (path rule) | Per endpoint/route |
| Best for | Single-region app, L7 routing + WAF | Multi-region / global app |

Also supported: **Application Gateway for Containers** and **Azure CDN** (WAF in preview — legacy, don't design on it). Application Gateway v1 (Standard and WAF_v1) ==!retired April 28, 2026==; WAF_v1 never supported WAF policies. Legacy *WAF configuration* on v2 can't be created since March 15, 2025 and retires **March 15, 2027** — use **WAF policy**.

**2. Modes.** **Detection** logs matches, blocks nothing — the default for a new policy. **Prevention** logs and blocks (HTTP 403). Roll-out: Detection, observe real traffic (one to two weeks), tune exclusions, switch to Prevention.

**3. Managed rules = anomaly scoring.** With DRS 2.1+ / CRS 3.2 a match doesn't block on its own. Each rule adds to a score: Critical 5, Error 4, Warning 3, Notice 2. ==@Score ≥ 5 blocks in Prevention== (logs in Detection). Logs show the individual rule as *Matched* and rule **949110** *Inbound Anomaly Score Exceeded* as the blocking event. **DRS 2.2** (based on OWASP CRS 3.3.4 plus Microsoft Threat Intelligence rules) is the recommended set for new policies; it runs at **Paranoia Level 1** by default. You can disable a rule or change its action per rule.

**4. Exclusions.** Remove a request element from inspection — match variable **request header / cookie / query-string argument / body argument name** (or keys/values), operator (Equals, Starts with, Contains...), selector (for example `Authorization`). Apply to ==+specific rules or rule groups==; a ==!global exclusion== removes that field from every rule and opens a hole.

**5. Custom rules.** Evaluated ==@before managed rules==, lowest priority number first. Match on IP, geo (country), URI, method, headers, query string, body, size. Actions: **Allow** (stops further evaluation, including managed rules), **Block**, **Log** (and JS challenge where supported). Uses: geo-blocking, allow-listing a pen-test range, blocking a bad user agent.

**6. Rate limiting** (custom rule type *Rate limit*). Threshold per **1 or 5 minutes**. Application Gateway groups by **ClientAddr** (default), **GeoLocation**, **None**, or the X-Forwarded-For variants; counters are per association (listener/gateway) and approximate. Front Door counts per socket IP by default and enforces per edge location. Rate-limit rules can't use **Allow**.

**7. Bot protection.** Bot Manager rule set sorts traffic into **Bad**, **Good** and **Unknown** bots (Microsoft threat intelligence). Typical: block bad, allow good, log unknown.

**8. Don't let attackers go around it.** Lock the back end to the WAF path: App Service access restriction for `AzureApplicationGateway` / `AzureFrontDoor.Backend` (+ `X-Azure-FDID`), or private endpoint. Send **ApplicationGatewayFirewallLog** via a diagnostic setting to Log Analytics.

## Where it lives

- **Azure portal > Web Application Firewall policies (WAF) > *policy***: **Policy settings** (mode, body inspection), **Managed rules** (rule set, per-rule state/action, **Exclusions**), **Custom rules**, **Associations** (gateway, listener, path rule / Front Door endpoint).
- **Application gateways > *gateway* > Web application firewall** (associated policy); **> Monitoring > Diagnostic settings**.

```bash
az network application-gateway waf-policy create -g rg -n waf-web --type Microsoft_DefaultRuleSet --version 2.2
az network application-gateway waf-policy policy-setting update -g rg --policy-name waf-web \
  --mode Prevention --state Enabled
az network application-gateway waf-policy custom-rule create -g rg --policy-name waf-web \
  -n ratelogin --priority 10 --rule-type RateLimitRule --action Block \
  --rate-limit-duration OneMin --rate-limit-threshold 100
```

```kql
AzureDiagnostics
| where Category == "ApplicationGatewayFirewallLog" and action_s == "Blocked"
| summarize count() by ruleId_s, requestUri_s
```

## Exam traps

- "Global e-commerce site, inspect at the edge" → ==+Front Door WAF==. "Single region, already using Application Gateway" → App Gateway WAF.
- "Front Door Standard with DRS" → ==!not available==; Premium.
- Detection mode and attacks "still getting through" → expected; Detection never blocks.
- One rule matched in Prevention but request wasn't blocked → anomaly score under 5.
- "False positive on the Authorization header for rule 942430" → per-rule exclusion on that header, ==!not== disabling the SQLi rule group, ==!not== a global exclusion.
- "Allow the pen-testing firm through" → custom **Allow** rule with their IP range (evaluated before managed rules).
- "Different rules for the payments path" → per-URI policy (overrides per-site and global).
- WAF in place but app still attacked directly → back end not restricted to the gateway / Front Door.
- "Block more than 100 login attempts a minute per IP" → rate-limit custom rule, group by ClientAddr.

## Skip

- **Skip:** the full rule-ID tables for every DRS/CRS group. Know the groups (SQLi, XSS, LFI/RFI, PHP, protocol enforcement, Java, MS-ThreatIntel) and rule 949110.
- **Skip:** paranoia levels 2–4 beyond "PL1 default; PL3/PL4 unsupported".
- **Skip:** request body size limits, file-upload limits and inspection toggles.
- **Skip:** the per-site PowerShell tutorial (VM scale set, IIS). Know the three association levels.
- **Skip:** JavaScript challenge / CAPTCHA, JA4 grouping and HTTP DDoS rule set previews.
- **Skip:** Front Door classic and CDN WAF configuration. Legacy.
- **Skip:** unit 4's App Gateway listener/back-end host-header steps. Routing, not WAF.

**Where the training module and product docs disagree (product docs win):** unit 3 calls **CRS 3.2** "the current recommended version". The rule-set reference now marks CRS 3.2 as legacy and recommends ==+DRS 2.2== for new policies. (The rate-limiting article still says "select CRS 3.2" to get the new engine — any DRS 2.x or CRS 3.2 runs on it.)
