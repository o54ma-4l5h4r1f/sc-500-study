## Azure first

- **Authentication** is proving who you are. **Authorization** is what you may do afterwards. This page is only about the first.
- **Microsoft Entra ID** checks the proof (password, phone, key…) and then issues tokens. Every Azure portal, Azure CLI and Microsoft 365 sign-in goes through it.
- An **authentication method** is one kind of proof. **MFA** (multifactor authentication) means two proofs from different kinds: something you know, have, or are.
- The **Authentication methods policy** is the tenant setting that says *which* methods *which* groups may use. You can open it in a free tenant; the Conditional Access pieces need **Entra ID P1**.

New to these? Read the Foundations pages listed in "Before you start".

## In one sentence

You decide *which* sign-in methods exist in the tenant (Authentication methods policy), *when* they are demanded (Conditional Access, or security defaults), and *how strong* they must be for a given resource (authentication strengths).

## Why it exists

Most of the identity incidents you triaged started with a phished or sprayed password. MFA stops the stolen password on its own. But ordinary MFA can still be phished: an attacker proxies the sign-in page and relays the code or the push approval. **Phishing-resistant** methods bind the sign-in to the real website with cryptography, so a fake page gets nothing useful.

Think of three front doors. A key (password) can be copied. Key plus a code texted to you (SMS MFA) — someone can trick you into reading the code out. A fingerprint reader built into a smart lock that only opens for *this* door (FIDO2, Windows Hello for Business) — there's nothing to hand over.

## What actually matters

**1. The methods and what each can do.**

| Method | Sign in alone (primary)? | Second factor? | Phishing-resistant? |
|---|---|---|---|
| Password | Yes | No | No |
| SMS / voice call | SMS sign-in only | Yes | No — ==!SIM-swap== risk, "legacy" |
| Microsoft Authenticator push / TOTP code | No | Yes | No |
| Authenticator passwordless (phone sign-in) | Yes | No | No on its own |
| Software / hardware OATH token | No | Yes | No |
| ==@Windows Hello for Business== | Yes | Yes | **Yes** |
| ==@Passkey (FIDO2)== — security key, passkey in Authenticator, synced passkey | Yes | Yes | **Yes** |
| ==@Certificate-based authentication (CBA)== | Yes | Yes | **Yes** (multifactor CBA) |
| Platform Credential for macOS | Yes | Yes | **Yes** |
| Temporary Access Pass | Yes | Yes | No |

Passwordless = no password typed: the device proves possession and a local PIN or biometric unlocks it. Push notifications always use **number matching** now — the user types the number shown on screen, which defeats "approve by accident" MFA fatigue.

**2. Authentication methods policy — the one place to enable methods.** Path: `Entra ID > Authentication methods > Policies`. Role: ==@Authentication Policy Administrator==. Each method is enabled for all users or chosen groups, with per-method settings (for example, whether Authenticator shows app name and location; FIDO2 key restrictions and attestation).

The old places — the legacy **MFA policy** (service settings) and **SSPR policy** — ==!can't manage methods since September 30, 2025==. Migration states: **Pre-migration** (new policy for sign-in only, legacy respected), **Migration in Progress** (new policy for sign-in and SSPR, legacy still respected), **Migration Complete** (only the new policy counts). Until complete, a method enabled in *any* policy is usable — so to stop a method you must disable it everywhere.

**3. Three ways to *demand* MFA.**

| Model | Licence | Notes |
|---|---|---|
| ==+Conditional Access== | Entra ID P1 | Recommended. MFA in context: by app, location, risk, role. |
| Security defaults | Free | Baseline MFA for everyone via Authenticator. No exclusions, no conditions. For tenants with no Conditional Access policies. |
| Per-user MFA | — | ==!Legacy==. Hard to manage, doesn't fit policy-based control. |

Use **named locations** (in Conditional Access) for trusted networks. The legacy **Trusted IPs** setting in MFA service settings ==!doesn't support IPv6==.

**4. Authentication strengths — "which MFA is good enough".** A Conditional Access grant control. Built-ins (can't be edited): **Multifactor authentication strength**, **Passwordless MFA strength**, **Phishing-resistant MFA strength**. Phishing-resistant allows Windows Hello for Business or platform credential, FIDO2 security key, and multifactor CBA. Passwordless also allows Authenticator phone sign-in. You can build **custom** strengths. Strength ==!doesn't stop the first factor== — a user can still type a password, then must complete the strong method.

**5. Registration is an attack surface.** If an attacker with a stolen password can register *their* phone, MFA is worthless. Users register in **combined registration** (MFA + SSPR methods in one flow, at the Security info page). Protect it with a Conditional Access policy on the user action **Register security information** — require a trusted location or a TAP.

**Temporary Access Pass (TAP)** is a time-limited passcode for onboarding and lost-device recovery, used to register a passwordless method.

| TAP setting | Default | Allowed |
|---|---|---|
| Minimum lifetime | 1 hour | 10 minutes – 30 days (43,200 minutes) |
| Maximum lifetime | 8 hours | 10 minutes – 30 days |
| Default lifetime | 1 hour | between min and max |
| One-time use | False | True / False |
| Length | 8 | 8–48 characters |

Enable TAP in the Authentication methods policy (Authentication Policy Administrator). Create passes as an **Authentication Administrator** (members only) or **Privileged Authentication Administrator** (admins and members). With a one-time TAP, register the passwordless method within 10 minutes. You can also push users with a **registration campaign**. The **MFA registration policy** in Entra ID Protection forces registration but needs ==@P2==.

**6. Pick methods by persona.** Admins and regulated users: FIDO2 security keys. Corporate Windows users: Windows Hello for Business. Mobile users: passkey in Authenticator. Shared/frontline devices: FIDO2 keys. BYOD: synced or Authenticator passkeys. Workloads can't do MFA: use **managed identities** in Azure (D1.1.6) and **certificates** rather than client secrets elsewhere. **Microsoft Entra Agent ID** (preview) gives AI agents their own identities, separate from users.

## Where it lives

| Task | Path (Microsoft Entra admin center) | Role |
|---|---|---|
| Enable/scope methods | `Entra ID > Authentication methods > Policies` | Authentication Policy Administrator |
| Migrate from legacy | `… > Policies > Manage migration` | Authentication Policy Administrator |
| Registration campaign | `Entra ID > Authentication methods > Registration campaign` | Authentication Policy Administrator |
| Create a TAP for a user | `Entra ID > Users > {user} > Authentication methods > Add authentication method` | Authentication Administrator |
| Authentication strengths | `Entra ID > Authentication methods > Authentication strengths` (used in Conditional Access) | Conditional Access Administrator |
| Named locations | `Entra ID > Conditional Access > Named locations` | Conditional Access Administrator |
| Security defaults | `Entra ID > Overview > Properties > Manage security defaults` | at least Conditional Access Administrator |
| Users register | `https://mysignins.microsoft.com/security-info` | the user |

In Microsoft Graph, each method's configuration is a resource under the authentication methods policy — for example `temporaryAccessPassAuthenticationMethodConfiguration` with `isUsableOnce`, `defaultLifetimeInMinutes`, `maximumLifetimeInMinutes`.

## Exam traps

- **"Enable FIDO2 in the MFA service settings."** ==!No== — manage methods in the ==+Authentication methods policy==.
- **"Microsoft Authenticator push is phishing-resistant."** ==!No.== Push and TOTP are MFA, not phishing-resistant. Phishing-resistant = WHfB, FIDO2/passkeys, CBA, platform credential.
- **"Require MFA" and "Require authentication strength" in one policy** — ==!not allowed==.
- **Disabled a method in the new policy but users still use it** — it's still enabled in a legacy policy and the tenant isn't at **Migration Complete**.
- **TAP defaults**: default lifetime ==@1 hour==, max ==@8 hours==, one-time use ==@off==, range up to ==@30 days==.
- **Trusted IPs vs named locations** — named locations support IPv6 and all Conditional Access conditions.
- **SMS for admins** — ==!no==. Weakest MFA, keep only as limited fallback.
- **WHfB in an authentication strength** works only if the user *signed in* with WHfB; a password user isn't prompted to switch.
- **Security defaults vs Conditional Access** — can't mix; security defaults are for tenants with no Conditional Access policies.
- **Service principal needs MFA?** Impossible. Use certificates or managed identities, and Conditional Access for workload identities (block-only).
