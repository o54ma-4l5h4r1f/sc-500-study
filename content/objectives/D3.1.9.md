## Azure first

- A **Foundry project** holds **model deployments** (the endpoints apps call) and **agents** (a model plus instructions plus **tools** it can call, built in the **Foundry Agent Service**).
- A **prompt** is what goes into the model; a **completion** is what comes out. An agent also makes **tool calls** (sending data to a tool such as search, a function or an MCP server) and receives **tool responses**.
- **Azure AI Content Safety** is the Azure service whose classifiers judge text for harm and attacks. Foundry guardrails run those classifiers for you — no separate resource to deploy.
- Foundry roles were renamed: **Foundry Account Owner**, **Foundry Owner**, **Foundry User**, **Foundry Project Manager** (formerly "Azure AI …").

See the Foundations pages listed above: Foundry basics, AI agents and MCP, RBAC.

## In one sentence

A Foundry **guardrail** is a named set of **controls**; each control says *which risk* to detect, *at which intervention point* (user input, tool call, tool response, output) and *what to do* (annotate, or annotate and block), and you assign the guardrail to model deployments and agents.

## Why it exists

A model will answer whatever it's asked, and an agent will act on whatever it reads. A jailbreak in a chat box, or an instruction hidden in a web page the agent fetched, can steer it to leak data or take an action nobody asked for.

Think of airport security with four checkpoints: the passenger at the door (user input), bags going to the hold (tool call), bags coming back (tool response), and the passenger at the gate (output). Each checkpoint has its own scanner list. A guardrail is that list.

For a SOC analyst: this is the *preventive* half. The alert you see from Defender for AI Services ([D3.1.8](D3.1.8.html)) often says "blocked by Prompt Shields" — that block was a guardrail.

Models get checkpoints 1 and 4. Agents get all four. ==@The agent's guardrail fully overrides its model's guardrail== — it does not add to it.

## What actually matters

1. **Risks you can pick.** Hate, Sexual, Self-harm, Violence (the four core harms). **User prompt attacks** (Prompt Shields, formerly "jailbreak risk detection"). **Indirect attacks** (Prompt Shields for documents — instructions hidden in retrieved content, email, web pages, tool output). **Protected material** for text and for code. **PII** (preview). **Task adherence** (preview). **Groundedness** (preview) and **Spotlighting** (preview) apply to ==!models only, not agents==. Groundedness in Azure OpenAI retires **April 30, 2027**.

2. **Blocking levels for the four harms.** **Off** · **Low** (blocks high severity only, least restrictive) · **Medium** (blocks medium and high) · **High** (blocks low, medium and high — most restrictive). Turning harms **off for outputs** needs Microsoft approval for **modified guardrails**. The core harm controls on input and output can't be deleted, only overridden.

3. **Actions.** **Annotate** (flag in the API response, let it through) or **Annotate and block**. ==!Agents support only Annotate and block.== Use annotate on models during rollout to measure false positives.

4. **Defaults.** Models get ==@Microsoft.DefaultV2==: the four harms at **Medium** on prompts and completions, user prompt attack detection on prompts, protected material (text and code) on completions. ==!Indirect (document) attack detection is off by default.== Default guardrails can't be edited — create a custom one. An agent with no guardrail of its own inherits its model deployment's guardrail. ==!Hosted agents differ:== if the hosted agent definition omits `rai_config`, there is ==!no guardrail at the agent boundary== at all (only the model deployment's own filter); `rai_config` without a policy name uses `Microsoft.DefaultV2`.

5. **Prompt Shields — two kinds.** *User prompt attacks* (direct): change-the-rules, conversation mock-ups, role-play, encoding attacks; scanned at **user input** only. *Document/indirect attacks*: scanned on document content at user input (wrap it in `<documents>` delimiters for model APIs) and, for agents, at **tool response** (preview). **Spotlighting** marks untrusted documents so the model treats them as data.

6. **Agent-specific controls.** **Tool call** and **tool response** checkpoints (preview, supported tools only). **Task adherence** flags a tool call that doesn't match what the user asked (user wanted to *read* the calendar; agent plans to *clear* it). **Network egress controls** (preview) for hosted agents restrict outbound destinations in the same guardrail. A **Guided guardrail set-up** (preview) asks about the agent's users, data and tools and proposes controls. Guardrails apply only to agents built in the **Foundry Agent Service** — ==!not to other agents registered in the Foundry control plane==.

7. **Blocklists.** Your own list of terms, each **Exact match** or **Regex**, added one at a time or by **Bulk add** (CSV with Term and Type columns). Attach to input and/or output. Reusable across guardrails.

8. **Govern guardrails at scale.** A **guardrail policy** (Foundry control plane, built on ==@Azure Policy==) governs which guardrail controls model deployments must use across a subscription or resource group (new Foundry portal only). Creating one needs **Owner** or **Resource Policy Contributor** — not a Foundry role.

## Where it lives

**Foundry portal** (`ai.azure.com`) **> *project* > Build > Guardrails > Create guardrail.** Step 1 add controls (risk → intervention points → action → **Add control**). Step 2 **Add agents / Add models**. Step 3 review, name, **Create**.

- Assign from the other side: **Build > Agents** (or **Models**) **> *item* > Guardrails > Manage > Assign a new guardrail**. Takes effect immediately.
- Test: select the guardrail **> Try in Playground**.
- Role: **Foundry Account Owner** or higher on the Foundry resource.
- API: a guardrail is an ARM **RAI policy** (`raiPolicies`); a deployment points to it with `raiPolicyName`. A request can override with the `x-policy-id` header.

## Exam traps

- **"Blocking level High" is the strictest**, not the most lenient. (APIM's `llm-content-safety` threshold runs the opposite way — 0 strictest. See [D3.1.7](D3.1.7.html).)
- **Jailbreak vs indirect attack.** Typed by the user = user prompt attack. Hidden in a document, email or tool output = ==@indirect/document attack==. Indirect is ==!off by default==.
- **Agent override.** Model at Violence High, agent at Violence Low → the agent scans at Low. Tool calls aren't scanned unless the agent's guardrail has tool-call controls.
- **Annotate on an agent?** Not supported — block only.
- **Guardrails don't authorise tools.** Whether an agent *may* call a tool is permissions, managed identity and network control ([D3.1.6](D3.1.6.html)); guardrails only inspect content.
- **Can't edit DefaultV2.** Create a custom guardrail.
- **Blocklists** are your words; **protected material** is Microsoft's detector for known copyrighted text and public GitHub code.
- **Latency:** about 50–100 ms per intervention point. "Turn everything on everywhere" has a cost.
