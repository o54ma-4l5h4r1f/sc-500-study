## Azure first

- **Deleting** an Azure resource normally removes it at once. Key Vault adds a waiting room: deleted things sit in a **soft-deleted** state and can be recovered. **Purging** is the second, final delete that empties the waiting room.
- A **customer-managed key (CMK)** is a key in *your* vault that another service (Storage, SQL, disks) uses to encrypt its data. If that key disappears, the data becomes unreadable forever.
- A **diagnostic setting** is the switch on an Azure resource that copies its **resource logs** (what happened inside it) to a Log Analytics workspace, a storage account or an event hub. Without one, the logs are not kept.
- **Event Grid** is Azure's notification bus: a resource publishes "something happened" events, and a Function, Logic App or webhook reacts.

See *diagnostic-settings-and-activity-log* and *log-analytics-workspace* in Foundations.

## In one sentence

Key Vault settings are the vault-wide switches that decide whether deleted objects can be brought back (soft delete, purge protection), which Azure platform services may pull secrets during deployment (resource access), and whether every operation is recorded (diagnostic logging).

## Why it exists

Think of the bank vault again. Soft delete is the shredder bin that is only emptied after a waiting period. Purge protection is a time lock on that bin: not even the bank manager can empty it early. The resource-access checkboxes are the standing permission for the armoured-van company to collect specific boxes. The diagnostic log is the sign-out sheet.

As an analyst you have triaged "a key was deleted" alerts. The engineer's question is earlier: *could* it be deleted for good, and *will* there be a log line to prove who did it?

## What actually matters

**1. Soft delete — always on.** Every new vault has it, and once on it ==!cannot be disabled==. Deleted vaults, keys, secrets and certificates stay recoverable for **7 to 90 days** (default **90**). The retention days are ==!set only at creation== and cannot be changed afterwards; the same interval also governs purge protection. During retention a vault name — or an object name inside a vault — ==!cannot be reused==. Soft-deleting a whole vault also deletes its RBAC role assignments and Event Grid subscriptions; recovering the vault does **not** bring them back.

**2. Purge protection — optional, irreversible.** Off by default. It needs soft delete. When on, nobody can purge a soft-deleted vault or object until the retention period ends — not a subscription Owner, not a **Key Vault Purge Operator**, not Microsoft. Recovery still works. Once enabled it ==!can never be turned off== (the property does not accept `false`). Most services that use a CMK from your vault, such as Azure Storage, ==@require purge protection==. Without it, anyone with purge rights can delete-then-purge an encryption key in seconds.

**3. Resource access (the three "enabled for" switches).** On **Access configuration**, three checkboxes let Azure platform services read from the vault on your behalf:

| Portal checkbox | Property | What it allows |
|---|---|---|
| Azure Virtual Machines for deployment | `enabledForDeployment` | The compute platform may pull **certificates stored as secrets** into a VM at creation |
| Azure Resource Manager for template deployment | `enabledForTemplateDeployment` | ARM may read **secrets** referenced as parameters in a template deployment |
| Azure Disk Encryption for volume encryption | `enabledForDiskEncryption` | **Azure Disk Encryption** may retrieve secrets and **unwrap keys** — ==@required for ADE== (D3.2.1) |

All three are off by default. Turn on only the one a scenario needs. The **permission model** radio button sits on the same tab (D1.2.3).

**4. Diagnostic logging — off until you add it.** The security log category is ==@AuditEvent== (shown as **Audit Logs**, inside the **audit** category group). A second category, **Azure Policy Evaluation Details**, only carries Azure Policy data-plane evaluation results. AuditEvent records every authenticated request on both planes, failed permission checks, unauthenticated 401 requests, and Event Grid notification events (near-expiry, expired, access-policy changed). Send it to a **Log Analytics workspace** (query and alert), a **storage account** (long-term archive, container `insights-logs-auditevent`) or **Event Hubs** (stream to a SIEM). Records arrive within about **10 minutes**. In the workspace they land in `AzureDiagnostics` (destination table "Azure diagnostics") or `AZKVAuditLogs` ("Resource specific"). Operation names follow an *ObjectVerb* pattern: `SecretGet`, `KeyDelete`, `VaultPatch`.

Role-assignment changes on an RBAC vault are ==!not in AuditEvent== — they are control-plane writes to `Microsoft.Authorization/roleAssignments`, recorded in the **Activity log**. Alert on both sources.

**5. Event Grid vs logs.** Logs are the full history, batched. Event Grid is the real-time trigger: `SecretNearExpiry`, `CertificateNearExpiry`, `KeyNearExpiry`, `SecretNewVersionCreated`, `CertificateExpired`. Use Event Grid to start rotation automation (D1.2.5).

**6. Enforce at scale with Azure Policy.** Built-ins: **Key vaults should have soft delete enabled** and **Key vaults should have deletion protection enabled** (effects Audit, Deny, Disabled), plus **Resource logs in Key Vault should be enabled**. Set deletion protection to **Deny** at management-group or subscription scope so no new vault ships without purge protection.

## Where it lives

All in the **Azure portal**, on the vault:

- **Key vaults > *vault* > Settings > Properties** — soft-delete days (read-only after creation), **Enable purge protection**.
- **Key vaults > *vault* > Settings > Access configuration** — permission model and the three resource-access checkboxes.
- **Key vaults > *vault* > Monitoring > Diagnostic settings > + Add diagnostic setting** — tick the **audit** category group (Audit Logs = AuditEvent), choose destinations.
- **Key vaults > *vault* > Events** — Event Grid subscriptions.
- **Key vaults** list **> Manage deleted vaults** — recover or purge soft-deleted vaults.

![Access configuration tab of the create wizard](https://learn.microsoft.com/en-us/azure/key-vault/media/rbac/new-vault.png){Access configuration: permission model (Azure RBAC recommended) and the three Resource access checkboxes}

```bash
az keyvault update -n kv-payroll-prod-01 -g rg-payroll-prod --enable-purge-protection true
az keyvault update -n kv-payroll-prod-01 -g rg-payroll-prod --enabled-for-disk-encryption true
az monitor diagnostic-settings create --name kv-audit-to-law \
  --resource <key-vault-resource-id> \
  --logs '[{"category":"AuditEvent","enabled":true}]' \
  --workspace <log-analytics-workspace-id>
az keyvault list-deleted                       # soft-deleted vaults
az keyvault recover --name kv-payroll-prod-01  # bring one back
```

## Exam traps

- "Reduce soft-delete retention on an existing vault from 90 to 30 days" → ==!not possible==. Retention is fixed at creation.
- "Turn off purge protection so we can delete the test vault today" → ==!not possible==. Wait out the retention period.
- "Prevent permanent deletion of keys even by Owners" → ==+purge protection==, not a resource lock. A **CanNotDelete lock** stops deleting the vault resource; it does nothing about purging objects inside it.
- "ADE fails: cannot access the key vault" → ==+enabledForDiskEncryption==. "ARM template can't read the admin password from Key Vault" → ==+enabledForTemplateDeployment==.
- "Who changed the vault's role assignments?" → ==+Activity log==, not AuditEvent.
- Soft delete is **not** a backup. Purge or retention expiry destroys the object. Backup/restore of individual objects is a separate operation.
- The training unit says to fix non-compliant vaults with a **remediation task**. ==!Remediation tasks only work for DeployIfNotExists and Modify policies.== The soft-delete and deletion-protection built-ins are Audit/Deny — they report or block; you fix existing vaults yourself (`az keyvault update --enable-purge-protection true`).

## Skip

- **Skip:** the long `operationName` tables in *Key Vault logging*. Know the *ObjectVerb* pattern and the handful above (`SecretGet`, `SecretDelete`, `SecretPurge`, `KeyDelete`, `VaultPatch`).
- **Skip:** the JSON blob layout of logs in the storage container and the `identity` claim XML URIs. The exam asks *where* logs go, not how to parse them.
- **Skip:** soft-delete billing notes (purge/recover count as operations; HSM key charges in the deleted state) — pricing trivia.
- **Skip:** the "custom role for listing deleted vaults" advice in the soft-delete article. Nice operations hygiene, not tested.
- **Skip:** the alert-routing advice in unit 3 ("route to on-call, not an inbox"). Correct, but it is SOC process you already know.
- **Skip:** Azure Monitor "Key Vault insights" workbook — a view on the same AuditEvent data.
