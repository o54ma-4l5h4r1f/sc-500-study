## Azure first

- An **Azure resource** such as a virtual machine (VM), App Service web app, Function app or Logic App often needs to call *another* resource — read a secret from Key Vault, write a blob to a storage account.
- To call it, the code needs a **token** from Microsoft Entra ID, and to get a token it needs an **identity**.
- **Azure RBAC** is how you then say what that identity may do: a **role assignment** = identity + role + scope (for example *Storage Blob Data Reader* on one storage account).
- This is fully lab-able in your Azure subscription: a small VM or Function app, a storage account, and a role assignment. Delete the resource group afterwards.
- **Coverage note:** Microsoft's training course has **no unit** for this bullet. This page is written from product documentation.

New to these? Read the Foundations pages listed in "Before you start".

## In one sentence

A managed identity is an Entra ID identity that Azure creates *for* a resource and whose credential Azure keeps and rotates, so code on that resource can get tokens with no secret anywhere in code or config.

## Why it exists

Connection strings and client secrets leak — into Git, into config files, into screenshots. As an analyst you've seen the alert for a secret found in a public repo. A managed identity removes the secret entirely. There is nothing to leak because you never see the credential.

Think of a staff ID badge built into a company car. Whoever is legitimately *driving that car* can open the car-park barrier. Nobody carries a separate key. When the car is scrapped, the badge is scrapped with it. That's a system-assigned identity. A user-assigned identity is a badge kept in the key safe that you clip into any car in the pool.

## What actually matters

**1. Two types.**

| | ==@System-assigned== | ==@User-assigned== |
|---|---|---|
| Created | As part of the resource (a toggle) | As a standalone Azure resource (`Microsoft.ManagedIdentity/userAssignedIdentities`) |
| Lifecycle | Deleted when the resource is deleted | Independent — ==!must be deleted explicitly== |
| Sharing | One resource only | Many resources |
| Name | Same as the resource (slot: `{app-name}/slots/{slot-name}`) | Whatever you call it |
| Best for | Per-resource audit trail; permissions that must vanish with the resource | Replicated or short-lived resources, access needed *before* deployment, fewer approvals |

A resource can have **one system-assigned plus several user-assigned** identities at once. Microsoft recommends user-assigned for most Microsoft services. Both are free.

**2. Under the hood.** A managed identity is a **service principal of a special type** with ==!no application object== — so it never appears under App registrations and you can't add a secret to it. The platform issues it a certificate and rolls it. On a VM, code asks the **Azure Instance Metadata Service (IMDS)** at `http://169.254.169.254/metadata/identity/oauth2/token` with a `resource` parameter (for example `https://management.azure.com/`) and, if the VM has several user-assigned identities, a `client_id` to pick one. IMDS is reachable only from inside the VM.

**3. Identity is not permission.** Turning the identity on grants ==!nothing==. You must authorise it on the *target*: an Azure RBAC role (Storage Blob Data Contributor, Key Vault Secrets User…) at the narrowest scope, or the target service's own access model. It works with any service that supports Entra authentication.

**4. The roles that control managed identities.**

| You want to… | You need |
|---|---|
| Turn on system-assigned on a VM | Write on the resource — e.g. ==@Virtual Machine Contributor== |
| Create or delete a user-assigned identity | ==@Managed Identity Contributor== |
| Attach a user-assigned identity to a resource | Write on the resource **and** ==@Managed Identity Operator== on the identity |
| Give the identity access to a target | ==@Owner== or ==@User Access Administrator== on the target |

Managed identities are managed in Azure, not Entra: even a Global Administrator can't edit a managed identity's settings in the directory. You can stop users creating user-assigned identities with an Azure Policy **deny** on that resource type.

**5. Security consequences.**

- Anyone who can **run code on the resource** inherits all its identity's permissions. Anyone with **Managed Identity Operator** can attach the identity to another resource and inherit them too. Treat both as privileged.
- Grant least privilege. Never "Contributor on the subscription" for a VM that reads one container.
- Managed identities ==!can't be PIM-eligible== (they can't do an interactive activation) and ==!aren't covered by Conditional Access==. Control them with narrow RBAC scope and **access reviews**.

**6. Operational gotchas.**

- Tokens are cached by the platform for **about 24 hours** per resource URI. Adding or removing the identity from a **group** or role can take hours to apply. Prefer role assignments directly on a user-assigned identity over group membership.
- Deleting an identity ==!doesn't delete its role assignments==. They linger as **Identity not found** (`ObjectType` = `Unknown`) and count against the subscription limit — clean them up.
- Creating many system-assigned identities quickly can hit the Entra object-creation rate limit (**HTTP 429**). A deleted system-assigned identity still counts against directory limits until purged after **30 days**.
- **Managed identity as a federated credential**: an app registration can trust a managed identity instead of holding a secret (workload identity federation) — up to ==@20== federated identity credentials per application (or per user-assigned managed identity).

## Where it lives

**Azure portal** — not the Entra admin center.

| Task | Path |
|---|---|
| System-assigned on a VM | `Virtual machines > {vm} > Security > Identity > System assigned > Status: On` |
| Create user-assigned | `Managed Identities > Create` |
| Attach user-assigned | `{resource} > Identity > User assigned > Add` |
| Grant it access | `{target resource} > Access control (IAM) > Add role assignment > Managed identity` |
| See its sign-ins | `Microsoft Entra admin center > Entra ID > Monitoring & health > Sign-in logs > Managed identity sign-ins` |

```bash
# System-assigned on an existing VM
az vm identity assign -g rg-lab -n vm1
# User-assigned: create, attach, authorise
az identity create -g rg-lab -n id-app
az vm identity assign -g rg-lab -n vm1 --identities id-app
az role assignment create --assignee-object-id <principalId> \
  --assignee-principal-type ServicePrincipal \
  --role "Storage Blob Data Reader" --scope <storageAccountId>
```

```bicep
resource uami 'Microsoft.ManagedIdentity/userAssignedIdentities@2023-01-31' = {
  name: 'id-app'
  location: resourceGroup().location
}
```

```bash
# From inside the VM: get a token for Azure Storage
curl 'http://169.254.169.254/metadata/identity/oauth2/token?api-version=2018-02-01&resource=https%3A%2F%2Fstorage.azure.com%2F' -H Metadata:true
```

## Exam traps

- **"Store the storage key in Key Vault and have the VM read it with a secret."** ==+Use a managed identity== and an RBAC data role — no secret at all.
- **Several VMs, same access, frequent rebuilds** — ==+user-assigned==. **Need to know which specific VM did it** or permissions must vanish with the resource — ==+system-assigned==.
- **Identity enabled, still 403** — no role assignment on the target, or the change hasn't propagated (token cache).
- **Least privilege to attach an existing user-assigned identity** — ==+Managed Identity Operator== (plus write on the resource), not Managed Identity Contributor.
- **Find the managed identity under App registrations** — ==!it isn't there==; it's an enterprise-app-type service principal with no app object.
- **Delete the VM — what happens?** System-assigned identity deleted; ==!role assignments stay== as "Identity not found". User-assigned identity untouched.
- **PIM or Conditional Access for a managed identity** — ==!neither applies==.
- **Code outside Azure** (GitHub Actions, on-prem) — managed identity ==!isn't available==; use an app registration with a federated credential or certificate (D1.1.4). For on-premises servers, Azure Arc gives a managed identity.
- **Multiple user-assigned identities on one VM** — the token request must include `client_id`.

## Skip

- **Skip:** the list of every service that supports managed identities. Know that VMs, scale sets, App Service, Functions, Logic Apps, AKS and others do.
- **Skip:** per-SDK code samples (Azure.Identity in .NET/Python/Java). Know code uses `DefaultAzureCredential`/MSAL and never handles the credential.
- **Skip:** ARM template API-version differences (`identityIds` vs `userAssignedIdentities`).
- **Skip:** the security-group workaround diagrams for system-assigned identities. Know user-assigned identities are the cleaner way to share permissions.
- **Skip:** PowerShell clean-up one-liners for orphaned role assignments. Know orphaned assignments exist and must be removed.
- **Skip:** Service Fabric and Azure Policy–driven identity assignment specifics.
