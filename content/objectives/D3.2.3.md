## Azure first

- A **network security group (NSG)** is a numbered list of allow/deny rules on a subnet or a VM's network card. Azure checks rules in priority order and ==stops at the first match==.
- **Azure Firewall** is a managed firewall in a VNet. **DNAT** (destination NAT) is a firewall rule that maps a public port on the firewall to a private port on a VM.
- **Microsoft Defender for Cloud** is Azure's posture-and-protection service. **Defender for Servers** is its paid plan for machines; it comes as **Plan 1** and **Plan 2**.
- The **Activity log** is the subscription's record of every control-plane change (who changed which resource, when). It keeps 90 days by default.

See the Foundations pages listed above, especially *defender-for-cloud-basics*.

## In one sentence

JIT VM access is a Defender for Servers Plan 2 feature that keeps a VM's management ports (RDP 3389, SSH 22, WinRM 5985/5986) **closed by an NSG or Azure Firewall deny rule**, and opens one port, for one source IP, for a limited time, when an authorised user asks.

## Why it exists

Open management ports are the most-scanned thing on the internet. As an analyst you have seen the resulting brute-force alerts. But admins do need RDP sometimes. JIT is the hotel key card that only opens your door between check-in and checkout. The door is locked by default. The front desk (Defender for Cloud) checks who you are (Azure RBAC), then opens it for the hours you asked for, then locks it again.

It is a **network** control, not an identity control. A JIT grant does ==!not== give you a Windows or Linux password, and it does ==!not== prove anyone actually signed in.

## What actually matters

**1. Prerequisites.** All of these, or the VM shows as *Unsupported*:

- ==@Defender for Servers Plan 2== on the subscription. ==!Plan 1 doesn't include JIT.== Plan 2 can't be switched on for one VM alone; a resource-level override can only drop a VM to Plan 1 or off.
- An Azure Resource Manager VM. ==!Classic VMs aren't supported.==
- An **NSG** on the NIC or subnet, or an **Azure Firewall in the same VNet**, or both.
- If Azure Firewall: it must use **Rules (Classic)**. ==!Firewall Policy and Azure Firewall Manager-controlled firewalls aren't supported.==
- AWS EC2 instances are supported in preview through the AWS connector. There JIT removes the security-group rules and adds a temporary security group.

**2. What JIT writes.** When you enable it, Defender for Cloud makes sure a *deny all inbound* rule exists for each selected port in the NSG and/or firewall. If no rule exists for that port, the deny goes in at top priority. ==!If an existing allow rule already covers that port, the existing rule wins.== So enabling JIT does not close a port that a broad allow rule (for example *allow 3389 from Any* at priority 100) keeps open. Check **Effective security rules** and remove the old allow.

On an approved request, JIT inserts an allow rule for the requested port and source IP, above the deny. At expiry it restores the previous rules. Connections already open are ==!not disconnected==.

**3. Policy settings, per port.** Port number, protocol, **allowed source IPs** (Any, or a CIDR such as your office egress), and **maximum request time**. The maximum can be from ==@5 minutes to 1 day== (ISO 8601, e.g. `PT3H`).

| Where you enable it | Ports offered | Max time | Source |
|---|---|---|---|
| Defender for Cloud > Just-in-time VM access | ==@22, 3389, 5985, 5986== recommended, editable | you set it | you set it |
| VM > Configuration (Windows) | 3389 | ==@3 hours== | Any |
| VM > Configuration (Linux) | 22 | 3 hours | Any |

The JIT policy name plus the VM name can't exceed **56 characters**.

**4. Request flow.** The user opens Defender for Cloud (*Configured* tab) or **VM > Connect** and picks ports, source IP and duration (within the maximum). Defender for Cloud checks only two things: Azure RBAC and the policy limits. ==!There is no built-in human approval queue.== If you need approval, put it in front of the RBAC grant (for example, PIM for the custom role). Behind Azure Firewall, the user gets a firewall address and a **DNAT-mapped port**, not the VM's own port.

**5. Least-privilege permissions.** The exam loves the custom role.

| Task | Actions needed |
|---|---|
| View JIT status | **Reader** + **Security Reader** (or custom) |
| Configure / edit a policy | `Microsoft.Security/locations/jitNetworkAccessPolicies/write` and `Microsoft.Compute/virtualMachines/write`, at subscription scope (resource group only via API/PowerShell) |
| Request access | `Microsoft.Security/locations/jitNetworkAccessPolicies/initiate/action`, `.../jitNetworkAccessPolicies/*/read`, `Microsoft.Compute/virtualMachines/read`, `Microsoft.Network/networkInterfaces/*/read`, `Microsoft.Network/publicIPAddresses/read` |

Reader and Security Reader ==!can't request==; they lack `initiate/action`. Microsoft ships a `Set-JitLeastPrivilegedRole` script to build the request-only role. The JIT policy is a separate `Microsoft.Security` resource, so a role assigned only on the VM may not cover it.

**6. Audit and enforce.**

- **Audit:** every enable, edit, request and delete is an operation on `Microsoft.Security/locations/jitNetworkAccessPolicies`. It lands in the **Activity log**. Open it from the VM row's **…** menu > *Activity Log* on the JIT page. The *Configured* tab also shows approved requests in the last 7 days, last access time and last user. The Activity log keeps ==@90 days==. For longer (a quarterly review), add a subscription **diagnostic setting** that exports to Log Analytics or Storage. Reading it needs Monitoring Reader, not a JIT role.
- **Enforce/monitor:** the Defender for Cloud recommendation and built-in Azure Policy *"Management ports of virtual machines should be protected with just-in-time network access control"*. Its effect is ==!AuditIfNotExists== (or Disabled). It ==!doesn't enable JIT, change NSGs or block VM creation==. To actually force JIT, add it to your deployment pipeline (`Microsoft.Security/locations/jitNetworkAccessPolicies` in ARM/Bicep, or PowerShell).

## Where it lives

- **Azure portal > Microsoft Defender for Cloud > Workload protections > Just-in-time VM access**. Three tabs: *Configured*, *Not configured*, *Unsupported*. Select VMs > **Enable JIT on VMs**; right-click a configured VM > **Edit**; **Request access**.
- **Azure portal > Virtual machines > *vm* > Configuration > Just-in-time access > Enable just-in-time** (defaults above).
- **Azure portal > Virtual machines > *vm* > Connect > Request access**.
- **Azure portal > Policy > Definitions**, search "just-in-time network access".

```powershell
$vm = @{ id = "/subscriptions/<sub>/resourceGroups/rg-app/providers/Microsoft.Compute/virtualMachines/vm1"
         ports = @(@{ number = 3389; protocol = "TCP"
                      allowedSourceAddressPrefix = @("203.0.113.10")
                      maxRequestAccessDuration = "PT1H" }) }
Set-AzJitNetworkAccessPolicy -ResourceGroupName rg-app -Location westeurope `
  -Name default -Kind Basic -VirtualMachine @($vm)

Start-AzJitNetworkAccessPolicy ...   # request access
Get-AzJitNetworkAccessPolicy ...     # read policy and request history
```

## Exam traps

- "Cheapest plan that supports JIT" → ==+Defender for Servers Plan 2==. Plan 1 and Defender CSPM are distractors.
- VM shows **Unsupported** → no NSG or firewall, a classic VM, or JIT disabled in the security policy. Not "the VM is stopped".
- Firewall managed by **Azure Firewall Manager** / **Firewall Policy** → ==!JIT can't use it==.
- "After the window ends, the admin's RDP session is cut" → ==!false==. Only new connections are blocked.
- JIT enabled, port still reachable → an existing higher-priority allow rule wins. Fix the NSG.
- "User can see JIT but can't request" → missing `jitNetworkAccessPolicies/initiate/action`.
- "Require a manager to approve each JIT request" → ==!not a JIT feature==. Use PIM or a process in front of the role.
- JIT vs Bastion: JIT time-boxes the VM's **own** port; Bastion removes the public path. They combine. With Bastion, the source the VM sees is the AzureBastionSubnet range, not the user's IP.
- JIT vs PIM: PIM time-boxes a **role**; JIT time-boxes a **network port**.
- Audit evidence older than 90 days → only if the Activity log was ==+exported with a diagnostic setting==.
- On-premises Arc servers → no NSG, so ==!no JIT==. JIT covers Azure VMs and AWS EC2 (preview).

## Skip

- **Skip:** the long PowerShell discussions in units 3 and 4 (typed models missing `publicIpAddress` / `mappedPort`, HTTP 202 `Initiating`, bounded waits). Know the three cmdlet names and that `maxRequestAccessDuration` uses ISO 8601. That's all.
- **Skip:** unit 2's "supporting tasks" permission table (Network Contributor for effective rules, Monitoring Contributor for export, Resource Policy Contributor to assign the audit policy). Useful at work; the exam asks the JIT actions themselves.
- **Skip:** unit 4's validation procedure (test from a second source, test after expiry). It's change-management practice, not a feature.
- **Skip:** the AWS JIT logic-flow diagram in detail. Know only that AWS JIT is preview and works through security groups.
- **Skip:** the documentation IP ranges (203.0.113.0/24, 198.51.100.0/24). They are examples, not settings.
