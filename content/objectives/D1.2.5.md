## Azure first

- **Asymmetric** keys come in pairs: a public half anyone may hold and a private half that must stay secret (RSA, elliptic curve). **Symmetric** keys are one shared value (AES).
- **Envelope encryption:** a service encrypts its data with a *data encryption key* (DEK), then asks Key Vault to **wrap** (encrypt) that DEK with your *key encryption key*. Rotating the vault key re-wraps the DEK; the data itself is not re-encrypted.
- Every Key Vault object has **versions**. A **versionless URI** (`.../secrets/db-conn`) always means "the current version"; a **versioned URI** (`.../secrets/db-conn/<32-char-id>`) pins one version.
- A **certificate authority (CA)** signs certificates so browsers trust them. A **CSR** (certificate signing request) is the form you send the CA.

See *keys-secrets-and-certificates* in Foundations.

## In one sentence

Managing vault objects means choosing the right key type and protection, keeping keys and secrets fresh with versions, expiry and rotation, and letting Key Vault issue and renew certificates through a certificate policy.

## Why it exists

A key that never rotates and a password that never expires are exposure windows that never close. Key Vault turns rotation into configuration: a rotation policy makes new key versions on schedule, Event Grid warns before secrets expire, and a certificate policy renews TLS certificates before browsers start showing warnings.

## Mental model

All three object types share one engine: **name → versions → attributes (enabled, nbf, exp)**. A certificate is not a separate store. It is a bundle: creating one also creates an addressable **key** and **secret** with the same name.

## What actually matters

**Keys**

| Key type | Sizes / curves | Where |
|---|---|---|
| RSA / **RSA-HSM** | 2048, 3072, 4096 bits | Standard (software) / Premium (HSM) |
| EC / **EC-HSM** | P-256, P-384, P-521, P-256K | Standard (software) / Premium (HSM) |
| **oct-HSM** (AES) | 128, 192, 256 bits | ==@Premium only, HSM-only, preview==; GA on Managed HSM |

The training unit says symmetric keys "can't be HSM-backed in Key Vault Premium" and lists software octet keys. The product docs now list **oct-HSM in Premium (public preview)** and no software symmetric keys in vaults. ==!The docs win.==

- **BYOK (bring your own key):** generate the key in your on-premises HSM and import it without it ever being plaintext outside an HSM. Create a **key exchange key (KEK)** — an RSA-HSM key in a Premium vault (or Managed HSM) whose only permitted operation is `import`. Download its public half, wrap your key with the vendor's BYOK tool, upload the BYOK file. Needs Premium or Managed HSM.
- **Rotation policy** (per key): *rotation time* (create a new version N days after creation or before expiry — minimum **7 days**), *expiry time* (applied to each new version), *notification time* (fires `KeyNearExpiry` to Event Grid; needs an expiry set). **Rotate Now** rotates on demand. Each scheduled rotation costs extra. Manage it with **Key Vault Crypto Officer**. Microsoft's guidance: rotate encryption keys **at least every two years**.
- Rotation makes a **new version with new key material**. Services that use the **versionless** key URI pick it up (Azure services take from 1 hour to 24 hours or more). ==!Keep old versions enabled== until every DEK is re-wrapped, or decryption breaks. Azure Disk Encryption is the exception: it keeps using the original key even after auto-rotation (D3.2.1).
- `nbf` (not before) and `exp` (expires) attributes bound a key version's usable window.

**Secrets**

- Any string up to **25 KB** (passwords, connection strings, API keys). A `contentType` hint (≤255 characters) and up to 15 tags are optional.
- Every update creates a **new version**; old versions remain. **Disable** a version to retire it while keeping the audit trail.
- `exp` on a secret is ==!informational==. A **get** on an expired secret still works (useful for recovery). Expiry's value is the **`SecretNearExpiry`** / `SecretExpired` Event Grid events that drive rotation.
- **Key Vault references** in App Service and Functions: an app setting of `@Microsoft.KeyVault(SecretUri=https://{vault}.vault.azure.net/secrets/{name})`. Versionless → the app picks up a new version **within 24 hours**, or at once on restart. The app's managed identity needs **Key Vault Secrets User**.
- **Rotation patterns:** *single-credential* — replace one value; a brief failure window. *Dual-credential* — the target holds two valid credentials (two SQL logins, Storage primary/secondary keys); rotate the idle one, store it as the new version, then rotate the other. A Function triggered by `SecretNearExpiry`, with **Key Vault Secrets Officer**, automates it.

**Certificates**

| Issuance path | Who signs | Autorenew? | Policy `issuer` |
|---|---|---|---|
| Self-signed | Key Vault itself | Yes | `Self` |
| Integrated CA | ==@DigiCert or GlobalSign== (OV or EV SSL) | ==+Yes, end to end== | name of the **issuer object** you created |
| Non-integrated CA | Any other CA (including an internal enterprise CA) | ==!No== — download CSR, get it signed, **Merge Signed Request** | `Unknown` |

- The **certificate policy** holds subject and SANs, key type and size, `exportable`, `ReuseKeyOnRenewal`, and **lifetime actions**. A lifetime action has a **trigger** (percentage of lifetime, or days before expiry) and an **action**: `AutoRenew` (needs a self-signed or integrated issuer) or `EmailContacts`.
- An **issuer object** stores your CA account credentials (Certificates > Certificate Authorities). It is usable only by certificates in the same vault.
- **Certificate contacts** are ==@vault-wide==, not per certificate. They get emails before expiry and after renewal success or failure. Use a team distribution list.
- **Exportable** certificates let the private key be retrieved through the secret as PFX or PEM. **Non-exportable** keep it in the vault. Only RSA and EC software keys can be exportable; ==!HSM-backed certificate keys are always non-exportable==.
- Creation is asynchronous (HTTP 202, poll the pending operation). Each renewal is a new version.

**Roles for this work:** Crypto Officer (keys, rotation policy), Secrets Officer (write secrets), Secrets User (read secrets, including a certificate's private-key secret), Certificates Officer (certificates, issuers, contacts), Certificate User (read full certificate). Details on D1.2.3.

## Where it lives

**Azure portal > Key vaults > *vault* > Objects > Keys / Secrets / Certificates.**

- Keys → *key* → **Rotation policy** (rotation, expiry, notification, **Rotate Now**).
- Secrets → *secret* → *current version* → **Expiration date**, **Enabled**.
- Certificates → **Certificate Authorities** (issuer objects), **Certificate Contacts**, *certificate* → **Issuance Policy** (lifetime action type and trigger), **New Version**.
- **Events** → + Event Subscription (`KeyNearExpiry`, `SecretNearExpiry`, `CertificateNearExpiry`).

```bash
az keyvault key create --vault-name kv1 --name cmk-storage --kty RSA-HSM --size 3072
az keyvault key rotation-policy update --vault-name kv1 --name cmk-storage --value ./policy.json
az keyvault key rotate --vault-name kv1 --name cmk-storage
az keyvault secret set --vault-name kv1 --name db-conn --value "<conn-string>" --expires 2027-05-01T00:00:00Z
az keyvault secret set-attributes --vault-name kv1 --name db-conn --version <id> --enabled false
az keyvault certificate create --vault-name kv1 -n web-tls -p "$(az keyvault certificate get-default-policy)"
```

```json
{
  "lifetimeActions": [
    { "trigger": { "timeAfterCreate": "P18M" }, "action": { "type": "Rotate" } },
    { "trigger": { "timeBeforeExpiry": "P30D" }, "action": { "type": "Notify" } }
  ],
  "attributes": { "expiryTime": "P2Y" }
}
```

## Exam traps

- "HSM-protected AES key" → ==+Premium (oct-HSM, preview) or Managed HSM==. Standard has no HSM keys at all.
- "Expired secret is still being read" → expected. ==!Secret expiry does not block get.== Disable the version to block it.
- "Rotate a key every 3 days" → ==!not allowed==; minimum rotation time is 7 days.
- "After rotation, old data can't be decrypted" → someone ==!disabled the old version== too early.
- "Certificate from our internal CA must renew automatically in Key Vault" → ==!not possible==. Only DigiCert, GlobalSign and self-signed autorenew; the others get `EmailContacts`.
- "Set different notification recipients for one certificate" → ==!no==; contacts are per vault.
- "Need to export the private key of an RSA-HSM certificate" → ==!impossible==; choose a software key with exportable = true.
- "App picks up the new secret immediately after rotation" — not guaranteed; Key Vault references refresh within 24 hours unless the app restarts.

## Skip

- **Skip:** the JSON Web Key / JWE / JWA specification links and the algorithm list per key type (RSA-OAEP-256, ES256…). Know key types and sizes, not every algorithm.
- **Skip:** the X.509 key-usage-to-operation mapping table. One fact is enough: default key usage is DigitalSignature + KeyEncipherment.
- **Skip:** the BYOK vendor list (Thales, Entrust, Fortanix, Utimaco…). Know the KEK pattern.
- **Skip:** the dual-credential step-by-step with `db-user-a` / `db-user-b`. Know *why* (two valid credentials, no outage window) and the trigger (`SecretNearExpiry`).
- **Skip:** certificate transparency (CT) logging notes. The integrated CA handles it; no setting exists.
- **Skip:** *Storage account keys* managed by Key Vault — the feature is **deprecated**; use Entra ID authorization for Storage.
- **Skip:** quantum-safe/post-quantum notes in *About keys*.
