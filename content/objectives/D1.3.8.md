## Azure first

- A **Recovery Services vault** is the Azure resource that stores backups of VMs, SQL Server and SAP HANA in VMs, Azure Files and on-premises servers (via the **MARS** agent). A newer **Backup vault** covers other sources (disks, blobs, PostgreSQL). Both hold **recovery points** — the restorable copies.
- A **backup policy** says how often to back up and how long to keep each recovery point (**retention**).
- A **customer-managed key (CMK)** is an encryption key you own in **Azure Key Vault**; the default is a **platform-managed key (PMK)** Microsoft owns.
- **PIM** (Privileged Identity Management, Entra ID P2) grants a role for a limited time after approval.

See the Foundations pages listed above, especially *keys-secrets-and-certificates*.

## In one sentence

Azure Backup protects backups from the attacker who has stolen a backup admin's account with four layers: **soft delete** (deleted data stays recoverable 14–180 days), **immutable vault** (nobody can delete recovery points or cut retention early), **multi-user authorization** via a **Resource Guard** (a second admin must approve destructive changes), and **least-privilege backup roles** — plus optional **CMK** encryption.

## Why it exists

You have seen the ransomware playbook from the SOC side: get backup-admin credentials, disable soft delete, stop backup and delete data, delete the vault, *then* encrypt production. No backups, no recovery, pay up. These features make that playbook fail even when the attacker holds a legitimate Backup Contributor account.

## What actually matters

**1. Soft delete.** Deleted backup data (and, with secure by default, deleted vaults) enters a soft-deleted state instead of vanishing. Retention is **14 to 180 days, default 14**. You can restore it to *Stop protection with retain data*. Soft delete is now **enforced by default** ("secure by default") for Recovery Services vaults and cannot be disabled in the portal or current APIs. **Always-on** soft delete makes the setting irreversible on that vault: retention can be raised, ==!never lowered or turned off== — not even by a Global Administrator. Recovery points lost by cutting policy retention are also soft-deleted.

> **Contradiction:** the training unit says soft delete keeps data "at no extra cost". Product docs: the **first 14 days** are free; days beyond 14 are charged at normal backup rates. The secure-by-default page also calls Recovery Services vault enforcement "preview" in its introduction but "General Availability, all Azure public regions" in its region table. Plan for GA behaviour.

**2. Immutable vault.** Three states: **Disabled** (default), **Enabled** (reversible; CLI value `Unlocked`), **Enabled and Locked** (`Locked`, irreversible). While enabled it blocks: stop protection **with delete data**, modifying a policy to **reduce retention**, and swapping to a policy with **lower retention**. Increasing retention and changing the schedule stay allowed. Choose immutability **based on backup policy** (default) or **for a specific duration**. Locking also switches the storage to **WORM** (write once, read many). ==!Locked immutability blocks subscription cancellation==, because cancellation requires deleting everything first.

**3. Multi-user authorization (MUA) with Resource Guard.**

- **Resource Guard** is a separate Azure resource owned by a **security admin**. Put it in ==+the same region as the vault== but ==+a different subscription or tenant== (different tenant = maximum isolation).
- The **backup admin** gets only **Reader** on the Resource Guard (needed to link it). ==!The backup admin must not hold Contributor, Backup MUA Admin or Backup MUA Operator on the Resource Guard== — any of these lets them approve themselves.
- To run a protected operation, the backup admin requests the ==@Backup MUA Operator== role on the Resource Guard, ideally as a **PIM eligible** assignment with approval. Azure Resource Manager checks that role at the moment of the operation. The security admin holds ==@Backup MUA Admin==.
- **Mandatory** protected operations (cannot be excluded): **Disable soft delete or security features**, **Remove MUA protection**.
- **Optional** (Recovery Services vault): Delete protection, Modify protection, Modify policy, Get backup security PIN (MARS), Modify encryption settings, Stop backup and retain data, Disable immutability, Delete hybrid container — all **on** by default — and **Restore**, ==!off by default==.
- MUA protects operations on the **vault**. Changes made directly to the source resource are outside its reach.

**4. Backup roles.**

| Role | Can | Cannot |
|---|---|---|
| ==@Backup Contributor== | create and manage backups, policies, vaults | delete the vault, grant access to others |
| ==@Backup Operator== | trigger backups, restore, monitor | remove backups, manage backup policies |
| ==@Backup Reader== | view everything | change anything |

Give automation and day-to-day staff **Backup Operator**; reserve Backup Contributor for the few who configure vaults.

**5. CMK encryption.** Default is PMK (AES-256). With CMK the vault's **managed identity** (system- or user-assigned) uses an **RSA** key in a Key Vault **in the same region**. Requirements: Key Vault **soft delete and purge protection** on; identity has **Get, List, Wrap Key, Unwrap Key** (access policy) or an RBAC role carrying them. ==+Least privilege is **Key Vault Crypto Service Encryption User**== — the Backup vault CMK article requires exactly that role; the Recovery Services article's example, **Key Vault Crypto Officer**, works but grants more than needed (same rule as every service CMK identity — see [D1.2.3](D1.2.3.html)). ==!Only new Recovery Services vaults that have never had an item registered — or even attempted== — can use CMK, and ==!you cannot go back to PMK== afterwards. MARS-agent backups are not supported on a CMK vault. A CMK vault cannot move between resource groups or subscriptions.

**6. Security levels.** Resiliency in Azure (formerly Azure Business Continuity Center) grades vaults and items:

| Level | Requires |
|---|---|
| ==+Excellent== | immutability **Locked** or soft delete **always-on**, **and** MUA |
| Good | immutability Locked **or** soft delete enabled |
| Fair | MUA only |
| Poor | nothing advanced, or only reversible settings |

New vaults start at **Good**, because soft delete is enforced.

## Where it lives

- **Azure portal > Recovery Services vault > Settings > Properties**: *Soft delete* (Update: retention days, always-on), *Immutable vault* (Update: enable, lock), *Multi-User Authorization* (Update: Protect with Resource Guard), *Encryption settings* (CMK).
- **Azure portal > Resource Guards > + Create** (Protected operations tab); its **Access control (IAM)** grants Reader / Backup MUA Operator.
- **Resiliency in Azure** for security levels across vaults.

![Multi-user authorization diagram](https://learn.microsoft.com/en-us/azure/backup/media/multi-user-authorization/configure-multi-user-authorization-using-resource-guard-diagram.png){MUA flow: backup admin requests Backup MUA Operator on the Resource Guard; ARM checks it before the critical operation}

![Security level of vaults](https://learn.microsoft.com/en-us/azure/resiliency/media/security-levels-concept/security-level-vault.png){Security level per vault in Resiliency}

```bash
az backup vault create --name rsv-prod --resource-group rg-backup --location eastus \
  --immutability-state Unlocked          # Disabled | Unlocked | Locked
az backup vault backup-properties set --name rsv-prod --resource-group rg-backup \
  --soft-delete-feature-state AlwaysOn --soft-delete-duration 90
az backup vault resource-guard-mapping update --resource-group rg-backup --name rsv-prod \
  --resource-guard-id <resource-guard-id>
```

## Exam traps

- "A compromised backup admin must not be able to disable soft delete or delete backups alone" → **MUA with Resource Guard** in another subscription/tenant; backup admin has only **Reader** there.
- "Backup admin can still approve their own requests" → they hold Contributor/Backup MUA Admin/Operator on the Resource Guard.
- "Recovery points must be undeletable before retention ends, irreversibly, for WORM compliance" → **immutable vault, Locked**.
- "Restore needs approval too" → turn on the optional **Restore** operation (off by default).
- "Enable CMK on the vault that already backs up 50 VMs" → not possible; create a new vault first.
- "Revert from CMK to PMK" → not possible.
- "Excellent security level" → irreversible deletion protection **plus** MUA.
- "Runbook account needs to trigger backups and restore" → **Backup Operator**.
- "Resource Guard in another region" → not supported; same region.
