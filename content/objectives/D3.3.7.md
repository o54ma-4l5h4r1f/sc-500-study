## Azure first

- **Azure App Service** hosts web apps and APIs without you managing VMs. An **App Service plan** is the set of VMs (size, tier) your apps share.
- Every app has two sites: the **main site** (`<app>.azurewebsites.net`, your code) and the **SCM / Kudu "advanced tools" site** (`<app>.scm.azurewebsites.net`, deployment and console).
- **TLS** is the encryption under HTTPS; versions 1.0 and 1.1 are old and unsafe, 1.2 and 1.3 are current.
- **Inbound** = clients reaching your app. **Outbound** = your app calling databases, Key Vault and APIs.

See the Foundations pages listed above, especially *app-service-and-functions-basics* and *virtual-networks-and-subnets*.

## In one sentence

App Service hardening is a short checklist of platform switches — HTTPS only, minimum TLS 1.2, FTP off (or FTPS only), basic-auth publishing off, Easy Auth with Entra, managed identity plus Key Vault references, access restrictions on both the main and SCM sites (or a private endpoint), VNet integration for outbound, optional client certificates — plus Defender for App Service for threat detection.

## Why it exists

A new web app is a shop with its shutters up and its back door open. Anyone on the internet can reach the front (main site), the staff entrance (SCM site), the loading bay (FTP) and the safe code written on a sticky note (connection strings in app settings). Every one of these has a platform setting that closes it without touching code. A penetration tester's first sweep checks exactly these.

## What actually matters

**1. Transport.**

- **HTTPS Only = On**: HTTP redirects to HTTPS.
- **Minimum inbound TLS version**: ==@TLS 1.2 is the default== for new apps and SCM endpoints. Don't lower it.
- **FTP state**: **All allowed**, ==+FTPS only== (needs TLS 1.2+) or ==+Disabled==. Disable if you don't deploy by FTP.

**2. Deployment credentials.** Two switches under **Configuration > General settings**: **SCM Basic Auth Publishing Credentials** and **FTP Basic Auth Publishing Credentials**. Both are ==@off by default for new apps==. Off means FTP and Kudu/Web Deploy accept only Entra ID. Attempts are logged in `AppServiceAuditLogs`. A custom role can stop lower-privileged users re-enabling them.

**3. Authentication (Easy Auth).** Same module as Functions (D3.3.5). Microsoft provider, **Require authentication**. Worth knowing: **Allowed token audiences** (reject tokens meant for other apps) and the **token store** (lets your code read the user's tokens from headers). Easy Auth authenticates; role checks stay in code.

**4. Client certificates (mTLS).** **Client certificate mode**: **Required**, **Optional** (browsers prompt), **Optional Interactive User** (no prompt). App Service only passes the certificate to your app (`X-ARR-ClientCert` header) — ==!your code must validate it==. Exclusion paths and Optional Interactive User need TLS renegotiation, which TLS 1.3/HTTP 2 don't support.

**5. Secrets and identity.** Enable a **managed identity**, grant data roles (*Key Vault Secrets User*, *Storage Blob Data Reader*...). Replace secret app settings with `@Microsoft.KeyVault(SecretUri=...)`. Without a version, rotation is picked up within **24 hours** or at restart. A firewalled vault needs VNet integration.

**6. Inbound network.**

- **Access restrictions**: priority-ordered allow/deny by IPv4/IPv6 CIDR, **service tag** (`AzureFrontDoor.Backend`, `AzureApplicationGateway`... ) or VNet subnet (service endpoint). Lowest number wins. **Unmatched rule action** (Allow/Deny) decides the rest; adding an allow rule normally means implicit deny. Front Door rules should also filter the `X-Azure-FDID` header to *your* Front Door instance.
- **SCM site** has its own list, or tick ==@Use main site rules==. Forgetting it leaves Kudu open.
- **Private endpoint**: private IP in your VNet; set **public network access** off. ==!Access restrictions don't apply to private endpoint traffic== — use NSGs on that subnet.

**7. Outbound network: VNet integration.** Regional integration uses a subnet delegated to `Microsoft.Web/serverFarms`. Outbound only; it ==!doesn't make the app private==. Inbound privacy = private endpoint. Full isolation = **App Service Environment** (dedicated, in your VNet).

| Need | Feature |
|---|---|
| Limit who reaches the public endpoint | Access restrictions |
| No public endpoint at all | Private endpoint + public access off |
| App calls private resources | VNet integration |
| Single-tenant, fully in VNet | App Service Environment |

**8. Defender for App Service.** A Defender for Cloud plan. Monitors requests, sandboxes and management interfaces for scanners, malicious IPs on FTP, suspicious commands, crypto-mining, and alerts on **dangling DNS** when an app is deleted but its custom domain still points at it. Related: new apps get **secure unique default hostnames** (`<app>-<hash>.<region>.azurewebsites.net`) to stop subdomain takeover.

**9. Behind a WAF.** Put Application Gateway WAF or Front Door in front, then lock App Service to that path only (access restriction with the service tag, or private endpoint). Without the lock, attackers hit `azurewebsites.net` directly and ==!bypass the WAF==. WAF itself is D3.3.8.

## Where it lives

- **Azure portal > App Services > *app* > Settings > Configuration > General settings**: HTTPS Only, Minimum inbound TLS, FTP state, SCM/FTP basic auth, client certificate mode.
- **> Settings > Authentication**; **> Settings > Identity**; **> Settings > Environment variables** (Key Vault references).
- **> Settings > Networking**: Inbound — Public network access / Access restrictions (Main site and Advanced tool site tabs), Private endpoints; Outbound — Virtual network integration.
- **Microsoft Defender for Cloud > Environment settings > Defender plans > App Service**.

```bash
az webapp update -g rg -n web --https-only true
az webapp config set -g rg -n web --min-tls-version 1.2 --ftps-state FtpsOnly
az resource update -g rg --namespace Microsoft.Web --resource-type basicPublishingCredentialsPolicies \
  --parent sites/web --name scm --set properties.allow=false
az webapp config access-restriction add -g rg -n web --rule-name appgw --action Allow \
  --service-tag AzureApplicationGateway --priority 100
az webapp config access-restriction set -g rg -n web --use-same-restrictions-for-scm-site true
```

## Exam traps

- "Restrict the app to Front Door, but other customers' Front Doors share the service tag" → service tag rule **plus** `X-Azure-FDID` header filter.
- "Main site locked, Kudu still reachable" → set SCM rules or **Use main site rules**.
- Private endpoint deployed, access restriction "Deny all" also set, and private clients still get in → ==+expected==; restrictions skip private endpoint traffic.
- "App must reach a private SQL database" → VNet integration, not a private endpoint on the app.
- "Block legacy clients on TLS 1.0" → minimum TLS 1.2. Already the default; the trap is someone lowered it.
- "Stop password-based deployments" → turn off SCM and FTP basic auth publishing credentials.
- Client cert mode Required but app accepts any cert → validation is ==!app code's job==.
- "Detect a subdomain pointing at a deleted app" → Defender for App Service (dangling DNS).
