## Azure first

- Defender for Cloud plans come in two families. **CSPM** plans judge *posture* (is it configured safely?). **CWP** (cloud workload protection) plans watch *running workloads* for attacks and raise **security alerts**. Defender for Key Vault is a CWP plan.
- Plans are switched on per **subscription**. Turning on Defender for Cloud does not turn on every plan.
- An **object ID** is the unique GUID Entra ID gives every user, group, service principal and managed identity — the thing you search for when an alert names an identity.

See *defender-for-cloud-basics* in Foundations.

## In one sentence

Microsoft Defender for Key Vault is a paid Defender for Cloud plan that watches how every vault in a subscription is accessed and raises an alert when the pattern looks like stolen-credential use — a TOR exit node, a suspicious IP, a burst of secret reads, an identity that never touched the vault before.

## Why it exists

A hardened vault is usually attacked with *valid* credentials: a phished developer, a token lifted from a laptop, a client secret found in a repo. RBAC and the firewall let those requests through, because they look legitimate. Defender for Key Vault is the guard who notices that the right badge is being used at 3 a.m. from another country. As an analyst you triaged these alerts; as the engineer you are the one who turns the plan on, and makes sure the logs exist to investigate them.

## Mental model

Posture vs threat — two plans, two questions:

| | Defender CSPM secrets scanning (D1.2.6) | Defender for Key Vault |
|---|---|---|
| Question | Are secrets sitting **outside** the vault? | Is someone **abusing access** to the vault? |
| Family | CSPM (posture) | ==@CWP (threat protection)== |
| Output | Recommendations, attack paths | ==@Security alerts== (MITRE-tagged) |
| Needs | Agentless scanning | Nothing on the vault — plan On |

## What actually matters

- **Off by default. Subscription-wide. No per-vault switch.** Turn it on under the subscription's Defender plans. Every existing and future vault in that subscription is covered at once, with nothing to configure on each vault. For many subscriptions, use the built-in policy **Configure Microsoft Defender for Key Vault plan** (DeployIfNotExists) at management-group scope; **Azure Defender for Key Vault should be enabled** (AuditIfNotExists) only reports.
- **What it detects** (from the live alert reference; most are severity **Medium**, MITRE tactic **Credential Access**):

| Alert | ID | What it means |
|---|---|---|
| Access from a TOR exit node to a key vault | `KV_TORAccess` | Caller hiding behind TOR |
| Access from a suspicious IP address to a key vault | `KV_SuspiciousIPAccess` | IP flagged by Microsoft Threat Intelligence |
| Denied access from a suspicious IP to a key vault | `KV_SuspiciousIPAccessDenied` | Same, but blocked — still a signal |
| High volume of operations in a key vault | `KV_OperationVolumeAnomaly` | Bulk reads, likely exfiltration |
| Suspicious policy change and secret query in a key vault | `KV_PutGetAnomaly` | Access policy changed, then secrets read — self-granting |
| Suspicious secret listing and query in a key vault | `KV_ListGetAnomaly` | List then Get — secret dumping |
| Unusual application / user / user-application pair accessed a key vault | `KV_AppAnomaly`, `KV_UserAnomaly`, `KV_UserAppAnomaly` | Identity new to this vault |
| User accessed high volume of key vaults | `KV_AccountVolumeAnomaly` | One identity sweeping many vaults |

**Contradiction:** the training unit writes the IDs with dots (`KV.TORAccess`) and lists an "unusual application usage" alert as `KV.AnomalousAccessOperation`. The live alert reference uses underscores, and the unusual-application alert is `KV_AppAnomaly`. ==!The product reference wins.==

- **Where alerts appear:** the vault's **Security** page, Defender for Cloud **Security alerts**, and the **Workload protections** dashboard. **Email notifications** are set per subscription.
- **Suppression rules** silence a known-good pattern (a documented scanner that reads many secrets). Suppress only verified sources, and review the rules periodically.
- **The four-step response** (both docs agree):
  1. **Identify the source.** Look up the object ID / UPN / IP. ==!Never dismiss an alert because you recognise the identity== — the plan exists to catch stolen credentials. Azure VMs use Microsoft IPs, so a Microsoft IP does not mean Microsoft did it.
  2. **Respond.** Unknown IP or TOR → enable the vault firewall and allow only trusted networks (D1.2.4). Unauthorized identity → remove its role assignment in **Access control (IAM)** (or its access policy on a legacy vault, then migrate to RBAC). Identity with an Entra admin role → escalate to the identity administrator.
  3. **Measure the impact.** The alert lists the secrets and keys touched. For the full history you need the **AuditEvent** diagnostic log (D1.2.2) — ==!if it wasn't on before the alert, there is no history to query==. Defender for Key Vault itself does not require diagnostic logs to raise alerts.
  4. **Take action.** Rotate or disable every accessed secret, key and certificate. Tell the application owners the compromise window. Watch the vault closely for 48–72 hours.
- **Pair it with posture.** Recommendations such as *Key vaults should have soft delete enabled*, *…purge protection enabled* and *Diagnostic logs in Key Vault should be enabled* shrink the blast radius the alerts warn you about.

## Where it lives

- **Azure portal > Microsoft Defender for Cloud > Environment settings > *subscription* > Defender plans** → **Key Vault** row → **On** → **Save**.
- **… > Environment settings > *subscription* > Email notifications** — who gets alert emails.
- **Microsoft Defender for Cloud > Security alerts** → select an alert → **Take action** / **Suppress similar alerts**.
- **Azure portal > Key vaults > *vault* > Security** — alerts for that one vault.

```bash
az security pricing create --name KeyVaults --tier Standard   # turn the plan on for the current subscription
az security pricing show --name KeyVaults
```

## Exam traps

- "Defender for Cloud is enabled, but no Key Vault alerts ever appear" → the ==!Key Vault plan is a separate toggle== and is off by default.
- "Enable Defender for Key Vault on just one vault" → ==!not possible==; it is per subscription.
- "Detect secrets stored in VM config files" → that is ==+Defender CSPM secrets scanning==, not Defender for Key Vault.
- "Alert from a known service principal — close it as benign" → ==!verify with the owner first==.
- "Investigate which secrets the attacker read over the last 30 days" → needs ==+AuditEvent logs already flowing== to Log Analytics; the alert alone shows only the objects in that alert.
- "Stop an active attack from a TOR IP fastest" → ==+vault firewall== (network), then remove access (identity), then rotate.
- Role-assignment changes made by the attacker on an RBAC vault are in the ==@Activity log==, not AuditEvent.

## Skip

- **Skip:** Defender for Key Vault pricing (per-transaction billing) — reference-page material.
- **Skip:** the techcommunity "validate threat detection" simulation walkthrough. Useful in a lab, not tested.
- **Skip:** memorising every alert's severity. Know the families (suspicious IP/TOR, volume anomaly, put-get, list-get, unusual identity) and that they map to Credential Access.
- **Skip:** the unit's AI-agent asides (agents authenticate as service principals or managed identities). Same investigation steps; nothing new to configure.
- **Skip:** SOC-side triage depth (KQL hunting across other services, lateral movement tracing). You already do that; the engineer's job is to make the logs exist.
