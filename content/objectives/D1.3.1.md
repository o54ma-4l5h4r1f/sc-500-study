## Azure first

- **Azure Resource Manager (ARM)** is the front door for every create, update and delete in Azure. Portal clicks, `az` commands, Bicep and Terraform all end up as a request to ARM. Azure Policy sits inside that front door.
- The **resource hierarchy** is management group → subscription → resource group → resource. Anything you attach at a higher level flows down to everything below it.
- A **managed identity** is an identity Azure creates for a resource (here, for a policy assignment) so it can act without a password. It still needs Azure role assignments, like any user.
- **JSON** is the text format policy rules are written in: `{ "name": value }` pairs, nested.

See the Foundations pages listed above, especially *azure-policy-basics*.

## In one sentence

Azure Policy is a rule engine inside Azure Resource Manager: each **definition** is a JSON `if`/`then` rule, you **assign** it to a scope, and its **effect** decides whether a non-matching resource is blocked, logged, changed, or fixed by a deployment.

## Why it exists

RBAC answers *who* can create a storage account. It cannot say *what kind* of storage account they may create. A Contributor can legally build one that allows HTTP and public blob access. Policy closes that gap. It is the building code inspector who checks every plan at the permit desk, whoever the builder is.

As an analyst you saw the aftermath: a public storage account in an incident. As an engineer you write the rule that stops it being created.

## Mental model

Every create or update request passes a checkpoint. Policy runs its effects in a fixed order, then lets the request through to the resource provider (the service that actually builds the thing). Two effects run *after* the resource exists.

## What actually matters

**1. The definition is JSON with three working parts.**

```json
{
  "mode": "Indexed",
  "parameters": {
    "effect": { "type": "String", "allowedValues": ["Audit", "Deny", "Disabled"], "defaultValue": "Audit" }
  },
  "policyRule": {
    "if": {
      "allOf": [
        { "field": "type", "equals": "Microsoft.Storage/storageAccounts" },
        { "field": "Microsoft.Storage/storageAccounts/supportsHttpsTrafficOnly", "notEquals": true }
      ]
    },
    "then": { "effect": "[parameters('effect')]" }
  }
}
```

- `mode` picks which resource types are evaluated. ==@All== evaluates resource groups, subscriptions and every type; ==@Indexed== evaluates only types that support tags and location. Use Indexed for tag/location rules on ordinary resources. A tag or location rule *on a resource group or subscription* uses All. Portal-created definitions use All. Resource Provider modes (`Microsoft.Kubernetes.Data`, `Microsoft.KeyVault.Data`, `Microsoft.Network.Data`) evaluate inside a service, such as pods in AKS or keys in a vault.
- `parameters` make one definition reusable. Types include String, Array, Object, Boolean, Integer, Float and DateTime. `allowedValues` limits the choices. Reference one with `[parameters('name')]`.
- `policyRule` has `if` (conditions joined by `allOf`, `anyOf`, `not`) and `then` (the effect, plus `details` for the effects that need them).

**2. Aliases are how a rule reads a property.** An **alias** is a stable name for one resource property, such as `Microsoft.Storage/storageAccounts/supportsHttpsTrafficOnly`. A `field` must be a built-in field (`type`, `name`, `location`, `tags`) or a real alias. ==!A property path from the resource's JSON is not automatically an alias.== Array aliases end in `[*]`. `modify` can only change properties whose alias is marked **Modifiable**.

**3. Know every effect, and which can fix things.**

| Effect | What it does | Fixes existing resources? |
|---|---|---|
| `audit` | marks non-compliant, allows the request | no |
| `auditIfNotExists` | audits a **related** resource (an extension, a diagnostic setting) | no |
| `deny` | blocks the create/update at ARM | no — never repairs what exists |
| `denyAction` | blocks **DELETE** requests on matching resources | no |
| `append` | adds fields to the request | no (Resource Manager modes only) |
| `modify` | adds/replaces/removes tags; adds/replaces Modifiable properties | ==+yes, via remediation task== |
| `deployIfNotExists` | deploys a template when the related resource is missing | ==+yes, via remediation task== |
| `manual` | you attest compliance by hand | no |
| `disabled` | rule off; useful as a parameter value | — |
| `mutate`, `addToNetworkGroup` | AKS add-on mutation; Virtual Network Manager group membership | — |

`audit`/`deny`/`modify` are often interchangeable as parameter values. `auditIfNotExists`/`deployIfNotExists` are interchangeable. ==!An effect parameter does not make an unsupported effect valid== — `auditIfNotExists` needs `details` that `audit` lacks.

**4. Initiatives, assignments, exclusions, exemptions.**

- An **initiative** (policy set, `policySetDefinitions`) bundles definitions into one assignable unit. Each member has a `policyDefinitionReferenceId`. The **Microsoft cloud security benchmark** initiative is the big built-in one; Defender for Cloud assigns it by default.
- A definition is saved at a **management group or subscription** (its *location*). It can be assigned only at that scope or below. Saving a definition enforces nothing.
- An **assignment** sets the scope, parameter values, `notScopes`, **enforcement mode**, a non-compliance message (shown when `deny` blocks), and — for `modify`/`deployIfNotExists` — a **managed identity** and its location.
- **Enforcement mode `DoNotEnforce`** (portal: "Disabled") still evaluates and reports compliance, but no effect is applied and nothing is written to the Activity log. ==!It is not the same as the effect `disabled`==, which stops evaluation of that rule.
- **Exclusion** (`notScopes`) removes a child scope from the assignment entirely; it is not evaluated or counted. **Exemption** keeps the resource in scope but marks it **Exempt**, with category ==@Waiver== (risk accepted) or ==@Mitigated== (another control meets the intent), optional `expiresOn`, and optional `policyDefinitionReferenceIds` for one initiative member. An exemption applies to **one assignment** only.
- Overlapping assignments are each evaluated on their own. The result is **cumulative most restrictive**. A child-scope Audit assignment never cancels a parent-scope Deny. ==!More RBAC rights never override a policy deny.==

- Only ==+`deployIfNotExists` and `modify`== can be remediated. `audit` and `auditIfNotExists` cannot.
- The definition's `roleDefinitionIds` lists the roles the identity needs. ==!That list is not itself a grant.== The portal creates the role assignments only if *you* may assign roles; scripts and SDKs do not.
- A remediation task targets **one** definition (one reference ID inside an initiative). Defaults: `resourceCount` 500 (max 50,000), `parallelDeployments` 10 (1–30). Task records are deleted 60 days after their last change. Cancelling a task does not roll back what it already deployed.

**6. Timing.** A new assignment takes about **5 minutes** to apply, then evaluation starts. A created or updated resource shows its result about **15 minutes** later. Every assignment is re-evaluated once every **24 hours**. Start an on-demand scan with `az policy state trigger-scan` (subscription or resource group; asynchronous).

**7. Who can do it.** ==@Resource Policy Contributor== (or Owner) creates definitions and assignments. ==!Contributor cannot== — it excludes `Microsoft.Authorization/*/write`. Attaching a user-assigned identity also needs `Microsoft.ManagedIdentity/userAssignedIdentities/assign/action` (for example **Managed Identity Operator**). Creating an exemption needs `Microsoft.Authorization/policyExemptions/write` plus `Microsoft.Authorization/policyAssignments/exempt/action`.

## Where it lives

**Azure portal > Policy** (search "Policy"). *Authoring > Definitions* (filter Category, open the JSON tab, *+ Policy definition*, *+ Initiative definition*); *Authoring > Assignments* (*Assign policy*, *Assign initiative*); *Compliance*; *Remediation*; *Exemptions*.

![Policy compliance page](https://learn.microsoft.com/en-us/azure/governance/policy/media/getting-compliance-data/compliance-page-small.png){Policy > Compliance: one row per assignment, filterable by scope, type and state}

![Remediation tab on a policy assignment](https://learn.microsoft.com/en-us/azure/governance/policy/media/remediate-resources/remediation-tab.png){Assignment > Remediation tab: system-assigned identity in a region, with the role (here Log Analytics Contributor) taken from roleDefinitionIds}

```bash
# Built-in definition, assigned at resource-group scope, with an effect parameter
az policy assignment create --name require-https \
  --policy "404c3081-a854-4457-ae30-26a93ef643f9" \
  --scope /subscriptions/<sub>/resourceGroups/rg-lab \
  --params '{"effect":{"value":"Deny"}}'

# Custom definition from a rules file + parameters file
az policy definition create --name https-only --mode Indexed \
  --rules policy.rules.json --params policy.parameters.json

# Assignment that can remediate: needs an identity and its location
az policy assignment create --name kv-diag --policy <definition-id> \
  --scope /subscriptions/<sub> --mi-system-assigned --location eastus

az policy remediation create --name fix-kv-diag --policy-assignment kv-diag
az policy state trigger-scan --resource-group rg-lab
az policy exemption create --name waiver1 --scope <resource-id> \
  --policy-assignment <assignment-id> --exemption-category Waiver --expires-on 2027-01-31T00:00:00Z
```

Find aliases with `az provider show --namespace Microsoft.Storage --expand "resourceTypes/aliases"` or by hovering in the Azure Policy extension for VS Code.

![Azure Policy extension for VS Code showing alias names](https://learn.microsoft.com/en-us/azure/governance/policy/media/extension-for-vscode/extension-hover-shows-property-alias.png){Hover a property in VS Code to see its alias names}

## Exam traps

- "Existing non-compliant storage accounts must be fixed" → ==+`modify` or `deployIfNotExists` + remediation task==. ==!Changing the assignment to Deny fixes nothing that already exists.==
- "Block creation" → `deny`. "Report only" → `audit`. "Check a child/extension resource (a VM extension, diagnostic setting)" → `auditIfNotExists`. "Stop deletion without a lock" → `denyAction`.
- `DoNotEnforce` vs `disabled`: the first tests impact while still reporting; the second switches the rule off.
- Exclusion vs exemption: excluded = not evaluated, not counted. Exempt = evaluated, counted as **Exempt**, carries a category and expiry. Exemption = one assignment.
- A Deny at the subscription and an Audit at a resource group: the Deny still wins. Two conflicting Denies (allowed region A vs allowed region B) can block everything.
- Custom definition saved in subscription A cannot be assigned in subscription B. Save it at a management group above both.
- Tag rule on resource groups uses mode **All**, not Indexed.
- Remediation fails with permission errors → the assignment's **managed identity** lacks the role, not you.
- An exemption is not proof of compliance; Compliance substate shows what the state would be without it.
