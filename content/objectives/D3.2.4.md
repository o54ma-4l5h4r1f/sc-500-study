## Azure first

- Azure can only govern things that exist as **Azure resources** (an object with a resource ID inside a subscription and resource group). An on-premises server or an AWS EC2 instance isn't one.
- **Azure Arc-enabled servers** fix that. You install the **Azure Connected Machine agent** on the machine. The machine then appears in Azure as a resource of type `Microsoft.HybridCompute/machines`.
- A **VM extension** is a small add-on program Azure pushes into a machine (Defender for Endpoint, Azure Monitor Agent, Machine Configuration). It runs as SYSTEM/root.
- A **service principal** is a non-human identity in Microsoft Entra ID that scripts use to sign in. A **managed identity** is an identity Azure creates and rotates for a resource.

See the Foundations pages listed above, especially *azure-arc-and-hybrid-machines*.

## In one sentence

Azure Arc puts an agent on servers outside Azure (on-premises, AWS, GCP) so each becomes an Azure resource that Azure RBAC, Azure Policy, VM extensions and Defender for Cloud can manage like an Azure VM, and the agent itself can be locked down locally so cloud admins can't push arbitrary code.

## Why it exists

Your Azure controls stop at the Azure boundary. The factory file server in the basement and the EC2 instances in AWS have no API Defender for Cloud can call. Arc is a **consular badge**: the server stays where it is, but carries an Azure identity and obeys Azure rules. As an analyst you have seen Defender alerts on "Machines - Azure Arc". This is how those machines got there.

The second half of the story is risk. Anyone who can push an extension can run code as root on that server. Arc therefore gives the server owner a **local veto**: an allow list that no Azure Owner or Global Administrator can override.

## What actually matters

**1. The agent.** The **Azure Connected Machine agent** has three parts that matter:

- **HIMDS** (Hybrid Instance Metadata service): holds the connection and the machine's Azure identity. Every Arc server gets a **system-assigned managed identity**, which extensions such as Azure Monitor Agent use instead of keys.
- **Extension agent**: installs, updates and removes extensions. Each package is checked against a signed catalog before it runs.
- **Machine configuration agent**: runs Azure Policy guest assignments (formerly *Guest Configuration*). A disconnected machine keeps its assignments for **14 days**.

Traffic is **outbound HTTPS 443 only**, optionally through a proxy, the Arc gateway or **Azure Arc Private Link Scope** (private endpoints). You ==!can't install the agent on an Azure VM==; the script detects Azure and rolls back.

**2. Onboarding methods.**

| Method | Scale | Notes |
|---|---|---|
| Portal-generated script (Azure Arc > Machines > Add, or Defender for Cloud > Environment settings > On-premises servers) | One or a few | Run as local admin; interactive sign-in |
| ==@Service principal== script | At scale | SP holds ==@Azure Connected Machine Onboarding==; push the script with ==@Group Policy, Configuration Manager, Ansible== or similar |
| PowerShell, Windows Admin Center, Azure Arc setup (Windows Server) | One or many | Variants of the above |
| Arc-enabled VMware vSphere / SCVMM | At scale | Discovers VMs and installs the agent (needs VMware Tools) |
| ==@Defender for Cloud AWS / GCP connector== (auto-provisioning) | At scale | Installs Arc on EC2 / GCP VMs automatically. Needs **Owner** on the Azure subscription; AWS needs the SSM agent |
| Multicloud connector enabled by Azure Arc | At scale | Same idea from the Arc side; can run alongside the Defender connector |

For AWS and GCP, Arc resources whose source VM is gone (or that sit Disconnected/Expired) are removed after **7 days**. Connector details belong to D4.1.4.

**3. Two RBAC roles, very different power.**

| Role | Onboard new servers | Change/delete existing | Deploy extensions |
|---|---|---|---|
| ==@Azure Connected Machine Onboarding== | Yes | No | ==!No== |
| ==@Azure Connected Machine Resource Administrator== | Yes | Yes | ==!Yes — effectively root/admin on the server== |

Give automation the Onboarding role. Give humans Resource Administrator through PIM.

**4. Local agent controls (the local veto).** Set with `azcmagent config` **on the server itself**. They ==!can't be changed from Azure==, even by Owner or Global Administrator.

| Setting | Effect |
|---|---|
| `extensions.allowlist "Publisher/Type,..."` | ==+Only== listed extensions can install, update or upgrade. Preferred, because new extensions are blocked by default |
| `extensions.blocklist "Publisher/Type,..."` | Listed extensions blocked; everything else allowed |
| `extensions.allowlist "Allow/None"` | Agent runs but no extensions at all (e.g. Arc used only for Windows Server 2012 Extended Security Updates) |
| `config.mode monitor` | Only Microsoft-maintained monitoring/security extensions (AMA, Defender); blocks script-running extensions; ==!disables machine configuration==; you ==!can't edit allow/block lists== in this mode |
| `config.mode full` | Default; everything allowed unless lists say otherwise |
| `guestconfiguration.enabled false` | Turns off machine configuration (guest) policies |
| `extensions.enabled false` | Turns off the extension manager entirely |

Rules to remember: ==@delete is always allowed== (so you can remove a bad extension). Extensions already installed ==!aren't removed== when you add a list. An extension in both lists is blocked. With no list configured, everything is allowed. Block the Custom Script Extension and Run Command unless you need them. Anyone who is local admin/root can still change these settings.

**5. Azure Policy on Arc servers.** Arc servers are ordinary resources, so assign policies at management group or subscription scope. Key built-ins named in the training:

- *Configure Azure Defender for Servers to be enabled (with 'P1' subplan) for all resources* (DeployIfNotExists).
- *Configure ChangeTracking Extension for Windows/Linux Arc machines* (for File Integrity Monitoring).
- *Windows/Linux machines should meet requirements of the Azure compute security baseline* (Machine Configuration; see D3.2.9).

DeployIfNotExists fixes new machines automatically. Machines that existed before the assignment need a ==@remediation task==. The assignment's managed identity needs rights to deploy the extension. A policy written for `Microsoft.Compute/virtualMachines` shows Arc machines as *Not applicable*. Policy is cloud-side and editable by anyone with `policyAssignments/write`, so pair it with the local allow list.

**6. Defender for Cloud on Arc.** Arc machines appear in **Inventory** as *Machines - Azure Arc*. They count in secure score, get recommendations and regulatory compliance, and get Defender for Servers coverage when the plan is on for that subscription (see D3.2.5). Not everything carries over:

| Feature | Azure VM | Arc server (on-prem) |
|---|---|---|
| Defender for Endpoint, alerts, FIM, compliance | Yes | Yes |
| Just-in-time VM access | Yes | ==!No== (no NSG) |
| Agentless scanning | Yes | ==!No== (Azure, AWS, GCP only) |
| Network-based alerts | Yes | No |

Without Arc, a server onboarded directly to Defender for Endpoint (**Direct onboarding**) still gets Plan 1 features plus only a subset of Plan 2; Arc-dependent Plan 2 features, Azure Policy and Machine Configuration need Arc.

## Where it lives

- **Azure portal > Azure Arc > Azure Arc resources > Machines > Add/Create > Add a single server / Add multiple servers**.
- **Azure portal > Microsoft Defender for Cloud > Environment settings > Add environment > On-premises servers** (same script), or **> Amazon Web Services / Google Cloud Platform** (connector with Arc auto-provisioning).
- **Azure portal > Azure Arc > Machines > *server* > Extensions**, **> Policies**, **> Security**.
- **Azure portal > Policy > Assignments** (scope a management group); **Remediation** for existing machines.
- **On the server:** `azcmagent` CLI.

```bash
# at-scale onboarding with a service principal (run by GPO/ConfigMgr/Ansible)
azcmagent connect --service-principal-id <appId> --service-principal-secret <secret> \
  --tenant-id <tenant> --subscription-id <sub> --resource-group rg-arc-dc1 --location westeurope

# lock the agent down locally
azcmagent config set extensions.allowlist "Microsoft.Azure.Monitor/AzureMonitorWindowsAgent,Microsoft.Azure.AzureDefenderForServers/MDE.Windows"
azcmagent config set config.mode monitor
azcmagent config list
```

## Exam traps

- "Prevent even a subscription Owner from installing extensions on this domain controller" → ==+local allow list via azcmagent==. Azure Policy and RBAC are distractors: both can be changed by a privileged cloud admin.
- "Service principal for mass onboarding, least privilege" → ==+Azure Connected Machine Onboarding==, not Resource Administrator or Contributor.
- Monitor mode + Machine Configuration baseline policies → ==!conflict==. Monitor mode turns machine configuration off. Use full mode with your own allow list.
- Allow list added, but an old extension is still there → lists don't uninstall. Delete it from Azure.
- "Onboard 500 on-prem servers" → service principal script pushed by GPO / Configuration Manager / Ansible, not 500 interactive scripts.
- "Onboard EC2 instances to Defender for Servers" → AWS connector with ==+Arc auto-provisioning== (needs subscription Owner and the SSM agent).
- Installing Arc on an Azure VM to "standardise" → ==!unsupported==.
- DeployIfNotExists assigned, existing servers still non-compliant → create a ==+remediation task==.
- "Use JIT for on-prem Arc servers" → ==!not available==.
