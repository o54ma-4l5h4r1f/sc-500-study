## Azure first

- A **virtual machine (VM)** boots from an **OS disk** and stores data on **data disks**. Both are **managed disks**: Azure-run storage objects you never see as files.
- A VM also gets a **temporary (temp) disk** on the physical server it runs on, plus a **disk cache** that speeds up reads and writes. Temp disk and cache are ==not== managed disks.
- A **key** in **Azure Key Vault** (or Key Vault **Managed HSM**) can wrap other keys. A **platform-managed key (PMK)** is one Microsoft holds. A **customer-managed key (CMK)** is one you hold in your vault.
- A **managed identity** is an identity Azure creates for a resource so it can call other Azure services without a password.

Before you start: Foundations **virtual-machines-and-disks**, **keys-secrets-and-certificates**, **azure-policy-basics**, **defender-for-cloud-basics**.

## In one sentence

Azure has four ways to encrypt VM disks — **server-side encryption (SSE)**, **encryption at host**, **Azure Disk Encryption (ADE)** and **confidential disk encryption** — and the exam wants you to pick the right one for the requirement, knowing that ==!ADE retires on September 15, 2028== and ==+encryption at host is the replacement==.

## Why it exists

Think of a filing room. SSE locks every filing cabinet (the managed disks) automatically. But clerks also leave papers on their desks (the temp disk) and in the out-tray (the cache). SSE does not lock those. Encryption at host locks the desks and trays too, in the building where the clerk sits. ADE hires a guard inside each office to lock things, using the office's own staff time. Confidential disk encryption builds a sealed office whose key only works inside that one office.

An auditor's question is usually one of three: *is everything encrypted* (temp disk, cache)? *who holds the key* (PMK or CMK)? *can even the cloud operator read it*? Each option answers those differently.

Two separate questions: **what is covered** (managed disks only, or temp disk and cache too) and **who holds the key** (PMK by default, CMK through a **disk encryption set**).

## What actually matters

**1. SSE is always on.** Every managed disk, snapshot and image is encrypted at rest with 256-bit AES by default, at no extra cost, using a PMK. It does ==!not== encrypt temp disks or disk caches.

**2. CMK goes through a disk encryption set (DES).** A DES is an Azure resource that points at one key in Key Vault or Managed HSM. Creating it creates a **system-assigned managed identity**. You grant that identity `get`, `wrapKey` and `unwrapKey` on the key (the portal banner does this for you). Disks then use **envelope encryption**: a data encryption key (DEK) encrypts the data, and your key wraps the DEK. Rules worth memorising:

- Key Vault and DES must be in the ==@same region== as the disks; the vault may be in another subscription.
- The vault must have **soft delete** and **purge protection** on.
- Only RSA keys of 2,048, 3,072 or 4,096 bits.
- Turn on **Auto key rotation** on the DES: disks move to the new key version within one hour, with no VM reboot.
- If the key is disabled, deleted or expires, VMs using it ==!shut down== and won't boot until the key is back. Disk I/O starts failing about one hour after.
- A DES's encryption type can't be changed after creation.

**3. Encryption at host closes the gap.** The server hosting your VM encrypts the temp disk and caches, and data flows encrypted to storage. It does not use the VM's CPU. Facts:

- You must first register the feature `EncryptionAtHost` in namespace `Microsoft.Compute` on the subscription.
- Existing VMs must be **deallocated** to turn it on (or off).
- Temp disks and ephemeral OS disks are encrypted with ==@platform-managed keys only==. Caches follow the disk's key type (PMK or CMK).
- It ==!can't be enabled on a VM that has ever had ADE==.

**4. ADE is legacy and retiring.** ADE encrypts inside the guest with **BitLocker** (Windows) or **DM-Crypt** (Linux), storing secrets in Key Vault, optionally wrapped by a **key encryption key (KEK)**. It uses the VM's CPU and doesn't work with custom Linux images. On ==!September 15, 2028== ADE disks will fail to unlock after a reboot. Microsoft's replacement: ==+encryption at host== for new VMs, or confidential VMs for confidential workloads. There is ==!no in-place conversion==: you build new disks and a new VM. Linux ADE OS disks can't be decrypted at all — build a new VM.

**5. Confidential disk encryption binds the OS disk key to the VM's vTPM.** Only on **confidential VMs** (AMD SEV-SNP or Intel TDX hardware, security type chosen at creation). The key is released only to that VM after attestation, bypassing the hypervisor and host OS. Options: `DiskWithVMGuestState` (encrypt the OS disk) or `VMGuestStateOnly` (encrypt only the small VM guest state blob). CMK uses a DES of type `ConfidentialVmEncryptedWithCustomerKey`. It covers the ==@OS disk only==; use encryption at host for data disks. Temp disk encryption is opt-in. The setting can't be changed after deployment.

**6. Double encryption at rest** adds a second platform-key layer with a different algorithm on persisted disks. Not supported on Ultra Disks or Premium SSD v2.

### Decision table

| | SSE (default) | Encryption at host | ADE (retiring) | Confidential disk encryption |
|---|---|---|---|---|
| OS + data disks at rest | Yes | Yes | Yes | OS disk only |
| Temp disk | ==!No== | Yes (PMK only) | Yes | Opt-in |
| Caches / compute-to-storage flow | No | Yes | Yes | Yes |
| Customer key control | With DES | With DES | With KEK | With DES |
| Uses VM CPU | No | No | Yes | Yes |
| Defender for Cloud status | Unhealthy | Healthy | Healthy | No recommendation |
| Pick it when | baseline only | ==+default answer for "encrypt everything"== | ==!never for new VMs== | protect from operator/insider |

## Where it lives

All in the **Azure portal**:

- `Azure portal > Disk Encryption Sets > + Create` — encryption type, key vault, key, **Auto key rotation**. Then select the banner to grant the DES access to the vault.
- `Azure portal > Virtual machines > Create > Disks` — **Encryption at host** checkbox, **Key management** (PMK / CMK + DES).
- Existing VM: stop it, then `Virtual machines > (your VM) > Disks > Additional settings > Encryption at host`.
- Confidential: `Virtual machines > Create > Basics > Security type = Confidential virtual machines`, then `Disks > Confidential OS disk encryption`.

```bash
az feature register --name EncryptionAtHost --namespace Microsoft.Compute
az vm deallocate -g rg -n vm1
az vm update -g rg -n vm1 --set securityProfile.encryptionAtHost=true
az vm start -g rg -n vm1
az vm show -g rg -n vm1 --query securityProfile.encryptionAtHost
```

![Customer-managed key workflow for managed disks](https://learn.microsoft.com/en-us/azure/virtual-machines/media/disk-encryption/customer-managed-keys-sse-managed-disks-workflow.svg){Key Vault admin creates the key → DES gets a managed identity → identity is granted key access → disks use the DES to wrap and unwrap their data keys}

**Policy and Defender for Cloud.** `Windows virtual machines should enable Azure Disk Encryption or EncryptionAtHost` and the Linux twin are **AuditIfNotExists** — they report, they don't block. `Virtual machines and virtual machine scale sets should have encryption at host enabled` detects only encryption at host. Defender for Cloud plans are covered in [D4.1.3](D4.1.3.html).

## Exam traps

- "Encrypt the temp disk and caches with no in-guest agent" → ==+encryption at host==, not ADE, not "SSE with CMK". SSE + CMK still leaves the temp disk unencrypted.
- "Customer controls the key" is ==@not an encryption type==. It's a DES added to SSE, encryption at host or confidential disk encryption.
- Encryption at host with CMK does ==!not== put the temp disk under your key. Temp disk is always PMK.
- Deleting or disabling the CMK stops the VM. That is the "crypto-shred / revoke access" answer, and also the outage trap.
- The DES needs its **own managed identity** granted on the vault. A missing grant is the classic "can't attach disk" fault.
- Key Vault in a **different region** from the disks → fails. Different subscription → fine.
- ADE and encryption at host are ==!mutually exclusive==, even on a VM that only *used to* have ADE.
- "Migrate ADE to encryption at host in place" → impossible. New disks, new VM.
- Confidential VM: you can't convert an existing Standard or Trusted launch VM. Security type is fixed at creation.
- The two "ADE or EncryptionAtHost" policies **audit**; they won't enable anything.

- **Skip:** units 1, 5 and 6 of *Implement disk encryption for Azure virtual machines* (introduction, knowledge check, summary).

> **Module vs product docs.** Unit 4 says you "can't create snapshots of confidential OS disks". The confidential VM docs list a **managed OS disk snapshot** as a valid image source, and Azure Backup for confidential VMs is in preview (v6 sizes). The product docs win. For the exam, remember that a confidential OS disk can't be attached to a different VM.
