## Azure first

- A **storage account** is one Azure resource that holds four data services: **Blob** (files/objects in *containers*), **Azure Files** (SMB/NFS shares), **Queue** and **Table**. Each has its own public URL, such as `https://contoso.blob.core.windows.net`.
- The account has a **management plane** (the account's settings, changed through Azure Resource Manager) and a **data plane** (reading and writing the blobs themselves). Most settings on this page are management-plane switches under **Settings > Configuration**.
- Every account comes with two **account keys**. A key is a master password for all data in the account. Using a key to sign a request is called **Shared Key authorization**.
- **Azure Key Vault** stores cryptographic keys. A **customer-managed key (CMK)** is a key you own in Key Vault that Azure uses to wrap the account's own encryption key.
- **Azure Policy** audits or blocks resource settings across a subscription.

Read first: storage-accounts-basics, keys-secrets-and-certificates, azure-policy-basics, azure-rbac-and-entra-roles.

## In one sentence

Storage account security configuration is a short list of account-wide switches: force HTTPS and TLS 1.2, block anonymous blob reads, turn off the account keys, block cross-tenant replication, and pick who owns the encryption key.

## Why it exists

A storage account is reachable from the whole internet by default. A leaked account key in a config file is a full read-write-delete pass to every blob, share, queue and table. As an analyst you have triaged the result: a "public container" incident, or an attacker listing blobs with a stolen connection string.

These switches close the doors that are open by default or were opened years ago. New accounts are safer than old ones, so the exam loves "an existing account created before the default changed".

## Mental model

Think of the account as a **warehouse with a loading dock**. Secure transfer and minimum TLS decide *what kind of truck* may pull in (armoured only). Anonymous access and Shared Key decide *who may sign for a parcel*: nobody without ID, and nobody waving the master key. Cross-tenant replication decides whether a conveyor belt may run to another company's warehouse. Encryption at rest is the safe the parcels sit in; CMK means you hold the safe's key, and infrastructure encryption is a second safe around the first.

## What actually matters

| Setting (portal label) | Property | Default | Safe value |
|---|---|---|---|
| Secure transfer required | `supportsHttpsTrafficOnly` | ==@Enabled== on new accounts | Enabled (HTTP rejected) |
| Minimum TLS version | `minimumTlsVersion` | 1.2 in the portal; property may be unset from CLI/PowerShell/ARM — but since 3 Feb 2026 the service rejects TLS 1.0/1.1 on every account | Version 1.2 |
| Allow Blob anonymous access | `allowBlobPublicAccess` | Disabled on new ARM accounts | Disabled (overrides every container) |
| Allow storage account key access | `allowSharedKeyAccess` | ==!null = allowed== | Disabled after migration |
| Allow cross-tenant replication | `allowCrossTenantReplication` | false for new accounts; old accounts may allow it | Disabled unless needed |
| Infrastructure encryption | `requireInfrastructureEncryption` | Off | On only for double-encryption compliance |

1. **Secure transfer** rejects any REST call over HTTP. It does not apply the same way to Azure Files, which uses its own SMB/NFS encryption-in-transit settings.
2. **Minimum TLS.** Storage accepts TLS 1.2 and 1.3, but ==!you cannot set 1.3 as the minimum==. Valid values are `TLS1_0`, `TLS1_1`, `TLS1_2`. ==!Dated fact:== on **3 February 2026** Azure Storage stopped supporting TLS 1.0 and 1.1 for **all existing and new accounts**; TLS 1.2 is now the floor whatever the property says ([migration article](https://learn.microsoft.com/azure/storage/common/transport-layer-security-configure-migrate-to-tls2)). The older configure article still has a sentence saying an unset property "permits TLS 1.0" — the retirement article supersedes it. Still set `TLS1_2` explicitly and enforce it with Azure Policy: the property is what Policy and Defender audit. A request below the minimum fails with HTTP 400. Before raising it, log the TLS version clients use (`StorageBlobLogs` in Log Analytics).
3. **Anonymous access has two layers.** The account switch and each container's access level (**Private**, **Blob**, **Container**). The account switch wins: when it is off, a container set to *Container* is still private. Anyone with `Microsoft.Storage/storageAccounts/write` (Owner, Contributor, **Storage Account Contributor**) can flip it.
4. **Disable Shared Key** only after you migrate clients. Find them with the **Transactions** metric split by **Authentication type = AccountKey/SAS**, or `StorageBlobLogs` by `AuthenticationType`. After disabling, account keys, **service SAS** and **account SAS** get HTTP 403; **user delegation SAS** and Microsoft Entra ID keep working (see D2.1.4). Watch Azure Files: the portal reaches file shares with Shared Key by default.
5. **Enforce at scale** with the built-in policy ==@Storage accounts should prevent shared key access==: assign with **Audit** first, then switch to **Deny**. Deny blocks new or re-enabled accounts; it ==!does not fix existing accounts== (remediate them yourself).
6. **Encryption at rest is always on.** Every account uses 256-bit AES service-level encryption with **Microsoft-managed keys** by default. Your options:
   - **Customer-managed key (CMK)** in Key Vault or Managed HSM. Azure Storage wraps the account encryption key with it. Requirements: ==@soft delete and purge protection on the vault==, an **RSA or RSA-HSM** key, and a managed identity with **get, wrapkey, unwrapkey**. At account creation you must use a **user-assigned** identity; on an existing account either type works. Omit the key version to have Storage pick up new versions automatically (it checks once a day). Queue and Table are only covered by CMK if you choose that at creation.
   - **Customer-provided key** is sent by the client on each Blob request. Different thing; Microsoft never stores it.
   - **Encryption scopes** let one container or blob use a different key from the rest of the account.
   - **Infrastructure encryption** adds a second AES-256 layer with a separate Microsoft-managed key. It can only be set ==!when the account is created== (general-purpose v2, premium block blob, premium page blob).

**Data-protection one-liners** (taught in docs, not in the mapped units):

- **Blob soft delete** keeps deleted or overwritten blobs for **1–365 days**. **Container soft delete** is a separate switch.
- **Immutable storage (WORM)** has **time-based retention** (1 to 146,000 days) and **legal hold**. A *locked* time-based policy can be extended but never shortened. Used for audit-log archives (D2.2.2).

## Where it lives

All in the **Azure portal**, on the storage account.

| Task | Path |
|---|---|
| HTTPS, TLS, anonymous, Shared Key, cross-tenant | `Storage account > Settings > Configuration` |
| Infrastructure encryption | `Create storage account > Encryption` tab (creation only) |
| CMK / encryption scopes | `Storage account > Security + networking > Encryption` |
| Soft delete | `Storage account > Data management > Data protection` |
| Find Shared Key callers | `Storage account > Monitoring > Metrics` (Transactions, split by Authentication) |
| Policy | `Azure portal > Policy > Assignments > Assign policy` |

```bash
az storage account update -g rg-sec -n contosodocs \
  --https-only true --min-tls-version TLS1_2 \
  --allow-blob-public-access false \
  --allow-shared-key-access false \
  --allow-cross-tenant-replication false
```

## Exam traps

- ==!"TLS 1.3 minimum"== is not offered on storage accounts. Correct answer: ==+TLS 1.2==.
- ==!"An account created by CLI/ARM with no TLS property accepts TLS 1.0"== — no longer true: since 3 Feb 2026 the service refuses TLS 1.0/1.1 on every account. But Policy/Defender still flag an unset or lower `minimumTlsVersion`, so the ==+fix is still to set TLS1_2 explicitly (and audit/deny with Azure Policy)==.
- "Make one container public without exposing the others": the account switch must allow anonymous access, then set that container's level. Better: move public content to a dedicated account.
- "Revoke a leaked service SAS quickly" is a D2.1.4 question, but "stop **all** key-signed access forever" is ==+Allow storage account key access = Disabled==.
- Policy **Deny** does not remediate existing accounts. Policy **Audit** never blocks.
- CMK needs **purge protection**. A vault without it is the distractor.
- Infrastructure encryption on an **existing** account: impossible. Create a new account and copy data.
- ==!Owner/Contributor/Storage Account Contributor do not grant data access through Entra ID==. But they include `listkeys`, so they *can* read data through the keys, which is one more reason to disable Shared Key.
