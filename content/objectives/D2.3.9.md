## Azure first

- A VM talks to the network through a **NIC** (network interface). An **NSG** can sit on the NIC, on its **subnet**, or both. **Azure Virtual Network Manager (AVNM)** can push **security admin rules** above both (D2.3.2).
- Every subnet has a **route table**: system routes plus any **UDRs** you add (for example, "0.0.0.0/0 → firewall").
- **Network Watcher** is a regional Azure service: one instance per region per subscription, named `NetworkWatcher_{region}` in resource group `NetworkWatcherRG`. It is ==@enabled automatically== when you create a VNet in a region.
- Flow logs land in a **storage account**; traffic analytics loads them into a **Log Analytics workspace** you can query with KQL.

Read first: virtual-networks-and-subnets, virtual-machines-and-disks, log-analytics-workspace, storage-accounts-basics.

## In one sentence

Network Watcher is the Azure toolbox that tells you, for a real VM, what rules actually apply (effective security rules), whether one flow is allowed and by which rule (IP flow verify, NSG diagnostics), where packets go next (next hop), and what traffic really happened (flow logs, traffic analytics, packet capture).

## Why it exists

A VM can be filtered by an AVNM admin rule, a subnet NSG and a NIC NSG at once. Reading one NSG is reading one page of a three-page contract. As an analyst you asked "was this connection blocked?". As the engineer you must prove the answer *before* the incident, and fix the rule that's wrong.

Rule order for one VM:

- **Inbound**: AVNM security admin rules → **subnet** NSG → **NIC** NSG.
- **Outbound**: AVNM security admin rules → **NIC** NSG → **subnet** NSG.

Traffic must be allowed at every NSG it meets. ==!An allow in the subnet NSG does not override a deny in the NIC NSG.==

> **Training vs product docs.** Unit 6 gives the order as "AVNM, then subnet NSG, then NIC NSG" with no direction. That's the **inbound** order only. The NSG doc reverses the NSGs for outbound. Product docs win.

## What actually matters

### The decision table

| Question | Tool | Key facts |
|---|---|---|
| What rules are in force on this NIC? | ==@Effective security rules== | Aggregates NIC NSG + subnet NSG + **AVNM admin rules**. Download as CSV. |
| Would TCP/UDP from X to this VM on port Y be allowed? Which rule decides? | ==@IP flow verify== | Inputs: direction, protocol, local/remote IP and port. Returns **Access allowed/denied** + rule name. **TCP and UDP only**; VM NICs only. ==+No agent needed.== |
| Same, but ICMP, a scale set, an Application Gateway v2, or a source given as prefix / service tag? | ==@NSG diagnostics== | Can also **add a higher-priority rule** to fix the result. |
| Is a UDR sending traffic to the wrong place? | ==@Next hop== | Returns next hop type, IP and **route table ID** (or *System Route*). Types: Internet, VirtualAppliance, VirtualNetworkGateway, VirtualNetwork, VirtualNetworkPeering, VirtualNetworkServiceEndpoint, MicrosoftEdge, **None** (= dropped). |
| Can this VM reach that FQDN/IP:port now? Why not? | ==@Connection troubleshoot== | Point-in-time test from VM, VMSS, Bastion or AppGW v2 to a VM, FQDN, URI or IP. Finds NSG and UDR blocks, guest OS firewall, DNS failures, no listener, high CPU/memory. Reports latency and hops. Agentless mode in preview. |
| What exactly was on the wire? | ==@Packet capture== | Needs the `AzureNetworkWatcherExtension` VM extension. Saves to local disk or blob. Default time limit **18,000 s (5 h)**. 5-tuple filters. |
| What traffic flowed, allowed or denied, over time? | ==@VNet flow logs== | Layer 4 records every minute, JSON, to a **Standard** storage account in the **same region**. Captures NSG **and AVNM** decisions, plus encryption status. |
| Show me patterns, top talkers, malicious IPs | ==@Traffic analytics== | Processes flow logs into Log Analytics (`NTANetAnalytics` table). Interval **60 min default**, **10 min** accelerated. |
| How is my network built? | ==@Topology== | Interactive map across subscriptions, regions and resource groups. Built from Resource Graph, so changes can take up to 30 hours to show. |
| Is the VPN gateway healthy? | VPN troubleshoot | Owned by D2.3.4. |
| Is A→B healthy over time? | Connection monitor | Continuous; connection troubleshoot is the one-off. |

### Five facts that decide questions

1. **Effective security rules vs IP flow verify.** Effective rules = the *whole list* in evaluation order. IP flow verify = the *verdict for one flow*. Use them together: IP flow verify names the rule, effective rules shows what sits above it.
2. **Usual culprits** when a flow is wrongly *denied*: a broad deny with a **lower priority number** above your allow; a NIC that isn't a member of the **ASG** the rule targets. When wrongly *allowed*: the default **AllowVnetInBound** rule; an AVNM security admin configuration that was created but **not deployed**.
3. **Network Watcher doesn't cover PaaS.** It is for IaaS. ==!Effective routes and security rules are not displayed for a private endpoint's NIC==, and NSG flow logs don't record inbound traffic to a private endpoint.
4. **NSG flow logs are retiring** on **30 September 2027**. ==!New NSG flow logs can no longer be created== (blocked since 30 June 2025). Use **VNet flow logs**. Don't run both on the same workload, or you get duplicate logging.
5. **Permissions.** Owner, Contributor or **Network Contributor**. Network Contributor alone lacks the storage, compute and Log Analytics actions that flow logs, packet capture and traffic analytics need. Restrict `packetCaptures/write`: a capture can include payload data.

### A verification routine that holds up in an audit

1. Open **effective security rules** on the target NIC. Confirm each expected rule appears, with the right source: AVNM admin configuration, subnet NSG or NIC NSG.
2. List the attack paths you care about, for example web tier → database on 1433, app tier → database on 1433, internet → any VM on 3389.
3. Run **IP flow verify** for each path. Record the verdict and the rule name. Test both directions: inbound at the destination and outbound at the source, because some rules block one way only.
4. If a route looks wrong, run **next hop** from the source VM.
5. Turn on **VNet flow logs** with traffic analytics so the evidence keeps coming after the change window closes.

## Where it lives

All in the **Azure portal**.

- `Azure portal > Network Watcher > Network diagnostic tools > IP flow verify | NSG diagnostics | Next hop | Effective security rules | Connection troubleshoot | Packet capture | VPN troubleshoot`.
- From the VM: `Virtual machines > {vm} > Networking > {NIC} > Help > Effective security rules` (and **Effective routes**).
- Logs: `Network Watcher > Logs > Flow logs > + Create` (flow log type: **Virtual network**; tick **Enable traffic analytics** and pick the workspace and interval).
- Map: `Network Watcher > Monitoring > Topology`.

```bash
az network watcher test-ip-flow -g rg-lab --vm vm-db --direction Inbound \
  --protocol TCP --local 10.1.3.4:1433 --remote 10.1.1.4:*
az network nic list-effective-nsg -g rg-lab -n vm-db-nic
az network watcher show-next-hop -g rg-lab --vm vm-web --source-ip 10.1.1.4 --dest-ip 8.8.8.8
az network watcher test-connectivity -g rg-lab --source-resource vm-web \
  --dest-address www.microsoft.com --dest-port 443
az network watcher flow-log create -g rg-lab -n fl-vnet --location eastus \
  --vnet vnet-lab --storage-account stflowlab \
  --traffic-analytics true --workspace law-lab --interval 10
```

```kql
NTANetAnalytics
| where SubType == "FlowLog" and FlowStatus in ("D", "Denied")   // schema doc says D; table reference says Denied
| summarize Denied = count() by SrcIp, DestIp, DestPort, AclRule
| top 20 by Denied
```

## Exam traps

- "Which rule is blocking RDP to VM1?" → ==+IP flow verify== (returns the rule name). Effective security rules is the *list*; next hop is routing, not filtering.
- "Test ICMP" or "test a scale set" → **NSG diagnostics**, not IP flow verify.
- "Traffic goes to the firewall instead of the internet" or "is dropped with no NSG deny" → **Next hop** (a UDR to VirtualAppliance, or a next hop of **None**).
- "VM can't reach `contoso.com`: is it DNS, NSG or the guest firewall?" → **Connection troubleshoot**.
- "Record allowed and denied flows for audit / Sentinel" → **VNet flow logs** (+ traffic analytics). Not packet capture, not NSG flow logs (no new ones).
- IP flow verify needs **no agent**; packet capture **does**.
- An NSG on the subnet allows, the NIC NSG denies → **denied**.
- Flow log storage account in another region → not supported; same region, Standard tier.
- Network Watcher must exist in the VM's **region and subscription**; you can't move it between regions.

## Skip

- **Skip** the connection troubleshoot response schema and its 50-row error list (`ARPMissing`, `UDRLoop`, `MultiNICsInSameSubnet`...). Know the issue *categories*: NSG, UDR, DNS, guest firewall, CPU/memory, no listener.
- **Skip** the flow log tuple field order, encryption codes (`NX_HW_NOT_SUPPORTED` and friends) and the version 5 PLS fields.
- **Skip** continuous packet capture ring-buffer settings (file count, 4 GB files, 7-day max).
- **Skip** the traffic analytics schema columns and the region availability tables.
- **Skip** Connection monitor setup and its limits (100 per region per subscription). It's monitoring, not rule evaluation.
- **Skip** unit 6's Contoso walkthrough lists. Keep the method: list effective rules, then IP-flow-verify each critical path, in both directions.
- **Skip** the "Usage + quotas" blade. Unrelated to security rules.
