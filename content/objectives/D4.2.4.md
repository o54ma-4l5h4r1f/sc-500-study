## Azure first

- The **Activity log** records control-plane events for a **subscription** (who created, changed or deleted what). **Resource logs** record what happens *inside* one resource (Key Vault reads, SQL queries, firewall hits).
- A **diagnostic setting** is the per-resource switch that sends those logs to a destination such as a Log Analytics workspace.
- **Azure Policy** can create diagnostic settings for you on every resource of a type, including ones created later, with a **remediation task** for the existing ones.
- **Microsoft Entra ID** and **Microsoft 365** are tenant services, not Azure resources. Their logs reach Sentinel through service-to-service (API) connections that need tenant-level Entra roles.

See the Foundations pages listed above: diagnostic settings and the Activity log, Azure Policy basics, Entra ID basics, Microsoft 365 tenants and licensing, Log Analytics workspace.

## In one sentence

Microsoft-service connectors pull logs into Sentinel in one of three ways — **API** (service-to-service), **diagnostic settings** (standalone or managed by **Azure Policy**), or **agent** — and each needs a specific role and sometimes a licence.

## What's new for an engineer

As an analyst you queried `SigninLogs` and `AzureActivity`. Someone had to turn them on, hold the right roles and pay for the volume:

1. **Install the solution first** from the content hub; the connector appears afterwards (D4.2.3).
2. **Every connector needs write on the workspace** (Microsoft Sentinel Contributor covers it) **plus** the connector's own prerequisite.
3. **Choose log types deliberately.** Each Entra ID log type lands in its own table and is billed per GB. Turn on only what your detections use.

## What actually matters

| Connector | Method | Extra role / licence | Table(s) |
|---|---|---|---|
| ==@Azure Activity== | Diagnostic settings **via Azure Policy** | ==@Owner== on the policy assignment scope (subscription) | `AzureActivity` |
| ==@Microsoft Entra ID== | Entra diagnostic settings | **Security Administrator** on the tenant; **Entra ID P1 or P2** for sign-in logs (any licence for audit logs) | `SigninLogs`, `AADNonInteractiveUserSignInLogs`, `AADServicePrincipalSignInLogs`, `AADManagedIdentitySignInLogs`, `AADProvisioningLogs`, `ADFSSignInLogs`, `AuditLogs`, plus risk tables |
| ==@Microsoft Entra ID Protection== | API | **Security Administrator**; **Entra ID P2** | `SecurityAlert` (alerts only, not the raw sign-ins) |
| ==@Microsoft 365== | API | **Security Administrator**; Microsoft 365 must be in the **same tenant** | `OfficeActivity` (Exchange, SharePoint, Teams) |
| Azure resource diagnostics (Key Vault, SQL, Storage, Firewall, AKS…) | Diagnostic settings, often **via Azure Policy** | Owner on the policy scope; read/write on the workspace | `AzureDiagnostics` or resource-specific tables (`AZFW*`, `StorageBlobLogs`…) |

- **Azure Policy connectors.** The connector page opens the **Azure Policy Assignment wizard**: pick scope (subscription, optionally resource group), pick the workspace in **Parameters**, and tick **Create a remediation task** on **Remediation** — without it, only *new* resources get the setting.
- **Standalone diagnostic settings** are done resource by resource: resource > Diagnostic settings > Add > **Send to Log Analytics workspace**. For a storage account, configure the parent account (Transaction metric) and each child service (blob, file, queue, table).
- **Azure Activity moved pipelines.** The old subscription-connection method is legacy; disconnect those subscriptions (**Disconnect All**) before using the policy-based connector.
- **Entra ID Protection incidents.** Selecting **Enable** under Create incidents turns on the analytics rule *Create incidents based on Microsoft Entra ID Protection alerts*. When you onboard to the Defender portal, the standalone Entra ID Protection connector is disconnected automatically — its alerts come through Defender XDR to the primary workspace instead.
- **Status lights for policy connectors** show green only if data arrived in the past 14 days.
- **Sign-in licence trap.** Sign-in logs need Entra ID P1/P2. Workload ID Premium is needed for risky service principal tables.

## Where it lives

| Task | Portal and path |
|---|---|
| Open a connector | Defender portal > **Microsoft Sentinel > Configuration > Data connectors** > select connector > **Open connector page** |
| Azure Activity / resource diagnostics | Connector page > **Launch Azure Policy Assignment wizard** > Basics (scope) > Parameters (workspace) > Remediation (task) > Create |
| Microsoft Entra ID | Connector page > tick log types > **Apply Changes** |
| Microsoft 365 | Connector page > Configuration > tick **Exchange / SharePoint / Teams** > Apply Changes |
| Entra ID Protection | Connector page > **Connect** > Create incidents: **Enable** |
| Check a policy remediation | Azure portal > Policy > Remediation |

## Exam traps

- ==!"Entra ID Protection connector gives you the risky sign-in events"== — it sends **alerts** to `SecurityAlert`. Raw risk events (`AADUserRiskEvents`, `AADRiskyUsers`) come from the **Microsoft Entra ID** connector.
- ==!"Contributor is enough to connect Azure Activity"== — the Policy assignment needs ==+Owner== on the scope.
- ==!"Assigning the policy fixes existing resources"== — only with a **remediation task**.
- **Sign-in logs missing, audit logs present** → no Entra ID P1/P2 licence.
- **Microsoft 365 logs in `OfficeActivity`**, not `CloudAppEvents` (that one is Defender XDR advanced hunting).
- **Contradiction:** the API-connector article lists **Entra ID P2** for Entra ID Protection; the connector reference says "P1/P2". Answer P2 — risk detections are a P2 feature.

## Skip

- **Skip** the long Entra ID log-type descriptions (Graph activity logs, network access traffic, remote network health). Know the sign-in/audit tables and the licence rule.
- **Skip** per-connector tables for every Azure service (Batch, DDoS, Data Lake…). Learn the pattern: diagnostic settings, often deployed by Policy, landing in `AzureDiagnostics` or a resource-specific table.
- **Skip** the Azure portal navigation steps in units 3–6 ("Content management > Content hub" in the Azure portal); the Defender portal path above is the one that survives March 31, 2027.
- **Skip** the module's description of Activity log contents (service health, ARM operational data). That's foundation material, covered in the diagnostic settings primer.
