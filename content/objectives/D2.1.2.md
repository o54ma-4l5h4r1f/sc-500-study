## Azure first

- A storage account answers on a **public endpoint**, such as `contoso.blob.core.windows.net`, that resolves to a public IP anyone can reach.
- A **virtual network (VNet)** is your private network in Azure, split into **subnets**. A **service endpoint** is a subnet setting that sends traffic for one Azure service (here `Microsoft.Storage`) over the Microsoft backbone and tags it with the subnet's identity.
- A **managed identity** is an Entra ID identity Azure gives a resource, so the resource can prove who it is without a password.
- A **private endpoint** is a network card in your subnet with a private IP that connects to one storage service. It is taught fully in D2.3.6.

Read first: storage-accounts-basics, virtual-networks-and-subnets, private-dns-and-name-resolution, entra-id-basics.

## In one sentence

The storage firewall turns the public endpoint from "allow everyone" into "deny everyone except the subnets, public IP ranges, named Azure resources and trusted Microsoft services I list", and it says nothing about traffic that arrives through a private endpoint.

## Why it exists

From SOC work: a valid SAS token or stolen key works from any café on earth while the account is open to all networks. Authentication asks "who are you?". The firewall asks "where are you calling from?". Both checks must pass. The firewall runs first, so a request from a blocked network fails before its credentials are even read.

## Mental model

A **mailroom that only accepts post from listed senders**. The mailroom door is the public endpoint. The list has four kinds of entries: internal departments (VNet rules), named outside addresses (IP rules), specific contractor badges (resource instance rules) and the national postal service (trusted services). A private endpoint is a **separate internal chute** straight into the mailroom; the door list never sees it.

## What actually matters

| Public network access (portal) | Effect | CLI |
|---|---|---|
| Enabled from all networks | default; no network filter | `--default-action Allow` |
| Enabled from selected networks | only listed sources reach the public endpoint | `--default-action Deny` |
| Disabled | public endpoint refuses clients (incl. service endpoints); use private endpoints — ==!but previously configured trusted-service exceptions and resource instance rules stay in effect== | `--public-network-access Disabled` |
| Secured by perimeter | rules come from a network security perimeter | (perimeter feature) |

1. **Rules do nothing until the default action is Deny** ("selected networks"). Adding an IP rule to an account still set to "all networks" changes nothing. Rules filter the ==@data plane only==. Control-plane calls through Azure Resource Manager (changing account settings, listing keys) are not blocked by the storage firewall.
2. **VNet rules** allow a subnet that has a storage **service endpoint**. `Microsoft.Storage` reaches accounts in the same region; `Microsoft.Storage.Global` reaches any region. ==!Only one of the two per subnet.== The VNet may be in any subscription or tenant. Up to **400** VNet rules. The portal turns on the service endpoint for you; CLI and PowerShell do not. For geo-redundant accounts, pre-create VNet rules from the paired region for failover.
3. **IP rules** allow **public** IPv4 ranges in CIDR. Up to **400**. ==!Private RFC 1918 ranges are rejected==, `/31` and `/32` are not accepted (enter a single address bare), and IP rules ==!do not match clients in the same Azure region==, which use private Azure addresses. For ExpressRoute **Microsoft peering**, allow its NAT public IPs. Turning on a service endpoint on a subnet makes its traffic use private source IPs, so any IP rule you wrote for that subnet stops matching.
4. **Resource instance rules** allow one named resource (resource type + resource ID) that runs on Microsoft-managed infrastructure, such as an Azure AI Foundry or Azure Machine Learning resource. It connects with its **managed identity**, and its **RBAC data role** decides what it can do. The resource must be in the **same Entra tenant** (any subscription). Up to **200** per account. Narrower and preferred over the trusted-services exception.
5. **Exceptions** (`--bypass`): **AzureServices** (*Allow Azure services on the trusted services list to access this storage account*), **Logging** and **Metrics** (read access to storage logs/metrics from any network). Trusted services include Azure Backup, Event Grid, Event Hubs capture, Azure Monitor, Azure networking (flow logs) and Site Recovery, registered in your tenant. It is ==!not "allow all of Azure"==.
6. **Private endpoints** (D2.3.6): one per sub-resource (`blob`, `file`, `queue`, `table`, `dfs`, `web`). DNS zone `privatelink.blob.core.windows.net`. Creating one ==!does not block the public endpoint==; set public access to Disabled afterwards. No firewall rule is needed for private endpoint traffic.

| | Service endpoint + VNet rule | Private endpoint |
|---|---|---|
| Storage IP seen by client | public | ==+private, in your VNet== |
| DNS answer | public IP | private IP |
| Public endpoint | ==!still exists== | can be disabled |
| Works from on-premises over ExpressRoute private peering/VPN | no | yes |

## Where it lives

`Azure portal > Storage account > Security + networking > Networking`. Public access is under **Public network access > Manage**. VNets, IP ranges, resource instances and **Exceptions** are under **Resource settings: Virtual networks, IP addresses, and exceptions > View**. Private endpoints are on the **Private endpoint connections** tab.

```bash
az storage account update -g rg-sec -n contosodocs --default-action Deny --bypass AzureServices
az storage account network-rule add -g rg-sec --account-name contosodocs --ip-address 203.0.113.0/24
az storage account network-rule add -g rg-sec --account-name contosodocs \
  --vnet-name vnet-app --subnet snet-func      # subnet needs the Microsoft.Storage endpoint
az storage account network-rule add -g rg-sec --account-name contosodocs \
  --resource-id <foundry-resource-id> --tenant-id <tenant-id>
```

Firewall changes take up to a minute to apply.

## Exam traps

- "On-premises servers at 10.10.0.0/16 must reach storage over the internet": ==!a private-range IP rule is invalid==. Allow the on-premises **public NAT** address.
- "App Service in the same region is blocked although its outbound IP is in an IP rule": same-region traffic ignores IP rules. Use a ==+VNet rule (VNet integration + service endpoint)== or a private endpoint.
- "Azure ML workspace / Foundry needs access but cannot join your VNet": ==+resource instance rule==, plus an RBAC data role for its managed identity.
- "Azure Backup / diagnostic logs stopped after enabling the firewall": ==+Allow trusted Microsoft services== exception.
- ==!Disabling public network access does not remove existing exceptions and resource instance rules.== Trusted-service access keeps the highest precedence and still works.
- "Restrict access to one container by IP": impossible. Network rules apply to the whole account endpoint. Use RBAC or a scoped SAS.
- A SAS with a `sip` IP range narrows the token; it ==!does not open the firewall==.
- Service endpoints do not hide the public endpoint. Only private endpoint + public access Disabled does.
