## Azure first

- **Microsoft Defender for Cloud** is Azure's security-posture and threat-protection service. It is split into **plans** you switch on per subscription. **Foundational CSPM** is free; the paid **Defender CSPM** plan adds the cloud security graph, attack path analysis and agentless scanning.
- A **disk snapshot** is a point-in-time copy of a VM's disk. Defender can read the copy without touching the running VM.
- A **deployment** (an ARM/Bicep template run, or an AWS CloudFormation stack) keeps its template, parameters and outputs as metadata in the cloud — readable later through the control-plane API.
- **Lateral movement**, from your SOC work: using what you found on one machine to reach the next.

See *defender-for-cloud-basics* in Foundations.

## In one sentence

Defender CSPM secrets scanning finds plaintext credentials that should have been in Key Vault — on VM disks, in cloud deployment templates and in code repositories — and shows which of them open a path to another resource.

## Why it exists

Key Vault only protects secrets that are actually in it. In practice a storage connection string ends up in `appsettings.json` on a VM, an admin password is pasted into a template parameter, a token is committed to Git. As an analyst you saw the end of that story: the attacker reads the file and pivots. Secrets scanning is the engineer's version — find the file *before* the attacker does.

## What actually matters

**1. Three scanning types, three plan answers.**

| Scanning type | How it works | Plan needed | Recommendation name |
|---|---|---|---|
| **Machine** (Azure VMs, AWS EC2, GCP VMs) | Agentless: disk snapshot through cloud APIs, analysed out of band | ==@Defender CSPM **or** Defender for Servers Plan 2== | *Machines should have secrets findings resolved* (AWS: *EC2 instances…*; GCP: *VM instances…*) |
| **Cloud deployment** (ARM deployments, AWS CloudFormation stacks) | Agentless: reads deployment templates, parameters and outputs through the control-plane API | ==@Defender CSPM only== | *Azure Resource Manager deployments should have secrets findings resolved* / *AWS CloudFormation Stack should have secrets findings resolved* |
| **Code repository** (Azure DevOps, GitHub) | Uses **GitHub Advanced Security** secret scanning on the whole Git history | GitHub Advanced Security licence; findings visible in Foundational CSPM; **Defender CSPM** for lateral-movement paths | — |

**Contradiction:** the training unit says Azure DevOps repository scanning "is included with the Defender CSPM plan" and only GitHub needs Advanced Security. The product page *Protect code repository secrets* says scanning relies on GitHub Advanced Security **for both GitHub and Azure DevOps**, with attack paths for exposed secrets ==@only for Azure DevOps repositories==. ==!The product doc wins.==

**2. Agentless means no agent, no network path, no performance hit.** Scans run once every **24 hours** on a fixed schedule; a stopped VM is skipped that cycle. VMs over **4 TB** total disk get only the OS disk scanned (and only if that OS disk is under 4 TB); data disks are skipped. VMs with disks encrypted by a **customer-managed key** need the scanner identity (*Microsoft Defender for Cloud Servers Scanner Resource Provider*) granted **Key Vault Crypto Service Encryption User** on that vault (or Get, Wrap Key, Unwrap Key access policies) — a neat link back to D1.2.3.

**3. Turning it on.** Enable **Defender CSPM** (or Servers P2), then make sure **Agentless scanning for machines** is **On** in the plan's settings. There is one agentless switch per subscription/account/project — you ==!cannot turn secrets scanning on or off separately== from vulnerability and inventory scanning. The scanner is only switched on automatically when a **Subscription Owner** enables the plan; a lower role can enable the plan but the agentless scanner stays off.

**4. What it finds.** Plaintext SSH private keys, Azure SQL / PostgreSQL / MySQL / Cosmos DB connection strings, storage connection strings and SAS tokens, AWS access keys, Entra ID client secrets, Azure DevOps and GitHub personal access tokens, OpenAI API keys and more. For **SSH keys** the engine checks whether the key actually authenticates to another reachable machine; keys it cannot verify show as **unverified**.

**5. Four ways to review findings.** Recommendations (under the **Remediate vulnerabilities** security control), the **asset inventory** per VM, **cloud security explorer** (predefined queries such as *VM with plaintext secret that can authenticate to another VM / a storage account / an SQL database*), and **attack path analysis** (for example *exposed vulnerable VM has insecure secrets that are used to authenticate to a storage account*). Explorer and attack paths need Defender CSPM. To view findings you need at least **Security Reader** (or Reader, Security Admin, Contributor, Owner).

**6. Remediation is always the same.** Remove the plaintext from the file, disk or template. Put the secret in Key Vault. Point the app at the vault with a managed identity or a Key Vault reference. **Rotate the exposed credential** — assume it is compromised. Adding a vault reference while leaving the old file in place ==!does not close the finding==.

## Where it lives

All in **Defender for Cloud** in the **Azure portal**:

- **Defender for Cloud > Environment settings > *subscription* > Defender plans** → **Defender CSPM** On → **Settings** → **Agentless scanning for machines** On (optional exclusion tags via **Edit configuration**).
- **Defender for Cloud > Recommendations** → filter *secrets findings resolved* → select a machine → secret type, file path, remediation steps.
- **Defender for Cloud > Inventory** → *VM* → all findings for that resource.
- **Defender for Cloud > Cloud security explorer** → secrets templates.
- **Defender for Cloud > Attack path analysis**.
- Code: connect Azure DevOps / GitHub under **Environment settings > Add environment**.

![Agentless scanning for machines setting](https://learn.microsoft.com/en-us/azure/defender-for-cloud/media/enable-vulnerability-assessment-agentless/turn-on-agentless-scanning-azure.png){Settings and monitoring: Agentless scanning for machines covers secrets, vulnerabilities and inventory together}

## Exam traps

- "Scan VM disks for secrets — cheapest plan, no other CSPM features needed" → both ==+Defender for Servers Plan 2== and ==+Defender CSPM== qualify. "Scan ARM deployment templates for secrets" → ==+Defender CSPM only== — Servers P2 does not.
- "Requires installing an agent / opening a port" → ==!no==; snapshot-based, agentless.
- Foundational (free) CSPM ==!does not== scan VMs or deployments for secrets.
- "Plan enabled but no secrets findings" → agentless scanning toggle off, the plan was enabled by a non-Owner, the VM was off at scan time, or CMK disks without the scanner's Key Vault role.
- Secrets scanning ==!does not generate security alerts==. It produces posture findings (recommendations, attack paths). Alerts on vault access are Defender for Key Vault (D1.2.7).
- Fixing the app config ==!without rotating== the exposed credential leaves the risk open.

## Skip

- **Skip:** the full 50-row supported-secrets table. Know the families (SSH keys, connection strings, SAS tokens, cloud access keys, client secrets, PATs) and that SSH keys get lateral-movement verification.
- **Skip:** AWS and GCP onboarding steps for agentless scanning (CloudFormation StackSets, GCP project selection). Multicloud connectors are D4.1.4.
- **Skip:** agentless *code* scanning (preview) — code vulnerabilities, IaC misconfigurations and SBOM. That is DevOps security, not secrets scanning.
- **Skip:** the unit's triage advice ("check when the secret was first committed"). Sensible, but it is incident handling you already do.
- **Skip:** the other Defender CSPM components (sensitive data discovery, CIEM, serverless protection, Kubernetes discovery). They belong to D4.1.1.
