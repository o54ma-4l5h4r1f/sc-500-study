## Azure first

- **Defender for Servers** is the paid Defender for Cloud plan for machines (Plan 1 or Plan 2). Its switches live in **Environment settings > *subscription* > Defender plans > Servers > Settings**. That blade is called **Settings & monitoring**.
- A **VM extension** is a small add-on program Azure installs inside a VM for you. Defender for Servers uses one called **MDE.Windows** or **MDE.Linux** to install the Defender for Endpoint sensor.
- **Microsoft Defender Vulnerability Management (MDVM)** is the vulnerability scanner built into Defender for Endpoint. Defender for Cloud reuses it.
- A **Log Analytics workspace** is the log database you know from Sentinel. FIM writes its change events there.

See Defender for Cloud basics, VMs and disks, Log Analytics workspace and the Defender portal tour in Foundations.

## In one sentence

Once the Servers plan is on, three settings decide what it actually does on each machine: **Endpoint protection** (deploy the MDE sensor for EDR), **Vulnerability assessment for machines** (MDVM, agent-based plus agentless), and **File Integrity Monitoring** (Plan 2, off until you configure it with a workspace).

## Why it exists

The plan is the contract; the settings are the services in it. As an analyst you saw the output: MDE alerts, CVE lists, "registry Run key modified" events. As an engineer you decide which sensors deploy, which scanner feeds the CVE list and which files are watched.

Think of a building alarm again. The contract (Plan 2) entitles you to motion sensors (EDR), a monthly inspection of locks (vulnerability scanning) and tamper seals on key cabinets (FIM). The installer still has to fit each one. Some are fitted automatically. Tamper seals are not.

Two are automatic. One (FIM) is not. That asymmetry is the exam's favourite question.

## What actually matters

1. **EDR = the Endpoint protection setting.** It is **On** by default in both plans. Defender for Cloud then auto-installs the MDE sensor through the **MDE.Windows** / **MDE.Linux** extension. Windows Server 2019 and later already carry the sensor. Defender for Cloud installs the **unified solution** on Windows Server 2016 and 2012 R2. Linux needs Python 3. If a machine is already onboarded to MDE in the **same** MDE tenant, it reuses that sensor. A machine onboarded to a *different* MDE tenant is ==!not== reassigned; offboard it first. The first subscription in a tenant takes up to **12 hours** to onboard; later machines take up to **1 hour**. VMs built from generalized images are not auto-provisioned.

2. **Opting out of EDR.** Turn **Endpoint protection** to **Off**. Do this when you deploy MDE another way (Intune, Group Policy) or a third-party EDR can't coexist. To remove MDE fully: switch it off, delete the extension, then offboard the device in MDE. On Linux, the tag `ExcludeMdeAutoUpdate` = `true` stops automatic MDE package updates. As an analyst you know the sensor. The engineer's job is deployment, health and licensing. Defender for Servers licenses MDE **per hour**, not per user. If you already own MDE for Servers licences, ask support for the discount to avoid double billing.

3. **Vulnerability scanning = MDVM, two modes.** **Agent-based** uses the MDE sensor: continuous, Plan 1 and Plan 2. **Agentless** reads disk snapshots every 24 hours: Plan 2 (or Defender CSPM), see D3.2.7. Both are ==@on by default==. When a machine reports both, ==@agent-based results are shown== (fresher). The setting is **Vulnerability assessment for machines** with **Edit configuration** to choose the solution. Premium MDVM features come with Plan 2 and show only in the Defender portal. MDVM's own plan-level settings belong to D4.1.5.

4. **Qualys is history.** The old built-in scanner "powered by Qualys" is retired; integrated MDVM replaced it and is now the only built-in scanner (current docs no longer list a Qualys built-in option). **BYOL** (your own Qualys or Rapid7 licence) is deprecated too. No new onboarding from **3 February**, and it was fully removed by **1 May** (the product article gives the days but no year). BYOL only ever worked on Azure VMs, not Arc. The answer today is ==+MDVM==.

5. **File Integrity Monitoring (FIM) = Plan 2, configured by you.** It watches OS files, Windows registry keys, application files and Linux system files. It records create, delete and modify events (size, ACL, content hash). It is ==!not enabled by default==. To turn it on you need Plan 2, the MDE agent through the Defender for Servers extension, and a **Log Analytics workspace** for the events. Agentless scanning is optional but adds **custom paths** and a daily check. MDE events arrive in near real time; agentless events arrive every 24 hours. FIM data counts toward the Plan 2 500 MB/day benefit. The limit is **500 rules**. To change FIM you need **Security Admin** and **Owner** on the workspace's subscription. **Security Reader** can view results. The old FIM built on the Log Analytics agent (MMA) or AMA is replaced; migrate to the MDE-based version.

6. **Health and permissions.** MDE health status (installation and heartbeat issues) needs Plan 2, or Defender CSPM plus Plan 1. It refreshes every **4 hours**. To deploy the vulnerability scanner you need **Owner** at resource-group level. To view findings you need **Security Reader**.

### Settings at a glance

| Setting (Servers > Settings) | Plan | Default | What it deploys / needs |
|---|---|---|---|
| Endpoint protection | P1 + P2 | ==+On== | MDE.Windows / MDE.Linux extension |
| Vulnerability assessment for machines | P1 + P2 | ==+On== | MDVM via MDE sensor (agent-based) |
| Agentless scanning for machines | P2 (or Defender CSPM) | ==+On== with P2 | disk snapshots every 24 h (D3.2.7) |
| File Integrity Monitoring | P2 | ==!Off== | MDE agent + Log Analytics workspace |

### Vulnerability scanning sources

| Source | Plan | Freshness | Status (Nov 2026) |
|---|---|---|---|
| MDVM agent-based (MDE sensor) | P1, P2 | continuous | ==+current default== |
| MDVM agentless (snapshot) | P2, Defender CSPM | every 24 h | ==+current== |
| Built-in Qualys | — | — | ==!retired — replaced by MDVM== |
| BYOL Qualys / Rapid7 | none needed | hourly | ==!deprecated== |

> **Contradiction — product docs win.** The training unit still presents BYOL Qualys and Rapid7 as a live alternative ("Use BYOL scanners as alternatives to Defender Vulnerability Management"). The product article now carries a deprecation warning: no new BYOL solutions from 3 February, and no data after 1 May. Treat BYOL as retired.

> **Contradiction — product docs win.** The unit says FIM needs agentless scanning as a data source alongside MDE. The product docs say agentless is **optional** (recommended for custom paths and daily validation). Only the MDE agent and Plan 2 are required.

## Where it lives

All in the **Azure portal > Microsoft Defender for Cloud > Environment settings > *subscription* > Defender plans > Servers > Settings** (Settings & monitoring).

- **Endpoint protection:** toggle **Status** to **On** > **Continue** > **Save**.
- **Vulnerability assessment for machines:** toggle **On** > **Edit configuration** > choose *Microsoft Defender Vulnerability Management* > **Apply** > **Save**.
- **File Integrity Monitoring:** toggle **On** > **Edit configuration** > pick a workspace > edit **Recommended to monitor** rules > optional **+ Add rule** > **Apply** > **Continue**. Review status under **Defender for Cloud > Workload protection > File Integrity Monitoring > Settings**.
- **Findings:** CVEs in the **Defender portal** (`security.microsoft.com`) **> Vulnerability management > Recommendations**, and in Defender for Cloud as the recommendation *Vulnerabilities in your virtual machines should be remediated*.
- **Check MDE on a VM:** **VM > Extensions > MDE.Windows** (or MDE.Linux) **> Provisioning succeeded**. On Linux run `mdatp health` and expect `healthy : true`, `licensed : true`.

## Exam traps

- ==!"FIM starts working when you enable Plan 2."== It does not. You turn it on and choose a workspace.
- ==!"FIM is in Plan 1."== Plan 2 only. The same goes for JIT and agentless scanning.
- ==!"FIM uses the Log Analytics agent."== Not any more. It uses the MDE agent, plus agentless scanning optionally. MMA/AMA-based FIM must be migrated.
- **"Which scanner should you deploy for VM vulnerability assessment?"** ==+Microsoft Defender Vulnerability Management== (built in). Not the Qualys extension. Not BYOL.
- **Both agent and agentless report a VM — whose result shows?** ==+Agent-based== (fresher).
- **Third-party EDR conflicts with MDE?** Turn **Endpoint protection** off (subscription) or exclude the VM from the plan (resource level). Don't uninstall the extension by hand only; Defender for Cloud redeploys it.
- **Moving a VM to another subscription in the same tenant:** delete the MDE extension; Defender for Cloud redeploys it.
- **Arc-only BYOL:** BYOL never supported Arc machines. A question offering BYOL for on-premises servers is wrong twice.
- **Roles:** FIM config = **Security Admin + Owner** (workspace subscription). Scanner deployment = **Owner** (resource group). View findings = **Security Reader**.

## Skip

- **Skip:** the MDE readiness PowerShell and Linux diagnostic commands, extension log paths and Client Analyzer steps. They are troubleshooting runbooks, not exam material.
- **Skip:** legacy opt-in steps for subscriptions created before spring 2022 or summer 2021 (the **Fix > Unified solution** flow). Know only that WS2012 R2/2016 get the unified solution.
- **Skip:** the four Azure Resource Graph health queries for MDE. Know that health status exists, needs P2 or CSPM + P1, and refreshes every 4 hours.
- **Skip:** the FIM recommended path list and custom-rule validation rules (three asterisks, 260 characters). Know "recommended items + custom rules, 500 rules maximum".
- **Skip:** BYOL deployment steps and the `New-ASCVASolution.ps1` script. The feature is deprecated.
- **Skip:** the unit's MDE resource figures ("less than 2% CPU and 100 MB of memory"). Not exam material.
- **Skip:** MDE data residency, attack surface reduction and next-generation protection. Endpoint topics, not plan settings.
