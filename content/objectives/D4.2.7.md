## Azure first

- A **Log Analytics workspace** stores data in **tables**. Built-in ("Azure") tables such as `SecurityEvent` have a fixed schema owned by Microsoft.
- A **custom table** is one you define. Its name ends in `_CL` (custom log).
- A **data collection rule (DCR)** describes the incoming data, an optional **transformation** (a KQL query run on each record before it is stored) and the target table.
- The **Logs Ingestion API** is the REST endpoint your own code calls to send JSON into a table through a DCR. The caller is an **app registration** (a non-human identity in Entra ID).

See the Foundations pages listed above: Log Analytics workspace, AMA and DCRs, Azure RBAC, and Entra ID.

## In one sentence

A custom log table is a workspace table you create (name ends in `_CL`) to hold data no built-in table fits; data reaches it through a DCR — from AMA, a codeless connector, or your own code calling the Logs Ingestion API.

## What's new for an engineer

As an analyst you queried tables like `ApacheHTTPServer_CL` that a connector made. As the engineer you create the table, choose its **plan**, write the DCR, and grant the sender the right role:

- **Decide whether you need one.** Check the Content hub first — many solutions already create `_CL` tables with parsers and workbooks.
- **Choose the table plan** at creation — that sets ingestion and query cost.
- **Wire identity.** The sending app needs **Monitoring Metrics Publisher** on the **DCR**, not a workspace role.

## What actually matters

1. **Naming.** The portal adds `_CL`; CLI, PowerShell, REST, ARM and Bicep ==!don't== — type it. The DCR stream is `Custom-MyTable_CL`. Custom **columns** added to a built-in table end in `_CF`.
2. **`TimeGenerated` is mandatory** (datetime). The portal adds it in the transformation if your sample lacks it.
3. **Table plans** (product names):

| Plan | Use | Query | Retention |
|---|---|---|---|
| **Analytics** | Detections, hunting, workbooks | Full, no per-query charge | Analytics retention 30 days default (==@90 days in a Sentinel workspace==), up to 2 years; total up to 12 years |
| **Basic** | Troubleshooting, high-volume | Billed per GB scanned; 30-day query window | Total up to 12 years |
| **Auxiliary / Lake** | Low-touch, audit, compliance | Billed per GB scanned; slow | Queryable for total retention, up to 12 years |

   In the Defender portal the same choice shows as **Analytics tier** vs **Data lake tier**. Once the workspace is onboarded to the **Sentinel data lake**, Auxiliary tables become part of the lake. DCR-based custom tables are mirrored to the lake; old MMA-style custom tables aren't. Table plan changes are limited to **one per table per week**.
4. **Logs Ingestion API pieces:** app registration + secret → the table → a DCR → **Monitoring Metrics Publisher** on the DCR (allow up to 30 minutes, else HTTP 403) → an endpoint. The endpoint is the DCR's own **logs ingestion endpoint** (DCRs created with `"kind": "Direct"`, since 31 March 2024) or a **data collection endpoint (DCE)**. A DCE is required ==@only for private link== or older DCRs. TLS 1.2+ is enforced from **1 March 2026**.
5. **Changes don't propagate.** Edit the table schema and ==!the DCR is not updated== — edit it yourself. You can delete custom tables, ==!not Azure tables==; deleting a custom table doesn't stop retention charges on its data.
6. **Roles.** **Log Analytics Contributor** to create or manage tables; **Monitoring Contributor** to create DCRs; **Monitoring Metrics Publisher** to send.

## Where it lives

**Azure portal (product docs route):** **Log Analytics workspaces > *workspace* > Settings > Tables > Create > New custom log (DCR-based)** → name, description, table plan → pick or create a DCR (and DCE if needed) → **Browse for files** (JSON sample) → **Transformation editor** → **Create**. This builds the table *and* the DCR.

**Defender portal:** **Microsoft Sentinel > Configuration > Tables** lists custom (`_CL`) tables with their tier and retention; **Manage table** changes them.

```bash
az monitor log-analytics workspace table create --resource-group rg-sentinel \
  --workspace-name law-sentinel --name AppAudit_CL \
  --columns TimeGenerated=datetime Message=string --plan Analytics
```

```kql
// Transformation in the DCR
source
| extend RiskScore = toint(risk_score)
| project-away risk_score
```

## Exam traps

- "Create table `AppAudit` via REST." ==+`AppAudit_CL`== — only the portal adds the suffix.
- "Add column `Region` to `SecurityEvent`." ==+`Region_CF`==.
- "App gets 403 posting logs." ==+Monitoring Metrics Publisher on the DCR==, not ==!Log Analytics Contributor on the workspace==.
- "A DCE is always required." ==!No== — only private link or older DCRs.
- "Cheapest storage for rarely queried compliance logs." ==+Auxiliary / data lake tier.==
- "Schema change updates the DCR." ==!False.==
- "Use the HTTP Data Collector API." ==!Legacy== (shared key, no DCR) — ==+Logs Ingestion API==.

## Skip

- **Skip** the client-library samples (.NET, Go, Java, Python) — know the call shape, not the SDK.
- **Skip** migrating classic (MMA-era) custom tables beyond "one-way migrate operation".
- **Skip** column-name reserved-word lists and data-type minutiae.
- **Skip** the Contoso trading-system schema walkthrough in the training unit — a sample, not a rule.
