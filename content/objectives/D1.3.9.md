## Azure first

- **Infrastructure as code (IaC)** means describing Azure resources in text files — **ARM templates** (JSON), **Bicep** (a shorter language that compiles to ARM) or **Terraform** — and deploying them from a pipeline.
- A **pipeline** (GitHub Actions workflow or Azure Pipelines YAML) runs automatically on a commit or **pull request (PR)** — a proposed change reviewed before it merges into the main branch.
- **Branch protection** (GitHub) or a **branch policy** (Azure DevOps) can require a check to pass before a PR may merge.
- Every deployment, from a pipeline or not, still lands on **Azure Resource Manager**, where Azure Policy runs.

See the Foundations pages listed above, especially *infrastructure-as-code-basics*.

## In one sentence

Security controls in IaC come in two independent layers: **scan the templates before they deploy** (Microsoft Security DevOps in the pipeline, or Defender for Cloud agentless code scanning, with findings in Defender for Cloud) and **enforce at deployment time** with **Azure Policy `deny`** managed as code — because not every change goes through the pipeline.

## Why it exists

As an analyst you met misconfigurations after the fact: a public storage account found in production. Fixing the template at review time is cheaper than an incident. But a scanner only sees the path it sits on. An engineer with CLI access, an emergency hotfix, or a third-party tool calling ARM never touches your pipeline. Policy is the backstop on every path.

## What actually matters

**1. Connect the repos.** Defender for Cloud > Environment settings > **+ Add environment** > **GitHub** (installs a GitHub App on the organization or chosen repos), **Azure DevOps** (OAuth authorization) or **GitLab**. A connector resource appears in Azure. DevOps recommendations then flow into the Recommendations page under the DevOps category.

**2. Microsoft Security DevOps (MSDO)** runs scanners inside the pipeline.

- GitHub: action ==@`microsoft/security-devops-action`== (product docs pin `@latest`; the training unit shows `@v1`). Azure Pipelines: task ==@`MicrosoftSecurityDevOps@1`==.
- `categories: 'IaC'` limits it to IaC scanners (values are case sensitive). Without it, MSDO also runs secrets, code and container tools.
- IaC scanners: **Template Analyzer** (ARM and Bicep; includes **PSRule for Azure** rules), **Checkov** (Terraform, Terraform plan, Bicep, ARM, CloudFormation, Kubernetes, Helm, Dockerfile and more), **Terrascan**. **Trivy** covers images and IaC. **IaCFileScanner** supports template-to-resource mapping.
- Results: in Defender for Cloud > **DevOps security** (no GitHub Advanced Security licence needed), or as GitHub **Code scanning alerts** if you have GitHub Advanced Security; as build results in Azure DevOps.
- Make the MSDO check **required** in branch protection / branch policy to block a merge on findings.

```yaml
# GitHub Actions
- name: Run Microsoft Security DevOps
  uses: microsoft/security-devops-action@latest
  with:
    categories: 'IaC'

# Azure Pipelines
- task: MicrosoftSecurityDevOps@1
  inputs:
    categories: 'IaC'
```

**3. Agentless code scanning (preview).** No pipeline change. Defender for Cloud reads the **default branch** of connected GitHub and Azure DevOps repos. Repository discovery every **8 hours**, code and IaC scans **daily**, repos under **1 GB**. IaC engines: Template Analyzer and Checkov. Turn it on in the connector settings and choose organizations/projects/repos and scanners. Use it for repos you cannot edit; use MSDO for fast PR feedback. They complement each other.

**4. What is free and what is paid.**

| Capability | Foundational CSPM (free) | Defender CSPM |
|---|---|---|
| DevOps inventory, IaC misconfiguration recommendations | yes | yes |
| **Pull request annotations** (inline findings in the PR) | ==!no== | yes |
| Code-to-cloud mapping, attack paths, Cloud Security Explorer, SBOM | no | yes |

PR annotations in **GitHub** additionally need **GitHub Advanced Security**. **IaC template mapping** (find the template that created a misconfigured resource) needs Defender CSPM, Azure DevOps, the MSDO **IaCFileScanner** tool, and templates tagged with `yor_trace` or `mapping_tag`.

**5. Policy as the platform backstop.** `deny` runs at ARM before the resource provider creates anything, so a Bicep deployment with `supportsHttpsTrafficOnly: false` fails with the policy name in the error — whoever runs it.

- **Policy as code workflow:** keep definitions, initiatives, assignments and exemptions as JSON in Git → **create/update** in Azure from the pipeline → **test** with the assignment's enforcement mode **disabled** (`DoNotEnforce`) or `audit` in a dev scope → check compliance results → grant the assignment identity its roles and **remediate** → **deploy** with enforcement **enabled** (`deny`) at production scope.
- **Enterprise Policy as Code (EPAC):** an open-source PowerShell module (`aka.ms/epac`) that deploys policy assignments to management groups from a pipeline and reports drift. ==!It is not a feature of Azure Policy or Defender for Cloud== — a community-maintained layer on the Policy API.
- **Azure Policy Compliance Scan** GitHub Action triggers an on-demand scan and can **gate the workflow** on the compliance result.

**6. Write safer templates.** Mark secret parameters `@secure()` (kept out of deployment history), pull secrets with `getSecret()` from an `existing` Key Vault instead of parameter files, and give resources **managed identities** instead of passing service principal credentials.

```bicep
@secure()
param adminPassword string

resource kv 'Microsoft.KeyVault/vaults@2023-07-01' existing = { name: 'kv-prod' }
// getSecret() works only when passing a value into a module's @secure() parameter:
// module sql 'sql.bicep' = { name: 'sql', params: { adminPassword: kv.getSecret('sqlAdmin') } }

resource st 'Microsoft.Storage/storageAccounts@2023-05-01' = {
  name: 'stprod001'
  location: resourceGroup().location
  sku: { name: 'Standard_LRS' }
  kind: 'StorageV2'
  properties: {
    supportsHttpsTrafficOnly: true
    minimumTlsVersion: 'TLS1_2'
    allowBlobPublicAccess: false
  }
}
```

## Where it lives

- **Connect:** Azure portal > Microsoft Defender for Cloud > **Environment settings > + Add environment** > GitHub / Azure DevOps / GitLab; connector **Settings** for agentless scanning.
- **Findings:** Defender for Cloud > **DevOps security** and **Recommendations** (DevOps category), for example *Azure DevOps repositories should have infrastructure as code scanning findings resolved*.
- **Pipelines:** GitHub > repo > `.github/workflows/msdevopssec.yml`; Azure DevOps > Pipelines > edit YAML; install the extension from Organization settings > Extensions > Marketplace.

## Exam traps

- "Block misconfigured storage accounts regardless of how they are deployed" → **Azure Policy deny**, not pipeline scanning.
- "Give developers feedback in the PR before merge" → MSDO with a required check; **inline PR annotations need Defender CSPM** (and GHAS on GitHub).
- "Scan hundreds of repos without touching pipelines" → **agentless code scanning**.
- "Scan only templates, keep pipeline fast" → `categories: 'IaC'`.
- "Terraform templates" → Checkov (or Terrascan); Template Analyzer covers ARM and Bicep only.
- "Find which template created this misconfigured resource" → IaC template mapping (Defender CSPM, Azure DevOps, tags).
- "Roll out a new deny policy safely" → audit or `DoNotEnforce` first in dev, then deny in prod.
- "Is EPAC an Azure Policy feature?" → no, open-source tooling.
- "Keep a password out of deployment history" → `@secure()`.

## Skip

- **Skip:** the MSDO tool list beyond IaC (AntiMalware, Bandit, BinSkim, ESLint). They are code-scanning tools, not this bullet.
- **Skip:** unit 2's step-by-step GitHub UI clicks (Actions > New workflow > Commit). The YAML snippet and the `categories` input are what matter; screenshots below cover the clicks.
- **Skip:** EPAC's folder layout and the Policy-as-Code file naming (`policy-v#.json`, `policyset-v#.definitions.json`). Know the workflow stages.
- **Skip:** GitLab connector specifics and GitHub Advanced Security secret/dependency scanning — other DevOps posture features.
- **Skip:** unit 2's claim that findings reach Defender for Cloud "within 24 hours" as a hard number, and its PSRule-as-separate-tool note; product docs bundle PSRule inside Template Analyzer.
