## Azure first

- A **virtual network (VNet)** is your private network in Azure, split into **subnets**. Machines in it get private IPs such as `10.1.2.4`.
- A **PaaS service** (storage account, Azure SQL, Key Vault, Azure OpenAI) is run by Microsoft *outside* your VNet. By default it answers on a **public endpoint**: a name like `contoso.blob.core.windows.net` that resolves to a public IP anyone on the internet can try.
- **DNS** turns names into IPs. A **private DNS zone** is a DNS zone that only VNets *linked* to it can see.
- **Azure Policy** checks every resource against rules and can audit, block or auto-fix.

Read first: virtual-networks-and-subnets, private-dns-and-name-resolution, storage-accounts-basics, azure-policy-basics.

## In one sentence

A private endpoint is a network card in your subnet, with a private IP, that connects to **one** PaaS resource (and one sub-resource of it), so you can switch that resource's public endpoint off.

## Why it exists

From SOC work you know the pattern: an attacker phishes a token, then signs in to `contoso.blob.core.windows.net` from a laptop at home. Microsoft Entra authentication answers "who are you?". It never asks "where are you connecting from?". The storage account sat on the internet, so a valid token was enough.

A private endpoint moves the front door inside the building. The service gets an address in *your* network. Then you brick up the street door (disable public network access). The stolen token now has no network path to use.

> **Service endpoints are not the same fix.** A service endpoint sends subnet traffic over the Microsoft backbone and lets the service allow-list that subnet. But the service keeps its public IP, DNS still returns that public IP, and an attacker with credentials connects from outside. ==!A service endpoint never removes the public endpoint.==

## Mental model

A private endpoint is a **private extension phone on your desk that rings one specific office** in another company. Dialling the office's public number still works until that office unplugs its public line. Your phone book (DNS) must list the extension number, or staff keep dialling the public number.

## What actually matters

1. **It is a real NIC with a private IP.** A read-only network interface is created for the endpoint's lifetime. Its IP comes from your subnet and never changes. The endpoint must be in the ==@same region and subscription as its VNet==. The target resource can be in another region.
2. **One endpoint = one resource + one sub-resource.** The "target sub-resource" (also called `groupId`) picks the service inside the resource: `blob`, `file`, `queue`, `table`, `dfs`, `web` for storage; `sqlServer` for Azure SQL (on the *server*, not the database); `vault` for Key Vault; `account` for Azure OpenAI / Foundry Tools. Blob plus file = ==@two endpoints==. A Data Lake (`dfs`) endpoint needs a `blob` endpoint too, because some calls are redirected between them. Private endpoints work only on **General Purpose v2** storage accounts.
3. **Connections are approved.** **Automatic** if you hold `Microsoft.{Provider}/{type}/privateEndpointConnectionsApproval/action` on the target. Otherwise **manual**: the connection sits as *Pending* until the owner approves. States: *Approved*, *Pending*, *Rejected*, *Disconnected*. ==!Only Approved endpoints carry traffic.== Connections are one-way: the service can never open a connection into your VNet.
4. **DNS makes or breaks it.** The public name gets a CNAME to `{name}.privatelink.blob.core.windows.net`. A **private DNS zone** with that `privatelink.` name holds an A record to the private IP. The zone needs a **virtual network link** to every VNet that resolves it. Choosing "Integrate with private DNS zone" creates a **private DNS zone group**: it writes and deletes the A records for you (up to five zones per group, one group per endpoint). Without the zone, clients get the public IP and bypass the endpoint.
5. **Disable public network access, last.** ==!A private endpoint does not block public access by itself.== Create the endpoint, test `nslookup` from inside the VNet, then set public access to **Disabled**. Disabling first gives confusing connection errors.
6. **Network policies are off by default.** On the endpoint's subnet, `privateEndpointNetworkPolicies` defaults to **Disabled**, so NSGs and UDRs do not apply to endpoint traffic. Enable it (NSG, route table, or both) to filter or force traffic through a firewall. Even then, a ==!0.0.0.0/0 UDR does not override== the endpoint's /32 route. The UDR prefix must be equal to or more specific than the VNet address space.

### On-premises name resolution

`168.63.129.16` (Azure DNS) is only reachable from inside a VNet. So on-premises DNS servers forward to something *in* Azure: an **Azure DNS Private Resolver** inbound endpoint (managed) or a DNS forwarder VM. Both sit in a VNet linked to the private zones. The conditional forwarder targets the ==+public zone name (`database.windows.net`)==, ==!not `privatelink.database.windows.net`==. Traffic then flows over VPN or ExpressRoute private peering.

### Service endpoint vs private endpoint

| | Service endpoint | Private endpoint |
|---|---|---|
| What you configure | A setting on a **subnet** + a VNet rule on the service | A **NIC** in a subnet, mapped to one resource |
| Service's IP | Stays **public** | **Private** IP in your VNet |
| DNS change | None | Private DNS zone required |
| Scope | Whole service type (all storage accounts, any tenant) | ==+One resource instance== |
| Exfiltration protection | No built-in (add **service endpoint policies** for Storage) | Yes, only the mapped resource is reachable |
| On-premises access | No (allow your NAT IPs in the service firewall) | Yes, over VPN / ExpressRoute |
| Disable public endpoint | No | Yes |
| Cost | Free | Hourly per endpoint + data processed |

### Enforce and audit adoption

The training sequence is **Audit → remediate → Deny**. Never start with Deny. Built-ins named in the training: *Storage accounts should use private link* (AuditIfNotExists), *Azure Key Vaults should use private link* (Audit, Deny), *Private endpoint connections on Azure SQL Database should be enabled* (Audit), *Azure AI Services resources should use Azure Private Link* (Audit). To *block* public access, deny on the `publicNetworkAccess` property, for example the built-in *Public network access on Azure SQL Database should be disabled* (Audit, Deny). *Configure Storage account to use a private link connection* (DeployIfNotExists) creates the endpoint for you. At scale, a **DeployIfNotExists** policy creates the DNS zone group in a central zone. Its managed identity needs **Private DNS Zone Contributor** on that zone. Defender for Cloud raises the same gaps under **Recommendations** (Networking). Azure Resource Graph finds them fast but enforces nothing.

## Where it lives

All in the **Azure portal**.

- Create from the resource: `Azure portal > {storage account} > Security + networking > Networking > Private endpoint connections > + Private endpoint`. For SQL: open the **server**, `Networking > Private access > + Create a private endpoint`, target sub-resource `sqlServer`.
- Central list: `Azure portal > Private Link Center (search "Private Link") > Private endpoints`. Pending approvals: same blade, **Pending connections**.
- Disable public access: storage `Networking > Public network access: Disabled`; Key Vault `Networking > Disable public access`; SQL server `Networking > Public access: Disable`.
- Subnet network policies: `Virtual networks > {vnet} > Subnets > {subnet} > Network policy for private endpoints`.
- Policy: `Azure portal > Policy > Assignments > + Assign policy`, then `Policy > Compliance`.

```bash
az network private-endpoint create -g rg-lab -n pe-blob \
  --vnet-name vnet-lab --subnet snet-pe \
  --private-connection-resource-id $(az storage account show -n stlab -g rg-lab --query id -o tsv) \
  --group-id blob --connection-name pe-blob-conn
az network private-dns zone create -g rg-lab -n privatelink.blob.core.windows.net
az network private-dns link vnet create -g rg-lab -z privatelink.blob.core.windows.net \
  -n link-lab -v vnet-lab -e false
az network private-endpoint dns-zone-group create -g rg-lab --endpoint-name pe-blob \
  -n default --private-dns-zone privatelink.blob.core.windows.net --zone-name blob
az storage account update -n stlab -g rg-lab --public-network-access Disabled
```

## Exam traps

- "Restrict the storage account so it is **not reachable from the internet** and has a private IP" → ==+private endpoint + disable public access==. Service endpoint is the distractor.
- "VMs still connect over the public IP after creating the endpoint" → missing **private DNS zone or VNet link**, not a missing NSG rule.
- On-premises can't resolve the endpoint → conditional forwarder to the **public** zone name, pointing at a DNS Private Resolver inbound endpoint or forwarder VM. Not directly at `168.63.129.16`.
- Key Vault's zone is ==@privatelink.vaultcore.azure.net==, not `privatelink.vault.azure.net`. Azure OpenAI needs **three** zones: `privatelink.openai.azure.com`, `privatelink.cognitiveservices.azure.com`, `privatelink.services.ai.azure.com`.
- An NSG on the endpoint subnet "isn't working" → `privateEndpointNetworkPolicies` is still Disabled.
- A 0.0.0.0/0 route to the firewall doesn't catch endpoint traffic → the /32 endpoint route wins on longest prefix.
- Endpoint created in another tenant's subscription stays **Pending** → the resource owner must approve.
- Data exfiltration to *another tenant's* storage account → only private endpoints (or service endpoint policies) stop it. Plain service endpoints do not.
- Private endpoint ≠ Private Link **service**. The endpoint is the consumer side. The service is how *you* publish your own app (D2.3.7).
