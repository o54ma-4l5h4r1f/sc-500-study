## Azure first

- An **enterprise application** is the object in Microsoft Entra ID that represents an app in your tenant. You assign users and groups to it, and Conditional Access policies can target it (D1.1.4).
- **Conditional Access** checks each sign-in against rules such as "require MFA" or "require a compliant device" (D1.1.2). It needs Entra ID P1.
- **Zero Trust network access (ZTNA)** means you get a connection to one named app after your identity and device are checked, never to the whole network.
- **Licence-blocked:** Private Access needs Entra ID P1/P2 plus a Private Access or Entra Suite licence. Your lab subscription has neither, so this page is a portal tour: the screenshots are the lab.

See the Foundations pages listed above, especially *conditional-access-basics* and *m365-tenants-and-licensing*.

## In one sentence

Microsoft Entra Private Access is a VPN replacement: a client on the user's device sends traffic for listed internal names, IPs and ports to Microsoft's cloud, which checks identity and Conditional Access per app and then passes the traffic through an outbound-only connector inside your network.

## Why it exists

A hardened VPN (D2.3.4) still lands the user on the network. Every port on every server is then reachable. In the training scenario a compromised P2S session reached dev, test and production. With Private Access, the same stolen session reaches only the apps that user was assigned, and only if Conditional Access is satisfied at that moment.

Think of a hotel. A VPN is a master key card for every floor. Private Access is a card that opens only room 412, re-checked each time you tap it.

## What actually matters

**1. Where it sits.** Private Access is one half of **Global Secure Access** (Microsoft's Security Service Edge). The other half, **Microsoft Entra Internet Access**, filters internet and SaaS traffic. Both are configured in the **Microsoft Entra admin center**, not the Azure portal.

**2. Three components.**

- **Global Secure Access client** on the user device. It captures only traffic to configured destinations (selective, not all traffic). The client device should be Microsoft Entra joined or hybrid joined.
- **Microsoft Entra private network connector**: a lightweight agent on **Windows Server 2016 or later** inside the network that holds the apps. It makes ==@outbound-only== connections (443 for the service, 80 for certificate revocation checks). No inbound firewall rules, no public IP. The same connector serves Entra application proxy.
- **Connector groups**: connectors that act as one unit for load balancing and high availability (use at least two per group). Each app is assigned to one group, so put a group in each network or region that can reach its apps.

**3. Quick Access vs per-app access.** Both create an enterprise application. Both need a connector group, user assignment and the Private Access traffic forwarding profile.

| | ==@Quick Access== | ==@Per-app access== (Global Secure Access app) |
|---|---|---|
| What you define | One primary set of FQDNs, IPs, ranges and ports | One app per resource, each with its own **application segments** |
| Granularity | Network-like: everything in the ranges | One destination + port + protocol per segment |
| Conditional Access | One policy set for all of it | A different policy per app |
| Microsoft's guidance | Transition step to retire the VPN | The Zero Trust end state |

An application segment is **destination** (FQDN incl. wildcard, IP, CIDR, or IP-to-IP range), **ports**, and **protocol** (TCP/UDP). Up to 500 segments per app; segments may not overlap between Private Access apps. One exception: a per-app segment may overlap Quick Access, and the ==@per-app app wins==. Users do not carry over: assign them to the new app or they lose access. Prefer FQDNs over IPs.

**4. Assignment is the gate.** Only users or groups assigned to the app (directly, ==!no nested groups==) can reach it. Changes can take up to 15 minutes to reach clients.

**5. Conditional Access per app.** Because each app is an enterprise application, a Conditional Access policy can target it as a **target resource**: require MFA, a compliant device, a hybrid-joined device, a named location, or block on sign-in risk. Start from `Global Secure Access > Applications > Enterprise applications > app > Conditional Access` and the app is pre-filled. Exclude break-glass accounts; test in report-only first.

**6. Traffic forwarding profile.** Nothing is captured until the **Private access profile** is enabled and assigned to users (`Global Secure Access > Connect > Traffic forwarding`). Enabling it alone grants nothing; the app and assignment still decide access.

**7. Licensing (exact).**

| Requirement | What |
|---|---|
| Prerequisite | Microsoft Entra ID P1 or P2 |
| Private Access itself | ==@Microsoft Entra Private Access== (standalone) or ==@Microsoft Entra Suite== (also in Microsoft 365 E7) |
| Microsoft Entra Suite contains | Private Access, Internet Access, ID Governance, ID Protection, Verified ID |

**8. Roles.** **Global Secure Access Administrator** + **Application Administrator** to configure apps and Quick Access; Application Administrator to manage connector groups (registering the very first connector needs Global Administrator); **Conditional Access Administrator** (or Security Administrator) for the policies.

**9. When to keep VPN.** Site-to-site links between networks, broad SMB file-share access, and legacy apps that need network-layer behaviour. Both can run side by side during migration.

## Where it lives

**Microsoft Entra admin center** (`entra.microsoft.com`).

- Connectors: `Global Secure Access > Connect > Connectors and sensors` → **Download connector service**; connector groups on the same page.
- Quick Access: `Global Secure Access > Applications > Quick Access`.
- Per-app: `Global Secure Access > Applications > Enterprise applications > + New application` → name, **connector group**, **Add application segment**.
- Assign: app → **Users and groups**.
- Conditional Access: app → **Conditional Access**, or `Entra ID > Conditional Access > Policies > + New policy` → Target resources → the app.
- Forwarding: `Global Secure Access > Connect > Traffic forwarding` → **Private access profile**.
- Client: `Global Secure Access > Connect > Client download`.

## Exam traps

- **"Open inbound 443 to the connector."** ==!No.== The connector only dials out.
- **Quick Access = Zero Trust end state.** ==!No.== Microsoft calls it a transition step; per-app access gives segmentation and per-app Conditional Access.
- **"Hardening the VPN gives least privilege."** No; only per-app access removes network-level reach.
- **Licence.** Entra ID P1 alone is not enough. Need Private Access standalone or Entra Suite on top of P1/P2.
- **Nested groups.** Not honoured for app assignment.
- **Portal.** Everything is in the Entra admin center; there is no Azure portal resource for it.
- **Connector placement.** It must have line of sight to the app and resolve its DNS names; the connector does the DNS lookup, not the client.
- **Private Access vs Internet Access.** Internal apps = Private Access; web and SaaS filtering = Internet Access.
- **Private Access vs Azure private endpoints.** Private endpoints (D2.3.6) give a PaaS service a private IP in your VNet; Private Access gives remote *users* app-level reach to internal resources.

## Skip

- **Skip:** custom Private Access traffic forwarding profiles (priorities 101–199, preview). Know the default profile must be on.
- **Skip:** session persistence (`trafficRoutingMethod`) via Microsoft Graph. Operational tuning.
- **Skip:** connector URL allow-lists and the HTTP/2 registry key. Implementation detail; the exam tests "outbound only".
- **Skip:** Private Access for domain controllers (Kerberos sensor) and Private DNS features. Beyond the bullet.
- **Skip:** Internet Access policies (web content filtering, TLS inspection). A different product half.
- **Skip:** the training unit's VPN-vs-Private-Access migration table as memorisation; know the three "keep VPN" cases.
