# D4 — how it all connects

Domain 4 has three parts. **Posture** (D4.1) is Defender for Cloud as an engineer: which plan, at which scope, for which cloud. **Collection** (D4.2) is the Sentinel pipeline you used as an analyst, now seen from the side that builds it. **Security Copilot** (D4.3) is a chain of setup decisions before anyone types a prompt. The objective pages teach each piece on its own. These pictures show how the pieces join up.

Dashed, muted boxes are **forward-links**: a construct from another domain that sits next to a D4 idea. They are pointers only. The detail lives in that domain.

## 1 · Defender for Cloud in three layers, and where you switch them

Two free-or-paid posture layers sit under one row of per-workload protection plans. Every switch lives in **Environment settings** at the subscription or connector, unless you go higher (management group) or lower (one resource, one workspace). ## 2 · Decision tree — how each environment gets in, and when Arc is needed

Start from where the resource lives. Azure needs nothing connected. AWS and GCP need a **keyless connector**. On-premises has **no connector at all** — Azure Arc is the onboarding. Then ask which plan you want: posture plans read cloud APIs, but machine and Kubernetes plans need Arc. [D4.1.4](../objective/D4.1.4.html) draws the three onboarding lanes and what each script creates; this tree is the exam-question version.

## 3 · The posture loop — find, rank, act, measure

Three sources feed one loop. Configuration checks come from CSPM, software CVEs from MDVM, internet-facing surprises from EASM. Everything becomes a **recommendation** with a fixed severity. Defender CSPM then ranks it by **risk** and shows the **attack paths** it sits on. You fix it or **exempt** it, and the result shows in secure score and in every compliance framework that maps to that recommendation. The framework fan-out is drawn on [D4.1.2](../objective/D4.1.2.html); the EASM discovery loop on [D4.1.6](../objective/D4.1.6.html).
