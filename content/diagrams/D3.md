# D3 — how it all connects

Domain 3 is compute: the AI apps and agents, the servers and VMs, and the app platform services. The objective pages teach each control on its own. These seven pictures show how the controls stack, which one a request or an admin meets first, and which constructs look alike. Read them after the objective pages, then again before the exam.

Dashed, muted boxes are **forward-links**: a construct from another domain that sits next to a D3 thing. They are pointers only; the detail lives in that domain. **Legend: dashed = another domain.**

## 1 · The AI workload security stack

Six layers protect an AI workload, from the data it can read to the registry that governs it. Read top to bottom. **Data**: fix overshared SharePoint sites and watch prompts with Purview DSPM. **Identity**: give agents sponsors and time-bound access, and block their tokens with Conditional Access. **Agent runtime**: Defender vets Copilot Studio tool calls; Foundry guardrails filter prompts and tool traffic. **Gateway**: the AI Gateway in API Management caps tokens and checks content. **Posture and threat**: Defender for AI Services raises alerts, the Data and AI dashboard shows coverage, and blast radius shows reach. **Governance**: the Agent 365 registry in the Microsoft 365 admin center approves, scopes and blocks agents. Plain boxes are licence-blocked for an Azure-only lab; accent boxes you can build yourself.

## 2 · Servers — how each machine gets in, and what it gets

Where a server lives decides its route into Defender for Servers, and the route decides the features. Azure VMs only need the plan on the subscription. On-premises servers need the **Azure Arc** agent first. AWS and GCP machines get Arc from the **multicloud connector**. **Direct onboarding** skips Arc but loses Azure Policy and Machine Configuration. The red text is the exam: ==!no JIT and no agentless scanning on on-premises Arc servers==. The Plan 1 vs Plan 2 split itself is in the cheatsheet.

## 3 · Reaching a VM — four admin paths

Four ways an admin reaches RDP or SSH, worst first. A public IP with 3389 open to Any is the thing every other path exists to remove. **JIT** keeps the VM's own port shut and opens it for one IP for a limited time; the VM keeps its public IP. **Bastion** removes the public path: the admin talks HTTPS 443 to Bastion and Bastion opens the session to the VM's private IP. **Premium private-only** removes Bastion's own public IP too. JIT and Bastion combine.

Page-local detail: the Bastion flow and the eight NSG rules on [D3.2.2](../objective/D3.2.2.html), the JIT request lifecycle on [D3.2.3](../objective/D3.2.3.html).

## 4 · Hardening a new VM — security type, then disk encryption

One decision tree for the two VM choices that are hard to change later. Pick the **security type** first: Confidential VM only when the threat is the cloud operator or data in use, otherwise Trusted launch. Then pick the **disk encryption**: encryption at host whenever the temp disk and caches must be covered. On any branch, "customer controls the key" adds a **disk encryption set** — it is not an encryption type of its own. ADE stands to the side because it is retiring and blocks encryption at host forever.

Page-local detail: the encryption-only tree and decision table on [D3.2.1](../objective/D3.2.1.html), the three security types stacked on [D3.2.8](../objective/D3.2.8.html).

## 5 · The container pipeline — a control at every hop

An image moves from the pipeline to the registry to a runtime. Each hop has its own control. The **pipeline** pushes with a push role and signs with Notation. The **registry** keeps the admin user off, stays private on Premium, and keeps anonymous pull off. Each **runtime** pulls with AcrPull through a managed identity, then applies its own sign-in, network and secret controls. **Defender for Containers** (the band at the bottom) covers the registry and the Kubernetes cluster, from scan-on-push to Deny at admission.

## 6 · The web and API front door

A request crosses four tiers, and each one checks something different. The **WAF** inspects the HTTP content. The **App Service** web app enforces transport, sign-in and who may reach it. **API Management** checks the caller's token and volume, then proves itself to the back end with a managed identity. The **back end** accepts only APIM's token and APIM's network path. The red box is the classic gap: a back end not locked to the WAF path can be called directly.

## 7 · Look-alikes — constructs that do a similar job

Six families of D3 constructs that distractors swap for each other. Each row is one job. Green is usually the right answer for the common scenario; red is the usual trap. Read each row as "which one, and why not the others". The AI row is the newest trap: Foundry guardrails and APIM content safety both block, but their strictness scales run in ==!opposite directions==, and Defender for AI Services only alerts.

Page-local detail: encryption on [D3.2.1](../objective/D3.2.1.html); WAF on [D3.3.8](../objective/D3.3.8.html); network features on [D3.3.7](../objective/D3.3.7.html) and [D3.3.5](../objective/D3.3.5.html); caller identity on [D3.3.5](../objective/D3.3.5.html) and [D3.3.9](../objective/D3.3.9.html); AI protection on [D3.1.3](../objective/D3.1.3.html), [D3.1.7](../objective/D3.1.7.html), [D3.1.8](../objective/D3.1.8.html) and [D3.1.9](../objective/D3.1.9.html); admin access on [D3.2.2](../objective/D3.2.2.html) and [D3.2.3](../objective/D3.2.3.html).
