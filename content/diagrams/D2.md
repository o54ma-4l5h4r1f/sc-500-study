# D2 — how it all connects

Domain 2 is the data and the network around it. The objective pages teach each control on its own. These six pictures show how the controls stack, which one a packet or a request meets first, and which constructs look alike. Read them after the objective pages, then again before the exam.

Dashed, muted boxes are **forward-links**: a construct from another domain that sits next to a D2 thing. They are pointers only; the detail lives in that domain. **Legend: dashed = another domain.**

## 1 · The traffic path — hub, spoke and the edge

One picture of the whole network subdomain. Traffic enters from four kinds of source. Site and user VPNs land on the **VPN gateway**, internet traffic hits **Azure Firewall**, and both pass through the hub to the spoke. In the spoke, a **UDR** sends traffic back through the firewall. Inbound packets then meet **AVNM security admin rules**, the **subnet NSG** and the **NIC NSG**, in that order. **Entra Private Access** users skip the hub: Microsoft's edge checks Conditional Access, and an outbound-only connector delivers the traffic. On Virtual WAN, a **secured virtual hub with routing intent** replaces the hub VNet and the hand-written UDRs.

Page-local detail: the NSG order picture on [D2.3.1](../objective/D2.3.1.html), the admin-rule actions on [D2.3.2](../objective/D2.3.2.html), the secured hub on [D2.3.3](../objective/D2.3.3.html), the connection types on [D2.3.4](../objective/D2.3.4.html), the Private Access flow on [D2.3.5](../objective/D2.3.5.html) and the rule-processing chain on [D2.3.8](../objective/D2.3.8.html).

## 2 · The network path to a storage account or SQL server

Every PaaS request meets **DNS first**. If the name resolves to a private IP (a `privatelink` zone linked to the VNet), the request rides a **private endpoint** and the service firewall is not consulted. If it resolves to the public IP, the **public network access** setting decides: Disabled refuses it, "all networks" lets it straight through, and "selected networks" (or SQL with public access on) checks the rule list. Storage and SQL use different rule lists. Authorization comes **after** the network check, never instead of it.

Page-local detail: the storage firewall decision on [D2.1.2](../objective/D2.1.2.html), the SQL firewall order on [D2.2.1](../objective/D2.2.1.html) and the private endpoint DNS flow on [D2.3.6](../objective/D2.3.6.html). The Key Vault firewall follows the same pattern.

## 3 · Storage access — which signature for which caller

Storage access is decided by **how the request is signed**. Start from the caller, not the mechanism. Azure workloads and tenant users get an **Entra token plus a data role**. An outsider gets a **user delegation SAS**. Only a legacy app that cannot use Entra should get a key-signed **service SAS**, and then always with a **stored access policy** so you can revoke it. The bottom band is the switch that ends the key-signed column: with **Allow storage account key access = Disabled**, column 4 gets HTTP 403 and columns 1–3 keep working.

Page-local detail: the authorization options picture on [D2.1.4](../objective/D2.1.4.html); the Shared Key switch and Policy enforcement on [D2.1.1](../objective/D2.1.1.html).

## 4 · Azure SQL defence layers — outside in

The Azure SQL objectives are one stack. Each layer removes one link of the attack chain: no public door, no passwords to spray, no readable disks, no plaintext for admins, no extra rows for clerks, then evidence and detection when the rest fails. The right column is the trap the exam attaches to each layer.

## 5 · Look-alikes — private connectivity and traffic filters

Two families of constructs that answer similar-sounding questions. **Top row:** five ways to reach something "privately". Only the private endpoint gives one PaaS resource a private IP and lets you close its public door. The Private Link service is the same plumbing seen from the provider side. Entra Private Access is about *users* reaching *apps*, not networks reaching PaaS. **Bottom row:** six things that "block traffic". Each sits at a different place and layer. Two of them live in other domains.

## 6 · Troubleshooting a flow — layer by layer

When a connection fails, or works when it should not, walk the layers in the order a packet meets them: **name**, **route**, **NSG and admin rules**, **firewall**, then **evidence**. Each row names the tool and the usual cause. This is the layered companion to the "which tool answers which question" map on [D2.3.9](../objective/D2.3.9.html), which stays the reference for tool facts.
